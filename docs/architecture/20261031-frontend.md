<a id="form"></a>
## 形态

- SwiftUI 应用，Swift Package（`frontend/Package.swift`）。只用系统框架，没有第三方依赖。
- 只支持 Apple 芯片（arm64），以及最近三个 macOS 大版本，目前是 macOS 15、26 和 27，最低 macOS 15（`Package.swift`、`Info.plist` 的 `LSMinimumSystemVersion`、`update.json` 的 `minimumSystemVersion` 三处一致）。新的大版本发布后，下一个 Janus 版本把最低版本提高一个大版本，CI 在最低支持的版本上运行应用测试。
- 它是 Janus 唯一的界面：所有数据和操作都通过 [HTTP API](../interfaces/20261031-http_api.md) 读写，编排器不提供网页。
- 安装包 `Janus.app` 里放着应用（`Contents/MacOS/Janus`）、Janus 服务（`Contents/MacOS/janus-server`，即 release 构建的 `janus`）和 Node.js（`Contents/Resources/node`），下载后不需要编译 Rust，也不需要安装 Node。

<a id="ui_language"></a>
## 界面语言

在 Janus「设置 › 通用 › 语言」中选择「跟随系统」「简体中文」或「English」。切换立即生效，重新打开应用时保留选择。默认「跟随系统」使用 macOS 为 Janus 指定的语言或系统首选语言，没有匹配项时使用简体中文。

菜单、按钮、状态、表单、系统通知和日期时间随界面语言显示。用户输入、Agent 的回复和原生选项、服务诊断详情及审计原文保留记录时的文字。Janus 注入 Agent 的固定系统层说明始终用英文，见 [ACP 集成](../interfaces/20261031-acp_integration.md#standing_instructions)。

<a id="ui_copy"></a>
## 界面文案

界面文字的口吻是轻松加科技感：像懂行的同事随口说明，而不是公文或说明书。

- **一句话**：说明最多一句，约 30 个字以内；更多解释放进悬停提示或文档，页面上不堆段落。
- **口语**：用「还没 / 先… / 没法… / 要是…」，不用「尚未 / 请… / 无法… / 若…」；对用户说「你」。删除确认统一写「删了就找不回来」或「找不回来」。
- **精确的技术词**：保留 Token、上下文、diff、快捷键、数字和 `·` 分隔；不出现内部实现词（编排器、ACP、墙钟、不变量、front matter、detached HEAD 等）。服务一律叫「Janus 服务」。
- **短标签**：状态和元信息写成「标签 · 数字」，例如「排队中 · 第 2 位」「验证没通过 · 打回修复」。设置路径写成「设置 › 数字员工」。
- **全局的工作口吻**：和值班一致，Agent 和任务的状态用「干活中、摸鱼中、待开工、已派活、等上游、上游出错、思考中、翻文件、改文件、跑测试、等队友、出错了」，负责人启动时是「上岗中」，开始任务的按钮是「马上开工」。

同一件事在所有页面用同一个词：

| 说法 | 只用于 |
| --- | --- |
| 待处理 | 需要用户动手的事（收件箱、侧栏、工作台、首页）；数量写「N 件待处理」 |
| 等你 + 动作 | 单个事项的状态：等你回答、等你审批、等你拍板、等你填写、等你回话、等你验收 |
| 可能卡住了 | 看门狗发现长时间没有进展 |
| 会话已结束 | 会话不再打开；对话列表的状态是「会话中 / 已结束」 |
| 检查 | Agent 配置的体检：未检查、去检查、检查没通过；「试运行」只是其中一步 |
| 验证 / 验收 / 核对 | 验证是协作者互查，验收是用户最后拍板，核对是 Janus 对证据；否定都写「X 没通过」 |
| 团队 / 对话 | 侧栏的两组：团队（工作区）和对话（一对一）。「对话」是功能名，「会话」只指 Agent 的一次连接 |
| 派 / 调度 | 负责人派出子任务（派工方案）；调度只指 Janus 安排先后 |
| 指令 / 自定义提示词 | 数字员工的叫指令，Agent 级的叫自定义提示词 |
| 挡住 | 本机环境里对 Agent 隐藏的路径 |
| 插话 / 排队 / 留言 / 新一轮 | 消息的四种送达方式：立刻插进这一轮、这一轮结束后、下次会话带给它、作为新的一轮 |
| 对不上 | 结果和工作目录不一致（不再叫「痕迹」） |
| 全员可用 | 资源库里的每项资源 |
| 下个任务起生效 / 立即生效 | 改动生效的两种时机 |
| 排队 / 等空位 / 分身 | 任务等并行名额叫排队；Agent 进程等名额叫等空位；一名数字员工的并发实例叫分身 |
| 继续 / 接上 | 任务从中断处继续；会话接上原会话；「重试」只用于失败的动作 |
| 协作者 | 做子任务的成员（不叫执行者） |
| 交付物 / 产物 | 交付物是负责人最后交给用户的；产物是每个子任务留下的 |

<a id="server_process"></a>
## 与 Janus 服务的关系

`Backend`（`Core/Backend.swift`）在启动时决定用哪个服务：

1. 读取 Janus 配置的地址：`JANUS_ADDR`，否则 `<Janus home>/config.toml` 的 `addr`，否则 `127.0.0.1:7878`，与服务自己的规则相同。
2. 这个地址上有 Janus 应答 `GET /api/meta`，并且它的 `home` 就是这个 Janus home（例如 `just start` 启动的 launchd 服务，或 `just dev`）时，直接连接它，不另起服务。端口上是别的程序，或是另一个 Janus home 的 Janus，都不算。
3. `<Janus home>/janus.pid` 记录的进程还活着时，说明已有 Janus 在用这个 home，只是不在配置的地址上：从 `logs/janus.log` 最后一行「`http://<地址>  ·  home <目录>`」取得它的地址并连接。连不上时提示先退出那个 Janus，不再启动第二个（[单实例](../operations/20261031-deployment.md#single_instance)）。
4. 第 2、3 步找到的服务是其他版本时（`/api/meta` 的 `version` 与应用的 `CFBundleShortVersionString` 不同，或没有 `version`），不使用它：启动页说明数据升级要由新版本的服务执行，提供「停止旧服务并重试」，向 `janus.pid` 中的进程发 `SIGTERM`、等它退出后重新走这几步（`Backend.isStale`、`stopRunning`）。从源码运行的应用（版本 `0`）不做这个检查。见 [ADR：数据随版本自动升级](../decisions/20261118-data_migrations.md)。
5. 否则启动服务程序：优先用应用包内的 `janus-server`，其次是 `JANUS_SERVER_BIN`，最后是 `just install` 安装的 `<Janus home>/bin/janus`。30 秒内没有应答、或服务退出时，启动页显示日志末尾，提供「重试」和「打开日志目录」。

<a id="port_conflict"></a>
### 端口被占用

应用自己启动服务时，先按服务的方式（`SO_REUSEADDR`）试绑定配置的端口：

- 端口空闲就用它。
- 被占用时，依次试后面 20 个端口，都不行就由系统分配一个空闲端口。选中的地址通过 `JANUS_ADDR` 传给服务，服务写进看板 MCP 地址的也是它。
- 检查和服务真正绑定之间端口仍可能被抢走：服务因 `Address already in use` 退出时，换下一个端口重试，最多 3 次。
- 改用了其他端口时，侧栏底部的地址下显示原因，例如「端口 7878 被其他程序占用，改用 7879」。`config.toml` 不会被改写，下次启动仍先试配置的端口。

### 应用启动的服务

- 标准输出和错误追加到 `<Janus home>/logs/janus.out.log`，和服务方式运行时一样。
- 从 Finder 打开的应用只有很短的 `PATH`，找不到 `git` 和 Agent CLI。应用用登录 shell（`$SHELL -ilc`）读取用户的 `PATH`，再补上 Homebrew、`~/.local/bin` 等常见位置，传给服务。
- 包内的 Node.js 排在这个 `PATH` 的最前面，并设为 `JANUS_NODE`：ACP 适配器用它运行，`npm` / `npx` 安装适配器时也用它，Agent 进程继承同一个 `PATH`。用户自己设置了 `JANUS_NODE` 或 `config.toml` 的 `node` 时不覆盖。
- 退出应用时停止服务（SIGTERM，3 秒后 SIGKILL）；被 `kill` 或 Ctrl-C 结束时也一样。还有进行中的 Run 或对话（`AppStore.working`，读需要关注的列表，不论多旧）时，退出前先确认：Run 会中断，下次可以「从中断处继续」；对话发下一条消息时重新打开会话。
- 连接的是别人启动的服务（launchd 服务）时，退出应用不影响它。
- 应用是否拥有服务只看它是否持有自己启动的子进程（`Backend.owned`），不另存标记。「重试」和「停止旧服务并重试」都从 `Backend.start` 重新走一遍，它先停掉应用之前启动的服务，避免把自己的子进程当成外部服务，退出时漏掉确认。

<a id="event_derivation"></a>
## 由事件推导状态

运行页不保存自己的业务状态。`derive(events)`（`Core/Derive.swift`）从头遍历事件，推导出任务、Agent 状态、待处理事项（`inbox`）、回答、消息、产物和交付结果；`boardFacts` 由此整理出待处理事项、结论、产物、交接和决定，进展时间线用其中的结论、产物、决定和待处理事项放置标记。每次尝试记录开始和结束时间（`Attempt.end`，在尝试成功、失败、被取消、Run 中断或新尝试开始时写入），时间线据此画任务条。回放时把前 N 条事件交给同样的函数。

这样做的约束：

- 新增或修改事件类型时，必须同步更新 `derive` 中对应的分支，否则界面不会反映新状态；看板条目依赖 `boardFacts` 对事件类型和 `data` 字段的解释。检查清单见[事件参考](../interfaces/20261031-events.md)。
- 缺少前提的事件（例如引用了看板上没有的任务）被跳过，不中断推导。
- 任务的后端状态只有 7 个（`TaskStatus`，见[任务状态](../domains/20261031-run_lifecycle.md#scheduling)）；`derive` 另外推导 `ready`、`assigned`、`verifying`、`verification_failed`、`waiting_input`、`waiting_approval` 等只用于显示的状态。
- 「待处理」分两类：用户要处理的事项（来自 `inbox`，含负责人可能卡住，标「等你拍板」，排在前面）和负责人在处理的事项（协作者的阻塞、拆分提议和提问、两个任务或负责人与任务改了同一个文件、任务或负责人改了别的任务负责的文件、结果和工作目录对不上、可能卡住的任务、失败的任务、依赖失败的任务，标「负责人处理」）。可能卡住的任务来自 `task.stalled`，收到 `data.resolved: true`、执行它的 Agent 再有任何事件、新的尝试开始或任务不再执行时移除。负责人可能卡住来自 `lead.stalled`，收到 `data.resolved: true`、负责人再有任何事件或 Run 结束时移除。改了同一个文件来自 `task.conflict`，两个任务都不再执行时移除；越界（`data.owned`）和负责人改文件（`data.byLead`）在受影响任务结束时移除。拆分提议来自 `task.split_requested`，负责人回复、重做、取消或任务结束时移除，同时作为看板上的一条传递记录保留。结果和工作目录对不上来自 `task.succeeded` 的 `data.traceGaps`，负责人重做（`task.reopened`）、修订结论（`result.amended`）或 Run 交付、验收、取消后移除。协作者的认领（`task.claimed`）作为看板上的一条传递记录显示。只有存在前一类时，这一栏才用警示色。还在路上的消息只显示在各会话的「待发送」区，不进入这一栏。
- 同一个待处理事项（按 `key`）在 `inbox` 中只保留一条。事项被回答、撤回（`decision.withdrawn`）或 Run 结束后，从「待处理」中移除。

<a id="evidence_methods"></a>
## 验收证据

结构化结果里每条 `check` 可以带 `method`，说明这条结论的依据是哪类证据；字段和核对规则见[证据方法](../interfaces/20261031-events.md#evidence_methods)，后端实现见 `backend/src/evidence.rs`。应用只展示和分组已记录的字段，不判断任务是否通过：通过与否仍由 `task.succeeded`、`verification.*` 和编排器的核对决定（`Core/Acceptance.swift`、`UI/Run/Evidence.swift`）。

- **方法写成文字**：`test` 显示「测试」、`command` 显示「命令」、`inspection` 显示「检查」、`reasoning` 显示「推理判断」、`unverified` 显示「未核实」；没有 `method` 的旧结果显示「未说明」；不是允许值的原样写成 `方法「vibes」不合法（未说明）`（`Check.methodLabel`、`MethodTag`）。颜色和图标只作辅助，深色模式下和 VoiceOver 读到的都是这些文字。
- **逐条、完整**：每条验收标准一行，显示 ✓ / ○ / ✗、证据方法、标准原文和完整 evidence，不截断，也不只取第一条；结果里多出来的 check 同样保留（`CriterionCheck.rows`）。evidence 可选中复制，行上的无障碍标签读出通过与否、方法、标准和证据。
- **分组**：协作者的 checks、协作者提交的其他 `evidence`、独立验证（`verifies` 指向这个任务的其它任务及其 `verdict` 判定与 checks，`RunState.verifiers(of:)`，子任务页和交付共用 `VerificationList`：验证任务完成核查且判定 `approved` 时才算已确认，`rejected` 或 `inconclusive` 显示判定胶囊并标为「结论没有得到确认」）、`traceGaps`、风险（`RiskList`）和执行者自己报告的提醒分开显示。「提醒（不影响是否通过）」列出 `reasoning`、`unverified` 和「未说明」的项（`EvidenceSummary.reminders`），不会被渲染成失败。
- **来源**：`result.submitted` 提供这次提交的 checks、evidence 和风险；`task.succeeded` 带着结论的完整结果（摘要、evidence、风险、`checks`），任务成功后以它为准，所以回放、重启和恢复后方法和证据不丢；`verification.*` 重复它核对过的 `checks`。没有 `method` 的 check 显示「未说明」，不当作 `reasoning`，也不因此在界面上判失败。
- **交付**：`run.delivered` 的 `acceptance` 按任务给出验收总数、通过数、方法计数、全部 checks、`verifications`、`traceGaps` 和 `risks`，Run 结果页据此显示「逐条验收」（`deliveryAcceptance`、`DeliveryTaskView`）。每个子任务默认只有一行：编号、一行标题、通过数、方法计数，以及不成功、风险、痕迹和提醒的文字标记；有未通过标准、痕迹、任务风险或未通过的独立验证时默认展开，提醒只标记不展开，手动切换的效果保留到关闭这个 Run。展开后是该任务每条标准的原文、方法、完整证据、提醒、独立验证（含其标准 / 证据 / 风险）、痕迹核对和任务风险，内容不截断、不改写。卡片顶部另有验收概览，按任务汇总通过数、方法计数、任务级风险和子任务风险、痕迹和未确认的独立验证；验收操作在概览和任务级风险之后、交付物和证据之前，不要求先展开证据。复制交付摘要也带每个任务的通过数和方法计数。
- **审计**：审计日志在选中 `result.submitted`、`verification.passed` / `verification.failed`、`task.succeeded` 时，除了原始 JSON，还列出逐条 checks 及其方法；会话里的「提交结果」点开后每条也带方法（`CheckRow`）。进展时间线的结论标记在悬停提示和无障碍标签里带上方法计数，详情在子任务页和审计日志。
- **汇总数字**：`EvidenceSummary` 只统计已有字段（验收标准数、通过数、五类方法计数、未说明条数、不合法条数），不改变 `derive` 推导的任务状态，也不新增事件类型。交付里的记录直接读后端写下的汇总（`EvidenceSummary(recorded:)`）。

<a id="usage_ledger"></a>
## 用量账本

Run 的用量汇总是从事件算出的只读账本：后端是 `ledger`（`backend/src/usage.rs`），应用是 `usageLedger`（`Core/UsageLedger.swift`，在 `derive` 时写入 `RunState.usage`），两边同一口径，用同一份用例 `backend/testdata/usage_cases.json` 测试（`UsageLedgerTests`）。它不改变调度、任务状态机、事件写入或交付条件，不新增事件类型。口径见[用量口径](../interfaces/20261031-events.md#usage_accounting)：每一轮的 token 都相加，Agent 按模型上报时以模型行为准（含子 Agent）；上下文快照只显示最近值、峰值和比例，永远不计入 token；费用取 Agent 上报的原值并保留币种，不按 token 估算。

- **范围与数字**：Run、负责人、协作者小计、每个任务、每个成员和每个会话都从同一段事件聚合，每个范围带同一组字段（token 及其输入、缓存读取、缓存写入、输出，轮数、上下文、费用、时长、完整性）；缺失的计数保持缺失。每次尝试只保留结局、说明和时长，不单独带用量范围。耗时是从创建到最后一条事件的总时长，等待用户、审批或表单的时间单独写成「其中等待你」，不冒充 Agent 执行时间。
- **完整性**：`未上报`、`完整`、`部分上报`，和应用里的胶囊标签一致。缺失的数字一律写「未上报」，不写 0；范围里还没有任何会话（例如任务还没开始）写「未开始」，和「未上报」分开。
- **Run 页**：工作台只显示一行摘要，依次是子任务进度、已上报的 token 及完整性、费用、总时长和上下文比例；缺失的项不写，耗时始终写，有会话用量事件时在行末出现「用量明细」；展开期间即使回放到还没有用量的位置，控件也保留，用来收起。展开后在同一位置显示账本（`UsageSection`，`UI/Run/Usage.swift`）：token 及完整性和构成（输入、缓存读取、缓存写入、输出）、费用、耗时（含「其中等待你」）、上下文（已用 / 上限 / 比例 / 峰值）、负责人与协作者小计和会话数；二级「子任务与成员明细」按任务（token、耗时，没开始的任务写「未开始」）和成员（token、会话数）列出同样的数字，点按跳到对应页面。账本里不重复摘要行的总量和提醒；有提醒时常驻在摘要行下一行，不随账本收起。折叠状态只对当前打开的 Run 有效，不写入 `UserDefaults`。会话卡片标题栏的上下文用量读的是同一次 `session.usage` 快照，标为「本会话」「上一轮」。每个子任务的用量只在「子任务与成员明细」里按任务列出，子任务页不显示用量。实时且未结束的 Run（服务器标记 live、不在回放位置、状态是 `planning` / `running`）的摘要行耗时取「当前时间 − 创建时间」，并与账本记录值取较大者，避免时钟回拨时数字倒退；摘要行（连同它的悬停提示和 VoiceOver 标签）由每秒的 `TimelineView(.periodic(from: .now, by: 1))` 重新生成（`RunState.usageForDisplay(now:live:)`，经 `RunModel.usageDisplayed(at:)`），除耗时外的数字仍来自同一份账本、不会变化。Run 结束后固定为记录值并停止每秒重绘；回放位置按回放前缀的账本值；`live=false` 的只读 Run 同样保持记录值。展开的用量明细不按秒刷新：账本和其中的 Run「耗时」仍是事件记录值，即 `run.created` 到最后一条事件。
- **交付与看板**：交付结果卡片不显示用量行，同样的数字只在运行卡片的摘要行和「用量明细」里；`run.delivered` 的 `usage` 字段保留，是同一份账本的后端版本。看板的 `task_detail` 给出任务的总量、每次尝试和每个成员按模型的用量（`task_lines`）。
- **Token 参考值**：Run 卡在用量摘要下显示快照中的 `config.tokenLimit`（如果已设置）。回放旧记录时，按当前位置显示当时追加的 Token 参考值。达到参考值后照常运行。
- **提醒**：默认阈值是 Run 累计 50 万 token、单个任务占 Run 的 60% 且 Run 不少于 5 万 token、5 个以上协作者 30 分钟没有任何任务成功、有 10 万 token 却没有任何费用上报。阈值在后端 `backend/src/usage.rs` 和 `Core/UsageLedger.swift` 各有一份，修改时两处同步。提醒只写文字，数据不完整时前缀「提醒（按已上报数据）」，不进收件箱，也不暂停、取消、重试或追加预算（`usageReminders`）。
- **回放与恢复**：账本是这段事件的纯函数，回放位置用前 N 条事件各自算（`RunModel.usage`），重启、历史 Run 和同一位置的重复计算得到同一组数字。按秒推进只发生在显示层：`usageForDisplay` 返回的副本只覆盖 Run 范围的时长，任务和尝试的时长、等待时间和提醒仍按事件记录，账本本身、交付摘要和看板 `task_detail` 的口径不变。Run 被取消时这个 Run 里仍在跑的尝试、任务被取消时这个任务仍在跑的尝试记「已取消」，已上报的用量照常计入；过期尝试（`attempt.late_result`）记「已过期但仍计入」。

<a id="usage_bill"></a>
## 用量账单（按时间段）

设置里的「用量账单」用收据的样式列出所选时间段里所有 Run 的用量花在了谁、哪个模型上（`UsageReceipt`，`UI/Run/Usage.swift`；数据在 `Core/UsageBill.swift`）。从上到下：标题和它覆盖的范围、大号的金额（有价格时是按 models.dev API 价格的估算，标「非账单」；没有价格时是 K / M / B 三位有效数字的 Token 总量，下面是完整数字和 Agent 上报的费用）、统计行、按付费方分组的模型、Token 总量与输入 / 缓存读取 / 缓存写入 / 输出和缓存命中率，最后是说明。所有数字都是可选中的文字，VoiceOver 按「标签：值」读出；虚线只是装饰。

- **时间段账单**：设置里的「用量账单」（`UsageBillView`，`UI/Settings/UsageBillView.swift`）。区间可选近 7 天、近 30 天、本月、上月，按本机日历算整天，选择记在本机；内容来自 `GET /api/usage`（见 [HTTP API](../interfaces/20261031-http_api.md#usage_bill)），按 Agent（Codex、Claude Code 等）再按模型列出，统计 Run 数、请求轮数、会话数、活跃天数和活跃日均。「复制账单」把同样的内容复制成纯文本，「同步价格」立即从 models.dev 下载价格。
- 每个付费方和模型在有价格时显示估算金额，旁边是 token；没有价格的只显示 token，轮数写在说明里。Agent 上报的费用另列在付费方名字旁边和金额下方，不和估算相加。没有上报 token 的会话数写在说明里，不计入数字。

<a id="server_sync"></a>
## 与服务同步

| 场景 | 行为 |
| --- | --- |
| 打开 Run | `GET /api/runs/{id}` 取全部事件，再订阅 `/api/runs/{id}/stream?after=<最后一个 seq>`。从首页或其他页面回到已打开的 Run 时同样重新读取。交付后负责人又提交了新任务时，应用从这条 `orchestration.accepted` 起把 Run 显示为运行中，不再提供上一次交付的验收，再次交付后恢复；返工改了验收标准时，子任务页从 `task.reopened` 起显示新标准；`run.recovered` 之后不再显示暂停 |
| 收到事件 | `seq` 必须正好是上一个加 1；出现缺口或收到 `lagged` 时重新读取整个 Run（在新的任务中读取，因为读取会先取消当前的事件流任务）。一批事件到达后合并成一次推导（60 毫秒），推导在后台线程进行，结果回到主线程替换；推导期间又到达的事件再推导一轮 |
| 事件流断开 | 2 秒后重新读取并订阅，只要这个 Run 还开着 |
| 发送操作 | 附加 `commandId`（去重）和 `expectedSequence`（当前最后一个 `seq`）；返回 409 时刷新一次再重试 |
| 中断的 Run | `resumeRun` 或 `message` 成功后重新连接 |
| 回放 | 审计页可以按 `seq` 回放；回放期间不发送任何操作，会话输入框显示「回放中」并只读（`SessionComposer.replay`），草稿保留。消息没有发出去时（请求失败）回到输入框，除非这期间又写了新的。审计页顶部的系统规则检查平时只显示一行结论，有不满足的项时自动展开 |
| 跟进所有 Run | 订阅一条[全局事件流](../interfaces/20261031-http_api.md#global_stream)（`AppStore.followEvents`），不轮询：某个 Run 有新事件时，收件箱只读这个 Run 的新事件；有新 Run、Run 状态变了或对话有了标题时，读一次列表（任务、需要关注的 Run、对话、工作区）。300 毫秒内的通知合并成一次读取。流打开、漏了通知（`lagged`）或断开时读一次全部，断开后 2 秒重连。另有一个每分钟一次、不发请求的时钟，让推迟的收件箱条目按时回来 |
| Agent 检查、登录、适配器安装 | 在服务端后台进行，应用轮询直到结束 |

<a id="run_page"></a>工作台以负责人的对话为中心，从上到下依次是：运行卡片、待处理、交付物、进展、负责人的对话和它旁边的检查器，没有内容的部分不显示。运行卡片只有状态胶囊、目标标题（长目标可展开）、暂停 / 停止、中断续跑提示和一行摘要；摘要行依次写子任务进度、已上报的 token 及完整性、费用、总时长和上下文比例，只写已上报的项，耗时始终写；实时且未结束的 Run，摘要行的总时时每秒推进（悬停提示和 VoiceOver 标签同步更新），Run 结束、回放位置和只读 Run 固定为账本记录值，展开的用量明细仍显示事件记录的账本值、不按秒刷新。有会话用量时行末出现「用量明细」，展开在卡片原位，没有用量事件时没有这个控件；有提醒时摘要行下常驻一行「提醒（按已上报数据）：…」。卡片不再显示四阶段指示和独立的子任务计数行。负责人的对话（`ChatCard`，`target: .agent("lead")`）和 Agent 页的对话是同一个，可以直接插话、接管。Run 交付后负责人的会话仍保留为常规对话：可以直接写下一轮任务，或用 `/goal` 设置新的目标。服务重启后会话不在内存中，第一次发送消息会重新打开负责人会话（能加载原会话就加载，否则新建会话并带上目标、交付摘要和最近的对话）。检查器（`RunInspector`）分四个页签：子任务（点按打开子任务页）、改动（最上面是「整个任务」的 diff，即相对任务开始时的全部改动，负责人自己改的也在内；下面是每个子任务最新的 diff；点「审阅」打开 [diff 审阅](#diff_review)；没有时写「还没有改动。」）、产物（其他文件）、团队（各 Agent 在做什么）。打开任务时只选一次页签：没有手动选择过时，无子任务显示「团队」，有子任务显示「子任务」；手动选择后写回 `janus.inspectorTab`，之后打开的任务沿用。窗口窄时检查器移到对话下方。对话和检查器在无子任务且负责人没有消息时高 320，否则取窗口内容高度的 0.7 倍并限制在 420–800；检查器落到对话下方时高 480。目标可能是一大段粘贴的说明，标题和 Run 列表只显示它的第一行（`goalTitle`），完整目标在运行卡片中展开查看。交付结果默认依次显示负责人的总结（过长时保留「展开全文」）、验收概览（通过数、方法计数、运行级和子任务风险、痕迹）、任务级风险与限制（默认列出前 5 条，更多时页内展开全部）、验收操作、交付物、证据、逐条验收和负责人建议写入共享资料的条目（`BriefSuggestions`，带「加入共享资料…」按钮），最后是在审计日志中逐条核对。在 worktree 中的 Run，交付卡片的验收标记下方写一句结果在哪里（`SessionView.worktreeNote`）：验收前「改动在这个任务单独的 worktree … 中，验收时合并回 … 的分支 …」，验收后「结果已合并到 … 的分支 …」，任务开始时处于 detached HEAD 的写「… 当前的 detached HEAD」，没有新的改动时说明没有提交。「团队与权限」的「分支」一行写「验收时合并回 …」或「已合并到 …」。逐条验收里每个子任务默认一行：编号、一行标题、通过数和方法计数；有未通过标准、痕迹核对、任务风险或未通过的独立验证时默认展开，有提醒时只在行内标记。改了文件却没有独立验证的子任务（`unverified`）在行内标「没有独立验证」，不默认展开；验收概览写「N 个子任务没有独立验证」，复制的交付摘要也带上这一条。负责人怎么核对这些子任务，看它的总结。展开任一行看到该任务每条标准的原文、方法、完整证据、提醒、独立验证、痕迹核对和任务风险，内容不截断。验收操作在总结、概览和任务级风险之后，交付物和逐条验收之前，所有子任务行收起时仍可用，不要求先展开证据。

<a id="queued_run"></a>排队中的任务（`queued`，见[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)）还没有开始任何东西，打开后不是工作台，而是 `QueuedView`：排位胶囊（「排队中 · 第 N 位」，取自这个任务的详情 `queuePosition`）、目标、一句说明（前面的任务做完、停止或暂停后自动开始，开始时才建 worktree、按那时的团队和资源库），随目标粘贴的图片，以及「取消任务」和「马上开工」（不等空位）。`run.queued` 推导出 `queued` 状态和目标，`run.starting` 推导出 `planning`（正在准备，不再显示这两个按钮），`run.requeued` 回到 `queued`。不在运行的任务推导出的状态变成进行中时，`RunModel` 重新读取，准备好后换成实时的工作台。打开着的排队任务在全局事件流说有 Run 状态变化时重读自己的排位，所以即使它不在 Run 列表的第一页也跟得上。

<a id="loops"></a>工作区的 [值班](../domains/20261121-loops.md)（`UI/LoopView.swift`、`Core/Loops.swift`）：

- **从哪里看到**：工作区首页在「待处理」和任务记录之间有「值班」一节（`LoopSection`），还没有值班时标题旁有一句说明（按时间表开工：看一眼、做判断，要改的事派成任务），每个值班一行：值班的身份标（`LoopBadge`，带底色的时钟循环图标，值班页标题处用同一个）、名字（`title`）、时间表（「每 30 分钟」「工作日 09:00」「每周一 09:00」「cron：…」「只在你叫它时」，`LoopText.schedule`，由 `LoopSchedule` 从 cron 认出常用写法）、状态胶囊（「摸鱼中 · 14:30 开工」，不是今天的带日期；「干活中」「已暂停」「出错了」，`LoopText.phase`）和「上次：」后面跟上次开工最后一条消息的第一行；标题旁的「+」打开表单（悬停提示「新建值班」）。侧栏不列值班：工作区一行的数量和绿点算上它的值班，值班有事等你处理时，首页「待处理」里有它的一行。值班列表在打开和重连时由 `GET /api/loops` 读出；全局事件流说某个值班变了（`loop`），或它派出的 Run 状态变了（`run` 通知带 `loop`）时，只重读那一个值班。
- **新建 / 编辑**（`LoopEditor`，表单，宽 600）：标题「新建值班 / 编辑值班」，下面一行写在哪个工作区、由哪名负责人来跑（负责人不在表单里选），再一行说明值班怎么干活（自己不改文件，要改的事派成任务，结果到收件箱，名字等它第一次开工时自己起），先看这个再写要它做什么。「要它做什么」是一个大输入框，空着时写提示该写什么，下面一排「从示例开始」的按钮（分拣 GitHub issue、每天看 CI、盯依赖更新）填入一段完整的提示。「什么时候开工」是两个单选按钮：「按时间表」和「只在你叫它时」。选按时间表时，它下面缩进一行频率菜单（每隔几分钟、每隔几小时、每天、工作日、每周、每月，分隔线后是「写 cron 表达式」）和对应的控件（分钟数、小时数、星期、几日、时间，或一个等宽的表达式输入框；时间是「时」「分」两个菜单，时 00–23，分每 5 分钟一档，编辑的值班不在档上的分钟也列出来，不用系统的时间输入框，因为它把两个数字之间超过约 1 秒的停顿当成输完，慢慢打 18 会变成 08；从别的频率切到写表达式时预填当前的表达式），再下面是服务端算出的「接下来」三次（`GET /api/loops/schedule`，停止改动 0.3 秒后请求，时区用这台 Mac 的），表达式不对时这里是红字的原因、保存不可用；最后是说明（按哪个时区、在干活时到点怎么办、Mac 睡眠时错过的只补一次、它可以自己约一次时间表之外的开工）。选只在你叫它时，下面只有一行说明。最后一行说明它自己不改文件、结果到收件箱、名字由它第一次开工时自己起；没有名字输入框。新建有「只创建」和「创建并马上开工」（默认，↩），编辑只有「保存」。
- **值班页**：打开值班就是打开它的会话 Run，`RunView` 看到 `kind` 为 `loop` 时显示 `LoopView`：标题行是值班的名字和状态胶囊，下面一行写时间表、负责人、开工几次、派出几个任务；下次开工是它自己约的（`nextWakeReason` 为 `self`）时，再下一行写「它约了 14:20 再看一次：<原因>」（`LoopText.asked`）；右边是「现在开工」（在干活时不可用）、「暂停」或「继续」，以及「编辑…」「删除值班…」。左边是和对话同一个会话卡片（`ChatCard`）：每次开工的提示是一条来自 Janus 的消息，可以随时给值班发消息、停止这一轮；系统层写「值班的工作方式」，`janus` 工具调用标「值班」，会话空闲时写「摸鱼中，等下次开工或你的消息」。标题行下的派出数量是服务端按状态计数（`status.dispatched`）之和。工作区不在 Git 仓库里时，标题下有一条提示：值班直接在你的目录里干活，看不出它改了哪些文件。右边一栏先是「待处理」（`InboxSection`，值班的问题在这里也能回答，没选项的问题填文字），然后是它派出的任务（`GET /api/runs?loop=`，每页 100 个，「更早的任务…」读下一页；计数变化时重读：目标、key、状态，悬停看来源链接，点按打开）和它记下的状态（最后一条 `loop.state_saved`）。菜单栏「任务」里的暂停、继续、停止对值班不可用，删除变成「删除值班…」。值班的会话一轮结束等下次开工是正常状态，不进待办；会话再次打开（包括第一次开工）时，打开着的值班页重读，按实时会话显示。
- **任务记录**：值班派出的任务在工作区首页的「待处理」和任务记录里，目标标题后面有一个灰色小标签（`LoopMark`：时钟循环图标加值班的名字），任务仍是这一行的主体；悬停看来自哪个值班（删除后写「已删除的值班」）、key 和来源链接。
- **收件箱**：值班的会话和对话一样作为候选（`GET /api/runs?kind=loop&attention=1`），它的 `ask_user` 问题、审批和表单照常出现。另有两类只属于值班的事项，都可以推迟：「值班改了工作区的文件」（`loop.touched`，下面写改了哪些文件）和「值班没能开工」（`loop.failed`）；下一次开工时撤下。值班的会话不论状态（取消的除外）都作为候选，所以服务重启后会话还没打开时，它的问题和开不了工的提醒也在收件箱里；`run.interrupted` 不清掉值班的问题。

<a id="team_memory"></a>工作区的[团队记忆](../domains/20261123-team_memory.md)（`UI/MemoryView.swift`、`Core/Memory.swift`）：

- **从哪里看到**：工作区首页右栏、共享资料卡片下面的「团队记忆」卡片（`MemoryCard`）：它和共享资料一样是这个工作区每个任务都会带上的上下文，所以放在同一栏、用同样的卡片，区别是共享资料由用户写，团队记忆由 Agent 写。标题旁是条数（有笔记时）和「?」（点开说明团队记忆怎么工作）。没有笔记时卡片里只有一行「还没有笔记。Agent 在任务里记下的会出现在这里。」；有笔记时每条一行：类型胶囊（事实、决定、坑、做法，坑用琥珀色）和标题，悬停显示摘要和来源（`MemoryText.source`：「谁 · 哪个任务 · 时刻」，用户改过的是「你 · 时刻」，来自被取消的任务的写明），点按打开笔记表单。默认列 5 条，多了底部有「展开全部（N）」；有过整理时底部右边是「上次整理：<时刻>」链接。标题行右边：正在整理时是「整理中」胶囊（点开是整理页），否则有笔记时是「现在整理」图标按钮，没有笔记时不显示。工作区页出现时读一次（`GET /api/workspaces/{id}/memories`），之后全局事件流的 `memory` 通知只让读过的工作区重读。
- **笔记表单**（`MemoryEditor`）：点一条笔记打开。标题「团队记忆」，下面一行是来源；类型菜单、标题、摘要（占位写明之后的任务在索引里看到这一行）和正文；一句说明这是 Agent 记的笔记、要团队必须遵守就加入共享资料。底部是「删除…」（确认后删除）、「加入共享资料…」（关掉这个表单，打开共享资料表单并把这条以「标题：正文」作为一行加在末尾，算作未保存）、「取消」和「保存」（有改动且没有空字段时可用）。
- **整理页**：`RunView` 看到 `kind` 为 `dream` 时显示 `DreamView`：标题「整理团队记忆」，下面写负责人和工作区，右边「打开工作区」；整理完了有一行绿色提示（改了几条、删了几条和它的总结，来自 `memory.consolidated`），没完成时是琥珀色提示；下面是和对话同一个会话卡片，系统层写「怎么整理团队记忆」，开头的分隔线写「整理团队记忆 · 时刻」。整理结束后输入框不可用，提示要再整理就到工作区页点「现在整理」。
- **收件箱**：整理作为候选（`GET /api/runs?kind=dream&attention=1`）。进行中时它的审批和表单照常出现；结束后只看 Run 的状态：已交付是「团队记忆整理好了」，失败或中断是「团队记忆没整理完」，都可以推迟，也可以标记为已处理。

### 本机环境

设置「通用」页「权限」一节的第二部分「本机环境」（`HostEnvView`，`UI/Settings/HostEnvView.swift`；`Core/HostEnv.swift`；`AppStore.openSettings(.hostEnv)` 打开通用页并滚到这里），见[安全边界：本机环境](../operations/20261031-security.md#host_env)。打开时读 `GET /api/host-env`（`AppStore.hostEnv`），读不出来时写明原因并可以重试。

- 顶部一句说明：Agent 和 MCP 服务器用的是你用户目录的镜像，登录、钥匙串、工具链直接能用，只有列出的路径被挡住，改动立即生效（正在运行的会话也一样）。
- 「挡住的路径」：标题旁是「恢复默认」（已是默认时不可用）和「+」（「添加要挡住的路径」）：「+」打开系统的选择窗口，从用户目录开始、显示隐藏的文件和文件夹、可以多选，选中的完整路径交给服务端换算成用户目录下的路径，用户目录以外的被拒；一段说明默认挡住常见 Agent 的配置和敏感数据，可以删也可以加，文件夹和单个文件都能挡（挡住深处的一个文件时，服务端把它上面的文件夹逐项镜像）。下面的列表只做展示，每个路径一行：等宽的路径、来由（「Agent 的配置」「敏感」「你加的」）和行尾的 × 按钮（点一下就不再挡住）；在用户目录里的 Janus home 排在最前，写「Janus 的数据」，不能移除。只列本机有的路径（`HostEnv.shown`）：默认清单里本机没有的不出现，你自己加的即使本机还没有也列出，标「本机没有」。每次增删都 `PUT` 整份清单，以服务端返回的为准，被拒时把原因显示在提示条里。
- 「试一条命令」：等宽输入框和「试一下」（`POST /api/host-env/try`，`AppStore.hostTry`），结果并排两块：「本机」和「Agent」，各有「成功」或「退出码 N」（没跑完时写「没有跑完」）和可以选择复制的输出。

<a id="inbox"></a>
## 收件箱

收件箱（`Screen.inbox`，`UI/InboxView.swift`，`Core/Inbox.swift`）汇总所有工作区、所有 Run 中等用户处理的事。有等处理的事或有进行中的 Run 时，应用启动后先打开收件箱，而不是某个 Run 的实时页面。侧栏最上面「全局」下的「收件箱」和菜单栏图标（`MenuBarLabel`）显示数量，菜单栏图标菜单的第一项也打开收件箱。

- **来源**：需要关注的 Run（`GET /api/runs?attention=1`，不论多旧）中进行中（`planning`、`running`）和已交付的 Run，以及会话打开着的对话，用 `GET /api/runs/{id}?after=<seq>` 只读新事件，在本地累积后用 `derive` 和 `boardFacts` 推导，取 `you: true` 的待处理事项。已交付的 Run 也读，因为负责人在交付后的对话里还可能发来审批或表单。条目和 Run 页「待处理」出自同一份推导，两处一致。已交付的 Run 产生「等你验收」，已中断和失败的 Run 产生「可以从中断处继续」，这几种只看 Run 列表的状态；对话和值班没有这几种：它们的会话在两条消息或两次开工之间关掉（Run 记为 `interrupted`）是正常的休息，由下一条消息或下一次开工重新打开。对话等下一条消息也不算等你处理。由全局事件流驱动：只有有新事件的 Run 才读；每个 Run 缓存收件条目，其余 Run 的状态、工作区名称和语言没变时直接用缓存。输入发生变化时在后台重新推导，过期的刷新结果丢弃。Run 交付后，详情撤回预算卡，收件箱显示验收项。
- **就地回答**：只是选择题的请求直接在收件箱里回答，按钮发出和 Run 页相同的操作（`OpenFact.actions`、`InboxModel.act`）：审批按 Agent 给的选项显示，文字按 `kind` 统一为「允许一次 / 始终允许 / 拒绝 / 始终拒绝」（`L.permissionOptions`，Agent 的原话和「始终」的影响在悬停提示中）；负责人交来的决定和协作者转来的提问按选项显示，负责人建议的那项突出。表单、自由回答和其他请求仍是「去处理」。
- **条目的写法**：标题和 Run 页的请求卡片一致，写「谁 请求你决定」，任务（「T3 · 清理旧构建」）写在下面一行。
- **三种处理**：「去处理」（有就地回答时是「详情」）打开对应的 Run；「稍后」推迟 1 小时、4 小时或到明天上午 9 点，到时间回到「待处理」；「标记已处理」只用于已中断和失败的 Run，不再提醒，Run 本身不变。
- **哪些可以推迟**：没有人在等的才可以：负责人用 `ask_user` 交来的决定（负责人会继续做别的事）、等验收的交付、负责人可能卡住、已停止的 Run。审批、表单、协作者转来的提问和等你消息的会话都会让 Agent 或 Run 停着，不能推迟（`InboxEntry.canWait`）。
- **条目的 key**：`<run id>/<什么>`，在请求关闭前保持不变，所以推迟和已处理跟着它走。
- **自动结束**：在别处处理了（Run 页、会话中、另一个客户端），下次刷新时条目消失，它的推迟或已处理记录一并清除。
- **进行中的 Run**：在「进行中」中列出，默认收起，减少盯着 Run 看进度的习惯；需要用户的事会出现在上方。
- 推迟和已处理只是这台电脑上这个用户的视图，存在 `UserDefaults`（`janus.inbox.snoozed`、`janus.inbox.settled`），不写入服务端，也不改变任务或 Run 的状态。

<a id="macos_permissions"></a>
## macOS 权限

「设置 › 通用 › macOS 权限」和首次启动时的权限面板共用 `MacPermissionsView`，滚动容器和标题由使用方提供。`AppModel` 持有 `MacPermissions`，在连接服务之前检查权限，因此服务启动失败时也能展示引导。源码运行时不发起系统权限申请，页面提示使用安装包。

| 权限 | 状态与动作 |
| --- | --- |
| 完整磁盘访问 | 打开系统 TCC 数据库（`/Library/Application Support/com.apple.TCC/TCC.db`）检测：只有拥有完整磁盘访问的进程能打开它，打开后立即关闭，不读内容。打开系统设置引导用户开启 |
| 应用程序管理 | 没有公开查询接口，用 TCC.framework 的 `TCCAccessPreflight` 查询当前应用的 `kTCCServiceSystemPolicyAppBundles`，不弹出提示，不通过改写其他应用试探。`NSAppBundlesUsageDescription` 说明管理应用的用途。打开系统设置引导用户开启 |
| 屏幕录制 | `CGPreflightScreenCaptureAccess` 查询当前状态，`CGRequestScreenCaptureAccess` 申请。不缓存申请结果，检查时不截图 |

三项都只显示 macOS 对当前进程的检测结果：「已授权」「未检测到授权」，或者系统没有给出答案时的「测不出来」。用户的操作不会被记成授权。

「一键开始授权」按表中顺序处理未授权的项目，一次只打开一个入口；回到 Janus 或点「重新检查」时重新检测，检测到授权后自动进入下一项。每一步可跳过，结束时仍列出未授权的项目。正在处理的一项仍未检测到授权时，卡片说明两种「系统设置里已打开却检测不到」的原因并提供「重新打开 Janus」：有的授权只对之后启动的进程生效；更新前的 Janus 在 macOS 看来可能是另一个同名应用（ad-hoc 签名按代码哈希识别，旧版本还用过另一个 bundle ID），要在系统设置中删除旧记录，再添加当前的 Janus.app。重新打开由一个短脚本在应用退出后执行 `open`，一分钟内应用没有退出（例如用户取消了退出）就放弃。系统设置链接打开失败时显示手动路径；无法打开具体页面时尝试打开隐私设置。

安装标识是 bundle ID 和签名身份（designated requirement，`CodeSigning.designatedRequirement`），也就是 macOS 授予权限时认的对象。用固定证书签名的各个版本标识相同，更新后不再弹出引导；标识变化（例如从 ad-hoc 签名的版本或旧 bundle ID 升级上来）时，如果有未授权的项目就弹出引导，全部已授权则不弹。Janus home 中的 `data/app/permissions.json`（`JanusHome.permissions`）只保存这个标识和是否处理过引导。同一标识处理过后不再自动弹窗，每次启动和回到应用时仍会检测三项权限。记录失败显示提示，不影响应用启动。状态、引导步骤与权限种类使用枚举；系统调用通过注入接口测试。

授权对象是当前 Janus，Agent 是否沿用它的权限由 macOS 的负责进程归属决定；独立服务或其他终端启动的 Agent 可能要单独授权。权限面板说明这个边界，并提醒授权后按系统要求重启应用、使用新的 Agent 会话。完整磁盘访问不绕过文件所有者权限、SIP 或 Agent 自身的沙箱。详见 [安全边界](../operations/20261031-security.md#macos_permissions)和 [ADR](../decisions/20261117-macos_permission_guidance.md)。

<a id="updates"></a>
## 应用内更新

`Updater`（`Core/Updater.swift`）从 Info.plist 的 `JanusUpdateRepo`（`duoyuli/Janus`）的最新 GitHub Release 更新 Janus.app。只有打包出的 `.app` 会检查，`swift run` 不会。发布产物和签名见 [CI 与发布](../operations/20261101-ci_release.md#update_parts)。

1. **检查**：启动 20 秒后检查一次，之后每 6 小时一次；菜单栏图标菜单中的「检查更新…」打开设置 › 通用、滚到「更新」一节并立即检查。结果只写在更新一节的状态行里，不弹对话框。读取 `releases/latest` 的 `update.json`，版本号按点分数字比较，新版本要求的 macOS 更高时不提示。
2. **提醒与安装**：侧栏底部显示「Janus <版本> 可以更新」（`UpdateBadge`），点击同样打开设置 › 通用的「更新」一节。这一节显示当前版本、状态、上次检查时间、新版本的发布说明、下载大小和「更新到 <版本>」；点击后直接开始下载，不再弹确认框。
3. **下载**：`plan` 决定下载哪些部分：应用部分总是下载；Node.js 部分只在 `update.json` 的内容哈希与本机 `update-parts.json` 不同时下载。下载前先清掉 `~/.janus/cache/updates/` 中 `previous/` 以外的一切（以前下载了没装的版本也在内，`clearStaged`），再下载到 `cache/updates/<版本>/`，逐个核对 SHA-256。
4. **拼装与校验**：解开应用部分，Node.js 用下载的部分，或用 `cp -c` 克隆本机的（APFS 上不占额外空间），去掉隔离标记。然后用 Security 框架校验：签名完整（含嵌套代码，`kSecCSStrictValidate`），版本号与发布一致；当前应用有固定签名者时，还要满足当前应用的指定要求，否则拒绝安装。沿用的 Node.js 导致签名不符时，改为下载 Node.js 部分再试一次。
5. **替换**：写出 `~/.janus/cache/updates/install.sh` 并在后台启动，停止应用自己启动的服务，然后退出应用（跳过「还有正在执行的任务」的确认）。窗口上有面板挡住退出时，5 秒后直接结束进程，保证安装脚本能继续。脚本等应用进程结束，把旧应用移到 `~/.janus/cache/updates/previous/Janus.app`，移入新应用并 `open`，记录写在 `~/.janus/logs/update.log`。移入失败时（跨卷移动是复制，失败时目标位置可能留下半个新应用）先删掉目标位置残留的部分，再放回旧应用；连放回也失败时，从 `previous/` 打开旧应用。

更新过程的状态是 `Updater.State`：`idle`、`checking`、`upToDate`、`available`、`downloading`、`verifying`、`relaunching`、`failed`。侧栏和更新一节只按状态显示，不再解析进度文字。

以下情况不能自动更新，更新一节给出原因：应用被 macOS 放在隔离位置运行（路径含 `AppTranslocation`，没有拖进「应用程序」就打开时会这样）、应用所在目录不可写、下载或校验失败。

应用自己下载的文件不带 `com.apple.quarantine`，所以 Gatekeeper 不会像对浏览器下载的 DMG 那样要求在「隐私与安全性」中允许。设计取舍见 [ADR：应用内增量更新](../decisions/20261102-in_app_updates.md)。

<a id="markdown_viewer"></a>
## 文档查看

团队交付的大多是 Markdown 文档（PRD、调研报告、发布说明、验收记录），应用内置渲染，不用切到别的编辑器。

| 入口 | 行为 |
| --- | --- |
| 运行页工具栏「文档」 | `DocumentsMenu` 分三组列出这个 Run 的 Markdown 文件（worktree 已经移除的 Run，例如验收后重启，worktree 里的路径改到它合并回的仓库里找，`RunDocs.Moved`）：交付物（`run.delivered` 的 `deliverables`）、任务产物（`artifact.created`）、Agent 写过或提到的文档。最后一组从事件的文本和 `data` 中找绝对路径和相对于 Run 目录的路径（`RunDocs.paths`），不看 `session.prompt` 和 `agent.status`；只列出存在的文件，每组按最近一次提到排序。事件增量扫描，重新读取 Run 时从头扫描；文件是否存在在每批事件推导后检查一次（`RunModel.documents`），不随每条事件或每次绘制检查 |
| 交付结果、子任务页的「查看」 | 打开对应的交付物或产物 |
| 会话和交付总结中的链接 | 指向本机 `.md` 文件的链接在 Janus 中打开（`DocLinks`），其他链接交给系统 |
| 文件 > 打开 Markdown 文件…（⌘O） | 选择任意 Markdown 文件打开 |

文档窗口（`ArtifactWindow`，`UI/DocumentViewer.swift`）每个文件一个，再次打开时把已有窗口提到前面并重新读取。窗口顶部可以切换「预览 / 源文本」、重新读取（Agent 可能还在修改文件）、复制内容或路径、在 Finder 中显示、用默认应用打开。非 Markdown 的产物按等宽文本显示。应用以用户身份运行，先直接读本机文件；读不了时再通过 `/api/file` 读取，这个接口只提供产物目录。

渲染分两步：`MDDoc.parse` 把文档解析成块（标题、段落、有序和无序列表及嵌套、任务列表、代码块、引用、GFM 表格及列对齐、分隔线、单独一行的图片），`MDBlocks`（`UI/Markdown.swift`）逐块绘制，行内格式（强调、行内代码、链接、删除线）交给 `AttributedString(markdown:)`。Agent 写在运行页里的文字（会话消息、完整目标、交付总结，`MarkdownText`）用同一套解析和绘制，只是换成正文字号、标题接近正文大小、块间距更紧的 `MDStyle.prose`；整条回复只有一行时，按「…： - 甲 - 乙」拆出列表（`MD.prose`）。会话每来一条事件就重绘可见的消息，所以解析结果按文本缓存（`MD.blocks`，最多 500 条）。中文行之间的软换行直接相连，不插入空格。相对链接和图片按文档所在目录解析：指向另一个 Markdown 文件的链接打开新的文档窗口，`#标题` 跳到本文档对应的标题，本地图片直接显示。不支持内嵌 HTML 和脚注。

<a id="run_timeline"></a>
## 进展时间线

工作台用一张时间线跟进这次 Run 是怎样推进的（`ProgressBoard`，`UI/Run/SharedBoard.swift`；绘制在 `RunTimeline`，`UI/Run/Timeline.swift`），取代原来分开的任务图和共享看板。它只回答「什么时候、谁做了什么、交给了谁」，细节到审计日志中看。它位于交付结果之后、负责人对话之前，默认折叠成一行「进展」+「展开进展」+「在审计日志中查看全部」，展开后在原位显示卡片，再点收起；标题不写子任务计数（计数在运行卡片摘要行），没有任务和标记时整块不显示，展开状态只对当前打开的 Run 有效。

- 每个任务一行，按开始时间从上往下排，还没开始的排在最后。左侧写任务标题、状态图标、协作者头像和名字，点按打开子任务页。
- 任务的每次尝试是一条任务条，颜色是协作者的颜色，失败的尝试是红色，进行中的用虚线框；条上写用时，重试写「第 N 次」。还没开始的任务以虚线框放在「现在」之后，写出它在等什么。
- 交接画成连线：从上游任务最后一次尝试的结束处，连到下游任务开始的地方。任务的结论和产物（多个时显示数量）是任务条末尾的小图标。决定（你的、负责人的）和待处理事项放在最上面一行「决定与待处理」，挨得太近时依次右移。待处理事项按种类用不同图标（审批、填写、决定、越界、同时改一个文件、结果对不上、阻塞、失败、可能卡住等，`TimelineMark.openKinds`），等你处理的是红色，负责人处理的是橙色。进行中的 Run 最后一段只画到「现在」，后面不留空白。
- 横轴是时刻。超过 3 分钟且超过总时长 8% 的空闲时段压缩成一段固定宽度的间隔（`TimeScale`），悬停显示空闲了多久，所以短时间内的密集工作不会被长时间等待挤成一条线。进行中的 Run 有一条「现在」线。
- 点按标记打开审计日志并定位到对应事件；悬停提示显示类型、时刻和摘要。时间线上不再展开详情卡片，也不提供筛选。

| --- | --- |

<a id="session_view"></a>
## 会话卡片

会话卡片照着 coding agent 自己的界面显示会话（`UI/Run/SessionParts.swift`，状态由 `Core/SessionView.swift` 从事件读出，事件见[会话中能看到什么](../interfaces/20261031-acp_integration.md#session_view)）：

- 标题栏下是 Agent 的计划清单（`PlanStrip`），已完成的划掉，进行中的用品牌色；全部完成后折叠成一行。
- 思考折叠成一行「思考 · …」，点开看全文；连续的回复片段合成一个气泡；进行中的工具调用显示「进行中」，完成后原地换成结果，改了文件的显示「改了 N 个文件」，点开看改动前后的行（`InlineDiff`，只显示改动和前后各 3 行）。工具输出里工作目录下的路径写成相对路径。
- 标题栏右侧是上下文用量（「上下文 26%」，Agent 不报上下文时显示上一轮的 token 数）。
- 对话按需构建（`ChatScroll`，惰性列表），几千条事件的会话也只构建看得到的行。打开时停在最新处；停在最底部时跟随新内容。往上翻之后，新内容不会把视图拉回底部，底部出现「回到最新」（这期间有新内容时写「有新消息」），点按回到最新并恢复跟随；发送消息，或在底部时切换显示档位，也回到最新。是否跟随由 `ChatFollow` 决定：只有用户自己滚动（`onScrollPhaseChange` 报告的拖动、滑动和滑动后的惯性）才会离开或回到底部；新回复、未构建的行被测量、SwiftUI 调整滚动偏移都不算往上翻，停在底部时继续跟到底。内容在可见区域下方还有多高由 `onScrollGeometryChange` 报告，滚到最新用 `ScrollPosition.scrollTo(edge: .bottom)`，打开时用 `defaultScrollAnchor(.bottom, for: .initialOffset)`。惰性列表还在估算未构建行的高度，macOS 15 上 SwiftUI 测量时还会移动偏移，所以到底之前最多再滚动 8 次；补充的滚动按刚报告的位置滚到具体的偏移（`scrollTo(y:)`），放到下一轮主循环发出，因为位置本来就是「底边」时再要求滚到底边，macOS 15 上视图不会动；仍到不了就停止跟随，显示「回到最新」。每个会话各自保持位置，切到另一个子任务的会话时从最新处开始。
- 输入框上方：开头输入 `/` 时列出 Agent 提供的斜杠命令，最后一个词以 `@` 开头时列出工作区中匹配的文件（`GET /api/runs/{id}/files`），点选补全这个词；`@路径` 随消息作为文件引用交给 Agent。
- 输入框下方左侧是 Agent 提供的模型、推理强度和模式，点开切换，立即对这个会话生效（`control` 操作）；只有一个选项的不显示。
- ⌘. 打断正在进行的一轮。
- 标题栏可以切换显示档位，所有会话共用一个设置，记在本机（`janus.chatDensity`）：只有两档（`ChatDensity`）：「详细」显示每次工具调用，默认是这一档；「摘要」只看对话、你和负责人的消息、请求、冲突和结果，每段工具调用缩成一行「· N 个操作」，Janus 发给 Agent 的提示、状态行和思考也隐藏。

<a id="session_messages"></a>
## 会话中的消息

会话视图（`ChatCard`）按[消息的流转](../interfaces/20261031-events.md#message_flow)显示用户和负责人发给 Agent 的消息：

| 状态 | 显示位置 |
| --- | --- |
| 刚发出（`pending`） | 输入框上方的「待发送」区，标注「发送中」 |
| 排队（`queued`）、留言（`next`），还没送达 | 「待发送」区，标注排队或留言 |
| 插入当前这一轮（`steer`） | 对话中 `message.routed` 的位置，用「插话」框显示，标注「插话 · 已插进这一轮，做完手头这步就会读到」；Agent 读到后（`message.delivered` 带 `applied`）改为「Agent 已读到」，不另显示一条 |
| 作为新一轮（`prompt`） | 对话中 `message.routed` 的位置，普通消息气泡 |
| 排队或留言后送达 | 对话中 `message.delivered` 的位置，即它真正进入会话的时刻 |
| 负责人打断这一轮后送达 | 「待发送」区显示「正在打断这一轮，马上送达」 |

会话中的其他内容：

- Agent 的消息按 Markdown 渲染，支持的语法与文档窗口相同（表格、代码块、引用、嵌套列表等，见[文档查看](#markdown_viewer)）；指向本机文件的绝对路径链接在 Janus 中打开。
- 每次工具调用一行，点开看完整输入和输出。Janus 看板工具按用途显示，例如「提交编排：T1 … → Researcher」「回复 T2：…」；同一次调用返回后替换「等待返回」那一行；Agent 自己上报的同一次看板调用（`mcp.janus.*`）不重复显示。连续超过 4 次工具调用折叠，只露出最后两次。
- 协作者问负责人的问题显示为「问负责人 · 负责人会回答，不需要你处理」。看板推送在负责人会话中显示为「看板推送 · 插入正在进行的这一轮」，点开看内容。两个任务改了同一个文件（`task.conflict`）在双方任务的会话中各显示一行；越界（`data.owned`）写成「越界：T2 改了 T1 负责的 …」，同一批文件已经报告为越界时，「同时在改」那一行不再显示。没通过验收核对、发回会话补充的提示显示为「验证没通过 · 打回修复」。结构化结果在会话中是一行「提交结果」，带通过数和风险数，点开看逐条的 ✓ / ✗、证据方法和完整证据；Agent 回复里只有结构化结果时不再显示空气泡。
- 每次尝试以一行标题开始（任务、尝试编号、Agent、模型），按 `attempt.started` 的 `data.continuation` 和 `data.reopen` 写明它在哪个会话、为什么开始（`SessionView.attemptNote`）：「接上了原会话」「接上原会话」「接着 T1 的会话」「新开会话（原会话上下文超过 75%）」「新开会话（这个子任务之前没有会话）」，以及「按 V1 的意见返工」「T1 返工后复审」。返工和复审回到同一个任务，所以在同一个会话卡片里接着显示，不是新的会话；子任务页执行轨迹里的尝试行也带同样的说明。在 worktree 中的 Run，每次尝试的标题下再写一行 Git 信息（`SessionView.gitNote`，来自 `attempt.started` 的 `data.git`）：「Git 仓库 … · 分支 main（或 detached HEAD）· 提交 abc12345 · worktree …」，执行轨迹的尝试行用它代替工作目录；负责人对话开头的目标分隔线下同样写一行，取 `run.created` 的起点提交和 worktree 路径。上游结果带入会话显示为「上游子任务 T1 的结果已带入本次子任务」，带判定的交接（返工时的验证意见）显示为「独立验证 V1 的意见已带入本次子任务」。负责人派出子任务后又改了文件（`lead.edited`）时，负责人的对话中显示一行警示色的「派出子任务后改了文件：… · 会写进交付风险」。负责人的重试在进展时间线中是一条决定，写明选的会话、依据哪个验证的意见和负责人的说明，返工时标题是「负责人让 T1 返工」。
- Agent 自主执行超过 20 秒没有新输出时，标题旁显示「N 秒没有新输出」，每 5 秒更新，原因写在悬停提示中。Agent 长时间思考或写大段内容时，ACP 不会有任何更新，这行字用来区分「在工作」和「卡住」。
- 输入框按会话状态提供插话、接管、打断、交还托管、以当前结果完成、留言或「发送并继续」，按[发送键](#send_key)发送。
- 目标输入框和会话输入框都可以附图片：⌘V 粘贴截图、浏览器「拷贝图像」或在 Finder 中拷贝的图片文件，把图片拖进来，或点回形针选择文件。剪贴板里同时有文字时（例如表格、富文本）按文字粘贴；只有一段链接时按图片粘贴，因为浏览器「拷贝图像」会把图片地址和图片一起放进剪贴板。剪贴板里只有图片时 ⌘V 也要能用：`ComposerField` 的 `NSTextView` 让「编辑 > 粘贴」在图片剪贴板上保持可用，标准文本框会禁用它，⌘V 就到不了粘贴处理（`paste(_:)`）。图片先显示为输入框上方的缩略图，可以逐张移除，发送时一起提交；超过 3.75 MB 的图片缩到最长边 2048 像素并转为 JPEG（`Attach.prepare`）。输入框是 `NSTextView`（`ComposerField`），因为 SwiftUI 的文本框只能粘贴文字。对话中的用户消息和目标显示图片缩略图，点击用「预览」打开，点名图片的 `[Image N]` 行会隐藏（`Attach.visibleText`）。

<a id="role_permissions"></a>
## 数字员工权限编辑

数字员工编辑器的「权限」区域只显示 Agent 声明的权限类控制项，其余控制项放在「会话选项」。权限选项按 Agent 原生的名字和说明显示，界面不标注「可写」「只读」，数字员工列表和工作区只显示 Agent 自己的权限模式名。Plan 类控制项和取值不显示。角色没有选择时选中连接数据中控制项的 `default`（Codex 是 Full access，Claude Code 是 Bypass permissions），并在该选项旁标注「默认」。只有 Claude Code 和 Codex 的数字员工可以开启「可以担任负责人」。规则见 [Agent、角色与工作区](../domains/20261031-agents_and_roles.md#permission_modes)。

<a id="diff_review"></a>
## diff 审阅

任务的 diff 产物和整个任务的 diff（`run_diff`）在应用内审阅（`UI/DiffReview.swift`，`Core/Diff.swift`），从子任务页的产物、工作台检查器的「改动」和交付物中的 diff（按钮是「审阅」）打开，每个 diff 一个窗口。整个任务的 diff 不属于哪一个协作者，窗口标题是「审阅整个任务的改动」，意见只能交给负责人：

- 左边是文件列表（改动行数；未跟踪的新文件单独标出），右边按文件和代码块显示改动，带改动前后两边的行号。未跟踪的新文件也带着相对 `/dev/null` 的 diff 记录内容，可以直接审阅和写意见；旧 diff 只有文件名时，审阅窗口从工作目录读出当前内容并标注；二进制、空文件或读不到的文件才提示到工作目录查看。
- 悬停在一行上点「+」写审阅意见，可以编辑和删除；底部可以再写一句总体意见。
- 「交给负责人」把所有意见合成一条消息发给负责人，由负责人决定让协作者修改、重做这个任务还是自己处理；「发给 <协作者>」直接发给做这个任务的 Agent，它在会话中时插入这一轮，否则在它下次会话开始时带给它。整个任务的 diff 没有「发给 <协作者>」。消息写明文件、行号、那一行的内容和意见。Run 结束后只能查看，不能发送。

<a id="notifications"></a>
## 系统通知

收件箱里出现新的事项（请求、交来的决定、交付等你验收），而 Janus 不在前台时，发一条系统通知，标题是事项的标题，正文是目标和内容，点击打开对应的 Run（`Core/Notifier.swift`）。应用启动时已经在等的事项不再通知，推迟到「稍后处理」的事项不通知，窗口在前台时也不通知。只有打包后的应用能发通知；从构建目录直接运行的可执行文件没有 bundle ID，不发通知。

<a id="interaction"></a>
## 交互约定

按 Apple 人机界面指南（HIG）统一的做法，新增界面时沿用：

- **菜单栏图标**：Janus 始终在屏幕顶部菜单栏右侧（和时钟、电量同一区域）显示图标（`MenuBarExtra`，`StatusMenu`）。图标上显示等你处理的数量（没有时只显示图标）。图标菜单有收件箱（带数量，点击打开收件箱）、打开 Janus、进行中的 Run 数、新目标、新对话、设置…、检查更新…、打开 Janus 日志和退出 Janus（⌘Q）。
- **Dock 图标跟随窗口**：有 Janus 窗口打开时是普通应用，显示 Dock 图标和下面的菜单；最后一个窗口关闭后隐藏 Dock 图标，只留菜单栏图标，应用不退出（`AppDelegate.followWindows`，监听窗口成为主窗口和关闭）。从图标菜单重新打开窗口后，Dock 图标和菜单恢复。每次启动都打开主窗口：应用忽略 AppKit 保存的窗口状态（`JanusApp.init` 注册 `ApplePersistenceIgnoreState`），否则上次关掉窗口、只留菜单栏图标时退出，下次启动就只有菜单栏图标；窗口的大小和位置由窗口自己的尺寸记录保存，不受影响。
- **菜单**：窗口里的命令在菜单栏都有对应项，不适用时禁用而不隐藏（`JanusCommands`，`App.swift`）。设置是 ⌘,。「文件」有新目标（⌘N）、新对话（⌥⌘N）、新建工作区（⇧⌘N）、打开 Markdown 文件（⌘O）、导出事件日志（⇧⌘E）；「显示」有工作台 / 审计与回放 / 团队与权限（⌘1 / ⌘2 / ⌘3）、返回工作台（⌘[）、刷新（⌘R）和显示 / 隐藏侧栏；「Janus」菜单有检查更新…；「任务」菜单有暂停 / 继续（⇧⌘P）、从中断处继续、停止、删除任务…、复制交付摘要（⇧⌘C）和回到实时。
- **标题旁的操作用图标**：添加、编辑、移除这类跟着标题或某一项的小操作用图标按钮（`IconButton`：「+」、铅笔、×），不写成「新建…」「编辑…」这样的文字链接；悬停提示和读屏说明写完整的文字。侧栏分组标题旁的「+」也是它。页面上的主要操作（「交给负责人」「新建数字员工」）和一排并列的动作（资源的编辑、刷新、删除）仍然用文字按钮。
- **Esc**：运行页先退出回放，再从子任务页或 Agent 页回到工作台。表单 sheet 中 Esc 等于「取消」。
- **停止 Run**：界面上 Run 级的 `cancel` 叫「停止」，状态显示「已停止」，避免和确认框的「取消」按钮混淆；任务级的取消仍叫「已取消」。
- **创建前的提醒**：提交新目标前，应用先读 [创建前的提醒](../interfaces/20261031-http_api.md#run_preflight)（`AppStore.createRun`）；有提醒（Git 仓库里没提交的改动不会带进任务，或非 Git 目录上已有进行中的任务）时弹出「继续执行？」，列出提醒，选「继续」才创建。
- **确认框**：`confirm` 的「取消」按钮响应 Esc。会造成数据丢失的操作（删除、停止 Run）先确认，按钮文字带「…」。删除任务前说明事件记录、子任务、产物和日志会删除且不可恢复，任务单独的副本也会删除、还没提交的改动先存成补丁，用户的工作目录和已经合并回去的结果不受影响，并带「不再提醒」勾选项；勾选后记在本机（`janus.deleteRunNoConfirm`），之后的删除直接执行。表单 sheet 有未保存的修改时，取消或 Esc 先问「放弃未保存的更改？」。
- **不能执行时禁用并说明原因**：目标、回答、消息为空，或表单还有必填项时，提交按钮禁用，悬停提示或旁边的说明写出原因，不在点击后弹出提示。
- **反馈**：底部的提示（`Toast`）只用于确认已完成的操作和报告请求失败，使用系统材质，VoiceOver 会朗读。
- <a id="design_tokens"></a>**颜色与字体**：冷色调，向 Claude 的克制看齐：层次靠底色深浅和细线，不靠彩色面板和阴影；品牌色只用在少数地方。所有颜色都定义了浅色和深色两个值（`UI/Components.swift`）：

  | 名称 | 浅色 | 深色 | 用途 |
  | --- | --- | --- | --- |
  | `Color.page` | `#f3f5f8` | `#1e2227` | 内容区底色 |
  | `Color.card` | `#ffffff` | `#282c34` | 卡片 |
  | `Color.soft` | `#eef1f5` | `#1b1f24` | 输入框、评论框（比卡片深一级的内嵌区域） |
  | `Color.sidebar` | `#e9edf2` | `#21252b` | 侧栏 |
  | `Color.line` | `#e1e6ec` | `#3a3f4a` | 卡片边框、分隔线 |
  | `Color.accent` | `#0757c2` | `#61afef` | 品牌色（信号蓝），也是全局 `.tint`：链接、当前阶段、「现在」、进行中的任务条、任务编号 |
  | `Color.ink` / `Color.onInk` | `#15181d` / 白 | `#e5e9f0` / `#1e2227` | 主按钮（`.buttonStyle(.primary)`）：近黑或近白的底，不用品牌色 |

  深色取 Zed 默认 One Dark 的中性灰和柔和蓝（`#282c34`、`#61afef`），不做蓝黑底和霓虹色。状态色（`Tone`）：绿 `#087049` / `#98c379`，橙 `#8a5800` / `#e5c07b`，红 `#c0283f` / `#ef8089`，紫 `#6a42d6` / `#c678dd`；`blue` 就是品牌色。品牌色和状态色在卡片上都不低于 4.5:1。

  - **标题**：页面和段落标题用系统衬线体（`Font.display`，英文是 New York，中文是宋体），其余文字用系统无衬线体。编号、序号和时间用等宽字体。
  - **卡片**：中性底色加一圈细线。需要注意的卡片（请求、对不上的结果）只把边框换成对应色调，底色不变。卡片里不再套带底色的框，用分隔线分组，例如 Agent 面板、检查器的列表。
  - **状态标签**（`Pill`）：中性的胶囊底，前面一个状态色圆点，文字是正文色，一屏多个标签时不会变成一片彩色。
  - **头像**：纯色圆角块。名字是汉字且头像较小时只显示第一个字。角色没有自己选颜色时是石板灰，负责人是品牌蓝，团队里只有负责人带颜色。
  - **时间线**：完成的尝试是协作者颜色的实心条，进行中的是品牌色虚线框，失败的是红色。
  - **收件箱**：每条事项前有一个中性底的类型图标，图标本身的颜色区分会卡住 Agent 的（红）、可以等的（橙）和等验收的（绿）。

  选中状态（选项、权限模式、Agent 类型）用系统强调色 `Color.accentColor`，并同时显示勾选图标，不只靠颜色区分。
- **指针与辅助功能**：自定义的可点按区域（任务节点、Agent 行、看板卡片、选项）加 `.hoverable()` 悬停反馈；只有图标的按钮用 `Label` 加 `.labelStyle(.iconOnly)` 提供文字标签；隐藏标签的选择器、开关和输入框也要给出标签文字。
- **不提 worktree**：任务和值班在 Git 仓库里用的 worktree，界面上叫「独立副本」「它自己的副本」，不出现 worktree 这个词，也不显示 Janus 目录下副本的路径（服务端的报错和交付摘要同样不写，路径只进日志）；用户关心的是结果在哪个提交、合并回哪个分支。
- **做减法**：没有内容的区域不显示，不放「还没有…」占位文字（进展时间线、交付结果中的交付物 / 证据 / 风险、「待处理」都是这样）。次要信息放进悬停提示、二级页面或页内展开：运行卡片只显示一行摘要和任务进度，负责人、工作区（worktree 中的 Run 另有工作目录和分支）和开始时间在「团队与权限」；用量明细、逐条验收、任务级风险的长列表和进展都默认折叠，一次页内展开即可看到全部内容；Agent 面板每行只显示名字、状态和当前在做的事，角色、运行时、模型和心跳在悬停提示中。
- **折叠控件**：带展开状态的按钮写出「展开 / 收起」文字和 `accessibilityLabel` 的完整名称（例如「展开用量明细」），图标只作辅助；摘要行作为一个元素读出完整数字，子任务行读编号、标题、通过数、方法计数和展开状态，展开后每条标准沿用 `CheckLine` 的朗读文本（通过与否、方法、标准和完整证据）。颜色只作辅助，状态都有文字。
- **验收操作**：放在总结、验收概览和任务级风险之后，交付物和逐条验收之前；不加强制阅读门禁，也不做随滚动固定的操作条。所有子任务行收起时按钮仍可用，旁边的文字写出未通过、任务级风险、子任务风险和对不上的数量，和概览使用同一组数字。
- **窄窗口**：工作台、子任务页和 Agent 页是主栏加侧栏（`AdaptiveColumns`）。窗口放不下侧栏时，侧栏移到主栏下方，主栏不会被挤成一条窄列。窄窗口下摘要行、验收行和标题操作换行显示、不截断，展开体占满主栏宽度、不出现横向滚动；请求卡片的说明文字放在按钮下面。
- **时间的写法**随界面语言变化，例如「今天 20:16」和「Today at 20:16」。日期不是今年时带年份。相对时间、用时和账单日期也采用所选语言，保留本机时区。
- **sheet 尺寸**：编辑器使用最小尺寸和理想尺寸，不写固定高度，窗口较小时也能完整显示。

<a id="send_key"></a>
## 发送键

目标输入框、任务会话和对话的输入框（`Composer`）用同一个发送键，在「设置 › 通用 › 发送消息」中选择，记在本机的 `janus.sendKey`。所有输入框和提示都从同一个 `SendKeySetting.shared` 读取，切换后已经打开的输入框也立即生效：

| 选择 | 发送 | 换行 |
| --- | --- | --- |
| ⌘↩ 发送（默认） | ⌘↩ | ↩ |
| ↩ 发送 | ↩，⌘↩ 也能发送 | ⇧↩（⌥↩、⌃↩ 同样换行） |

小键盘的 Enter 与 ↩ 相同。输入框的占位提示和发送按钮的悬停提示写的是当前的发送键。输入法正在组合时按发送键不发送，见[实现约束](#constraints)。

<a id="constraints"></a>
## 实现约束

- 界面文案通过 `L.text` 读取。简体中文使用 Swift 源字符串，新增或修改源字符串时同步维护 `en.lproj/Localizable.strings`。带插值的资源键使用 Foundation 格式占位符，译文可以按位置调整参数顺序。端口、路径和其他标识符作为字符串传入。
- 视图中的局部状态用 `Local`（`SwiftUI.State` 的别名）声明：新 SDK 中 `@State` 是宏，宏插件只随 Xcode 提供，只装命令行工具时无法编译。别名展开为同一个属性包装器，两种环境都能构建。
- 输入法的组合内容不能当作普通草稿读写：`ComposerField` 在 `hasMarkedText()` 时跳过绑定文本的写回，`textDidChange` 只写已上屏的文字；否则 SwiftUI 的任意重绘都会用旧草稿覆盖正在输入的候选字，表现为吞字。组合期间发送键也不发送：⌘↩ 等组合上屏，单独的 ↩ 交给输入法上屏。
- 带数字插值的界面文字用 `Text(verbatim:)` 或 `String(...)`，否则 SwiftUI 会按地区格式加千位分隔符（`#1,295`）。
- 长列表用惰性容器，只构建看得到的行：会话（`LazyVStack`）、子任务页的执行轨迹（`LazyVStack`）、审计日志（`List`）。每一行的构建不能遍历整份事件，需要的汇总在列表外算一次再传进去。
- 正则表达式用 `regex(_:)`（`Core/Format.swift`）写成 `static let`，只编译一次。视图和逐条事件的处理中不用 `String.range(of:options: .regularExpression)` 或带 `.regularExpression` 的 `replacingOccurrences`：它们每次调用都重新编译。日期格式器同样只创建一次（`L.clock`、`L.dateTime`）。
- `JSON.parse` 把字符串和对象的键复制成原生 UTF-8（`makeContiguousUTF8`）。`JSONSerialization` 返回的是延迟桥接的 NSString，之后的每次切分、比较和取键都要经过 Foundation，长对话的 Markdown 解析因此慢约十倍；复制在后台线程解析时做一次。
- 随全局事件流重读的数据（Run 列表、收件箱）只在内容变化时赋值，否则每次重读都让侧栏和依赖它的页面重绘一次。
- 读取数据的 `.task`、`.onAppear` 不挂在可能为空的容器上：`Group { if … }` 条件不成立时是空视图，不会出现在屏幕上，挂在它上面的 `.task` 不会执行。数据还没读到时也要放一个占位视图（例如高度为 0 的 `Color.clear`），否则「没读到就不显示、不显示就不去读」，列表永远是空的（`WorkspaceHistory`）。
- 本地只用 `UserDefaults` 记住上次打开的工作区（`janus.ws`）、设置浮层打开的面板（`janus.settingsTab`）、界面语言（`janus.language`）、应用外观（`janus.appearance`）、输入框的发送键（`janus.sendKey`）、会话的显示档位（`janus.chatDensity`）、新建对话上次选的数字员工（`janus.chatRole`）、工作台检查器的页签（`janus.inspectorTab`）、删除任务时不再确认的选择（`janus.deleteRunNoConfirm`），以及收件箱的推迟和已处理记录（`janus.inbox.snoozed`、`janus.inbox.settled`）。
- 工作台检查器的页签在打开任务时只选一次：没有手动选择过时按状态选择，无子任务「团队」、有子任务「子任务」，之后本次打开期间不随任务出现自动切换；手动选择后写回 `janus.inspectorTab`，之后打开的任务沿用。用量明细、进展、任务级风险长列表和逐条验收的折叠状态放在 `RunModel`（`usageOpen`、`progressOpen`、`risksOpen`、`taskOpen`），只对当前打开的 Run 有效，不写 `UserDefaults`；回放时按回放位置的数据计算默认展开，只读 Run 的展开和收起与实时一致。
