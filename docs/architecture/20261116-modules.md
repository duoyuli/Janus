# 模块与启动顺序

本文列出编排器每个源码模块的职责，以及进程启动时的执行顺序。组件之间的关系和一次 Run 的数据流见[架构索引](index.md#components)，存储细节见[数据模型与存储](20261031-data_model.md)，应用的源码结构见 [macOS 应用](20261031-frontend.md#source_layout)。

<a id="modules"></a>
## 模块划分

| 文件 | 职责 |
| --- | --- |
| `backend/src/main.rs` | 命令行参数、启动顺序、按固定间隔运行的后台任务（`periodic`） |
| `backend/src/http.rs` | HTTP API 和会话的 MCP 端点：全部路由（`router`）、统一的错误（`ApiError`：状态码加直接显示的中文信息，`App` 返回的 `anyhow::Error` 是 400，`Refused` 按种类是 404、409 或 400）、只给本机应用的内容的判断（`from_local_app`）。处理函数只做 HTTP 和 `App` 之间的转换，按服务对象分在子模块：`setup`（Agent、角色、工作区、适配器）、`library`（资源库）、`runs`（Run、对话、用量、文件）、`streams`（事件流和 MCP） |
| `backend/src/wire.rs` | `wire_enum!`：存储和传输时用固定字符串的枚举，每个值的字符串只写一次，`as_str`、`parse`、`ALL`、`Display` 和 serde 都由它生成 |
| `backend/src/migrations.rs` | 数据升级：数据版本 0 的表、迁移列表和执行、升级前备份、`janus migrate --dry-run` 的预览，见[数据升级](20261031-data_model.md#migrations) |
| `backend/src/data_shape.rs` | 每类存储对象登记的字段和检查，以及 `testdata/data_shape.json` 的快照 |
| `backend/src/config.rs` | Janus home、配置项（环境变量与 `config.toml`）、Janus 日志。配置只在启动时读一次，写进 `App.cfg`（home、监听地址、Node 路径）；其余代码只读 `App.cfg`，所以指向另一个 home 的 `App`（例如测试的）不会碰到用户的 `~/.janus` |
| `backend/src/git_probe.rs` | 只读 Git 查询的共用入口：设置 `GIT_OPTIONAL_LOCKS=0`，不与同一工作目录中 Agent 的 git 操作抢 `index.lock`。和 HEAD 比较用 `git diff-index`，因为 `git diff` 不受这个变量控制，仍会刷新索引 |
| `backend/src/adapters.rs` | `App` 的适配器部分：清单、按需安装、检查更新、升级与回滚。进行中的安装、查到的最新版本和会话占用的版本（`AdapterState`）由 `App` 持有，不是进程级的全局变量 |
| `backend/src/acp.rs` | 基于官方 `agent-client-protocol` SDK 的 ACP 客户端：启动子进程、`initialize`、请求与通知收发、超时 |
| `backend/src/agents.rs` | `App` 的设置部分的公共部分：设置对象的类型名、命令拆分、id 与 slug 等共用函数；子模块如下 |
| `backend/src/agents/catalog.rs` | Agent 类型和登录方式 |
| `backend/src/agents/runtime.rs` | 运行时（`Runtime`：Codex 或 Claude Code）和每个运行时不同的地方：隔离目录和 CLI 路径的变量、登录方式带来的环境变量、环境变量是否可能带凭据、系统层的注入通道（`InstructionChannel`）、Skill 包的目录和加载方式、打开会话的 `_meta`、是否要先信任工作区、是否有可读回的原生会话记录、默认权限模式、本机配置目录。其他代码问 `Runtime`，不自己按运行时分支 |
| `backend/src/agents/connections.rs` | Agent 连接的保存与删除、隔离目录和密钥、会话的启动命令和沙箱环境 |
| `backend/src/agents/environment.rs` | Agent 私有凭据文件的读写、Claude 环境变量的公开和私有值及升级 |
| `backend/src/agents/checks.rs` | 配置检查（适配器、运行时、凭据、会话、试运行）和账号登录 |
| `backend/src/agents/roles.rs` | 角色、角色选择的资源、默认角色的写入和随版本更新（`sync_seeds`）；默认角色读自 `backend/roles/` 中的 Markdown 文件和头像（`ROLE_FILES`，编译时打进二进制）；数字员工的头像（`set_role_avatar`） |
| `backend/src/agents/workspaces.rs` | 工作区和由工作区组成的 Run 团队；角色到成员快照的转换（`role_member`，对话也用它） |
| `backend/src/agents/session_options.rs` | 会话控制项的解析、角色保存的值、Plan 模式不运行的规则 |
| `backend/src/agents/local_config.rs` | 「复制本机配置」：把本机 Agent 的设置复制到隔离目录 |
| `backend/src/library.rs` | `App` 的资源库部分：资源（Skill、MCP 服务器）的类型、新建、编辑、导入、删除和应用读到的列表。子模块 `offers` 扫描本机目录和 Git 来源可导入的资源，`store` 和 `skill` 管理 Skill 内容，`mcp` 管理服务器定义和值，`sources` 管理 Git 来源，`deliver` 生成资源包和会话参数。见[资源库](../domains/20261116-resource_library.md) |
| `backend/src/orchestrator.rs` | `App` 的运行部分的核心：Run、任务和尝试的内存状态，事件的写入与广播，等待者和状态转移；子模块如下 |
| `backend/src/orchestrator/lifecycle.rs` | 创建和驱动 Run：调度循环、停滞检测、交付 |
| `backend/src/orchestrator/lead.rs` | 负责人：目标会话、主会话的对话循环（交付后负责人的对话，以及对话 Run 的会话）、负责人说明和推送进会话的看板消息 |
| `backend/src/orchestrator/chat.rs` | 和一名数字员工的对话：创建对话 Run、它的工作目录和系统层说明，见[对话](../domains/20261120-chats.md) |
| `backend/src/orchestrator/board.rs` | 看板 MCP：负责人和协作者的工具调用、角色统计 |
| `backend/src/orchestrator/mcp_server.rs` | 看板和资源库路由这两个 MCP 服务共用的部分：会话令牌（`session_token`，由 Run 的密钥和 `who` 派生）和 Run 密钥（`random_token`）、会话拿到的服务地址（`session_server`）、按令牌找到 Run（`session_run`）、`initialize` 的回答和 JSON-RPC 的结果与错误 |
| `backend/src/orchestrator/board_tools.rs` | 看板提供和输出的内容：工具定义、编排校验、负责人读到的看板消息 |
| `backend/src/orchestrator/messages.rs` | 用户和负责人发给会话的消息：记录、插入正在进行的一轮或排队 |
| `backend/src/orchestrator/attempts.rs` | 任务的一次尝试：会话、结果核对、改动和产物 |
| `backend/src/orchestrator/turn.rs` | ACP 会话中的一轮提示：把更新转成事件、插话、控制项和 Agent 的请求 |
| `backend/src/orchestrator/session.rs` | 为成员打开 ACP 会话：启动 Agent 并登记会话（`open_session`），会话结束时撤销登记、撤回它等待的决定并停止 Agent（`close_session`），以及会话打开时的参数（`opening`：成员的资源、看板和系统层）和角色要求的控制项。负责人和每个任务的会话用 `SessionKey` 区分，任务 id 可以取任何看板允许的值 |
| `backend/src/orchestrator/prompts.rs` | 发给会话的说明和任务提示，以及结构化结果的解析 |
| `backend/src/orchestrator/actions.rs` | 用户操作、验收归档的交付、重启后的恢复与继续 |
| `backend/src/orchestrator/tests.rs`、`flow_tests.rs`、`flow_tests/` | 编排器的单元测试和端到端流程测试；`flow_tests.rs` 是共用的夹具和任务生命周期的流程，其余按主题分在 `flow_tests/` |
| `backend/src/teamwork.rs` | 编排中的团队结构：任务负责的文件（`owns`）和独立验证（`verifies`）的校验、协作者的认领、谁负责某个文件、协作者提示中的对应段落、负责人说明中「团队怎么组织」一节 |
| `backend/src/goal_settle.rs` | 负责人的 `/goal` 一直不自己结束时：会话安静一段时间后问负责人，确认完成后通过 `_session/goal` 清除目标 |
| `backend/src/acp_view.rs` | ACP 会话中人能看到的部分：把思考、计划、斜杠命令、模式和选项变化、用量、工具调用的 diff 转成事件；会话打开时的选项；消息里 `@路径` 的文件引用；`@` 菜单的文件列表 |
| `backend/src/layout.rs` | Janus home 中每个位置的唯一来源（`Layout`，由 `App.cfg` 持有）：顶层分类 `TOP`、Agent / 资源 / Run 和对话各自的路径与删除时要删的全部路径、沙箱的 `HOME` 和 `TMPDIR`（`Sandbox`）、哪些文件可以经 `/api/file` 读或作为附件发出；子模块 `relocate.rs` 是移动布局的数据升级（`Relocation`、数据版本 14），见[目录规范](../operations/20261031-deployment.md#layout) |
| `backend/src/attachments.rs` | 用户随目标或消息粘贴的图片：按文件头识别类型并保存到 Run 或对话的 `attachments/`（`RunDirs::attachments`），在文字中用 `[Image N] <路径>` 点名，发出提示时在 Agent 支持图片的情况下附上 ACP 图片块，见[图片附件](../domains/20261031-run_lifecycle.md#attachments) |
| `backend/src/evidence.rs` | 验收证据：check 的证据方法、结果核对（`gaps`）、证据汇总（`Summary`）和交付中每个任务的验收记录 |
| `backend/src/usage.rs` | Run 级用量账本：从事件日志实时派生的只读汇总，覆盖 Run、任务、成员、尝试和单个会话；每轮的 token 相加并按模型归集，上下文快照不计入，缺失如实标注，不改调度和交付 |
| `backend/src/bill.rs` | 按时间段的用量账单：跨 Run 按 Agent 和模型汇总区间里的 token 和上报的费用 |
| `backend/src/prices.rs` | 模型价格：每天从 models.dev 同步，每个模型取厂商的 API 价格，给账单估算花费。正在用的价格表（`PriceBook`）由 `App` 持有 |
| `backend/src/traces.rs` | 任务在工作目录里留下的痕迹：每个任务改过的文件和每个文件最后的修改者、diff 产物的范围、结果与痕迹的对账、完成后又被改过的文件 |
| `backend/src/status.rs` | Run 的类型（`RunKind`：目标或对话），Run、任务、尝试和 Agent 阶段的状态枚举；Run 和任务的合法转移集中在 `can_transition_to` |
| `backend/src/db.rs` | SQLite 表结构与读写 |
| `backend/testdata/fake_acp.py` | 测试用的脚本化 ACP Agent |
| `frontend/` | macOS 应用（Swift Package），结构见 [macOS 应用](20261031-frontend.md#source_layout) |

`agents.rs`、`adapters.rs`、`library.rs` 和 `orchestrator` 的各个子模块都在 `impl App` 上添加方法；`App` 结构体定义在 `orchestrator.rs`。

<a id="startup"></a>
## 启动顺序

`main` 按以下顺序执行：

1. 处理命令行参数（`--version`、`--help`、`migrate --dry-run`、`migrate --shape`）。读取配置项：Janus home（`JANUS_HOME`，默认 `~/.janus`，权限设为 `0700`）、监听地址和 Node 路径，见[配置](../interfaces/20261031-configuration.md#settings)。
2. 对 `janus.pid` 加独占锁（`lock_home`）：同一个 Janus home 已有实例在运行时报错退出，见[部署方案](../operations/20261031-deployment.md#single_instance)。拿到锁后清空 `tmp/`：这时还没有进程在用它。
3. 打开 SQLite 并升级到当前数据版本：数据库还在顶层时（数据版本 14 之前的布局）先移到 `data/`（`adopt_db`）；有数据时先备份到 `backups/`，再执行缺少的迁移；数据来自更新的 Janus 时拒绝启动，见[数据升级](20261031-data_model.md#migrations)。顶层有不属于 Janus 的东西时（`Layout::foreign`）写一行日志，不读也不删它们。
4. `recover`：把上次未结束的尝试标记为中断，未结束的 Run 标记为 `interrupted`。
5. `sync_seeds`：第一次启动时写入 7 个默认角色（PMO、通用数字员工、4 个产品上线团队的专职角色和「老友」）；之后把用户没改过的默认职责和指令换成这个版本的文本，改过的保留（删掉的默认角色不会回来），见[默认角色](../domains/20261031-agents_and_roles.md#product_launch_roles)；`reset_stale_checks`：重启前没跑完的配置检查改回「未检查」。
6. 启动三个后台任务：启动 30 秒后检查资源库 Git 来源是否有更新，之后每 6 小时一次（`check_sources`）；启动 45 秒后向 npm 检查已安装的 ACP 适配器有没有新版本，之后每 6 小时一次（`check_adapter_updates`，见[自动检查新版本](20261031-adapters.md#update_check)）；启动 60 秒后同步模型价格，之后每小时检查一次、每天重新下载一次（`sync_prices`）。
7. 注册路由并开始监听（`JANUS_ADDR`）。
