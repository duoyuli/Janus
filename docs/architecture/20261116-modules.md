# 模块与启动顺序

本文列出编排器每个源码模块的职责，以及进程启动时的执行顺序。组件之间的关系和一次 Run 的数据流见[架构索引](index.md#components)，存储细节见[数据模型与存储](20261031-data_model.md)，应用的源码结构见 [macOS 应用](20261031-frontend.md#source_layout)。

<a id="modules"></a>
## 模块划分

| 文件 | 职责 |
| --- | --- |
| `backend/src/main.rs` | 命令行参数、启动顺序、按固定间隔运行的后台任务（`periodic`）；在一切之前先识别隐藏子命令 `run-code-helper`（`coderun::main`） |
| `backend/src/http.rs` | HTTP API 和会话的 MCP 端点：全部路由（`router`）、统一的错误（`ApiError`：状态码加直接显示的中文信息，`App` 返回的 `anyhow::Error` 是 400，`Refused` 按种类是 404、409 或 400）、每个请求先过的鉴权（`devices::guard`，请求来自本机应用还是配对的设备：`Client`；从哪个监听进来：`Via`）和只给本机应用的内容的判断（`from_local_app`、`local_app_only`）。处理函数只做 HTTP 和 `App` 之间的转换，按服务对象分在子模块：`setup`（Agent、角色、工作区、适配器）、`library`（资源库）、`runs`（Run、对话、用量、文件）、`loops`（值班）、`memory`（团队记忆）、`views`（Run 的视图、输入框的建议和收件箱）、`files`（客户端读 Run 的文档、图片、diff 和运行组件日志）、`streams`（事件流和它的实时预览、MCP）、`devices`（配对、设备和手机访问的开关）、`lan`（局域网监听）、`web`（其余路径：编译时嵌进来的 [Web 客户端](20261126-web.md#serving)） |
| `backend/build.rs` | 编译时把 `web/dist` 的文件嵌进二进制（`http/web.rs` 读它生成的 `FILES`）；没有构建时什么也不嵌 |
| `backend/src/events.rs` | 事件类型（`EventKind`）：Janus 写的每种事件都是一个值，代码按种类找事件；日志按文字保存，早先版本写下、这个版本不再写的类型读成 `Unknown`，见[事件](../interfaces/20261031-events.md#event_types) |
| `backend/src/wire.rs` | `wire_enum!`：存储和传输时用固定字符串的枚举，每个值的字符串只写一次，`as_str`、`parse`、`ALL`、`Display` 和 serde 都由它生成 |
| `backend/src/migrations.rs` | 数据升级：数据版本 0 的表、迁移列表和执行、升级前备份、`janus migrate --dry-run` 的预览，见[数据升级](20261031-data_model.md#migrations)。子模块 `steps/` 是各数据版本的 `Custom` 和 `Home` 步骤，按所改的部分分文件（`roles`、`agents`、`library`、`runs`、`settings`），只为把旧数据带到当前的结构而存在；`relocate.rs` 是移动 Janus home 布局的机制（`Relocation`，数据版本 14 用它，启动时先把顶层的数据库移进 `data/` 的 `adopt_db` 也在这里） |
| `backend/src/data_shape.rs` | 每类存储对象登记的字段和检查，以及 `testdata/data_shape.json` 的快照 |
| `backend/src/config.rs` | Janus home、配置项（环境变量与 `config.toml`）、Janus 日志。配置只在启动时读一次，写进 `App.cfg`（home、监听地址、Node 路径）；其余代码只读 `App.cfg`，所以指向另一个 home 的 `App`（例如测试的）不会碰到用户的 `~/.janus` |
| `backend/src/git.rs` | Janus 运行的每个 `git` 的入口，都从 `command` 起步（不继承启动环境里指向别处的变量、不等终端输入、关掉文件系统监视程序）：只读查询（`read_only`、`output`、`scoped_output`、`read`、`query`）设置 `GIT_OPTIONAL_LOCKS=0`，不与同一工作目录中 Agent 的 git 操作抢 `index.lock`，和 HEAD 比较用 `git diff-index`，因为 `git diff` 不受这个变量控制，仍会刷新索引；写入（`write`）关掉仓库的钩子；`fetch` 给资源库的 Git 来源用，带超时 |
| `backend/src/coderun.rs` | MCP 路由代码模式（`run_code`）的脚本运行器：父进程一侧（`run`，起 `janus run-code-helper`、按 JSON 行转发工具调用、限制并发和时间）、带代码的 Skill（`skill_source`）和结果的格式；`coderun/script.rs` 是辅助进程里的 QuickJS 事件循环，`coderun/prelude.js` 在脚本前运行，提供 `tools`、`skills`、`args`、`console`。见 [ADR：MCP 路由的代码模式](../decisions/20261126-run_code.md) |
| `backend/src/text.rs` | 截断文字的唯一规则（按字符数，截掉时加 `…`）：`clip`、`one_line`、`squash`（并成一行，不截）、`cut_at_word`（在词边界截，给 Agent 读的说明用）、`tail`（输出的最后一段）、`first_line`、`short_sha`；时长的文字：粗略的 `span` 和到秒的 `duration`，都按语言写；以及做文件名和 id 用的 `slug` |
| `backend/src/front_matter.rs` | Markdown 开头的 YAML 元数据：Skill 的 `SKILL.md` 和[数字员工文件](../domains/20261031-agents_and_roles.md#role_files)共用的读法（`field`、`body`）和写法（`quote`） |
| `backend/src/util.rs` | 当前时间（`now_ms`）、由时间生成的唯一 id（`new_id`，同一毫秒内也不重复）、展开 `~`、整个写入一个文件（`write_whole`：先写旁边的临时文件再改名） |
| `backend/src/devices.rs` | 配对的浏览器和手机：一次性配对码、设备令牌（只存 SHA-256，`data/secrets/devices/`）、取消配对，以及手机访问的开关（`configs` 的 `lan_access`）；HTTP 一侧的鉴权在 `http/devices.rs` 的 `guard`，局域网监听在 `http/lan.rs`，见[配对的设备](../operations/20261031-security.md#paired_devices) |
| `backend/src/host_env.rs` | 本机环境：每个 Agent 和 MCP 服务器的 HOME 镜像用户的家目录，只挡列出的路径（Agent 自己的设置和用户认为有风险的），列表的保存、默认值和「试运行」，见[本机环境](20261031-frontend.md#host_env) |
| `backend/src/lang.rs` | 给 Agent 的文字用的语言：`Lang`（中文或英文）、两版文字里选一版的 `tr!`，应用语言这项设置的读写（`/api/language`），见[注入的语言](../domains/20261031-goal_mode.md#prompt_language) |
| `backend/src/seats.rs` | 同时开着的 Agent 进程数（座位）：每个 ACP 会话启动前拿一个座位，进程退出时还回；座位满时按用户在等的、时间表启动的、团队协作者的顺序分配 |
| `backend/src/schedule.rs` | 值班的时间表：五段 cron 加时区，按那个时区的墙上时间算下一次 |
| `backend/src/worktrees.rs` | Git 仓库上的 Run 各自的 worktree：创建、重建、移除和修复，交付或验收时把结果带回开始时的分支（`accept`），读出工作区在 Git 中的位置（`Checkout`），见[工作目录](../domains/20261031-run_lifecycle.md#workspace_model) |
| `backend/src/adapters.rs` | `App` 的适配器部分：清单、按需安装、自动升级、固定与回滚。进行中的安装、查到的最新版本和会话占用的版本（`AdapterState`）由 `App` 持有，不是进程级的全局变量 |
| `backend/src/acp.rs` | 基于官方 `agent-client-protocol` SDK 的 ACP 客户端：启动子进程、`initialize`、请求与通知收发、超时 |
| `backend/src/agents.rs` | `App` 的设置部分的公共部分：设置对象的类型名、命令拆分、id 与 slug 等共用函数；子模块如下 |
| `backend/src/agents/catalog.rs` | Agent 类型和登录方式 |
| `backend/src/agents/runtime.rs` | 运行时（`Runtime`：Codex 或 Claude Code）和每个运行时不同的地方：隔离目录和 CLI 路径的变量、登录方式带来的环境变量、环境变量是否可能带凭据、系统层的注入通道（`InstructionChannel`）、Skill 包的目录和加载方式、打开会话的 `_meta`、是否要先信任工作区、是否有可读回的原生会话记录、默认权限模式、本机配置目录。其他代码问 `Runtime`，不自己按运行时分支 |
| `backend/src/agents/connections.rs` | Agent 连接的保存与删除、隔离目录和密钥、会话的启动命令和沙箱环境 |
| `backend/src/agents/environment.rs` | Agent 私有凭据文件的读写、Claude 环境变量的公开和私有值及升级 |
| `backend/src/agents/checks.rs` | 配置检查（适配器、运行时、凭据、会话、试运行）和账号登录 |
| `backend/src/agents/roles.rs` | 角色（`Role`，编辑器送来的是 `RoleInput`）、默认角色的写入和随版本更新（`sync_seeds`）；默认角色读自 `backend/roles/` 中的 Markdown 文件和头像（`ROLE_FILES`，编译时打进二进制）；数字员工的头像（`set_role_avatar`） |
| `backend/src/agents/role_files.rs` | 数字员工文件（`RoleFile`）的读写和核对、导出（`role_file`），按核对过的内容新建数字员工（`make_roles`，对话的提议用），以及整组改名和改用 Agent（`rename_role_group`、`bind_role_group`），见[分组](../domains/20261031-agents_and_roles.md#role_groups) |
| `backend/src/agents/workspaces.rs` | 工作区（`Workspace`，编辑器送来的是 `WorkspaceInput`）和由工作区组成的 Run 团队，删除工作区连同它的值班和团队记忆；角色到成员快照的转换（`role_member`，对话也用它） |
| `backend/src/agents/session_options.rs` | 会话控制项的解析、角色保存的值、Plan 模式不运行的规则 |
| `backend/src/agents/local_config.rs` | 「复制本机配置」：把本机 Agent 的设置复制到隔离目录 |
| `backend/src/library.rs` | `App` 的资源库部分：资源（Skill、MCP 服务器）的类型、新建、编辑、导入、删除和应用读到的列表。子模块 `offers` 扫描本机目录和 Git 来源可导入的资源，`store` 和 `skill` 管理 Skill 内容，`mcp` 管理服务器定义和值，`sources` 管理 Git 来源，`deliver` 生成资源包和会话参数，`skill_router` 生成唯一交给 Agent 的 `janus-skills` 和它的目录，`quality` 给出 Skill 描述好不好找的提示。见[资源库](../domains/20261116-resource_library.md) |
| `backend/src/orchestrator.rs` | `App` 的运行部分的核心：Run、任务和尝试的内存状态，事件的写入与广播，给应用全局事件流的变化（`Change`：Run 的状态、值班、团队记忆、Agent 改了资源库，一条广播），各自只让一种改动同时发生的锁（`Gates`），等待者和状态转移；子模块如下 |
| `backend/src/orchestrator/merge.rs` | 把 worktree 里的结果带回用户的分支：每次交付时（`run.merged`），以及验收一次没能带回的交付时（`risk.accepted`）；记下这次留下的提交，下一次从它开始 |
| `backend/src/orchestrator/parking.rs` | 闲置的会话关掉 Agent 进程、还回座位（`session.parked`）：过了 `idle_after`，或有人在等座位时最闲的先关；下一条消息或醒来重新打开 |
| `backend/src/orchestrator/mcp_router.rs` | 资源库的 MCP 路由（`janus-tools`）：每个 Run 一个端点，按成员快照提供资源库的 MCP 服务器，只给 Agent `find_tools`、`call_tool`、`run_code`；第一次调用时启动或连接，同一个 Run 共用一个进程。`mcp_router/say.rs` 写 `instructions`，`find.rs` 找工具，`code.rs` 是代码模式 |
| `backend/src/orchestrator/mcp_client.rs` | MCP 路由连到一个资源库服务器的连接，不管传输方式（stdio 命令、Streamable HTTP、旧的 SSE）：回答服务器自己的请求，停止等待的请求在服务器上取消 |
| `backend/src/orchestrator/memory.rs` | 工作区的团队记忆：笔记的读写规则和 `recall`、`remember`、`forget` 工具、注入会话系统层的那一节、交付后自动开始和手动开始的整理（`kind` 为 `dream` 的 Run），见[团队记忆](../domains/20261123-team_memory.md) |
| `backend/src/orchestrator/loops.rs` | 工作区值班：设置、时钟（开工与摸鱼）、开工的提示、系统层和值班的 MCP 工具，见[工作区值班](../domains/20261121-loops.md) |
| `backend/src/orchestrator/queue.rs` | 派发队列：创建目标 Run、按槽位补位、开始时准备 worktree 和快照，见[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue) |
| `backend/src/orchestrator/lifecycle.rs` | 驱动 Run：调度循环、停滞检测、交付、删除 |
| `backend/src/orchestrator/lead.rs` | 负责人：目标会话（`lead_goal`）、负责人说明（`goal_brief`）、推送进会话的看板消息，交付之后的一轮怎样收尾，以及记下系统层和发出的提示（`record_system`、`record_session_prompt`） |
| `backend/src/orchestrator/conversation.rs` | Run 的主会话作为对话：对话、值班的会话、整理团队记忆和交付后负责人的对话（`lead_conversation`），打开时能加载旧会话就加载（`open_conversation`），之后一轮一轮接用户的消息；和目标会话共用开会话后的准备、每一轮和收尾（`main_session_ready`、`main_turn`、`end_main_session`） |
| `backend/src/orchestrator/resume.rs` | 负责人在重启或会话中断后回到目标：子任务各在哪里（`board_on_resume`）、什么打断了它，新会话写进说明，加载回原会话时写进下一条提示 |
| `backend/src/orchestrator/report.rs` | 负责人一轮的报告：按说明要求的标题把最后一条回复拆成结论、需要你决定和共享资料建议（`LeadReport`），以及之后的会话读到的交付文字 |
| `backend/src/orchestrator/chat.rs` | 和一名数字员工的对话：创建对话 Run、它的工作目录和系统层说明，见[对话](../domains/20261120-chats.md) |
| `backend/src/orchestrator/board.rs` | `janus` MCP 服务：调用者（`Caller`：负责人、协作者、值班、整理记忆、对话里的招聘顾问）决定的说明、工具列表，工具调用的记录和分派 |
| `backend/src/orchestrator/lead_tools.rs` | 负责人的看板工具：编排、`wait`、回答、返工（`retry`）、修订或接受结果（`amend`）、取消、交给用户决定（`ask_user`），以及被验证任务有新结果后的自动复审 |
| `backend/src/orchestrator/board_views.rs` | 看板给会话看的内容：一个子任务的全部信息（`board` 带 `task`）和协作者眼里的其他子任务（`board`） |
| `backend/src/orchestrator/stats.rs` | 角色统计（`role_stats`）：最近的 Run 里每个角色的任务完成、一次通过、验证没通过的次数和用时 |
| `backend/src/orchestrator/hand_in.rs` | 协作者的看板工具：交结果（`janus.submit`，交来时就核对，不合格的同一轮退回）、给负责人的提问（`janus.ask`，`Question`，可附拆分提议）、写进展（`board_post`）；交的东西在这一轮结束时由尝试取走 |
| `backend/src/orchestrator/views.rs` | 一个 Run 的视图（`App::run_view`，回放时按事件前缀重算）和跨 Run 的收件箱（`App::inbox`：挑出需要关注的 Run，读它们的视图，按用户的推迟和忽略分好），以及推迟、忽略的记录（`App::mark_inbox`） |
| `backend/src/orchestrator/live.rs` | 实时预览（`Live`）：Agent 正在写、正在想、正在跑的内容，在成为事件之前随 Run 的事件流（`event: live`）送给应用；不存储，事件仍是记录 |
| `backend/src/orchestrator/mcp_server.rs` | 看板和资源库路由这两个 MCP 服务共用的部分：会话令牌（`session_token`，由 Run 的密钥和会话的席位 `SessionKey` 派生）和 Run 密钥（`random_token`）、会话拿到的服务地址（`session_server`）、按令牌找到 Run（`session_run`）、`initialize` 的回答和 JSON-RPC 的结果与错误 |
| `backend/src/orchestrator/board_tools.rs` | 看板提供和输出的内容：负责人和协作者的工具（`LeadTool`、`MemberTool`，名字和定义在同一个枚举上）、编排校验、负责人读到的看板消息 |
| `backend/src/orchestrator/messages.rs` | 用户和负责人发给会话的消息：记录、插入正在进行的一轮或排队 |
| `backend/src/orchestrator/attempts.rs` | 任务的一次尝试：会话、结果核对、改动和产物 |
| `backend/src/orchestrator/turn.rs` | ACP 会话中的一轮提示：把更新转成事件、插话、控制项和 Agent 的请求 |
| `backend/src/orchestrator/records.rs` | 一轮提示进行时每 20 秒、结束时再一次读这个会话的会话记录（`agent_records`），记为 `session.usage`；读取位置在会话的多轮之间保留在 Run 的内存里 |
| `backend/src/orchestrator/session.rs` | 为成员打开 ACP 会话：启动 Agent 并登记会话（`open_session`），会话结束时撤销登记、撤回它等待的决定并停止 Agent（`close_session`），以及会话打开时的参数（`opening`：成员的资源、看板和系统层）和角色要求的控制项。负责人和每个任务的会话用 `SessionKey` 区分，任务 id 可以取任何看板允许的值 |
| `backend/src/orchestrator/prompts.rs` | 发给会话的说明和任务提示，以及结构化结果的解析 |
| `backend/src/orchestrator/actions.rs` | 用户操作、验收归档的交付、重启后的恢复与继续 |
| `backend/src/orchestrator/tests.rs`、`flow_tests.rs`、`flow_tests/`、`testkit.rs` | 编排器的单元测试和端到端流程测试，`testkit.rs` 是各模块测试共用的 `test_app`（新的 Janus home 加上替身适配器）；`flow_tests.rs` 是共用的夹具和任务生命周期的流程，其余按主题分在 `flow_tests/` |
| `backend/src/teamwork.rs` | 编排中的团队结构：任务负责的文件（`owns`）和独立验证（`verifies`）的校验、谁负责某个文件、`amend` 不能改验证任务（`amend_refused`）、协作者提示中的对应段落、负责人说明中「团队怎么组织」一节 |
| `backend/src/goal_settle.rs` | 负责人的 `/goal` 一直不自己结束时：会话安静一段时间后问负责人，确认完成后通过 `_session/goal` 清除目标 |

<a id="startup"></a>
## 启动顺序

`main` 按以下顺序执行：

1. 处理命令行参数（`--version`、`--help`、`migrate --dry-run`、`migrate --shape`）。读取配置项：Janus home（`JANUS_HOME`，默认 `~/.janus`，权限设为 `0700`）、监听地址和 Node 路径，见[配置](../interfaces/20261031-configuration.md#settings)。
2. 对 `janus.pid` 加独占锁（`lock_home`）：同一个 Janus home 已有实例在运行时报错退出，见[部署方案](../operations/20261031-deployment.md#single_instance)。拿到锁后清空 `tmp/`：这时还没有进程在用它。
3. 打开 SQLite 并升级到当前数据版本：数据库还在顶层时（数据版本 14 之前的布局）先移到 `data/`（`adopt_db`）；有数据时先备份到 `backups/`，再执行缺少的迁移；数据来自更新的 Janus 时拒绝启动，见[数据升级](20261031-data_model.md#migrations)。顶层有不属于 Janus 的东西时（`Layout::foreign`）写一行日志，不读也不删它们。
4. `recover`：把上次未结束的尝试标记为中断，未结束的 Run 标记为 `interrupted`。
5. `sync_seeds`：第一次启动时写入 7 个默认角色（产品研发组的 PMO 和 4 个专职角色，对话组的「老友」和「招聘顾问」）；之后把用户没改过的默认职责和指令换成这个版本的文本，改过的保留（删掉的默认角色不会回来），见[默认角色](../domains/20261031-agents_and_roles.md#product_launch_roles)；`reset_stale_checks`：重启前没跑完的配置检查改回「未检查」。
6. 启动三个后台任务：启动 30 秒后检查资源库 Git 来源是否有更新，之后每 6 小时一次（`check_sources`）；启动 45 秒后向 npm 检查已安装的 ACP 适配器有没有新版本并自动安装，之后每 6 小时一次（`check_adapter_updates`，见[自动检查与升级](20261031-adapters.md#update_check)）；启动 60 秒后同步模型价格，之后每小时检查一次、每天重新下载一次（`sync_prices`）。
7. 注册路由并开始监听（`JANUS_ADDR`）；打开了手机访问时，再在所有接口的同一端口上监听一份（`http::lan::apply`），见[网络暴露](../operations/20261031-security.md#network_exposure)。
