# ACP 适配器管理

本文说明 ACP 适配器怎样按需下载、在磁盘上怎样存放、怎样升级和回滚，以及会话怎样找到要用的版本。Janus 怎样通过适配器和 Agent 通信见 [ACP 集成](../interfaces/20261031-acp_integration.md)，部署时的目录规范见[部署方案](../operations/20261031-deployment.md#layout)。实现在 `backend/src/adapters.rs`。

<a id="catalog"></a>
## 适配器清单

每个内置运行时通过一个发布在 npm 上的 ACP 适配器接入。清单写在代码里（`ADAPTERS`）：

| id | 用于 | 来源 | 版本号 |
| --- | --- | --- | --- |
| `codex` | Codex | npm `@agentclientprotocol/codex-acp` | 包版本，例如 `2.6.0` |
| `claude` | Claude Code（包括通过环境变量指向其他厂商 Anthropic 兼容接口的） | npm `@agentclientprotocol/claude-agent-acp` | 例如 `0.107.0` |

每个 Agent 都通过适配器启动，Agent 和适配器的对应关系由连接的基础运行时（`base`）决定（`for_base`）。新增内置运行时要在 `backend/src/adapters.rs` 的 `ADAPTERS` 中登记它的适配器，`spec_for` 通过 `for_base` 找到它。

Codex 和 Claude Code 的适配器自带对应的 CLI，用户不需要另外安装。Grok 和 Pi 已不再支持，见 [ADR：内置运行时只保留 Codex 和 Claude Code](../decisions/20261116-codex_and_claude_only.md)。

插话使用官方约定的 `_session/steering` 扩展，见 [ACP 集成](../interfaces/20261031-acp_integration.md#steering)。

<a id="layout"></a>
## 存放方式

```text
~/.janus/cache/adapters/<id>/
├── <version>/                    # 一个已安装的版本
│   ├── .janus-adapter.json       # id、版本、npm 包、安装时间
│   └── node_modules/…            # 适配器包和它的依赖
├── <previous-version>/           # 上一个版本，用于切回
├── pinned                        # 用户固定的版本号（内容就是版本号，没有这个文件就跟随最新）
└── current -> <version>          # 当前版本，相对符号链接
```

- 只有带 `.janus-adapter.json` 的目录才算已安装的版本。
- 适配器的入口文件从包的 `package.json` 的 `bin` 字段读取，不写死路径（`entry_in`）。
- 用户在界面上切回的版本写在 `pinned` 里，自动升级不再动它；恢复自动更新时删除这个文件。它属于可以重新生成的 `cache/`，但固定状态跨服务重启保留（`Layout::adapter_pin`）。
- 适配器在 `cache/` 中：可以重新下载，停止 Janus 后删掉它，下次用到时重新安装（失去切回用的旧版本和固定状态）。
- 安装和升级的完整输出追加到 `~/.janus/logs/adapters/<id>.log`。

<a id="on_demand"></a>
## 按需安装

适配器在第一次被需要时安装：

1. 在「设置 › 数字员工」检查某个 Agent 时，第一步「运行组件」调用 `ensure_adapter`。已安装就直接通过；没有安装就当场安装最新版本，安装完成后继续后面的检查。
2. 也可以在 Agent 卡片的运行组件一行手动安装。
3. 创建 Run 或启动会话时如果适配器不存在，直接报错，提示去运行配置检查。会话不会在运行中途触发下载。

<a id="install_steps"></a>
## 安装步骤

安装在临时目录 `<id>/.staging-<时间>` 中进行：

1. 检查 Node 版本（至少 22.19）。
2. 写一个空的 `package.json`，执行 `npm install --omit=dev --ignore-scripts --no-audit --no-fund <包>@<版本，默认 latest>`。生命周期脚本被禁用，安装和升级不执行包自带的脚本。
3. 版本号取实际安装的包版本，确认入口文件存在。
4. 写入 `.janus-adapter.json`（含包名），把临时目录改名为 `<version>`。同一版本的包已经装过时，保留原来的副本，丢弃这次的。
5. 原子地切换 `current`：先建一个新链接，再改名覆盖旧链接（`switch_current`）。
6. 清理：保留当前版本和切换前的版本，删除更老的版本和残留的临时目录（`prune`）。

任何一步失败都会删除临时目录，`current` 保持不变，正在用的版本不受影响。同一个适配器同一时间只有一个安装或检查在进行。

<a id="upgrade_rollback"></a>
## 自动升级、固定与回滚

| 操作 | 行为 |
| --- | --- |
| 自动升级 | 定时检查发现比当前新的版本时，后台安装并设为当前版本（`job.action` 是 `auto`），不需要用户操作 |
| 切回 | 把 `current` 指向另一个已安装的版本，并把该版本记为固定的版本 |
| 恢复自动更新 | 解除固定；最新版已经装过就直接切过去，没装过才下载 |

界面上只有每个 Agent 卡片底部的运行组件一行（`AdapterLine`）：当前版本和一个灰色的「切回历史版本」菜单。没有手动检查更新的入口，接口见 [HTTP API](../interfaces/20261031-http_api.md#adapters)。安装接口可以指定版本。

<a id="update_check"></a>
### 自动检查与升级

适配器会不时发布新版本，Janus 自动检查并安装，不询问用户：

- **服务端**：启动 45 秒后检查一次，之后每 6 小时一次（`check_adapter_updates`，`backend/src/adapters.rs`）。只检查已安装、没有任务在跑、没有被固定的适配器。每个适配器执行一次 `npm view <包> version`，结果记为 `latest` 和 `checkedAt`；查到比当前版本新的版本时，按[安装步骤](#install_steps)在后台安装并切换，`job` 记为 `action: auto`。安装失败只写日志和 job 的 `error`，当前版本不变、Agent 照常可用，下一次检查还会重试。查询失败（离线、没有 npm）只记进 Janus 日志，不产生 job。
- **固定**：用户在界面上切回的版本记在 `cache/adapters/<id>/pinned`。固定期间检查照常进行，只更新 `latest`，不安装、不切换；服务重启后仍按这个文件保持固定。清理（`prune`）不删固定的版本，菜单随时可以切回它。
- **恢复自动更新**：手动 `install` 先解除固定。最新版已经装过时直接切过去，不重新下载；没装过才下载。之后又按最新版本自动升级。
- **是否有新版本**（`updateAvailable`）：npm 上的版本按点分数字比当前版本新时才算，忽略预发布后缀；手动装了比 npm 更新的版本，或两者相同，都不算。切回旧版本后，npm 上的版本比它新，算有新版本（但固定期间不安装）。
- **自动升级保留旧版本**：切换前的版本留在磁盘上，供「切回历史版本」使用，之后的清理也会保留它和固定版本。
- **应用**：打开「设置 › 数字员工」时读一次 `GET /api/adapters`；这一页显示期间每 2.5 秒再读一次（`AppStore.watchAdapters`，页面或设置关闭即停止），所以服务端在后台自动升级时，页面不必等重新打开或 `reload` 就能显示「更新中…」和「已自动更新」。这种刷新只跟着这一页，不随 Agent 数量增长，其他页面不轮询。有任务在跑时另有一个 1.5 秒的轮询直到结束，用于收尾提示。自动升级进行中只显示「更新中…」；完成不弹 Toast 和通知；失败时行内显示「更新没成功」和原因入口，弹层里是服务端措辞的原因和 Janus 自己记录的最近步骤（`job.detail` 与 `log` 中以 `==` 开头的行），安装工具的命令行和输出只在「查看日志」打开的完整日志里，不出现在界面上。侧栏、收件箱、通知和菜单栏都没有适配器提醒。升级只影响之后启动的会话，见[正在运行的会话](#running_sessions)。

<a id="running_sessions"></a>
## 正在运行的会话

启动会话时，`adapter_entry` 把 `current` 解析成具体的版本目录，再从那里启动适配器进程。所以：

- 升级或切换版本只影响之后启动的会话，正在运行的会话继续用启动时的版本。
- 升级后保留当前和上一个版本，更老的版本被清理（`prune`）；但还有会话在用的版本不会被清理，无论它有多老。每个会话从 `adapter_entry` 拿到一个 `VersionPin`，随 `RuntimeSpec` 交给连接（`AcpConn`），会话结束、连接释放后这个版本才可以在下一次清理时删除。

<a id="api_shape"></a>
## 状态数据

`GET /api/adapters` 为每个适配器返回：`current`（当前版本）、`versions`（已安装的版本及安装时间）、`pinned`（当前版本是用户切回的、自动升级暂停）、`latest` 和 `checkedAt`（上次检查的结果）、`updateAvailable`、`job`（进行中或上一次安装的状态和结果）、`log`（安装和升级日志的最后 15 行，含安装工具的输出，供「查看日志」和排查用；界面只把其中 `==` 开头的 Janus 自己的步骤放进失败弹层的「最近日志」）。`job.action` 对自动升级是 `auto`，对用户手动的安装和恢复自动更新是 `install`；`job.state` 是 `running`、`ok` 或 `error`，`started` 和 `ended` 是毫秒时间。任务只在内存中，进程重启后没有遗留的「进行中」；固定状态不在这里，它来自 `pinned` 文件。安装和升级在后台线程中执行；应用在「设置 › 数字员工」页显示期间每 2.5 秒重读这份数据，有任务进行时另有每 1.5 秒一次的收尾轮询。
