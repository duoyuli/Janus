# ACP 适配器管理

本文说明 ACP 适配器怎样按需下载、在磁盘上怎样存放、怎样升级和回滚，以及会话怎样找到要用的版本。Janus 怎样通过适配器和 Agent 通信见 [ACP 集成](../interfaces/20261031-acp_integration.md)，部署时的目录规范见[部署方案](../operations/20261031-deployment.md#layout)。实现在 `backend/src/adapters.rs`。

<a id="catalog"></a>
## 适配器清单

每个内置运行时通过一个发布在 npm 上的 ACP 适配器接入。清单写在代码里（`ADAPTERS`）：

| id | 用于 | 来源 | 版本号 |
| --- | --- | --- | --- |
| `codex` | Codex | npm `@agentclientprotocol/codex-acp` | 包版本，例如 `2.6.0` |
| `claude` | Claude Code（包括通过环境变量指向其他厂商 Anthropic 兼容接口的） | npm `@agentclientprotocol/claude-agent-acp` | 例如 `0.107.0` |

每个 Agent 都通过适配器启动，Agent 和适配器的对应关系由连接的基础运行时（`base`）决定（`for_base`）。新增内置运行时要在 `backend/src/adapters.rs` 的 `ADAPTERS` 中登记它的适配器，`spec_for` 通过 `for_base` 找到它。

Codex 和 Claude Code 的适配器自带对应的 CLI，用户不需要另外安装。Grok 和 Pi 已不再支持，见 [ADR：内置运行时只保留 Codex 和 Claude Code](../decisions/20261116-codex_and_claude_only.md)。

插话使用官方约定的 `_session/steering` 扩展，见 [ACP 集成](../interfaces/20261031-acp_integration.md#steering)。

<a id="layout"></a>
## 存放方式

```text
~/.janus/adapters/<id>/
├── <version>/                    # 一个已安装的版本
│   ├── .janus-adapter.json       # id、版本、npm 包、安装时间
│   └── node_modules/…            # 适配器包和它的依赖
├── <previous-version>/           # 上一个版本，用于回滚
└── current -> <version>          # 当前版本，相对符号链接
```

- 只有带 `.janus-adapter.json` 的目录才算已安装的版本。
- 适配器的入口文件从包的 `package.json` 的 `bin` 字段读取，不写死路径（`entry_in`）。
- 安装和升级的完整输出追加到 `~/.janus/logs/adapters/<id>.log`。

<a id="on_demand"></a>
## 按需安装

适配器在第一次被需要时安装：

1. 在「设置 → 数字员工」检查某个 Agent 时，第一步「ACP 适配器」调用 `ensure_adapter`。已安装就直接通过；没有安装就当场安装最新版本，安装完成后继续后面的检查。
2. 也可以在 Agent 卡片的适配器一行手动安装。
3. 创建 Run 或启动会话时如果适配器不存在，直接报错，提示去运行配置检查。会话不会在运行中途触发下载。

<a id="install_steps"></a>
## 安装步骤

安装在临时目录 `<id>/.staging-<时间>` 中进行：

1. 检查 Node 版本（至少 22.19）。
2. 写一个空的 `package.json`，执行 `npm install --omit=dev --ignore-scripts --no-audit --no-fund <包>@<版本，默认 latest>`。生命周期脚本被禁用，安装和升级不执行包自带的脚本。
3. 版本号取实际安装的包版本，确认入口文件存在。
4. 写入 `.janus-adapter.json`（含包名），把临时目录改名为 `<version>`。同一版本的包已经装过时，保留原来的副本，丢弃这次的。
5. 原子地切换 `current`：先建一个新链接，再改名覆盖旧链接（`switch_current`）。
6. 清理：保留当前版本和切换前的版本，删除更老的版本和残留的临时目录（`prune`）。

任何一步失败都会删除临时目录，`current` 保持不变，正在用的版本不受影响。同一个适配器同一时间只有一个安装或检查在进行。

<a id="upgrade_rollback"></a>
## 检查更新、升级与回滚

| 操作 | 行为 |
| --- | --- |
| 检查更新 | 执行 `npm view <包> version`。结果保存在内存中，应用显示「有新版本」。服务也会定时自动检查，见[自动检查新版本](#update_check) |
| 升级 | 按[安装步骤](#install_steps)安装最新版本并设为当前版本 |
| 切回 | 把 `current` 指向另一个已安装的版本，不需要下载 |

应用在每个 Agent 卡片的适配器一行（`AdapterLine`）提供这三个操作，接口见 [HTTP API](../interfaces/20261031-http_api.md#adapters)。安装接口可以指定版本。

<a id="update_check"></a>
### 自动检查新版本

适配器会不时发布新版本，Janus 自动检查，提醒用户升级，但不自动安装：

- **服务端**：启动 45 秒后检查一次，之后每 6 小时一次（`check_adapter_updates`，`backend/src/adapters.rs`）。只检查已安装的适配器，正在安装的跳过。每个适配器执行一次 `npm view <包> version`，结果和手动检查一样记为 `latest` 和 `checkedAt`。自动检查不写适配器的 `job`：查不到（离线、没有 npm）只记进 Janus 日志，卡片上不出现没人要求的失败。
- **是否有新版本**（`updateAvailable`）：npm 上的版本按点分数字比当前版本新时才算，忽略预发布后缀；手动装了比 npm 更新的版本，或两者相同，都不算。切回旧版本后，npm 上的版本比它新，算有新版本。
- **应用**：启动时、启动 90 秒后（服务的第一次检查已经结束）和之后每 10 分钟读一次 `GET /api/adapters`，菜单「刷新」（⌘R）也会读。有可以升级且没有在安装的适配器时，侧栏底部显示「N 个 ACP 适配器有新版本」（`AdapterUpdatesBadge`），悬停写出每个适配器的当前版本和新版本，点按打开设置的「数字员工」页，在对应 Agent 卡片的适配器一行「升级到 …」。升级只影响之后启动的会话，见[正在运行的会话](#running_sessions)。

<a id="running_sessions"></a>
## 正在运行的会话

启动会话时，`adapter_entry` 把 `current` 解析成具体的版本目录，再从那里启动适配器进程。所以：

- 升级或切换版本只影响之后启动的会话，正在运行的会话继续用启动时的版本。
- 升级后保留当前和上一个版本，更老的版本被清理（`prune`）；但还有会话在用的版本不会被清理，无论它有多老。每个会话从 `adapter_entry` 拿到一个 `VersionPin`，随 `RuntimeSpec` 交给连接（`AcpConn`），会话结束、连接释放后这个版本才可以在下一次清理时删除。

<a id="api_shape"></a>
## 状态数据

`GET /api/adapters` 为每个适配器返回：`current`（当前版本）、`versions`（已安装的版本及安装时间）、`latest` 和 `checkedAt`（上次检查的结果）、`updateAvailable`、`job`（进行中或上一次手动安装、检查的状态和结果）、`log`（安装日志的最后 15 行）。`job.state` 是 `running`、`ok` 或 `error`；任务只在内存中，进程重启后没有遗留的「进行中」。安装和检查在后台线程中执行，应用在有任务进行时每 1.5 秒刷新一次。
