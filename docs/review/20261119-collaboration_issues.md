## 结论摘要

- 上一轮[多 Agent 协作改造方案](20261118-collaboration_improvement_plan.md)的 13 项里，C-01 至 C-03、C-05 至 C-13 已落地；C-04（负责人看到协作者的资源）没有采纳，2026-11-18.2 起负责人只按名字和职责了解协作者。MA-01 至 MA-07 也基本落地。本文不重复这些已完成项。
- 当前最清楚的问题是**信号质量**：停滞检测把正常的连续编辑误报为原地打转；看板把信息性事件也当成需要负责人立即处理的唤醒；跨模型验证的指引与团队可见性互相矛盾。这三项不改产品范围，先处理收益最直接。
- 第二层是**协作成本与质量**：局部修订没有局部复验，验证覆盖和协作开销没有可观察指标，负责人承担了约四成的 token 开销。
- 第三层是**结构性能力**：团队仍是 Run 创建时的固定快照，负责人看不到协作者的能力和资源，没有可复用编排模板，同一个工作目录上的多个 Run 之间没有协调。这些需要产品决策和独立 PRD/ADR，不是这一轮能顺手改掉的。
- 基线数据：5 个已结束 Run 共 120 次带回消息的 `wait`，其中 37 次只有「开始」；26 条 `task.stalled` 全部是同一文件的连续 `Edit`；负责人 token 占 5 个 Run 总量的 43%（142.2M / 331.9M）。这些数字是基线，不是当前实现的验收值。

## 3. 已确认的机制问题

### CO-01 停滞检测把正常的连续编辑误报为原地打转

**结论（F）**：当前的循环指纹只用工具类型、标题和 `summarize_input` 的结果。对 `edit` 类工具，`summarize_input` 只取 `path` 或 `file_path`（`backend/src/orchestrator/turn.rs:962-978`），不看这次编辑改了什么；`watch_call` 再用 `kind + title + input` 做哈希（`backend/src/orchestrator/lifecycle.rs:381-385`）。因此同一个文件连续编辑多次时，即使每次内容完全不同，也会在连续 5 次后写 `task.stalled`（`reason: loop`）。

**证据**：

- 5 个已结束 Run 共 26 条 `task.stalled`，全部是 `reason: loop`、全部是 `Edit` 同一个文件；这批数据中没有一例是周期 2 或 3（数据早于 C-05 的交替检测）。典型例子是 `rmwljgnif` 的 seq 1527、2835、2891、2979、3031、3755，以及 `rmwkfyupn` 的 11 条同类事件。
- 抽查这些连续编辑的 `tool.call` 数据，内容确实在变化：`rmwljgnif` 的 seq 1496、1504、1518、1526 是同一个文件的连续编辑，diff 长度分别为 7,079、4,828、6,057、4,928 个字符；`rmwkfyupn` 的 seq 1877、1887 的 diff 长度分别为 260、339；`rmwkncv09` 的 seq 2874 至 2887 的 diff 长度分别为 585、103、281、371、243。这些任务后来都继续推进并完成（其中 `perf-analysis` 经过一次重试）。
- C-05 新增的周期 2、3 检测同样只看调用，不看调用结果。正常的「编辑 → 跑测试 → 再编辑 → 再跑测试」过程中，测试输出每轮都不同，仍会命中 `ABABABAB` 或 `ABCABCABC`，而实际是在推进。

**影响（I）**：每条同形态事件都会唤醒或推送负责人（`task.stalled` 在 `needs_lead` 中），让负责人花一个回合判断；如果负责人据此 `reply`、`retry` 或 `cancel`，还会打断本来正常的工作。它也会降低负责人对「停滞」信号的信任，真正卡住时更容易被当成噪声。基线中 26 条同形态事件分布在 5 个 Run，平均每个 Run 超过 5 条；抽查到的连续编辑都在改不同内容，按当前指纹机制应判为误报。

**判断（J）**：这是 C-05 的副作用，不是设计取舍。修复方向是让「同一个调用」包含完整参数和这次调用的结果（例如 `rawInput`、`diffs`、输出内容），只在操作和结果都没有变化时累计重复；仍然保留周期 1、2、3 和现有看板文案。内存里只存哈希，不保存完整内容。需要用脚本化测试覆盖「同一文件连续编辑但内容不同」「edit/test 交替但输出变化」和「完全相同的调用仍然报警」三种情况。

**边界（U）**：如果某个工具的参数或输出本身不稳定（例如带时间戳的命令），把结果纳入指纹可能降低对真实循环的灵敏度；可以用空闲超时（`STALL_AFTER`）和周期检测兜底，并在实现时单独评估。

### CO-02 信息性事件也会唤醒负责人，产生可避免的回合

**结论（F）**：`wakes_board_wait` 目前会让 16 类事件唤醒正在 `wait` 的负责人，其中一部分不需要负责人立即做决定：`attempt.started`（任务开始）、`board.posted` 中的 `progress` 和 `note`、`task.claimed`（协作者认领）、`question.answered` 中负责人自己回答的、`task.skipped_by_decision`（通常是负责人的 `cancel` 造成的）、`approval.requested` 和 `input.requested`（负责人不能代为审批）、`attempt.failed`（系统会自动重试）、`task.stalled` 中 `resolved` 为真的那条（`board_tools.rs:305-325`）。真正需要立即处理的，是提问、冲突、拆分请求、阻塞、最终失败、未解决的停滞、带痕迹问题的完成和用户的回答。

**证据**：

- 5 个已结束 Run 中，120 次带回消息的 `wait` 有 37 次只包含「开始」，占 31%。这 37 次唤醒没有产生任何需要负责人决定的事。
- 负责人的 token 占 5 个 Run 总量的 43%（142.2M / 331.9M）。这个数字是上限，不是纯协调开销：负责人也自己做工作、写交付摘要；但每个仅因「开始」而起的回合都要重新处理一次上下文，成本不可忽略。
- C-01 已经消除了旧的 45 秒轮询空转；这里剩下的是另一个层次的问题：哪些事件值得立即换一个负责人回合，哪些可以等到下一次唤醒或超时一起返回。

**影响（I）**：负责人回合数、token 和上下文增长；任务开始或普通进展本身并不需要负责人行动，晚一点看到不会损失决策。

**判断（J）**：可以在 `wait` 内区分「唤醒」和「送达」：只有需要行动的类别立即返回；`[开始]`、普通进展和备注等仍写进下一次 `wait` 的返回内容，或在超时时一并返回，不丢消息。这样不改变看板工具的参数和事件格式，只改变唤醒时机。需要测试确认：只有「开始」时不提前返回；下一次完成消息会带上之前的「开始」；真正的失败、提问和冲突仍立即返回。

**边界（U）**：如果负责人正在等待一个长时间任务的开始信号来判断是否启动下一批工作，延后送达可能让它晚几十秒看到；可以通过超时返回和 `orchestrate` 的即时响应补偿。具体收益需要在当前代码上重新测一次，不能用 2026-11-17 的基线直接外推。

### CO-03 跨模型验证的指引与团队可见性冲突

**结论（F）**：负责人说明要求「Prefer a different model when the team has multiple models or Agents」（`backend/src/teamwork.rs:273`），文档也写了「团队有不同模型或 Agent 时优先交叉核验」（`docs/domains/20261031-goal_mode.md#lead_brief`）。但 `team_lines` 只输出成员 id、名字和职责（`backend/src/orchestrator/lead.rs:776-788`），负责人看不到协作者使用的 Agent 或模型；2026-11-18.2 的更新记录还明确写了负责人不再看到 Agent、模型、权限模式和用量。负责人无法执行这条指引。

**影响（I）**：这条指引在真实 Run 中要么被忽略，要么让负责人凭名字猜测；文档和提示词对同一件事给出互相矛盾的说法，后续维护者容易再次改错。

**判断（J）**：先做产品决定，再改文案或代码。两个方向：

- 保留「负责人只按职责选人」，删掉跨模型的话，并把文档里的同一句一起改掉。这样最简单，但放弃了跨模型独立验证这个质量杠杆。
- 只向负责人暴露 Agent 和模型名称（不暴露权限模式和用量），让「优先换模型」可执行。更新记录里的产品决定需要相应修订，并说明为什么模型名称不构成偏见或隐私问题。

不建议在不改可见性的情况下保留这句指引。

### CO-04 局部修订没有局部复验

**结论（F）**：编排数据里没有「复验范围」这一项。`TaskDef` 只有 `verifies`（`backend/src/orchestrator.rs:160-183`）；验证任务的提示总是拿到被验证任务的完整验收标准、完整 diff 和全部改动文件（`teamwork.rs` 的 `VerifiedContext`）；验证没通过后，`accept_refused` 和负责人说明都要求「派修复任务和新的验证任务」，没有只复验受影响条目的入口。

**证据**：

- Codex 日志分析的 §5 已经指出「一条证据等级修正引发 2.5M token 的完整重新验收」，并把「按版本和影响范围复验」列为 P1。
- `rmwljgnif` 的尝试序列是一个具体例子：`perf-analysis` 三次尝试（361 秒、1011 秒、848 秒），之后 `perf-verify` 970 秒、`perf-revise` 622 秒、`perf-recheck` 326 秒、`perf-erratum` 103 秒、`perf-final-check` 110 秒。最后的勘误和最终核对虽然很短，但仍然各自启动了一个完整会话，并重新走了一遍验证语义。

**影响（I）**：小修订也要重新读完整产物、重新核对全部标准；负责人要多派任务、多看完成消息；交付时间变长。它不是错误，因为当前规则确实要求确认修复后的产物，但成本和质量之间缺少中间档。

**判断（J）**：建议增加显式的「局部复验」协议，而不是放宽 `accept`：

- 验证任务可以声明复验范围，例如只覆盖上次未通过的验收标准加上一组回归项，并附上被验证任务的最新 diff。
- 验证者仍然给出 `approved`、`rejected` 或 `inconclusive`，但交付里要写明这次复验覆盖了哪些标准、哪些没有重新检查，未覆盖的部分作为风险保留。
- 涉及核心结论、公共接口或无法判断影响面的改动，仍然要求完整复验。

这需要新的编排字段、校验、提示词、交付记录和 ADR；不建议在没有产品裁定的情况下直接实施。

## 4. 产品与流程缺口

### CO-05 团队能力与资源对负责人不可见，团队仍是固定快照

**结论（F）**：Run 创建时 `team_for` 把角色展开成成员快照，之后 `run.team` 不再变化；代码里没有 `add_member`、`team.proposed` 或 `team.member_added` 之类的事件。负责人只能把任务派给快照里的成员，也不能在 Run 中给成员临时加 Skill 或 MCP。`team_lines` 不输出成员挂载的资源。

**影响（I）**：任务需要浏览器、数据库或某个审查 Skill 时，负责人只能按职责猜；用户必须在 Run 前把角色和资源配好，运行中发现缺口只能停下或新建 Run。这也是 2026-11-17 动态数字员工研究的起点。

**判断（J）**：这是产品机会，不是缺陷。研究文档已经把路线分成「任务级资源附加」「Run 创建前的 TeamPlan」「Run 中补员」三步。第一步不新建员工，只在 Run 创建前把用户确认过的资源写进现有成员的快照，风险和改动最小；第二步和第三步需要新事件、资源包原子写入和恢复重放。建议先做第一步并验证「选择 + 授权 + 失败回退」，再决定是否继续。

### CO-06 每个 Run 从零编排，没有可复用模板或跨 Run 经验

**结论（F）**：代码里没有编排模板的存储或入口；每个 Run 由负责人在当时的目标下重新调用 `orchestrate`。工作区的共享资料可以承载长期事实，但负责人的交付建议需要用户手动采纳，不是自动的 Run 复盘。

**影响（I）**：相似目标的团队结构、`owns` 划分、验收标准和验证方式每次都要重想；质量依赖负责人的当下判断；新 Run 的首次编排时间较长。市场研究已经把「可复用编排模板」列为 P1。

**判断（J）**：可以先做「从成功 Run 保存模板」：保存任务图、依赖、按职责而不是按人名的分配、`owns` 和 `verifies` 结构，以及验收标准模板；创建 Run 时作为建议给负责人，要求按当前目标和目录调整并在提交时重新校验。模板会诱导照抄，必须显示「按当前目标调整」并校验路径和资源版本。跨 Run 记忆可以复用现有的共享资料建议机制，不必另建一套。

### CO-07 同一个工作目录上的多个 Run 没有跨 Run 协调

**结论（F）**：`create_run` 只检查工作目录存在、负责人合法和适配器可用，不检查同一个目录是否已有活跃 Run。文件改动痕迹和冲突检测都在单个 Run 内（`traces`、`task.conflict`）；两个 Run 同时改同一个目录时，彼此看不到对方的 `owns`、认领或冲突。

**影响（I）**：两个 Run 可能静默覆盖同一个文件；各自的结论都可能基于已经被另一个 Run 改过的内容；交付摘要和 diff 的范围会变得难以解释。当前 5 个 Run 是顺序执行的，没有观察到这类事故，但代码没有阻止它。

**判断（J）**：这是一个风险，不是已确认的缺陷。最低成本的缓解是在创建 Run 时检测同一工作目录的活跃 Run，提示用户「这个目录已有任务在跑」，并让用户选择继续或先停掉旧任务；是否需要更强的每目录互斥，需要产品决定。

### CO-08 验证覆盖与协作质量缺少可观察指标

**结论（F）**：交付记录会列出已经存在的独立验证，但不会标出「有文件改动却没有验证」的任务；`role_stats` 只有任务数、成功数、失败数、首次通过、验证失败数和平均时长，没有负责人开销、等待次数、停滞误报、验证覆盖率或返工链长度。

**证据（F）**：5 个已结束 Run 中，带 `owns` 且不是验证任务的子任务共 19 个，其中有独立验证任务的 12 个，覆盖率约 63%；各 Run 差异很大（有一个 Run 是 1/6，另一个是 4/6，也有 2/2 和 3/3）。负责人说明只写了「重要改动安排独立验证」，没有结构性的提醒或交付风险。

**影响（I）**：用户和负责人都无法判断一个团队配置是否真的有效；验证覆盖依赖负责人的自觉；「协作成本高不高」只能靠 token 账本猜。

**判断（J）**：建议先做只读的 Run 级协作摘要（负责人 token、带回消息的等待次数、仅信息性唤醒次数、首次通过率、独立验证覆盖率、返工任务数），再考虑在交付里对「有 `owns`、没有验证」的任务加一条不阻断的风险。不要把它做成新的状态或审批；按现有记忆里的偏好，子任务页不放用量账单，指标放在 Run 页或用量页。

### CO-09 任务调度的结构性限制

**结论（F）**：`TaskDef` 的依赖只支持「全部成功」（`orchestrator.rs:160-183`）；没有优先级、重新分配执行者或条件依赖。负责人要把一个任务换人或改变优先级，只能取消后重新编排，可能丢失原会话。

**影响（I）**：负载不均时只能串行等待；某个任务失败后，下游只能阻塞或取消；复杂的「失败也要收尾」流程需要额外任务。当前日志里没有把它列为主要痛点，所以优先级低于前面的问题。

**判断（J）**：先记录，不建议现在扩展编排协议。等动态组队或模板落地后，再评估是否需要优先级、重分配或条件依赖，避免过早增加状态机和校验复杂度。

<a id="relations"></a>
## 5. 问题之间的关系

这些问题的根因可以归成四组：

1. **信号来自摘要而不是事实**：CO-01 用路径摘要判断循环，CO-02 用事件类型而不是「是否需要行动」判断唤醒。两者都会放大负责人开销，修好 CO-01 也会减少 CO-02 里的一类噪声。
2. **验证协议只有「全部」和「不做」两档**：CO-04 的局部复验缺失，CO-08 的覆盖率不可见，都会让负责人要么过度复验，要么无法证明验证充分。它们应一起设计，而不是单独放宽 `accept`。
3. **团队是静态快照**：CO-05 的资源不可见和动态补员缺失，CO-06 的模板缺失，都是「每次 Run 重新组队」的不同表现。先做资源附加和模板，能验证用户是否真的需要动态成员。
4. **缺少跨 Run 层**：CO-07 的同目录协调和 CO-06 的跨 Run 经验都在单 Run 边界之外；Janus 目前只有工作区共享资料这一条跨 Run 通道。

<a id="order"></a>
## 6. 建议的处理顺序（只排序，不实施）

1. **先做产品决定，不改代码**：CO-03 的模型可见性、CO-08 的验证覆盖提醒、CO-07 的同目录策略。三项都不需要工程改动，但会决定后面怎么做。
2. **CO-01 停滞检测**：最明确的机制缺陷，改动集中在指纹和测试，风险低。先修它，能立刻减少负责人被误唤醒的次数，也能让后续的协作指标可信。
3. **CO-02 唤醒分层**：在 CO-01 之后做，先用当前代码测一次基线，再决定哪些事件立即唤醒、哪些延后送达。
4. **CO-08 指标 + CO-03 文案**：低成本，先让用户和负责人看得见协作质量，再谈优化目标。
5. **CO-04 局部复验**：需要新的编排字段和 ADR；先写清楚复验范围、回归项和未覆盖风险，再实现。
6. **CO-05 资源附加、CO-06 模板**：产品级投入，先做其中更小的一步（任务级资源附加或模板），用真实 Run 验证收益。
7. **CO-07 同目录提示、CO-09 调度扩展**：按实际事故和用户反馈决定，不先扩大协议。

| 带回消息的 `wait` 次数 | 120 | `tool.completed` 中 `janus.wait` 的输出 | 不含空超时 |

<a id="decisions"></a>
## 8. 需要用户决定的事项

1. **模型可见性**：负责人是否应该看到协作者的 Agent 和模型名称，以便执行跨模型验证？如果保留当前「只按职责选人」，就删掉跨模型的指引；如果希望跨模型核验，就只暴露名称，继续隐藏权限和用量。建议后者，但这是产品取舍。
2. **验证覆盖**：有文件改动的任务是否默认要求独立验证，还是保持负责人判断？如果保持判断，至少要在交付里标出没有验证的任务。
3. **局部复验**：是否接受「按影响范围复验 + 回归抽查 + 交付写明未覆盖范围」的协议？如果接受，需要新的编排字段和 ADR；如果不接受，就继续承担完整复验的成本。
4. **动态团队**：下一步优先做任务级资源附加、Run 创建前的 TeamPlan，还是先做可复用编排模板？三者都需要独立 PRD，建议先从改动最小、可验证的资源附加开始。
5. **同目录多 Run**：检测到同一工作目录已有活跃 Run 时，提示后允许继续、直接拒绝，还是提供每目录互斥？建议至少提示，不默认阻止。
