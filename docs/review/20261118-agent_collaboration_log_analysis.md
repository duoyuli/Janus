<a id="idle_wait"></a>
## 1. 优先让 PMO 在没有事件时休眠，减少用模型维持等待循环

5 次运行共调用 `janus.wait` 380 次，260 次返回「没有新消息，子任务仍在进行」，占 68.4%。其中 354 次调用选择了 45 秒等待；另外还有 40 秒、30 秒和 1 秒等待。

这与当前机制直接对应：[board.rs:208](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/orchestrator/board.rs#L208) 把单次等待限制在 1–45 秒，超时后返回文字，让模型决定下一步；[lead.rs:667](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/orchestrator/lead.rs#L667) 明确要求「没有新消息就再调用」。这把本可由运行时处理的等待变成了反复推理。

原生会话还显示了第二层开销：Codex 通过 `functions.exec` 调用 `janus.wait` 时，外层工具可能先返回 `Script running with cell ID ...`，模型随后再调用 `functions.wait`。市场研究运行中，84 次 Janus 等待对应了 135 次仅进行等待的模型请求，其中包括 51 次外层继续等待。

按 Claude `message.id`、Codex `response_id` 去重后，对负责人的原生请求做了归因：只有该次响应的工具动作全部属于 Janus 等待或其可追溯的外层等待，才计入「只等待」。混合了读文件、执行命令、回复成员等动作的请求不计入。

| 运行 | PMO 原生模型请求 | 其中只等待 | 只等待请求的 token | 无新增信息后继续等待的 token |
| --- | ---: | ---: | ---: | ---: |
| 扫雷 | 164 | 111 | 5.68 M | 3.30 M |
| 市场研究 | 203 | 135 | 21.55 M | 13.18 M |
| 动态员工研究 | 121 | 46 | 11.70 M | 5.77 M |
| 工作区 UX | 280 | 98 | 18.50 M | 11.17 M |
| 性能分析 | 188 | 90 | 10.02 M | 4.72 M |
| 合计 | **956** | **480** | **67.45 M** | **38.12 M** |

「无新增信息后继续等待」是更保守的子集：上一次结果只有空等待或工具仍在运行，期间没有用户消息、其他工具结果或附件/系统更新，下一次响应仍只发起等待。共识别出 **276 次请求、38,123,622 token**，其中缓存读取 37,810,304，输出只有 14,396。主要消耗是重复读取上下文，缩短等待回复的文字解决不了这个问题。

原生 PMO 总量是 138.11 M，与账本 PMO 的 131.07 M 不同：前者包括中断会话中的请求，但不包括所有后台辅助调用；二者不能直接相加。等待相关的 67.45 M 占原生 PMO 总量 48.8%，也不能全部视为可删除消耗，正常接收完成消息仍有价值。

建议把「等待到新事件或检查期限」交给运行时。PMO 完成当前派工后进入可恢复的等待状态；任务完成、阻塞、失败、用户输入、预算或期限触发时再唤醒。普通心跳与无变化的进展保留在看板，不启动推理。休眠时保存游标与未完成目标，不能把 PMO 暂时结束一轮误判为整个 Run 已交付。

现有系统已经支持看板消息推送，可以在其上调整调度。不能只把 45 秒改成更长超时：外层工具的等待、连接中断和恢复也需要纳入设计。**38.12 M 是有明确日志证据的优化范围，实际能省多少必须通过改动后的配对运行测量。**

<a id="verdict"></a>
## 2. 分开「审查任务完成」和「被审查产物合格」，同时避免误报通过与无效重试

性能报告运行出现了两个明确的状态与结论不一致：

| 被审查任务 | QA 的实际结论 | 最终交付记录中的验证状态 |
| --- | --- | --- |
| `perf-analysis` | 合成日志导致约 2 倍高估；遗漏序号分配风险，修订后才可使用 | `perf-verify: passed = true` |
| `perf-revise` | 15,160 是 5 次累计 checksum，单次约 3,032；仍需勘误 | `perf-recheck: passed = true` |

证据：`rmwljgnif / #2537、#3624、#3962`。当前 [lifecycle.rs:437](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/orchestrator/lifecycle.rs#L437) 用 `v.status == TaskStatus::Succeeded` 计算验证的 `passed`，没有单独读取产物判定。QA 的验收条目如果是「完成核对并给出结论」，即使发现阻断问题，也能全部填 `passed: true`。

另一种写法又走向相反的问题。动态员工研究把报告的 R1–R18 直接作为 QA 验收标准。QA 发现 R10/R14/R18 不满足并如实填 `false` 后，系统把这次有效审查判成任务未达标，要求同一个只读 QA 「修复后重新验证」。QA 再次确认文件哈希没变，重复报告原来的问题，然后该尝试失败。

这条路径的事件是 `rmwkfyupn / #3005 → #3007 → #3008 → #3063 → #3064`。无改动后的补验一轮，`#3059` 单独上报 **697,055 token**。对应逻辑在 [attempts.rs:382](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/orchestrator/attempts.rs#L382) 和 [evidence.rs:268](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/evidence.rs#L268)。

这两个问题有共同根因：一个布尔值同时承担「我完成了检查」和「被检查对象合格」两种含义。

建议保留三个独立信息：审查是否执行完成；产物判定是通过、需要修改还是证据不足；判定覆盖哪个版本和哪些验收条目。QA 找到阻断问题时应成功交付审查结果，由 PMO 把缺陷交给产物负责人修复。只有结果缺字段、证据不可定位等审查交付本身的问题，才退回 QA 补齐。

这次性能报告最后经过修订和最终核验，日志支持「最终可用」；这里指出的是中间状态和交付历史中的语义错误，**没有把它说成最终交付了错误报告**。修正协议可以减少对 PMO 逐字阅读长结论的依赖。

## 3. 先补齐失败、中断、取消会话的消耗，再用角色占比决定如何裁减协作

53 个账本会话中，5 个没有 token 上报。在其中 4 个 Claude 原生会话里，可以按消息 ID 去重恢复如下已记录请求用量：

| 运行 / 会话 | 中断或结束原因 | 账本 token | 原生可核对 token |
| --- | --- | --- | ---: |
| UX / `a12d6b1b…`，W2 首次实现 | 超过 30 分钟 | 未上报 | 19,604,915 |
| UX / `e9be8e0e…`，W3 验证 | 用户追加删卡片，原验证取消 | 未上报 | 3,806,194 |
| 性能 / `eae729f3…`，原 PMO 会话 | 编排器重启 | 未上报 | 4,645,558 |
| 性能 / `2a6c689a…`，分析会话 | 重启后恢复，随后上游 524 | 未上报 | 12,788,682 |
| 合计 |  |  | **40,845,349** |

这些会话的完整路径在 `metrics.json`。它们不与已上报会话相加重复；表中只纳入账本总量为空的会话。这个数字还没有包含其他会话里可能只上报了一部分的消耗，也不等同于供应商最终账单。

因此，这批运行已能核到的消耗至少是 **315.74 M**：账本 274.90 M，加上这四个完全未上报会话的 40.85 M。失败会话的消耗不全是浪费，其中的文件修改、测量结果可能被后续尝试复用。

漏记会改变团队诊断。例如 UX 运行的 PMO 占比，账本显示 68.3%；只补入两个已知缺失的工作会话后，按这组已知数据重算就变成约 **52.3%**。不能直接拿 68.3% 得出「PMO 应该被删掉」的结论。

建议尽可能逐请求持久化 usage，以运行时、会话和请求 ID 去重。适配器只有结束时才给总量的，应在异常结束后从原生日志或可靠的运行时计数器补齐，并标明来源。不能拿上下文 `used` 顶替消耗，也不能把未上报写成零。

重试需要按原因处理。这批日志中，扫雷的两次 QA 中断是编排器重启；性能分析遇到重启和 524；UX 实现遇到固定 30 分钟期限。它们不能合并成「专业 Agent 质量差」。对已经留下可验证进展的尝试，恢复时交接产物版本、已完成检查与待做项，减少重读和重复分析；是否延长期限应结合进度与预算，不能无限重试。

<a id="acceptance"></a>
## 4. 产品定义的验收标准，应成为作者和 QA 共用的任务契约

市场研究运行中，PM 和研究者在 `#33` 并行启动。PM 在 `#335` 已写出边界，在 `#428` 正式交付 SC-1 至 SC-9。研究者在 `#737` 才完成报告，时间上具备同步标准的机会。

但研究任务仍使用最初 4 条验收标准；后续第一次 QA 又使用单独的 3 条标准。PMO 在这期间给研究者的两条消息（`#576、#619`）主要催促收尾，没有把 SC-1 至 SC-9 同步成共同验收契约。到 `#1538` 的产品验收，才因 SC-3/SC-7 缺口要求补充与旧报告的增量比较和用户决策输出。

这不是「角色再写详细一点」就能解决的。每个角色都可能把自己的任务做好，但最终检查的不是同一组标准。

建议让 PM 在早期形成编号稳定的验收清单；PMO 将它分配到作者、技术核查和 QA 的覆盖范围，并记录变更。资料搜集可以继续并行，定稿和最终验收应基于同一个已确认版本。若用户改变范围，更新契约并只使受影响的结论失效。

交接也需要传递关键决定、未决项、约束与证据位置，而不仅是「已完成」的摘要。当前 [attempts.rs:112](https://github.com/duoyuli/Janus/blob/57a35ddc62223b55bd74bf33a1e7d896f78464a9/backend/src/orchestrator/attempts.rs#L112) 为依赖结果提供截断摘要和产物路径，运行时已有文件、产物与修订记录，可在现有结构上补充契约引用。

<a id="scoped_reverify"></a>
## 5. 小修订默认复验受影响范围，避免每次重新走完整产品验收

同一市场研究后期，对一条 Anthropic 证据的 F/U 等级作修正，产生了以下链条：

| 子任务 | 工作内容 | 已上报 token |
| --- | --- | ---: |
| `MKT-EVIDENCE-FIX` | 修正证据等级，原生记录只有 1 次 Edit | 363,655 |
| `QA-RESEARCH-4` | 验证等级修正、结构和相关引用 | 748,617 |
| `PM-ACCEPT-3` | 再次逐条核对 SC-1 至 SC-9 | 1,395,446 |
| 合计 | 不含同期 PMO 消耗 | **2,507,718** |

证据：`rmwj9mn9t / #2853、#2996、#3001、#3199、#3204、#3463`。修正事实等级值得做；成本问题在于一次局部改动重新启动了两个完整会话，并再次要求产品角色全面验收。

日志也已经出现了可复用的做法。动态员工报告的 `review-final` 明确保留此前通过的 15 项，仅修复并重点复核 3 个阻断项，再抽查其他部分。性能报告的最终 QA 用全文 diff 证明只有 6 行变化，其余 624 行未变，然后核对受影响数字与引用。

建议把这种做法固定为验收协议：每条结论绑定产物哈希、覆盖条目和依赖证据；文件变化后计算受影响范围，局部复验并抽查回归。若改动触及核心结论、公共依赖或无法判断影响面，才扩大复验。现有产物记录已有 SHA-256，不需要另起一套协作平台。

不能只按「改动行数少」决定安全。例如改一个成本倍数或权限边界就可能改变整体推荐，仍需产品重新判断。应以结论依赖关系决定范围。

<a id="qa_evidence"></a>
## 6. 保留独立 QA 的质疑权，同时让数值证据脱离自由文本转述

性能报告的 QA 发现了两类有价值的问题：合成日志的会话建模使部分测量约高估 2 倍；批量落库建议遗漏 `expectedSequence/max_seq` 的序号一致性风险。移除 QA 可能让不准确的性能判断和有正确性风险的优化建议直接成为实施依据。

但 QA 自己也引入了一个新的数字错误。`rmwljgnif / #2534` 把「5 次复跑累计 checksum 为 15,160」描述成「20k 事件产生 15,160 个账本会话」。PMO 在 `#2556` 把这个数字写入修订任务，作者据此修改。下一次 QA 在 `#3624` 才指出单次应是 `15160 / 5 = 3032`，随后又发生勘误和最终核对。

这是证据在角色间转述时丢失计量口径的具体例子。报告字句更严谨、增加一轮同模型讨论，都不能稳定替代对计算来源的检查。

建议由测量脚本输出带字段的结果：样本规模、重复次数、单次值、累计值、单位、聚合方式、脚本版本与源日志位置。QA 从这些字段独立复算，修订任务引用证据 ID；不要把审查者的一段自然语言直接升级为事实。

论文与市场研究也可用同样原则：事实条目需要来源、访问时间、实际支持该结论的位置、适用条件与不确定性。QA 主要检查证据是否支持结论，而不只是有没有链接或是否用了 F/I/U 标签。

<a id="roles"></a>
## 7. 调整角色启动条件和交付内容，不必增加新的常驻角色

日志并不支持「Janus 还没有验证依赖链」的判断。动态员工研究已有 `report → review-report → product-accept`，UX 已有 `W2 → W3 → W4`，后续范围变化也重新编排了验证。应该改进这些链的语义和失效范围。

扫雷运行明确要求展示团队合作，完整市场、产品、研发、QA 流程属于用户目标。UX 的取消验证来自用户追加需求，市场研究的一次复验取消来自外部文档路径迁移。这些情况不能全部计为无效协作。

基于这批证据，五个角色可以这样收紧运行职责：

| 角色 | 建议的启动与交付约束 |
| --- | --- |
| PMO | 有派工、阻塞、失败、范围或预算决策时运行；维护当前契约、依赖与交付状态。全部成员正常工作且无待决事项时休眠。 |
| 市场 / 研究 | 存在外部事实、竞品或用户证据缺口时启动；交付可定位的事实与反例，避免与总报告作者重复写整篇综述。 |
| 产品 | 在范围、用户价值和成功标准需要判断时启动；维护编号验收清单。事实等级局部修正且不改变产品结论时，通常无需全面重验。 |
| 研发 / 分析 | 对实现或技术结论负责；交付产物版本、可复跑证据、已完成项和待做项，供中断恢复与 QA 使用。 |
| QA | 独立核对产物与证据，明确通过、需修改、证据不足；修复回到产物负责人，复验范围跟随变更与结论依赖。 |

例如「只分析 UI 卡顿并出报告」，主要需要 PMO、技术分析和独立 QA；只有范围或用户体验取舍不清时才临时引入产品。外部市场角色没有必然职责。动态员工可行性研究则同时有产品、外部证据和代码现状三类独立问题，保留相应专业角色有合理性。

这批 Claude 会话的请求与响应模型标识均指向网关的 DeepSeek Flash 路由；前三次 PMO 使用 Codex，后两次 PMO 也走该路由。这些标识不能证明网关背后的实际模型配置，但至少说明现有日志不是一组受控的「异构团队与单模型」对照。模型档位和混合配置应在等待、统计、验证协议调整后单独实验，否则很难知道收益来自哪里。

<a id="order"></a>
## 实施和验证顺序

| 顺序 | 调整 | 首先验证什么 |
| --- | --- | --- |
| P0 | 审查完成状态与产物判定分离 | 用两种历史案例回放：负面审查正常交付，产物不标通过；未修改产物时，不要求只读 QA 再次「修复」。 |
| P0 | PMO 事件驱动休眠 | 空等待与外层「仍在运行」不启动模型；完成、阻塞、用户输入与期限仍可及时唤醒；重启后不丢游标、不提前交付。 |
| P0 | 异常会话的 usage 持久化与补记 | 成功、失败、中断、取消均可追踪请求用量；恢复和重复回报不重复计数；无法收齐时明确保留缺口。 |
| P1 | 编号验收契约与交接证据 | PM、作者和 QA 检查同一版本的标准；范围变化只使相关条目失效。 |
| P1 | 按版本和影响范围复验 | 小修订保留未受影响结论；会改变整体建议的修订能正确扩大检查。 |
| P1 | 结构化测量证据与恢复记录 | 单次/累计、实测/推算不再在转述中混淆；故障后能复用可信进展。 |
| P2 | 角色启用策略、模型与推理档位 | 固定任务、仓库版本和验收，再单独比较配置，避免多因素同时变化。 |

先利用现有事件做离线调度和状态回放，检查「是否多唤醒、漏唤醒、错误放行」，不需要先重跑全部高成本任务。随后各选一个研究任务和一个代码任务做配对验证，固定输入、仓库版本、模型路由与工具权限；若差异受运行波动影响，再扩充样本。

评估至少同时观察：首次交付的实质错误数与关键验收覆盖；修订轮数与错误放行；总 token、非缓存输入、缓存读取、输出及实际可获得的费用；无新增信息的模型调用；用量缺失会话；首次交付耗时。不能只比较 `task.succeeded` 数量或总账本费用。

以上调整与此前公开研究中「控制协作范围、传递目标与验收约束、以匹配预算验证收益」的方向相符。[GAD 研究](https://arxiv.org/html/2610.39193v1)可作为交接设计的参考，[Vals 的多 Agent 编码实验](https://www.vals.ai/blogs/multi-agent-vibe-code-bench)可作为设置对照的参考。这里的优先级来自 Janus 本地记录，没有把外部实验的节省比例直接套用到 Janus。

<a id="limits"></a>
## 复核与限制

复算脚本是同一附件目录中的 `reproduce.py`，原生请求归因逻辑在 `parsers.py`，均未放进仓库。脚本只读 SQLite 和原生日志，不访问网络，也不操作应用。它按各运行的快照最大事件序号截断，因此后续新增接受记录不会改变本次事件口径。

```sh
python3 <附件目录>/reproduce.py
```

已在冻结的 SQLite 快照上执行：5 次运行的账本、角色、任务汇总，380/260 次等待计数，原生等待归因及 4 个缺失会话用量均与保存结果一致，`checks_passed: true`。原始 SQLite 和完整会话没有复制进报告目录；复算依赖本机原始日志，日志被清理后需另行提供来源。

一个中断过的 Codex 会话有 4 行非有效 JSON，解析时跳过；无法可靠识别的复合工具调用也不纳入「只等待」。原生消息按唯一请求去重，重复流式块不重复计费；Claude 的 2,063 组带 usage 的消息中，同一消息 ID 的 usage 均一致。后台辅助调用、失败会话和不同运行时的上报方式存在差异，因此原生主循环与 Janus 账本分别呈现。

这是 5 个自然发生任务的观察性分析，没有单 Agent 基线，也没有对最终交付物重新做全面质量审计。日志能证明已经发生的空等待、用量缺口、状态语义冲突及具体返工链；对整体节省比例、交付速度提升和模型替换效果，仍需改动后的对照验证。
