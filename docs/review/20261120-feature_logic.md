# Janus 现有功能与流程一致性审查

审查日期为 2026-11-20。对象是 Rust 服务、macOS 应用及二者之间的 HTTP、ACP、事件和存储约定。首轮核对版本为 `d75d2e8`，分页合入后再对照 `02c4b31`。以下源码行号以 `02c4b31` 为准。文中的 Run 指一次目标任务或一对一对话，worktree 指 Git 为一次目标任务创建的独立工作目录。

共记录 21 项流程问题，其中 18 项经过专项实测，3 项按源码推演。前 8 项优先处理，它们关系到文件保留、交付和验证结果、全局待办、资源变更和重启恢复。另列 4 处文档或界面说明与实现不一致的地方。

## 高影响问题

### FL-01　备份未提交改动失败后仍删除 worktree

**实测。** 协作者生成了只在 worktree 中的文件。模拟 Git 索引正被占用后，从正常的删除接口删除这次 Run。服务返回 HTTP 200，再查为 404。worktree 已删除，源仓库中没有这个文件，也没有生成承诺保留的补丁。Git 暂存失败或读不出差异时，删除函数会跳过备份并继续清理目录。已经开始写补丁时，文件系统写入错误会向上返回。服务启动时清理已验收 worktree 也调用这个函数。[保留补丁与删除目录](../../backend/src/worktrees.rs#L254-L282) · [删除 Run](../../backend/src/orchestrator/lifecycle.rs#L650-L674) · [启动清理](../../backend/src/orchestrator/actions.rs#L801-L811)

**修复验收。** 暂存、生成补丁或落盘任一步失败时，保留原目录和 Run 记录并返回具体原因。故障解除后重试，确认补丁能还原该文件，再删除目录。

### FL-02　交付目录缺失时仍能验收成功

**实测。** 在临时仓库生成交付文件，交付后移走 worktree，再点验收。服务返回 HTTP 200，Run 变成 `accepted`，验收事件记录 `commit: null`，源目录没有交付文件。目录缺失和「核对后确认无改动」共用同一个返回值。[目录缺失分支](../../backend/src/worktrees.rs#L168-L180) · [验收结果和状态](../../backend/src/orchestrator/actions.rs#L320-L331) · [验收文案](../../backend/src/orchestrator/actions.rs#L349-L360)

**修复验收。** 交付目录缺失时保留 `delivered`，提示缺失路径和可恢复位置。完整且确实无改动的任务仍能正常验收。覆盖服务重启前后两种验收入口。

### FL-03　验收后让负责人补写文件，原验收状态覆盖了新工作

**实测。** 输入框提示可以写「接下来要做的」。已验收后，通过普通消息请负责人补写说明。文件写入了 worktree，源目录没有得到它，Run 仍是 `accepted`，交付事件只有一条，再次验收返回 HTTP 400。服务重启后清理了 worktree，补写的文件只留在 `worktrees/deleted/` 的补丁里。普通对话轮与新 `/goal` 轮使用了不同的交付条件。[会话输入提示](../../frontend/Sources/Janus/UI/Run/Session.swift#L176-L185) · [负责人续聊](../../backend/src/orchestrator/lead.rs#L333-L362) · [重启清理](../../backend/src/orchestrator/actions.rs#L801-L811)

同一处状态分歧发生在**首次验收之前**。交付后用普通消息要求负责人跟进，负责人发来表单。任务详情有待填表单，全局收件箱只显示「等你验收」。表单仍未处理时验收返回 HTTP 200。用户可能在负责人仍在等答复时就确认交付。[收件箱按 Run 状态选数据](../../frontend/Sources/Janus/Core/Inbox.swift#L118-L139) · [验收条件](../../backend/src/orchestrator/actions.rs#L320-L331)

**修复验收。** 明确哪些续聊会产生新交付。沿用「直接交办」入口时，补写的文件应有可见的待验收状态和合回入口。只询问已有结果时应保留原验收记录。跟进中的表单应在收件箱可见，验收动作应能识别尚在进行的工作。

### FL-04　独立验证可以把旧版本的通过结论带到新版本

**实测。** 验证员读取只有一行的文件。负责人让执行者返工，验证员在事件 45 提交通过结论，执行者在事件 52 才完成第二版。最终文件有两行，验证员只执行了一次，交付仍把第二版列为 `approved`、`passed: true`。返工逻辑会重新打开已经完成的验证任务，正在运行的验证任务收到上游返工提醒。交付按子任务 ID 关联验证，缺少被验证的那次尝试或结果版本。[返工与复审](../../backend/src/orchestrator/board.rs#L419-L455) · [给执行中下游的提醒](../../backend/src/orchestrator/board.rs#L527-L539) · [交付中的验证判定](../../backend/src/orchestrator/lifecycle.rs#L523-L545)

**修复验收。** 将验证结论关联到执行任务的具体结果。无论验证先结束还是返工先结束，只有对最终版本完成的核查才能显示为通过。上一版结论仍可在审计页回看。

### FL-05　用户已切换到更早的游离提交，验收仍会移动其工作目录

**实测。** 源目录在游离提交 B 上启动任务，用户随后切到 B 的父提交 A。验收返回 HTTP 200，把用户的 HEAD 从 A 快进到任务结果，B 才有的文件重新出现。已采纳的决策要求核对创建时的提交或上次验收提交。实现只核对当前是否仍然游离以及提交之间的祖先关系，A 也满足快进条件。[验收决策第 5 条](../decisions/20261120-merge_back_on_accept.md#决策) · [读取当前 HEAD](../../backend/src/worktrees.rs#L102-L115) · [判定和快进](../../backend/src/worktrees.rs#L190-L218)

**修复验收。** 用户切到父提交、旁支提交或有名分支时，保留其选择并提示手工合并。仍位于约定提交时可以正常快进。

<a id="inbox_coverage"></a>
### FL-06　较早任务正在等人处理，却会从全局收件箱消失

**实测。** 一个真实运行的任务发来表单，macOS 收件箱能看到。向临时数据库补入 50 条更新的已验收目标记录后，收件箱移除了表单。直接打开原任务仍能看到请求并作答。收件箱从最近一页目标列表筛选待办，列表按创建时间排序。一个长期任务在别的工作区新增许多任务后也会受影响。分页版本给工作区历史加了后续页，全局待办仍使用默认首页。[目标列表默认页](../../backend/src/main.rs#L421-L437) · [应用轮询](../../frontend/Sources/Janus/Core/AppStore.swift#L89-L97) · [收件箱候选来源](../../frontend/Sources/Janus/Core/Inbox.swift#L110-L140)

**修复验收。** 只要问题、审批或表单尚待作答，后续新增多少历史记录都应保留其全局入口。作答后，收件箱和任务详情同时移除它。覆盖多个工作区。

### FL-07　资源库对旧 Run 同时给出「固定版本」和「删除后停用」两种承诺

**源码推演。** Run 快照保存 MCP 定义，领域文档承诺后续编辑不影响该 Run。资源库决策又把删除作为停用服务器的办法。保存或删除确实会停止已启动的实例，但旧 Run 下一次枚举从成员快照取定义，启动时再按资源 ID 取当前配置值。修改命令或地址后可能出现旧定义与新配置值组合，删除后，能独立启动的旧定义仍具备重新启动的条件。此次只核对资源选择与生命周期代码。[快照约定](../domains/20261116-resource_library.md#delivery) · [资源库决策](../decisions/20261120-library_routed_only.md#取舍) · [编辑和删除](../../backend/src/library.rs#L525-L533) · [旧 Run 的资源选择及启动](../../backend/src/orchestrator/mcp_router.rs#L212-L259)

**修复验收。** 为修改定义、修改配置值、删除资源分别约定对新旧 Run 的生效时点。用本地无凭据测试服务器核对列表、正在运行的实例和再次启动三个结果，让资源库界面说明同一套规则。

### FL-08　关键事件写入失败后，编排仍可能返回成功

**源码推演。** 负责人派发时，服务先把任务加入内存，再写 `orchestration.accepted`。写库失败时不会广播该事件，但调用方仍唤醒调度并返回成功。恢复只从已持久化的编排事件重建任务。在某次事件写入失败而后续操作成功的条件下，当时已经开始的工作可以在重启后从看板中缺失。这里核对了错误传播路径，未向用户数据库或测试数据库注入写入故障。[接纳与启动顺序](../../backend/src/orchestrator/board.rs#L218-L235) · [写入失败和返回值](../../backend/src/orchestrator.rs#L1157-L1185) · [恢复来源](../../backend/src/orchestrator/actions.rs#L480-L495)

**修复验收。** 对单次关键事件写入失败做故障测试。客户端得到的结果、当时是否派发、重启后能否重建应一致。重试后每个子任务只执行一次。

<a id="inconsistent_guidance"></a>
## 四处会误导使用者的说明

- **角色资源。** 工程索引和角色文档开头仍说角色指定或选择 Skill、MCP。当前已采纳的方案将资源库经路由提供给所有数字员工，编辑器已移除逐角色选择。读者按旧说明配置，会寻找已经去掉的入口。[工程术语](../index.md#glossary) · [角色说明](../domains/20261031-agents_and_roles.md) · [资源路由决策](../decisions/20261120-library_routed_only.md#决策)
- **Run 的范围。** 工程术语把 Run 定义为在工作区提交并走到验收的目标。一对一对话同样写入 `runs`，却没有工作区和验收。按这个旧定义判断「运行中」，容易在退出确认和统计中漏掉对话。[工程术语](../index.md#glossary) · [对话数据与生命周期](../decisions/20261120-chats_as_runs.md#决策)
- **停止与恢复。** 生命周期文档把「取消或失败」一起写成可以从中断处继续。界面确认明确写着停止后不能继续，服务也只允许特定状态恢复。应分别交代保留的文件、能否重开会话、能否继续调度。[生命周期说明](../domains/20261031-run_lifecycle.md#workspace_model) · [恢复条件](../../backend/src/orchestrator/actions.rs#L406-L425) · [停止确认](../../frontend/Sources/Janus/UI/Run/Requests.swift#L430-L434)
- **预算耗尽。** 墙钟预算事件告诉用户可以「接受部分结果」。预算卡提供追加和停止，用户验收接口只接受 `delivered`。用户在 `waiting_input` 看见这条指引时无法直接完成所说的动作。[预算事件](../../backend/src/orchestrator/lifecycle.rs#L357-L371) · [预算卡](../../frontend/Sources/Janus/UI/Run/Requests.swift#L396-L427) · [验收条件](../../backend/src/orchestrator/actions.rs#L320-L326)
