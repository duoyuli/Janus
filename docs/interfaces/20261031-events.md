# 事件参考

本文列出事件的结构和全部事件类型。事件是 Run 的唯一事实来源：应用、看板、恢复和导出都从事件读取。为什么这样设计见 [ADR：事件是唯一事实来源](../decisions/20261031-events_as_source_of_truth.md)。

<a id="event_shape"></a>
## 结构

```json
{
  "run_id": "rmvvdi046",
  "seq": 42,
  "ts": 1793350000000,
  "type": "question.asked",
  "actor": "developer",
  "to": "lead",
  "task": "T2",
  "attempt": 1,
  "text": "给笔记定个名字",
  "data": { "key": "q-T2-1-0", "question": "...", "options": [], "blocking": true }
}
```

| 字段 | 说明 |
| --- | --- |
| `run_id` | Run id |
| `seq` | Run 内从 1 开始递增的序号 |
| `ts` | 毫秒时间戳 |
| `type` | 事件类型，SQLite 中的列名也是 `type` |
| `actor` | 发出者：`user`、`janus`、`lead` 或成员 id |
| `to` | 可选，接收者 |
| `task`、`attempt` | 可选，关联的任务和尝试序号 |
| `text` | 给人看的一句话，中文 |
| `data` | 可选，结构化数据，字段随类型变化 |

约束：

- 事件只追加，不修改。`seq` 只由数据库在写入时分配：插入语句取这个 Run 已有的最大序号加一并返回（`Db::insert_event`），进行中的 Run、不在内存里的 Run（`App::record`）和出队（`Db::leave_queue`）都走这一处，不会有两个写入方拿到同一个序号；`Run.last_seq` 只记下最近一次写入得到的序号，供需要「日志现在到哪」的地方读取。写入 SQLite 后才广播，广播带的是数据库给的序号；写入失败的事件不广播（`App::store`），所以应用看到的事件都在日志中。同一个 Run 的写入和广播在一把锁内完成（`Run.emitting`），事件流按 `seq` 顺序送出，应用把序号缺口视为漏收，重新读取一次整个 Run。
- `text` 用于展示，程序逻辑只读 `type` 和 `data`。
- 等待用户或负责人处理的事件，在 `data.key` 中带一个唯一键；回答、撤回和转交都用这个键关联。键只用来关联，程序不从键的形状读出任何信息：谁在等这个决定（某个任务的某次尝试，或负责人）记在编排器内存中的待处理决定上（`Pending.owner`），会话结束时只撤回它自己的决定；事件中由 `task` 和 `to` 表明它属于谁。用户对负责人 `ask_user` 问题的回答是没有 `task`、`to` 为 `lead` 的 `question.answered`。

事件类型在服务端是枚举 `EventKind`（`backend/src/events.rs`），应用是同名的枚举（`frontend/Sources/Janus/Core/EventKind.swift`），代码按种类找事件，不写出类型的字符串；日志里仍按文字保存，早先版本写下、这个版本不再写的类型读成 `Unknown`（应用是 `.unknown`），审计视图照原文显示。新增或修改事件类型时，两个枚举一起改，并同步检查：给客户端的推导 `backend/src/run_view.rs`（见[读服务端的状态](../architecture/20261031-frontend.md#event_derivation)）、看板的 `board_entry`（[看板 MCP 工具](20261031-board_mcp.md#wait)）、恢复逻辑 `resume_run`。改 `session.usage` 的字段时还要改用量账本（[用量口径](#usage_accounting)）`backend/src/usage.rs`，并在 `backend/testdata/usage_cases.json` 加用例。

<a id="message_flow"></a>
## 消息的流转

用户在会话页发的消息、负责人通过看板 `reply` 发给协作者的补充，都按同一流程记录：

1. **发出**：立即写 `user.message`（`delivery: "pending"`），带唯一的 `data.id`。`to` 是目标 Agent，从任务会话发出时带 `task`。
2. **路由**：会话处理到这条消息时写 `message.routed`，`data.delivery` 说明它的去向：

   | `delivery` | 含义 | 何时出现 |
   | --- | --- | --- |
   | `steer` | 已插入正在进行的这一轮 | Agent 支持 `_session/steering` 且插入成功，见[插话](20261031-acp_integration.md#steering) |
   | `queued` | 排队，这一轮结束后作为新一轮发送 | 用户的消息，Agent 不支持插话或插入失败；Agent 正在等用户处理请求；用户接管着会话时负责人发来的消息（交还托管时送达） |
   | `interrupt` | 打断正在进行的这一轮，立即作为新一轮发送 | 负责人的 `reply`，Agent 不支持插话或插入失败 |
   | `prompt` | 直接作为新的一轮发送 | 人工接管中一轮已结束、正在等消息时；或在等待提问回答时发送 |
   | `next` | 留言，下次会话开始时带给它 | 这个 Agent 当前没有会话 |

3. **送达**：`queued`、`interrupt` 和 `next` 的消息真正进入会话时写 `message.delivered`，`data.ids` 列出送达的消息。`steer` 的消息在 `_session/steering` 返回 `injected` 时写 `message.delivered`，`data.applied` 为 `true`，表示消息已经进入模型的输入。用户接管会话期间，排队的消息不会自动发出，交还托管时随交还提示一起送达。负责人跟随进行中的目标时，插不进去的消息立即作为新的一轮发送，写 `message.delivered`，不等目标结束。

Janus 自己发给会话的两种消息也走插话，但不记 `user.message`：看板推送记为 `session.prompt`（`channel: "board"`），见[看板推送](../domains/20261031-goal_mode.md#board_push)；冲突提醒随 `task.conflict` 发出，见[同时改同一个文件](../domains/20261031-goal_mode.md#conflicts)。

留言记着它是发给哪个任务的：发给某个任务的（例如负责人对还没开始的任务的 `reply`），只带进这个任务的会话，不会被同一协作者先开始的另一个任务带走；只发给 Agent 的，带进它的下一次会话。重启后，没有 `steer` / `prompt` 也没有被送达的消息会恢复为留言，在 Agent 下一次会话时带入。

<a id="event_types"></a>
## 事件类型

### Run

| 类型 | 说明 |
| --- | --- |
| `run.queued` | 目标进入[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)，`actor` 是 `user`（用户的目标）或 `lead`（[值班](../domains/20261121-loops.md) 派发的）；`data` 含 `goal`、`workspace`（`id`、`name`）、`images` 和 `origin`（`kind` 为 `user`，或 `loop` 加上 `loop`、`key`、`sourceUrl`）。每个目标 Run 的第一条事件；开始时再记 `run.created`，取消时记 `run.cancelled`，没能开始时记 `run.failed` |
| `run.starting` | 离开派发队列、开始准备：`actor` 为 `janus`（有了空位）或 `user`（立即开始）。和状态改为 `planning` 在同一个事务里 |
| `run.requeued` | 领走后没准备完（服务停了，或没能开始后用户让它继续）的 Run 回到队列 |
| `run.created` | 创建；[对话](../domains/20261120-chats.md)的 `data` 是 `kind: "chat"`、`cwd`、`git: false` 和 `role`（数字员工的 `id`、`name`）；[值班](../domains/20261121-loops.md) 的会话是 `kind: "loop"`、`cwd`（工作区目录）、`git: false`、`loop`（`id`、`name`）和 `role`（负责人）；其余字段只属于目标 Run。目标 Run 的 `data` 含 `goal`、`cwd`、`git`、`baseRef`、`workspace`（工作目录的一句话描述）、`images`（随目标粘贴的图片，见[图片附件](../domains/20261031-run_lifecycle.md#attachments)）；在 worktree 中的 Run 另有 `worktree`：`repo`（原仓库）、`included`（`.worktreeinclude` 带过去的文件）、`branch`（创建时检出的分支，验收时合并回这里；detached HEAD 时为 `null`） |
| `run.delivered` | 交付，审的是这一轮（上一次交付之后的事），见[交付](../domains/20261031-goal_mode.md#delivery_in_goal_mode)；`data` 是交付结果：`headline`（负责人报告的「结论」一节，没写时为空）、`summary`（报告的其余部分，不截断）、`decisions`（「需要你决定」一节的问题）、`briefSuggestions`（负责人建议写入工作区共享资料的条目，见[工作区共享资料](../domains/20261031-agents_and_roles.md#workspace_brief)）、`merge`（`state`：`merged`、`nothing`、`resolving`、`conflict`、`blocked` 或 `inPlace`；`note`：结果在哪里的一句话）、`changed`（这一轮改的文件）、`leadEdits`（负责人这一轮自己改的文件）、`deliverables`（整个任务的 diff、这一轮各任务的 diff，以及这一轮最新的一份任务回复：最后一个任务被取消、没有回复时取更早的任务的）、`evidence`（这一轮每个任务的全部证据，`text` 以任务 id 开头）、`acceptance`（这一轮每个任务的验收记录：验收总数、通过数、证据方法计数、`checks`、独立验证、`traceGaps` 和任务自己报告的 `risks`，见[证据方法](#evidence_methods)）、`risks`（Janus 查出来的风险，不含任务自己报告的：每条 `{"task", "text"}`，`task` 是它说的子任务，和整个 Run 有关的没有） |
| `risk.accepted` | 用户验收。在 worktree 中的 Run 另有 `data.repo`（原仓库）、`data.branch`（合并回的分支，detached HEAD 时为 `null`）、`data.commit`（这次带回源分支的提交，没有新改动时为 `null`）和 `data.result`（结果所在的提交，源分支已经有它时也记；下一次验收或合并从它开始，继续这个 Run 时 worktree 从它重建）。验收失败时不写这个事件，见[工作目录](../domains/20261031-run_lifecycle.md#workspace_model) |
| `run.merged` | 交付时 Janus 把 worktree 中的结果合并回源分支（`actor` 为 `janus`），紧接着是这次交付的 `run.delivered`；没有新的改动或没能合并时不记。`data` 和 `risk.accepted` 相同：`repo`、`branch`、`commit`（这次带回的提交，源分支已经有它时为 `null`）、`result`。之后的合并从 `data.result` 开始，见[工作目录](../domains/20261031-run_lifecycle.md#workspace_model) |
| `run.failed` | Run 失败；`data.error`。对话的会话打不开或异常结束时也记这一条，下一条消息会重新打开会话 |
| `run.cancelled` | 用户取消 |
| `run.interrupted` | 编排器重启时 Run 未结束；`data.after` 是之后怎样：`goes_on`（自动继续）、`paused`、`no_progress`、`person`（等用户或下一条消息），见[中断与恢复](../domains/20261031-run_lifecycle.md#recovery) |
| `run.recovered` | 从中断处继续；服务重启后自动继续的 `actor` 为 `janus`、`data.auto` 为 `true` |
| `run.paused` / `run.resumed` | 暂停 / 继续 |

### 值班（Loop）

记在值班的会话 Run 里，见[工作区值班：开工与摸鱼](../domains/20261121-loops.md#waking)。每次醒来的提示是一条 `actor` 为 `janus` 的 `user.message`。

| 类型 | 说明 |
| --- | --- |
| `loop.woke` | 醒来；`data.reason`（`timer`、`self`、`manual`、`answer`、`dispatch`）、`n`（第几次）、`since`（上次睡下的时刻，没有时为 `null`）、`watchesFiles`（工作区在 Git 仓库里，值班在自己的副本里干活，能看出改动） |
| `loop.slept` | 这次醒来结束；`data.until`（下次醒来的时刻，没有时为 `null`）、`reason`（那时为什么醒）、`summary`（这次醒来最后一条消息的第一行） |
| `loop.scheduled` | 下次自己醒来的时刻变了（新建、睡下、改时间表、暂停、继续、醒不来）：`until`（没有时为 `null`）、`reason`（`timer` 时间表，`self` 它约的）。服务启动时从最后一条读回时钟 |
| `loop.next_wake` | 值班在醒来的一轮里用 `next_wake` 约了这一轮结束后再醒一次：`seconds`、`reason`（值班页显示它） |
| `loop.dispatch_ended` | 它派出的 Run 交付、失败或被取消：`run`、`key`、`status`；随后以 `dispatch` 唤醒值班（暂停时不唤醒），下次开工的提示列出两次开工之间的这些记录，见[派出的 Run 结束](../domains/20261121-loops.md#dispatch_ended) |
| `loop.moved` | 工作区换了目录，值班的会话跟过去：`from`、`to` |
| `loop.touched` | 这次开工值班在自己的副本里改了文件（没提交的或它私自提交的，副本下次开工前清掉）：`files`，`to` 为 `user`，进收件箱 |
| `loop.failed` | 没能醒来，或会话在醒来的一轮中途断了：`error`，进收件箱；比它新的 `loop.woke` 或 `loop.slept` 出现前，值班的状态是 `failed` |
| `loop.paused` / `loop.resumed` | 用户暂停、继续 |

### 团队记忆

记在写笔记的那个 Run 里（目标 Run、值班的会话或整理），见[团队记忆](../domains/20261123-team_memory.md)。用户在应用里改、删笔记不记事件，只发全局事件流的 `memory` 通知。

| 类型 | 说明 |
| --- | --- |
| `memory.saved` | 会话用 `remember` 写了或更新了一条笔记：`actor` 是成员 id；`data.id`、`title`、`kind`、`created`（新写的为真） |
| `memory.forgotten` | 整理用 `forget` 删了一条笔记：`data.id`、`title`、`reason` |
| `memory.consolidated` | 整理的一轮结束：`data.saved`、`forgotten`（这一轮改写和删除的条数）、`summary`（最后一条消息的第一行）；随后整理的 Run 为已交付 |

### 负责人与目标

| 类型 | 说明 |
| --- | --- |
| `goal.status` | Agent 报告的 `/goal` 状态变化，见 [Codex 的目标状态](20261031-acp_integration.md#goal_status)；负责人向 Janus 确认完成后由 Janus 结束目标时，`actor` 为 `janus`，`data.by` 为 `janus`，见[目标不自己结束时](../domains/20261031-goal_mode.md#goal_settle) |
| `lead.failed` | 负责人会话异常结束；`data.error`，`data.next` 为 `reopen`（稍后回到它的会话继续）或 `stop`（不再重开） |
| `skill.used` | Agent 读了资源库某个 Skill 的 `SKILL.md`（经 [Skill 路由](../domains/20261116-resource_library.md#skill_uses)的目录找到）：`actor` 是读它的会话，协作者的带 `task` 和 `attempt`；`data.skill`（名字）、`data.item`（资源 id）、`data.revision`。同一轮里读同一个 Skill 只记一次；读目录本身不算 |
| `mcp.routed` | 一次经 [MCP 路由](../domains/20261116-resource_library.md#mcp_router)对资源库服务器的真实工具调用（经 `call_tool`、`run_code` 脚本里的每次调用，或直接 `tools/call`；`find_tools` 不记）：`actor` 是调用的会话（`lead` 或子任务），协作者的带 `task`；`data.server`、`data.tool`（路由名 `<服务器>__<工具>`）、`data.ms`、`data.error`（成功时为 `null`）。不记参数 |
| `lead.routed` | 负责人派出子任务后经 [MCP 路由](../domains/20261116-resource_library.md#mcp_router)调用了资源库的工具，`to` 为 `lead`，`data.tool`（路由的工具名）、`data.server`。同一个工具只记一次。需要负责人处理，看板上是「[负责人用了资源库工具]」；交付时列为风险 |
| `lead.edited` | 负责人派出子任务后改了工作目录里的文件，`to` 为 `lead`，`data.paths` 是这次第一次被它改到的文件（同一文件只记一次）。需要负责人处理，看板上是「[负责人改了文件]」；交付时负责人这一轮自己改的文件都列在 `run.delivered` 的 `leadEdits` 里。见[负责人的职责](../domains/20261031-goal_mode.md#lead_role) |
| `lead.stalled` | 停滞检测发现负责人会话没有进展，`to` 为 `user`。`data.reason` 是 `idle`（`data.idleMs`）或 `loop`（`data.tool`、`data.repeats`、可选 `data.period`）；负责人再有动静时写一条 `data.resolved: true` 的 `lead.stalled`，见[停滞检测](../domains/20261031-run_lifecycle.md#watchdog) |
| `orchestration.accepted` | 编排通过校验；`data.plannedSeq` 是任务加入看板时已分配的最后一个事件序号，`data.tasks` 是写入看板的任务（含 `owns`、`verifies`、`continues`，验证任务和续接任务的 `deps` 已包含目标任务），恢复时据此重建看板 |
| `orchestration.rejected` | 编排没有通过校验；`data.errors`、`data.submitted` |
| `board.posted` | 协作者写回看板；`data.kind`（`progress` / `blocker` / `note`）、`data.text` |

### 任务与尝试

| 类型 | 说明 |
| --- | --- |
| `task.assigned` | 任务分配给执行者 |
| `task.ready` | 依赖满足，可以启动 |
| `attempt.launch_requested` / `attempt.started` | 请求启动 / 尝试开始；`attempt.started` 的 `data.config` 是实际生效的设置（其中 `resources` 见下）；尝试续接已经结束的会话时另有 `data.continuation`（`from` 是会话原来所属的任务，返工和复审时就是这个任务自己；`session`、`loaded`，回退新建会话时附 `fallback`：`context_over_75pct`、`unsupported`、`load_failed`，或 `no_session`（要接着的任务从来没开过会话，例如开始前就被取消））；回到断掉的会话继续时 `data.resumed` 为 `true`，`data.brokeOff` 写明会话是怎么断的：`restart`（服务重启）或 `failure`（上一次尝试失败）；任务结束后又被打开时另有 `data.reopen`，记录这次尝试为什么开始：`{reason: "lead.retry", session: "continue" \| "new", from?}` 或 `{reason: "target.reworked", target}`；在 worktree 中的 Run 另有 `data.git`：`repo`（原仓库）、`branch`（验收时合并回的分支，detached HEAD 时为 `null`）、`worktree`（worktree 的路径）和 `head`（尝试开始时 worktree 所在的提交），应用在尝试的标题下显示 |
| `context.handoff` | 上游结果交给下游；负责人 `retry` 带 `from` 时，那个验证的意见也以同样的格式交给被返工的任务；独立验证任务的 `data.verdict` 和 `data.checks` 保留判定、逐项结果和证据。下游启动提示单列验证判定和未通过项。`data.handoff` 是上游专门给下游的交接说明，`data.riskItems` 是上游风险列表，`data.amendments` 是负责人对上游结论的修订，`data.files` 是上游改过的文件，`data.stale` 是上游完成后又被别的任务或负责人改过的文件（`[{path, by}]`，负责人改过时 `by` 为 `负责人`），见[工作目录里的痕迹](../domains/20261031-goal_mode.md#traces) |
| `result.amended` | 负责人修订已完成任务的结论（`janus.amend`）；`data.text` |
| `result.submitted` | 尝试提交结构化结果；`data.summary`、可选 `data.handoff`、验证任务的可选 `data.verdict`（`approved` / `rejected` / `inconclusive`）、`data.checks`（逐条验收：`criterion`、`passed`、`evidence`，可选的 `method` 见[证据方法](#evidence_methods)）、`data.evidence`、`data.risks`；Git 工作目录中另有 `data.files`：提交结果时的文件状态（`head` 和与它不同的文件的 SHA-256），见[证据复用](../domains/20261031-goal_mode.md#evidence_reuse) |
| `artifact.created` | 保存产物；`data.name`、`data.kind`、`data.path`、`data.hash`、`data.bytes`。任务的产物带 `task` 和 `attempt`；整个任务的 diff（`kind` 为 `run_diff`，`actor` 为 `janus`）两者都没有 |
| `attempt.failed` | 尝试失败；`data.error` |
| `attempt.late_result` | 过期尝试的结果被忽略 |
| `task.retry_scheduled` | 安排下一次尝试，回到断掉的会话继续（回不去时新建会话） |
| `task.succeeded` / `task.failed` | 任务成功 / 失败。`task.failed` 的 `data.reason` 是 `verification`（验证没通过，不自动重试）或 `attempts`（用完尝试次数）。`task.succeeded` 带完整的结论：`data.summary`、可选 `data.handoff`、验证任务的 `data.verdict`（`approved` / `rejected` / `inconclusive`）、`data.evidence`、`data.risks`、`data.checks`（逐条验收及其 `method`）和 `data.acceptance`（验收总数、通过数、证据方法计数、提醒），恢复和应用都从它读回结果；负责人用 `amend` 接受没通过验收核对的结果时，`actor` 为 `lead`，`data.acceptedBy` 为 `lead`，另有 `data.reason`（`amend` 的 `text`），`data.checks` 来自被接受的那次 `result.submitted`，`data.risks` 末尾加上没通过核对的原因和接受理由。协作者完成的 `task.succeeded` 带 `data.traceGaps`：结果和工作目录对不上的地方，没有时为空数组，见[工作目录里的痕迹](../domains/20261031-goal_mode.md#traces)；还带 `data.files`（同 `result.submitted`）、`data.durationMs`（这次尝试从开始到完成的时长）和 `data.contextRatio`（会话最近一次上报的上下文占用，没有上报时不带），看板的「[完成]」条目写成「用时：… · 会话上下文 …%」 |
| `task.blocked` | 硬依赖失败；`data.dependency`。依赖是判定 `rejected` / `inconclusive` 的独立验证任务、而本任务在判定之前就已编排时，`data.verdict` 是那个判定。一个依赖处理好后仍有别的依赖失败时再写一条，指向那个依赖 |
| `task.stalled` | 停滞检测发现尝试没有进展，`to` 为 `lead`。`data.reason` 是 `idle`（`data.idleMs`：多久没有动静）或 `loop`（`data.tool`：重复的调用或调用序列，`data.repeats`：连续次数或轮数，`data.period`：步长 1、2 或 3）。没有动静的尝试再次有更新时，会再写一条 `data.resolved: true` 的 `task.stalled`，见 [Run 生命周期](../domains/20261031-run_lifecycle.md#watchdog) |
| `task.conflict` | 两个同时执行的任务改了同一批文件，或负责人修改了正在执行的任务的文件；`to` 为 `lead`，`data.other` 是另一方，`data.paths` 是相对工作目录的文件。`data.owned` 为 `true` 时表示改了对方负责的文件（越界）；`data.byLead` 为 `true` 时表示负责人会话修改了 `task` 负责或正在修改的文件（`data.other` 为 `lead`）。见[同时改同一个文件](../domains/20261031-goal_mode.md#conflicts) |
| `task.split_requested` | 协作者提问时附上拆分提议（`ask` 的 `split`），提议当场写下，不等这一轮结束；`actor` 是执行者，`to` 为 `lead`，`data.reason` 是原因，可选 `data.completed` 是已完成部分，`data.subtasks` 是建议子任务数组（`title`、`owns`、`accept`），见[看板 MCP 工具](20261031-board_mcp.md#ask) |
| `task.skipped_by_decision` | 负责人用 `cancel` 取消（`actor` 为 `lead`，`data.reason`，连带取消的有 `data.dependency`） |
| `task.reopened` | 任务重新开始。`data.reason` 是 `lead.retry`（负责人重试或返工，`actor` 为 `lead`，`data.session` 是 `continue` 或 `new`，可能带 `data.from`（依据哪个验证的意见）、`data.note`、新的 `data.instructions`、`data.accept`）、`target.reworked`（被验证的任务返工，这个验证在它完成后复审，`actor` 为 `janus`，`data.target` 是被返工的任务）或 `upstream.retry`（因上游被取消而连带取消的任务，随上游的重试恢复，`actor` 为 `janus`，`data.upstream` 是上游任务），见[看板 MCP 工具](20261031-board_mcp.md#retry_tool) |

### 验证

| 类型 | 说明 |
| --- | --- |
| `verification.started` | 开始核对结果；`data.accept` |
| `verification.passed` / `verification.failed` | 核对结果；`data.checks`、`data.acceptance`（验收总数、通过数、证据方法计数和提醒，见[证据方法](#evidence_methods)），失败时另有 `data.failures`（每条没核对、没证据、没达到或方法不合法的标准） |

<a id="evidence_methods"></a>
### 证据方法

每条 `check` 可以带可选的 `method`，说明这条验收结论的依据是什么：

| `method` | 含义 |
| --- | --- |
| `test` | 运行自动化测试得到的结果 |
| `command` | 运行命令、脚本或检查工具得到的结果 |
| `inspection` | 检查代码、文件、界面或实际状态得到的结果 |
| `reasoning` | 根据推理或自我判断得到的结果 |
| `unverified` | 证据缺失、无法复现或暂时无法核实 |

- 方法只说明依据的类型，不代表结论一定真实：Agent 仍可能把推理写成 `test`，关键结果由负责人自己核对。
- 没有 `method` 的 check 显示为「未说明」，不当作 `reasoning`，也不因此判失败。
- `method` 存在时必须是上表中的值。其他值原样记录在 `result.submitted` 和 `verification.failed` 的 `data.checks` 中，`evidence::gaps` 报出「不是允许值」并让这次核对失败，不会静默换成合法方法。
- `reasoning`、`unverified` 和没有方法只产生提醒（`data.acceptance.reminders`），不阻断任务。
- `data.acceptance` 的结构（`verification.*`、`task.succeeded` 和 `run.delivered` 的 `acceptance` 条目）：`criteria`（验收标准总数）、`passed`（通过数）、`methods`（`method`、`label`、`count` 的数组，按上表顺序）、`unspecified`（没有方法的条数）、`invalid`（不合法的值）、`reminders`（要负责人注意的提醒）。交付中的条目另有 `task`、`title`、`status`、`label`、`checks`、`verifications`、`unverified`（已完成、改了文件、没有独立验证，验证任务自己不算）、`traceGaps`、`risks`。

<a id="usage_accounting"></a>
## 用量口径

Run 的用量账本是从事件实时算出的只读汇总，只在服务端算一份（`ledger`，`backend/src/usage.rs`，用例在 `backend/testdata/usage_cases.json`）；应用经 `GET /api/runs/{id}/usage` 读它，只负责写成文字（`frontend/Sources/Janus/Core/UsageLedger.swift`）。账本不读专门的表，也不改变调度、任务状态机、事件写入或交付条件。全部输入是 `session.usage`，再加上 `session.controls` / `session.control` 给出的模型。

### 三种用量事件

| 形态 | 来源 | 字段 | 性质 |
| --- | --- | --- | --- |
| 上下文快照 | ACP `usage_update` | `used`、`size`、可选 `cost` | 某个时刻的上下文窗口，不是消耗；`cost` 是会话的累计费用 |
| 一轮的 token | `session/prompt` 的返回 | `inputTokens`、`outputTokens`、`totalTokens`、`cachedReadTokens`、`cachedWriteTokens`、`thoughtTokens`，以及按模型的 `models` | 这一轮提示自己的用量 |
| 会话记录的读数 | Agent 自己的会话记录（`agent_records`） | `source: "records"`、`session`、`turnEnded`，按模型的 `models`（每行的字段同上） | 这个原生会话到读的时候为止的累计用量 |

<a id="usage_records"></a>
### 会话记录

`session/prompt` 的返回只在一轮正常结束时才有：进行中的一轮显示 0，崩溃、超时或被杀掉的一轮永远没有。Claude Code 和 Codex 自己把每次模型请求的用量写在会话记录里，Janus 读这些记录作为 token 的来源。只读 Janus 隔离的 Agent 配置目录（`data/agents/<id>/config`，即 `CLAUDE_CONFIG_DIR` / `CODEX_HOME`），不读用户自己的 `~/.claude`、`~/.codex`，不写任何文件，也不跟随符号链接。

| Agent | 文件 | 怎样计 |
| --- | --- | --- |
| Claude Code | `projects/<项目>/<会话>.jsonl`，以及子 Agent 的 `projects/<项目>/<会话>/subagents/*.jsonl` | `type` 为 `assistant` 的行的 `message.usage` 和 `message.model`；同一个响应会写好几行，按 `message.id` 加 `requestId`（新版本是 `requestId` 改名的 `requestRef`）去重，取最后一行。`input_tokens` 不含缓存，总量是输入、输出、缓存读取（`cache_read_input_tokens`）和缓存写入（`cache_creation_input_tokens`）之和，思考取 `output_tokens_details.thinking_tokens` |
| Codex | `sessions/<年>/<月>/<日>/rollout-<时间>-<会话>.jsonl`（ACP 的会话 ID 就是 Codex 的 thread ID，`codex-acp` 的 `newSession` 返回 `thread.id`） | `token_count` 事件的 `info.total_token_usage` 是整个 thread 的累计值，取相邻两次的差，归入当时最近一条 `turn_context` 的模型；累计值重复时不算新的请求，变小时（thread 被回退）取这一次的 `last_token_usage`。Codex 的 `input_tokens` 包含缓存读取和缓存写入，和适配器一样减去 `cached_input_tokens` 与 `cache_write_input_tokens`；思考取 `reasoning_output_tokens` |

- **什么时候读**：每一轮提示进行时每 20 秒读一次，按模型的累计值有变化才记一条 `session.usage`（`turnEnded: false`）；这一轮结束时无论怎样结束（正常返回、出错、超时、被打断、Agent 进程退出、Run 被取消）都再读一次并记下（`turnEnded: true`）。还没找到记录文件时什么也不记（`orchestrator/records.rs`）。
- **增量读取**：每个会话的读取位置和去重表保存在 Run 的内存里，在这个会话的多轮之间复用，每次只读新追加的完整行，没写完的最后一行留到下一次。服务重启后第一次读会从头读一遍，得到的仍是同样的累计值；文件变短时从头重读。
- **账本怎样用**：会话记录的读数是累计值，和费用一样按原生会话（成员加会话 ID）、再按模型，取相邻读数的增量（`SessionReadings`），增量归入后一次读数的任务、尝试和账单时段；续接同一原生会话时，后一个任务只算它之后的增量。有会话记录读数的原生会话只按读数计 token：它的 `session/prompt` 返回里的 token 不再计入，不论返回在读数之前还是之后，所以不会重复计数；没有读数的会话（其他 Agent、找不到记录的会话、更早的 Run）照旧按每轮的返回计。上下文快照和费用不受影响。
- **轮次**：有会话记录的会话，每条 `turnEnded: true` 的读数算一轮；账单里一轮只在它第一次有增量的那一行计一次，一个模型在一轮里只计一次。
- **差别**：Claude Code 的会话记录包含主循环和子 Agent，但不含不写进记录的辅助调用（例如生成会话标题）：实际数据中，没有子 Agent 的会话和返回的 `usage` 完全一致，比 `_meta.quota.model_usage` 约少万分之一；模型名取响应里的 `message.model`，经代理时可能和请求时的模型名不同。Codex 子 Agent 的 thread 有自己的记录，和适配器的返回一样不计入父会话。

- 一轮的 token 是这一轮的，不是到这一轮为止的累计。ACP v2 的 `Usage` 写明是「the completed work」；Claude Code 适配器在每轮开始时清零（`accumulatedUsage`），Codex 适配器取这一轮结束时的会话总量减去开始时的总量（`PromptTokenUsage`）。因此同一会话的每一轮都相加，不按数字是否上涨去猜口径：对话越长，每轮带的历史越多，单轮的数字本来就会上涨。
- `models` 来自返回值的 `_meta.quota.model_usage`，Claude Code 和 Codex 适配器用同一种形状发送。Claude Code 的 `usage` 只算主循环，`model_usage` 还算上子 Agent 和压缩等内部调用（Claude Agent SDK 注明计费以它为准），所以有 `models` 时这一轮按它计，每行带模型名；没有时按 `usage` 计，模型取这个成员当时的模型（`session.controls` 的 `model.current`，或之后切换成功的 `session.control`），也没有时写「未知模型」。
- `inputTokens` 不含缓存，`totalTokens` 是输入、缓存读取、缓存写入和输出之和；`thoughtTokens` 是输出的一部分。某一行没有 `totalTokens` 但有输入或输出时，按各部分之和计。缺的字段写 `null`，不写 0。
- 上下文快照每次更新都原样记录，不去重。`used` / `size` 只取最近值、峰值和比例，`used` 小于等于 0 的快照忽略（与会话卡片一致），永远不进 token 总量。

### 费用

- 账本的费用只取 Agent 上报的 `cost`，原值加币种，不做任何换算，也不按 token 估算。
- `cost` 是会话的累计费用（Claude Agent SDK 的 `total_cost_usd`：每次带「到目前为止」的总数，应读最新值）。同一成员的原生会话按币种计算相邻读数的增量，归入上报时的任务、尝试和账单时段。续接会话沿用上次读数，同一成员并行执行的不同会话分别计费；读数比上一次小说明累计重新开始（例如会话中途 `/clear`），之前达到的数额保留并加上之后的读数；一次正数之后读到 0 是出错的结果，忽略。
- 同一币种的会话合计成一个数；不同币种分别列出并标「币种或口径不同，未合并」；没有币种的每条单列并标「未标注币种」。
- 账单另有按 models.dev 价格的估算（[ADR：按 models.dev 的价格估算用量](../decisions/20261115-model_prices.md)），它和上报的费用分开显示，不写进账本或事件。

### 归集与范围

事件已带 `actor`、`task`、`attempt`，每个数字都能追溯到对应的 `session.usage`。账本按成员、任务、尝试和会话 ID 归集轮次。续接同一原生会话时，每次尝试各自统计这一段的用量，汇总中的会话数按这些分段计数。`attempt.started` 是 Janus 在启动尝试时写的，那个会话属于 `to` 指向的 Agent（`actor` 是 janus），其余事件的 `actor` 就是会话主人。打开的会话即使一条用量都不上报，也算一个「未上报」的会话。

| 范围 | 内容 |
| --- | --- |
| Run | 负责人和协作者的全部会话，以及墙钟时长 |
| 负责人 / 协作者小计 | Run 总量包含负责人，两者另外单列 |
| 任务 | 这个任务所有尝试的会话；没有会话时是「未开始」，不是「未上报」。任务账单再按成员和模型分开（`task_bill`） |
| 成员 | 一个 Agent 在这个 Run 里的全部会话，含它做过的多个任务 |
| 尝试 | 一次尝试的会话、结束状态和时长 |
| 会话 | 这个会话自己的最近用量，会话卡片显示为「本会话」「上一轮」 |

跨 Run 按时间段的账单见 [HTTP API](20261031-http_api.md#usage_bill)。

### 完整性

`完整`、`部分上报`、`未上报` 三种，按该范围里的会话计数：没有任何会话上报 token 是「未上报」，部分会话上报、部分没有是「部分上报」，全部上报是「完整」。会话记录的读数显示了 token 的会话，在它的第一轮结束之前就算已上报。缺失的数字位置写文字，不写 0；上报了 0 就写 0。范围里还没有任何会话（任务没开始）写「未开始」，和「未上报」分开。

### 时间

时长是墙钟时长：Run 从 `run.created` 到最后一条事件，任务从它的第一条事件到最后一条，尝试从 `attempt.started` 到结束事件；被重启打断、没有结束事件的尝试，结束于同一任务下一次尝试开始的时刻。`question.asked`、`approval.requested`、`input.requested` 到对应的回答、处理或撤回之间的时间单独记为等待时间（`waitMs`），界面写成「其中等待你」，不冒充 Agent 执行时间。没有会话的范围没有时长，写「没有时长记录」，不写 0。时间统计不替代 Run 预算，也不改变预算状态。

每次尝试按它的时间花在哪里分为三类（账本的 `attempts[].kind`，`AttemptKind`）：独立验证任务（`verifies`）的尝试都是 `verify`（复审也是）；其他任务的第一次尝试是 `work`，之后的尝试和负责人 `retry` 发回的是 `rework`；只是在重启后接回原会话继续的尝试（`attempt.started` 的 `data.brokeOff` 为 `restart`）沿用它上一次尝试的类别。账本的 `time`（`TimeSplit`）把三类尝试的时长分别相加（`workMs`、`verifyMs`、`reworkMs`），并给出第一次尝试开始到最后一次结束的跨度（`spanMs`）；同时进行的尝试各算各的，所以三者之和可以大于跨度。应用在 Run 的一行用量摘要末尾写出这三类时长，例如「子任务 42 分（执行 20 分 · 验证 15 分 · 返工 7 分）」。

### 取消、过期和失败

- `run.cancelled` 取消整个 Run：取消时刻仍在跑的尝试全部记「已取消」，备注「Run 被取消」，结束时间取取消时刻或更晚的结束时间。
- `task.skipped_by_decision` 只取消一个任务：只有这个任务仍在跑的尝试记「已取消」，备注「负责人取消了这个子任务」；同一个 Run 里其他任务的尝试不受影响。
- 两种取消都不覆盖取消前已经结束的尝试：失败、验证没通过、过期保持原状态。已经上报的用量照常计入。Janus 不为取消写尝试级事件，杀连接后可能还有一条失败事件，也不算真的失败。
- `attempt.late_result` 的尝试记「已过期但仍计入」；`verification.failed`、`task.failed` 的尝试带结束原因。
- 失败的 Run 保留已经发生的用量；隐藏它会低估成本。

### 回放与恢复

账本是这段事件的纯函数：全量读取、重启后重新读事件、历史 Run 和回放位置（前 N 条事件）都得到同一组数字。Run 页、看板 `board` 的任务详情、交付摘要和 `GET /api/runs/{id}/usage` 读的是同一份结果，见 [HTTP API](20261031-http_api.md#run_usage)。

### 提醒

默认阈值：Run 累计 100,000,000 token；单个任务占 Run 的 60% 且 Run 不少于 100,000,000；5 个以上协作者 30 分钟没有任何任务成功；Run 有 100,000 token 却没有任何费用上报。阈值只在 `backend/src/usage.rs`；提醒带着它的数字送给应用（`Reminder`），应用按界面语言写成文字，完整性不是「完整」时前缀「提醒（按已上报数据）」；它不进收件箱，也不暂停、取消、重试或追加预算。

账本不需要新增事件类型：模型、子 Agent 的用量和费用都来自 Agent 已经发来的字段。
