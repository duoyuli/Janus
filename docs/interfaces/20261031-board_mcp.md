# 看板 MCP 工具

本文是共享看板 MCP 服务的接口参考：端点、方法、负责人工具、协作者工具、编排校验规则和验收标准。看板在协作中的作用和提问的流转见[目标模式与共享看板](../domains/20261031-goal_mode.md)。

## 导航

- [端点与传输](#transport)：修改看板 MCP 的地址、令牌和身份时阅读。
- [工具标注](#tool_annotations)：修改工具的只读标注时阅读。
- [负责人工具](#lead_tools)：修改 `orchestrate`、`wait`、`reply` 等负责人工具时阅读。
- [协作者工具](#member_tools)：修改 `board_post`、`board`，或交结果的 `submit` 和提问的 `ask`（含拆分提议）时阅读。
- [值班的工具](#loop_tools)：修改值班会话的 `dispatch`、`next_wake` 等工具时阅读。
- [团队记忆的工具](#memory_tools)：修改 `recall`、`remember`、`forget` 时阅读。
- [对话的工具](#chat_tools)：修改对话里提议数字员工的 `propose_employees` 时阅读。
- [验收标准](#acceptance_criteria)：修改验收标准的写法和核对时阅读。

<a id="transport"></a>
## 端点与传输

```text
POST http://<JANUS_ADDR>/mcp/{run}/{token}/lead
POST http://<JANUS_ADDR>/mcp/{run}/{token}/task/{task}
```

| 路径参数 | 说明 |
| --- | --- |
| `run` | Run id。Run 不在内存中运行时返回 403 |
| `token` | 这个会话的令牌：由负责人启动时为 Run 生成的随机密钥和会话的席位（`lead` 或 `task/<id>`）一起做 SHA-256 得到（`session_token`）。为空或与席位不匹配时返回 403 |
| `lead` / `task/{task}` | 会话的席位（`SessionKey`）：负责人（值班、整理团队记忆的会话也是这个席位），或正在执行的子任务 |

- 令牌和席位绑定：协作者把 URL 改成 `lead` 或其他子任务都会得到 403，所以协作者拿不到负责人工具，也不能以其他任务的身份写看板。席位写在路径里，不从 id 推断：id 恰好是 `lead` 的子任务，URL 是 `task/lead`，拿到的是协作者的工具和自己的令牌。Run 的密钥只在内存中，服务重启后恢复的会话拿到新的 URL。
- MCP streamable HTTP 传输，响应直接在对应的 POST 中以 JSON 返回，不使用 SSE。
- `GET` 返回 405，服务不主动推送消息。
- 没有 `id` 的消息（通知）返回 202，无响应体。
- 支持的方法：`initialize`、`ping`、`tools/list`、`tools/call`；其他方法返回 JSON-RPC 错误 `-32601`。
- 调用者是谁由 Run 的类型和席位一次定下（`Caller`）：目标 Run 的负责人（看板）、协作者（看板）、值班的会话（[值班的工具](#loop_tools)）或整理团队记忆的负责人（只有[团队记忆的工具](#memory_tools)）；对话只有在它的数字员工打开了 `hires` 时才有这个服务器（只有[对话的工具](#chat_tools)），其余对话令牌对了也返回错误。`tools/list`、`tools/call` 和 `initialize` 的 `instructions` 都按调用者决定：`instructions`（`Caller::instructions`，按 Run 的语言）是服务器的自我介绍，第一行「Janus 的协作工具。每个工具的详细用法和限制写在它自己的说明里，用到时再看：」，下面一个工具一行，只说它是做什么的（例如 `- orchestrate：把一组子任务派给协作者……`，`retry` 和 `cancel`、`recall` 和 `remember` 合成一行）。两种 Agent 开局只加载工具名或命名空间，Claude Code 把它放在「MCP Server Instructions」一节，Codex 当作命名空间的描述，所以 Agent 从这里知道有哪些工具；工具怎么用只写在各自的说明里。负责人说明、协作者约定、值班和记忆整理的系统层不再列工具，见 [ADR：MCP 路由照 magpie 只给三个工具](../decisions/20261126-mcp_router_three_tools.md)。每组工具是一个枚举（`LeadTool`、`MemberTool`、`LoopTool`、`ChatTool`、`MemoryTool`），工具的定义和处理都按枚举登记，列出的工具和能调用的工具是同一份；调用不属于自己的工具返回「没有这个工具」。
- `initialize` 的 `protocolVersion`：客户端请求的版本 Janus 支持就用它，否则回答 Janus 最新的版本（支持的版本和 MCP 路由相同，见[资源库](../domains/20261116-resource_library.md#mcp_router)），服务名 `janus`。

会话中的 MCP 服务器条目：

```json
{ "type": "http", "name": "janus", "url": "http://127.0.0.1:7878/mcp/<run>/<token>/task/T1", "headers": [] }
```

URL 的主机和端口取 `JANUS_ADDR`。

<a id="tool_annotations"></a>
## 工具标注

所有工具都带 MCP 工具标注：负责人和协作者的 `board`、`wait`、`board_post` 标为只读，`orchestrate`、`reply`、`retry`、`amend`、`cancel`、`ask_user`、`submit`、`ask` 标为非破坏性操作。标注的作用是避免 Codex 把调用看板当作需要用户审批的操作。

工具调用的错误以 `isError: true` 的文本内容返回，不使用 JSON-RPC 错误。

<a id="lead_tools"></a>
## 负责人工具

`who` 为 `lead` 时，`tools/list` 返回以下八个工具。

每个工具怎样用、有什么限制，只写在它自己的说明和参数说明里（`LeadTool::definition`），负责人说明不列工具，见 [ADR：Janus 只注入协作规则](../decisions/20261125-collaboration_only_injection.md)。例如 `wait` 何时返回、最长等多久、推送过的消息不再出现，`retry` 的 `session` 和 `from`，`amend` 不能改独立验证的判定，`orchestrate` 的 `verifies`、`continues` 和 `owns` 的规则。工具的说明、返回、错误和看板消息都按 Run 的语言（`Run.lang`）写中文或英文，见[注入的语言](../domains/20261031-goal_mode.md#prompt_language)；下文引用的文字是中文版。返回、错误和看板消息只写事实，不显然时加一句下一步（点出要用的工具，不解释用法）；负责人说明、协作者约定和工具说明里已有的规则不再重复，见 [ADR：Janus 只注入协作规则](../decisions/20261125-collaboration_only_injection.md) 的第 4 条。

<a id="task_detail"></a>
### `board`

```json
{ "task": "T2" }
```

`task` 可选。

不带 `task`（`board_team`）时返回协作者（名字和职责，与负责人说明中的[协作者名单](../domains/20261031-goal_mode.md#lead_brief)相同）和看板上所有任务的当前状态，每个任务一行：id 和标题、执行者 id、按 Run 语言写的状态（`TaskStatus::label_in`）。不含用量：每个任务的用量带 `task` 查看。

带 `task`（`task_detail`）时按 id 返回一个任务的全部信息：执行者和状态、说明、验收标准、负责的文件、验证对象、续接会话的前置任务、上游和下游任务（带状态）、完整结果（验证判定、给下游的交接说明、逐条验收及其证据方法和通过数、证据方法计数、只提醒不阻断的项、其他证据、风险）、独立验证这个任务的验证任务及其判定（两者分开展示）、负责人的修订、最近一次没通过验收或尝试失败的原因、改过的文件、产物、看板上的进展、阻塞、拆分提议、提问、回答和冲突（含负责人改文件的冲突），最后是用量。验证判定写成 Run 语言的说法，不写原始值。负责人可以顺着上下游的 id 继续查看相关任务。任务不存在时返回错误。

用量段（`task_lines`）在最后，给出这个任务的总量、费用、墙钟时长（含「其中等待用户」）、token 构成、上下文快照，每个尝试一行（编号、执行者、结局、token、结束原因、用时，包括失败、验证没通过、已过期但仍计入和已取消的尝试），以及每个成员的 token 和按模型的分布（`task_bill`，例如「成员 实现者：2,000 tokens · 模型 gpt-6-astra 1,500、gpt-6.1-sol 500」）。任务还没有会话时写「用量：未开始（子任务 T2 还没有会话）」，不等于「未上报」。英文 Run 中这一段也是英文（`task_lines` 带 Run 的语言），每个尝试的结束原因（例如「验收没通过」）和没写模型的会话记作的「未知模型」是账本里的数据，保持中文。

用量是只读的：读事件失败或用量缺失时按空账本输出，仍然正常返回，不报错、不阻塞任务，调度与任务状态不受影响。

<a id="orchestrate"></a>
### `orchestrate`

提交一份编排，即一组交给协作者的任务。

校验通过后，Janus 先把 `orchestration.accepted` 写进事件日志，写入成功才把任务放上看板、开始调度。写入失败（例如磁盘满）时工具返回错误，说明编排没有生效、没有子任务开始，负责人可以原样重试；重试成功后每个任务只执行一次。重启后看板从事件日志重建，所以看板上的任务和日志里的编排始终一致。

```json
{
  "tasks": [
    {
      "id": "T1",
      "title": "实现解析器",
      "instructions": "背景……需要做……注意……",
      "assignee": "developer",
      "deps": [],
      "accept": ["空输入返回明确的错误", "新增测试覆盖空输入并通过"],
      "owns": ["src/parser"]
    },
    {
      "id": "V1",
      "title": "验证解析器",
      "instructions": "独立核对 T1 的改动……",
      "assignee": "qa",
      "accept": ["运行解析器的测试并给出命令和输出"],
      "verifies": "T1"
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 字母、数字、`-` 和 `_`，最长 32 个字符，在整个看板内唯一 |
| `title` | string | 是 | 任务标题 |
| `instructions` | string | 是 | 给执行者的完整说明。执行者看不到负责人的对话 |
| `assignee` | string | 是 | 协作者 id，不能是负责人 |
| `deps` | string[] | 否 | 必须先成功完成的任务 id，可以引用之前编排中的任务 |
| `accept` | string[] | 是 | 可核对的验收标准，至少一条，见[验收标准](#acceptance_criteria) |
| `owns` | string[] | 否 | 这个任务负责修改的文件或目录，相对工作目录，目录包含其下所有文件。见[团队结构](../domains/20261031-goal_mode.md#team_structure) |
| `verifies` | string | 否 | 被验证任务的 id（同批或之前编排的任务）。这个任务是它的独立验证，见[团队结构](../domains/20261031-goal_mode.md#team_structure) |
| `continues` | string | 否 | 要续接原 ACP 会话的前置任务 id（同批或之前编排的任务），执行者必须相同，用于要用到那个任务上下文的**新**工作，见 [ADR：热会话续接](../decisions/20261118-session_continuation.md)。验证没通过后的返工不新建任务，用 [`retry`](#retry_tool) |

成功时返回已写入看板的任务；失败时返回全部错误，一个任务都不启动。

<a id="orchestration_validation"></a>
#### 校验规则

`validate_orchestration` 一次检查全部问题：

- `tasks` 必须是非空数组。
- `id` 格式合法，且不与看板上已有的任务或同批任务重复。
- `title` 和 `instructions` 不能为空。
- `assignee` 必须是协作者。
- 依赖必须存在，不能依赖自己，同批任务之间不能成环。
- 每个任务至少有一条验收标准。
- `owns` 是工作目录内的相对路径，不能是绝对路径，不能含 `..`。`.` 和多余的 `/` 去掉（`src/./a.rs`、`src//a.rs` 都是 `src/a.rs`）；比较两个路径是否重叠时不分大小写，macOS 默认的文件系统里 `src/Utils.rs` 和 `src/utils.rs` 是同一个文件。
- `deps` 中重复的 id 只算一次。
- 校验和写入看板在同一把锁里依次进行：同时提交的两份编排先后校验，不会让同一个 id 进看板两次。
- 可能同时执行的两个任务（彼此都不在对方的上游，比较对象是同批任务和看板上未结束的任务）`owns` 不能重叠：同一路径，或一个是另一个所在的目录。
- `verifies` 指向的任务存在、不是它自己、执行者不同；验证任务不能写 `owns`；Janus 把被验证的任务加入它的依赖，加入后不能成环。
- `continues` 指向的任务存在、不是它自己、执行者与当前任务相同；验证任务（带 `verifies`）不能写 `continues`；Janus 把 `continues` 指向的任务加入依赖，加入后不能成环。

`owns`、`verifies` 和 `continues` 的检查在 `teamwork::check` 中，前面的基本检查都通过后才执行。

通过校验的任务按固定策略执行：最多尝试 `MAX_ATTEMPTS`（2）次，需要结构化结果。任务能否修改文件由执行者的 Agent 权限模式决定，编排中没有读写字段，见[权限交给 Agent 原生模式](../decisions/20261031-agent_native_permissions.md)。

<a id="wait"></a>
### `wait`

```json
{ "timeout_sec": 50 }
```

取回看板上的新消息。新消息中有需要负责人处理的（与[看板推送](../domains/20261031-goal_mode.md#board_push)相同的那些：提问、失败、阻塞、未解决的停滞、阻塞类写回、冲突、拆分请求、负责人派出子任务后改了文件、带痕迹问题或验证未通过的完成、用户的回答）、有任务完成（`task.succeeded`）或 Run 被取消时立即返回（`ends_board_wait`）；否则通过事件通知（`Run.board_wake`）挂起等待，这类事件到来时毫秒级唤醒返回，最多等待 `timeout_sec` 秒（1 到 50，默认 50，`WAIT_MAX_SECS`）。上限要低于 Agent 等一次 MCP 工具调用的时间：Claude Code 和 Codex 都是 60 秒，超过就判这次调用失败（「The operation timed out.」），负责人拿到的是报错而不是看板消息和实时进展。Agent 放弃时 Janus 这边的请求随之取消，已读位置只在 `wait` 真正返回时推进，所以消息不会丢。只是告知的消息（`[开始]`、`[进展]`、`[备注]`、`[尝试失败]`、`[等用户]`、负责人自己回答或取消留下的记录）不单独唤醒负责人，留到下一次返回时一起带上，或在超时时返回，不会丢。看板上没有未结束的任务时直接返回；等待超时且仍有任务在执行时，附带每个运行中任务的实时心跳（当前阶段、最近工具、已运行时长、已改动文件数）和等待启动的任务数。

返回的消息：

每条消息形状相同：「- [标记] 任务「标题」· 执行者：事实」，需要时后面跟缩进两格的明细行（`board_entry`）。英文 Run 中标记也是英文，括号里是对应的英文标记。验证判定和任务状态写成 Run 语言的说法（「通过」「需要修改」「证据不足」），不写原始值。消息只写事实，必要时加一句下一步；接受、返工、取消各做什么，派出后不自己接手，这些写在负责人说明和工具说明里，消息不再列出。

| 标记 | 来源事件 | 内容 |
| --- | --- | --- |
| `[开始]`（`[Started]`） | `attempt.started` | 任务、执行者、第几次尝试 |
| `[完成]`（`[Done]`） | `task.succeeded` | 摘要（验证任务通过时开头写「验证 T1，判定「通过」」）、用时和会话上下文、验收总数和通过数、证据方法计数（测试 / 命令 / 检查 / 推理判断 / 未核实 / 未说明，见[证据方法](20261031-events.md#evidence_methods)）、只提醒不阻断的项、逐条验收（✓ / ✗、证据方法、标准、证据）、执行者的其他证据、独立验证的判定（验证任务已结束时）、风险、产物路径，以及结果和工作目录对不上的「痕迹核对」（`data.traceGaps`，见[工作目录里的痕迹](../domains/20261031-goal_mode.md#traces)）。超过限额的部分删去，并提示带 `task` 调用 `board` 查看，见[完成消息的限额](#inline_budget) |
| `[验证未通过]`（`[Verification not passed]`） | 验证任务的 `task.succeeded`（`verdict` 为 `rejected` 或 `inconclusive`） | 验证者完成了独立核查，判定「需要修改」或「证据不足」，明细与 `[完成]` 相同；多一行「返工用 janus.retry 发回有问题的子任务，from 填 V1」，有受这个判定阻塞的旧下游时列出它们的 id。对已完成且未通过的验证调用 `cancel` 时，工具返回错误并保留原判定 |
| `[尝试失败]`（`[Attempt failed]`） | `attempt.failed` | 失败原因，还会重试 |
| `[没通过验收]`（`[Acceptance not met]`） | `task.failed`（`reason: "verification"`） | 协作者交的结果仍有标准没达到（交的时候提醒过它可以修好再交一次），每条一行明细 |
| `[失败]`（`[Failed]`） | `task.failed`（`reason: "attempts"`） | 用完尝试次数和最后的错误 |
| `[用户介入]`（`[User stepped in]`） | 用户对协作者会话的 `user.message`、`control.taken`、`control.released`、`session.interrupted` | 用户直接在协作者的会话里发了消息、接管、交还、打断或让它以当前结果结束；只告知，不提前唤醒 `wait`。写明以用户的意思为准，不要改回去 |
| `[负责人改了文件]`（`[Lead changed files]`） | `lead.edited` | 负责人派出子任务后又改了的文件，写明这些改动没有经过任何子任务的验收；交付时单独列出 |
| `[负责人用了资源库工具]`（`[Lead used a library tool]`） | `lead.routed` | 负责人派出子任务后经 MCP 路由调用了资源库的工具（每个工具记一次），写明这次调用会列为交付风险 |
| `[无法开始]`（`[Cannot start]`） | `task.blocked` | 依赖失败，处理好依赖后自动继续；或依赖的独立验证判定「需要修改」/「证据不足」（`data.verdict`），验证复审通过后自动开始 |
| `[停滞]`（`[Stalled]`） | `task.stalled` | 协作者很久没有动静，连续重复同一个调用，或连续重复 2 步 / 3 步交替调用序列 |
| `[用户已回答]`（`[User answered]`） | `question.answered`（不是负责人回答的） | 用户在会话或应用中直接回答了协作者的提问，负责人不用再回答 |
| `[用户决定]`（`[User decision]`） | `question.answered`（`ask_user` 的问题） | 用户对负责人所提问题的回答 |
| `[进展]` `[阻塞]` `[备注]`（`[Progress]` `[Blocker]` `[Note]`） | `board.posted` | 协作者写回的内容 |
| `[请求拆分]`（`[Split requested]`） | `task.split_requested` | 协作者发现任务过大，提问时附上拆分提议（[`ask`](#ask) 的 `split`）：拆分原因、已完成部分和建议子任务列表 |
| `[冲突]`（`[Conflict]`） | `task.conflict` | 两个同时执行的任务改了同一批文件（请负责人确认分工后用 `reply` 告诉它们），或负责人直接修改了正在执行的任务负责 / 正在改的文件（`data.byLead: true`） |
| `[越界]`（`[Out of scope]`） | `task.conflict`（`data.owned: true`） | 任务改了另一个可能同时执行的任务负责的文件，请负责人确认分工后用 `reply` 告诉它 |
| `[提问]`（`[Question]`） | `question.asked` | 问题和选项 |
| `[等用户]`（`[Waiting for the user]`） | `approval.requested`、`input.requested` | 协作者在等用户审批或填写 |

除 `[用户决定]` 外，只有带任务 id、且任务在看板上的事件才会返回。

负责人的 Agent 支持插话时，需要负责人处理的消息还会直接推送进它的会话，推送过的消息算作已读，不再由 `wait` 返回，见[看板推送](../domains/20261031-goal_mode.md#board_push)。

<a id="inline_budget"></a>
#### 完成消息的限额

`[完成]` 消息让负责人能决定下一步，完整结果带 `task` 调用 `board` 查看，长 Run 不会把负责人的上下文占满：摘要最多 300 个字符，每条验收的标准 60 个、证据 160 个字符，证据、风险和提醒各列前 3 条（每条 160 个字符）并注明总数；逐条验收全部列出，但每条整体截断到同一限额。有删节时末尾提示「完整结果见 janus.board T1」。交给下游任务的上游摘要同样最多 300 个字符。

### `reply`

```json
{ "task": "T2", "text": "用 alpha 作为名字" }
```

| 情况 | 行为 |
| --- | --- |
| 任务有等待中的提问 | 作为回答发回协作者的会话（`question.answered`，`via: "lead"`） |
| 任务正在执行，没有提问 | 以「负责人：」（英文 Run 为「The lead: 」）开头立即送达：Agent 支持插话时插入当前这一轮，否则打断当前这一轮后作为新一轮发送；用户接管着这个会话时排队，交还托管时送达。见[消息的流转](20261031-events.md#message_flow) |
| 任务还没开始 | 消息保留到该协作者下一次开始工作 |
| 任务已经结束（完成、失败或已取消） | 返回错误，提示要它接着做就用 `retry`。这样消息不会被带进这个协作者之后的其他任务 |
| 任务不存在或 `text` 为空 | 返回错误 |

<a id="retry_tool"></a>
### `retry`

```json
{ "task": "T1", "session": "continue", "from": "V1", "note": "可选，负责人这一轮的判断", "instructions": "可选，新的完整说明", "accept": ["可选，新的验收标准"] }
```

让一个已经结束的任务再做一次，重新给满尝试次数：失败、已取消、被负责人取消的任务，或者已完成但需要返工的任务（例如独立验证判定没通过）。还没结束的任务返回错误，补充指示用 `reply`。

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `session` | 是 | `continue`：回到这个任务自己上一次的 ACP 会话，上下文都在；`new`：新开会话。不填或填别的值返回错误。原会话上下文超过 75% 时 `continue` 返回错误，说明占用多少、改用 `new`（`note` 里写清这一轮要知道的上下文，参数说明写着）；这个任务从来没开过会话时新开，返回结果当场说明；Agent 不支持 `loadSession` 或加载失败时在尝试开始时改为新会话，看板上这次「开始」写明原因。见 [ADR：热会话续接](../decisions/20261118-session_continuation.md) |
| `from` | 否 | 一个已经给出判定的独立验证任务。它的判定、没通过的标准和证据、交接说明和风险原样进入下一次尝试的提示，并记一条 `context.handoff`。被重试的任务依赖 `from` 时返回错误 |
| `note` | 否 | 负责人对这一轮的补充 |
| `instructions`、`accept` | 否 | 替换任务说明和验收标准；`accept` 不能是空数组 |

记为 `task.reopened`（`reason: "lead.retry"`，`data.session`，以及可选的 `data.from`、`data.note`、`data.instructions`、`data.accept`），恢复时按它们重建任务。回到原会话时，提示只有验证意见、负责人的说明、改过的说明、上次失败的原因和验收标准；新开会话时是完整的任务提示再附上这些。

这个任务已完成的独立验证，以及 `from`，都回到待执行并在它完成后重新核对（`task.reopened`，`reason: "target.reworked"`，`data.target` 是被重试的任务；`from` 验证的不是它时，把它加入 `from` 的依赖）。复审回到验证者自己的会话，先核对上一轮指出的问题，再做回归。已经用了旧结果的下游（依赖它的任务，与 `amend` 用同一段逻辑 `Takers`）不会被重做或停下，由负责人决定：正在执行的立即收到一条 Janus 的通知「[Janus] 上游子任务 T1 正在返工……」（`user.message` 的 `actor` 为 `janus`，与 `reply` 相同的送达方式），返回结果中列出它们，并说明它们可能和返工改同一批文件；已经基于旧结果完成的也列在返回结果中，是否返工由负责人决定；还没开始的自动等返工完成，交接时拿到新结果。

被它阻塞的任务在它成功后自动继续；因取消它而被连带取消的任务（`cancel` 的 `data.dependency` 指向它）一并恢复（`task.reopened`，`reason: "upstream.retry"`），负责人点名取消的任务不恢复。见 [ADR：返工由负责人用 `retry` 发回原任务](../decisions/20261119-rework_in_original_session.md)。

<a id="amend_tool"></a>
### `amend`

```json
{ "task": "T4", "text": "改用经典 8 邻域规则，3D 只用于呈现" }
```

`task` 和 `text` 必填。按任务的状态做两件事中的一件（`board_amend`）：

| 任务 | 行为 |
| --- | --- |
| 已完成 | 修订它的结论，见下文 |
| 没通过验收核对（`task.failed`，`reason` 为 `verification`） | 接受它的结果（`accept_result`）：用它最后提交的结构化结果把任务标记为完成（`task.succeeded`，`actor` 为 `lead`，`data.acceptedBy: "lead"`，`data.reason` 是 `text`），没达到的部分和 `text` 记为风险，依赖它的任务继续执行。`text` 写负责人核对了什么、为什么没达到的部分不影响目标 |
| 独立验证任务（带 `verifies`），不论状态 | 返回错误（`teamwork::amend_refused`）：验证的判定和结论都不由负责人改写。验证没通过要靠 `retry` 返工后重新验证，或者用 `cancel` 留下取消的理由 |
| 其他（还在执行、因尝试用完而失败、已取消） | 返回错误；还在执行的用 `reply` |

修订已完成任务的结论（`result.amended`）时，工作目录不动、任务不重跑。负责人推翻协作者的结论时用它，让下游以同一个结论为准；工作本身要改时用 [`retry`](#retry_tool) 返工。两者都改变了下游用过的结果，找出下游并通知、列出的逻辑相同（`Takers`）：

- 正在执行的下游任务立即收到一条 Janus 的通知「[Janus] 负责人修订了上游子任务 T4 的结论，以修订为准：…」（`actor` 为 `janus`，与 `reply` 相同的送达方式）。
- 还没开始的下游任务在交接时拿到修订：任务说明的上游结果中附「负责人修订了这个结论，以修订为准：…」，`context.handoff` 的 `data.amendments` 列出修订。
- 已经基于旧结论完成的下游任务列在返回结果中，由负责人决定是否 `retry`。

任务被重试后，之前的修订作废。

<a id="cancel_tool"></a>
### `cancel`

```json
{ "tasks": ["T3"], "reason": "这部分不做了，写进交付风险" }
```

取消任务：还没开始的不再开始，执行中的会话被停止，依赖它们的任务一并取消（都记为 `task.skipped_by_decision`，`actor` 为 `lead`，连带取消的在 `data.dependency` 记录原因）。已完成的任务不受影响。取消后可以用 `retry` 恢复，连带取消的下游会随它恢复。

<a id="ask_user_tool"></a>
### `ask_user`

```json
{ "question": "部署到哪个环境？", "why": "需要用户的账号", "options": ["测试", "生产"], "recommend": "测试" }
```

把只有用户能做的决定交给用户：写 `question.escalated`（`actor` 为 `lead`，没有任务，`data.from` 为 `lead`），应用在「待处理」中显示。工具立即返回，不等待；用户回答后，`wait` 返回 `[用户决定]`。负责人会话结束时，未回答的问题被撤回。`question` 和 `why` 必填。目标范围内的做法和取舍不应使用这个工具，见[谁来做决定](../domains/20261031-goal_mode.md#decision_ownership)。

<a id="member_tools"></a>
## 协作者工具

子任务的会话（席位 `task/<id>`）`tools/list` 返回 `board_post`、`board`、`submit` 和 `ask`。负责人调用协作者工具返回「没有这个工具」：负责人用 `owns` 分配文件、用 `orchestrate` 拆分任务，自己的结论写在最终回复里。协作者没有扩大自己负责范围的工具：要改负责范围以外的文件时先用 `ask` 问负责人，见[团队结构](../domains/20261031-goal_mode.md#team_structure)。

和负责人工具一样，工具的用法和限制只写在各自的说明里（`MemberTool::definition`），协作者的约定不介绍看板工具；说明、返回和错误按 Run 的语言写。说明里写着：`board_post` 的 `kind=blocker` 立即送到负责人那里；`board` 带 `task` 看一个任务的完整结果；做完用 `submit` 交结果，需要负责人决定时用 `ask` 提问，子任务过大时在提问里附上拆分提议，见下面的 [`submit`](#submit) 和 [`ask`](#ask)；它们在一次尝试里怎样被取走、什么也没交时怎样，见[交结果和提问](../domains/20261031-run_lifecycle.md#structured_result)。

### `board_post`

```json
{ "kind": "blocker", "text": "缺少测试数据，先用样例继续" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `kind` | 否 | `progress`（默认）、`blocker` 或 `note` |
| `text` | 是 | 写到看板的内容，最多 8000 个字符（`POST_MAX_CHARS`）。长内容写进文件，在消息里给出路径 |

写入 `board.posted` 事件后立即返回「已写到看板」，不等待回答。`blocker` 是需要负责人处理的消息，立即唤醒 `wait` 或推送进负责人的会话；`progress` 和 `note` 随负责人下一次取回看板消息送达（工具说明写着）。需要负责人做决定才能继续时，协作者用 `ask` 提问并结束这一轮。

<a id="peers"></a>
### `board`

```json
{ "task": "T1" }
```

`task` 可选（`board_peers`）。不带 `task` 时返回看板上的其他任务：状态、未结束任务负责的文件、和调用者的关系（你的上游、依赖你、和你改了同一批文件），正在执行的任务改过的文件，已完成任务完成后又被改过的文件，以及最近 5 条其他任务写回看板的内容（没有时不列这一节）。带 `task` 时返回那个任务的全部信息，与负责人的 [`board`](#task_detail) 带 `task` 时相同，例如上游任务的完整证据和负责人的修订。

<a id="submit"></a>
### `submit`

```json
{
  "summary": "加了 mod，两条标准都核对过",
  "checks": [
    { "criterion": "mod(7, 3) 返回 1", "passed": true, "method": "test", "evidence": "python3 -m unittest 通过" },
    { "criterion": "mod(1, 0) 抛出 ZeroDivisionError", "passed": true, "method": "test", "evidence": "新增的测试通过" }
  ],
  "handoff": "mod 和 divide 共用同一个除零检查",
  "evidence": ["test_calc.py 新增 2 个测试"],
  "risks": []
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `summary` | 是 | 一句话结果 |
| `checks` | 是 | 每条验收标准一项，按顺序；每项必填 `criterion`（原样复述）、`passed`、`evidence`（做了什么、看到了什么，没达到时写原因），可选 `method`（`test`、`command`、`inspection`、`reasoning`、`unverified`，见[证据方法](20261031-events.md#evidence_methods)） |
| `handoff` | 否 | 给下游子任务的接口、关键决定和注意事项，最长 1200 个字符 |
| `evidence` | 否 | 其他可核实的证据 |
| `risks` | 否 | 已知风险 |
| `verdict` | 验证任务必填 | 只有独立验证任务填：`approved`、`rejected` 或 `inconclusive` |

交结果（`hand_in::board_submit`）。当场核对格式（`evidence::gaps_for`）：`summary` 为空、漏了标准、某条没有证据、`method` 或 `verdict` 不是允许值、`verdict: "approved"` 却有 `passed: false`，都返回错误并列出全部问题，结果不收下，Agent 在同一轮里改好再交。格式没问题就收下，返回「已收下」；有标准写了 `passed: false` 时，第一次返回「已收下，但这些标准你写了没达到」并列出它们，说明能修好就修好再交一次，同一次尝试里再交就照收。收下的结果在这一轮结束时由这次尝试取走（`take_handed`），之后才写 `result.submitted` 并做最后一次核对；同一轮里再交会替换上一份。调用者的子任务不在执行时返回错误。

<a id="ask"></a>
### `ask`

```json
{ "text": "名字用 alpha 还是 beta？", "options": ["alpha", "beta"], "recommend": "alpha" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `text` | 是 | 问题 |
| `options` | 否 | 可选的答案 |
| `recommend` | 否 | 建议的选项 |
| `split` | 否 | 拆分提议，见下文 |

向负责人提问（`hand_in::board_ask`），返回「已记下」并请 Agent 结束这一轮。问题在这一轮结束时由这次尝试写成 `question.asked`，交给负责人（负责人不在看板上时转给用户），回答作为下一轮提示发回同一个会话；提问的流转见[提问的流转](../domains/20261031-goal_mode.md#question_routing)。同一轮里先提问后交结果，以最后一次为准。

<a id="split_proposal"></a>
#### 拆分提议

协作者发现当前任务远超预期范围、需要拆成多个子任务或调整负责边界时，在提问里附上结构化的拆分提议：

```json
{
  "text": "按这样拆可以吗？",
  "split": {
    "reason": "涉及解析器与代码生成两个独立子系统，单次改动过大",
    "completed": "已完成 AST 定义",
    "subtasks": [
      { "title": "实现解析器", "owns": ["src/parser.rs"], "accept": ["单测通过"] },
      { "title": "实现代码生成", "owns": ["src/codegen.rs"], "accept": ["单测通过"] }
    ]
  }
}
```

| `split` 的字段 | 必填 | 说明 |
| --- | --- | --- |
| `reason` | 是 | 为什么需要拆分或调整边界 |
| `completed` | 否 | 当前已经完成、可保留的部分 |
| `subtasks` | 是 | 建议拆出的子任务列表（1 到 8 项，`SPLIT_MAX_SUBTASKS`），每项含必填 `title`，可选 `owns`（路径校验规则与 `orchestrate` 相同）和 `accept` |

拆分提议当场校验并立即写入 `task.split_requested`（`propose_split`），唤醒 `wait` 并推送给负责人，不等这一轮结束；问题仍在这一轮结束时转给负责人。负责人决定是否用 `orchestrate` / `cancel` 重新编排，或用 `reply` 指示继续。拆分提议不合法（缺 `reason`、`subtasks` 为空或超过 8 项、建议的子任务缺 `title`、路径不合法）或调用者是验证任务（带 `verifies`）时，整个提问被拒绝，问题也不记下。伴有拆分提议的提问不计入连续 4 轮普通提问上限（总暂停硬上限为 8 轮）。

<a id="loop_tools"></a>
## 值班的工具

[值班](../domains/20261121-loops.md) 的会话连到同一个 `janus` 端点（`/mcp/{run}/{token}/lead`），端点见到 `kind` 为 `loop` 的 Run 时给出下面的工具，不给看板工具；看板工具名调用返回「没有这个工具」。每个工具怎样用、什么时候用和它的限制都写在它自己的说明里（`LoopTool::definition`），值班的系统层不重复；说明、返回和错误按 Run 的语言写中文或英文。

| 工具 | 参数 | 结果 |
| --- | --- | --- |
| `dispatch` | `goal`、`key`（必填），`source_url` | 在值班的工作区新建目标 Run，进[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)，`origin` 为 `loop`。工作区已经有这个 `key` 的 Run 时不新建，按下表处理（`dispatched_again`）。Run 结束前由它自己闭环，结束时以 `dispatch` 唤醒值班 |
| `ask_user` | 同负责人的 [`ask_user`](#ask_user_tool) | 问题进收件箱，不阻塞；回答以 `answer` 唤醒值班，问题和回答写在那次醒来的提示里 |
| `next_wake` | `after_seconds`（60 到 86400，超出时取边界）、`reason` | 约这一轮结束后再醒一次，原因显示给用户；时间表照旧。等派出的 Run 不用它，Run 结束会唤醒值班。时间表在那之前就会到点时不约，告诉它时间表的下一次；不在醒来的一轮里或值班暂停时返回错误 |

用派出过的 `key` 再调用 `dispatch`，从不新建 Run（同一件事一个 key，工具说明写着不要换个 key 再派）：

| 已有的 Run | 结果 |
| --- | --- |
| 这个值班派出、正在开始或进行中（`planning`、`running`，且在内存中运行） | `goal` 作为新情况转给它的负责人：来自 `janus` 的消息，开头写明「（来自工作区的值班「…」，不是用户本人）」，按那个 Run 的语言写，与 `reply` 相同的送达方式。返回「没有再派：goal 已转告给它的负责人」 |
| 这个值班派出、排队中、还没开始运行或中断了（`queued`、`planning`、`interrupted`） | 返回已有的 Run 和状态，说明它现在没有在工作、转告不了，等它开始工作后再转告 |
| 别的值班或用户派出的 | 返回已有的 Run 和状态，说明不是这个值班派出的、转告不了 |
| 已经结束的 | 返回已有的 Run 和状态，交付了的附交付摘要，失败的附失败原因（最多 600 个字符） |

派出的 Run 现在怎样不用工具查：每次醒来的提示列出这个值班派出、还没结束的 Run 和上次醒来后结束的 Run，见[醒来](../domains/20261121-loops.md#waking)。

`dispatch`、`ask_user`、`next_wake` 标为非破坏性操作。值班的会话另有团队记忆的 `recall` 和 `remember`。

<a id="memory_tools"></a>
## 团队记忆的工具

工作区的会话都在 `tools/list` 末尾多两个工具，读写这个工作区的[团队记忆](../domains/20261123-team_memory.md)：负责人和每个协作者（看板工具之后）、值班的会话（值班的工具之后）。[整理](../domains/20261123-team_memory.md#dream)的会话（`kind` 为 `dream` 的 Run）连到同一个端点，只有这两个和 `forget`，看板和值班的工具名调用返回「没有这个工具」。对话没有团队记忆：能提议数字员工的对话也只有 `propose_employees`。什么时候检索、记什么不记什么、合并时先写后删，都写在工具自己的说明里（`MemoryTool::definition`），会话的系统层只写有没有笔记；说明、返回和错误按 Run 的语言写中文或英文。

| 工具 | 参数 | 结果 |
| --- | --- | --- |
| `recall` | `id`，或 `query`，或都不给 | 给 `id` 时返回这条笔记的全文和来源（谁、在哪个 Run、最后修改的日期）；给 `query` 时按相关程度返回最相关的 5 条全文（标题命中最重，其次摘要、正文；中文按相邻两字也能命中，见[怎么检索](../domains/20261123-team_memory.md#memory_read)）；都不给时列出笔记目录（`id`、类型、标题、摘要，最多 50 条）。工作会话检索不到被取消的 Run 写的笔记，整理会话能；别的工作区的 `id` 当作不存在 |
| `remember` | `kind`（`fact`、`decision`、`pitfall`、`howto`）、`title`（最多 80 个字符）、`hook`（最多 150 个字符）、`body`（最多 4000 个字符），可选 `id` | 没有 `id` 时新写一条，有 `id` 时改写这一条（只能是本工作区的）；写入的成员和 Run 成为它的来源，记 `memory.saved`。空字段、未知类型、像凭据的内容、超过长度，以及工作区已有 300 条时新写，都返回错误 |
| `forget` | `id`、`reason`（都必填） | 只有整理有：删掉这一条，记 `memory.forgotten`；负责人和协作者调用返回「没有这个工具」 |

`recall` 标为只读，`remember` 标为非破坏性操作，`forget` 标为破坏性操作。

<a id="chat_tools"></a>
## 对话的工具

数字员工打开了 `hires`（默认只有招聘顾问）的[对话](../domains/20261120-chats.md#proposed_employees)，主会话连到 `/mcp/{run}/{token}/lead`，只有一个工具（`ChatTool`，调用者 `Caller::Hiring`）。成员的 `hires` 取自 Run 快照（`Member::hires`），对话开始后再改数字员工不影响这个对话。

| 工具 | 参数 | 结果 |
| --- | --- | --- |
| `propose_employees` | `employees`：1 到 20 位，每位 `name`、`desc`、`instructions`（必填），`group`、`color`、`init`、`lead`（可选） | 逐个核对（`RoleFile::checked`），合格时记 `roles.proposed`，返回「已交给用户：N 位（名字）」和用户确认后才创建、再交会替换这一批；有一位不合格时整批退回，返回「第 N 位：原因」，不记任何事件 |

`propose_employees` 标为非破坏性操作。它不创建任何数字员工：创建只由用户在应用里确认，见[接口](20261031-http_api.md#proposed_employees)。

<a id="acceptance_criteria"></a>
## 验收标准

每个任务都必须有验收标准（`accept`），它是执行者验证自己工作的依据。Janus 不替执行者运行任何验证命令，设计取舍见 [ADR：按验收标准自行验证](../decisions/20261101-criteria_over_commands.md)。

- **负责人写标准**：写预期的结果和怎样认出它，不写做法的步骤。需要特定的验证方式时，写进标准或说明。
- **执行者自己验证**：协作者约定要求执行者结束前逐条回报，怎样验证由它自己和它的数字员工指令决定，在 `submit` 的 `checks` 中按顺序逐条写明 `passed`、`evidence` 和可选的 `method`。`method` 是 `test`（运行自动化测试）、`command`（运行命令或脚本）、`inspection`（检查代码、文件、界面或实际状态）、`reasoning`（推理或自我判断）或 `unverified`（证据缺失或暂时无法核实），只说明依据的类型，不代替证据。标准本身不合理或当前环境无法验证时，用 `ask` 请负责人调整。
- **Janus 核对结构**：每条标准都有对应的 check、有证据、没有自认未达到的、给出方法时是允许的值，才算通过，见[验证](../domains/20261031-run_lifecycle.md#verification)。旧结果没有方法时显示「未说明」并继续按原规则核对；`reasoning`、`unverified` 和没有方法只产生提醒，不自动判失败。
- **独立核对由负责人决定**：执行者的证据是它自己的说法。是否安排独立验证、怎样核对，由负责人的数字员工指令决定，Janus 的说明不要求；交付标出改了文件却没有独立验证的子任务，负责人在摘要里交代怎样核对的。见 [ADR：Janus 只注入协作规则](../decisions/20261125-collaboration_only_injection.md)。

修改这些规则时，同步更新 `orchestrate` 工具中 `accept` 的描述、任务说明（`task_prompt`）和负责人说明（`goal_brief`）中的验收标准一节。
