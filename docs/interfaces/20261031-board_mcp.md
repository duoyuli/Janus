本文是共享看板 MCP 服务的接口参考：端点、方法、负责人工具、协作者工具、编排校验规则和验收标准。看板在协作中的作用和提问的流转见[目标模式与共享看板](../domains/20261031-goal_mode.md)。

<a id="transport"></a>
## 端点与传输

```text
POST http://<JANUS_ADDR>/mcp/{run}/{token}/{who}
```

| 路径参数 | 说明 |
| --- | --- |
| `run` | Run id。Run 不在内存中运行时返回 403 |
| `token` | 这个会话的令牌：由负责人启动时为 Run 生成的随机密钥和 `who` 一起做 SHA-256 得到（`session_token`）。为空或与 `who` 不匹配时返回 403 |
| `who` | `lead` 表示负责人；否则是协作者正在执行的任务 id |

- 令牌和 `who` 绑定：协作者把 URL 中的 `who` 改成 `lead` 或其他任务 id 都会得到 403，所以协作者拿不到负责人工具，也不能以其他任务的身份写看板。Run 的密钥只在内存中，服务重启后恢复的会话拿到新的 URL。
- MCP streamable HTTP 传输，响应直接在对应的 POST 中以 JSON 返回，不使用 SSE。
- `GET` 返回 405，服务不主动推送消息。
- 没有 `id` 的消息（通知）返回 202，无响应体。
- 支持的方法：`initialize`、`ping`、`tools/list`、`tools/call`；其他方法返回 JSON-RPC 错误 `-32601`。
- `initialize` 的 `protocolVersion`：客户端请求的版本 Janus 支持就用它，否则回答 Janus 最新的版本（支持的版本和 MCP 路由相同，见[资源库](../domains/20261116-resource_library.md#mcp_router)），服务名 `janus`。

会话中的 MCP 服务器条目：

```json
{ "type": "http", "name": "janus", "url": "http://127.0.0.1:7878/mcp/<run>/<token>/<who>", "headers": [] }
```

URL 的主机和端口取 `JANUS_ADDR`。

<a id="tool_annotations"></a>
## 工具标注

所有工具都带 MCP 工具标注：`team`、`wait`、`task_detail`、`board_post`、`claim`、`peers` 标为只读，`orchestrate`、`reply`、`retry`、`accept`、`amend`、`cancel`、`ask_user`、`request_split` 标为非破坏性操作。标注的作用是避免 Codex 把调用看板当作需要用户审批的操作。

工具调用的错误以 `isError: true` 的文本内容返回，不使用 JSON-RPC 错误。

<a id="lead_tools"></a>
## 负责人工具

`who` 为 `lead` 时，`tools/list` 返回以下十个工具。

### `team`

查看协作者（名字和职责，与负责人说明中的[协作者名单](../domains/20261031-goal_mode.md#lead_brief)相同）和看板上所有任务的当前状态。无参数。不含用量：每个任务的用量用 `task_detail` 查看。

用量是只读的：读事件失败时按空账本输出，仍然正常返回，调度与任务状态不受影响。

<a id="orchestrate"></a>
### `orchestrate`

提交一份编排，即一组交给协作者的任务。

校验通过后，Janus 先把 `orchestration.accepted` 写进事件日志，写入成功才把任务放上看板、开始调度。写入失败（例如磁盘满）时工具返回错误，说明编排没有生效、没有子任务开始，负责人可以原样重试；重试成功后每个任务只执行一次。重启后看板从事件日志重建，所以看板上的任务和日志里的编排始终一致。

```json
{
  "tasks": [
    {
      "id": "T1",
      "title": "实现解析器",
      "instructions": "背景……需要做……注意……",
      "assignee": "developer",
      "deps": [],
      "accept": ["空输入返回明确的错误", "新增测试覆盖空输入并通过"],
      "owns": ["src/parser"]
    },
    {
      "id": "V1",
      "title": "验证解析器",
      "instructions": "独立核对 T1 的改动……",
      "assignee": "qa",
      "accept": ["运行解析器的测试并给出命令和输出"],
      "verifies": "T1"
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 字母、数字、`-` 和 `_`，最长 32 个字符，在整个看板内唯一 |
| `title` | string | 是 | 任务标题 |
| `instructions` | string | 是 | 给执行者的完整说明。执行者看不到负责人的对话 |
| `assignee` | string | 是 | 协作者 id，不能是负责人 |
| `deps` | string[] | 否 | 必须先成功完成的任务 id，可以引用之前编排中的任务 |
| `accept` | string[] | 是 | 可核对的验收标准，至少一条，见[验收标准](#acceptance_criteria) |
| `owns` | string[] | 否 | 这个任务负责修改的文件或目录，相对工作目录，目录包含其下所有文件。见[团队结构](../domains/20261031-goal_mode.md#team_structure) |
| `verifies` | string | 否 | 被验证任务的 id（同批或之前编排的任务）。这个任务是它的独立验证，见[团队结构](../domains/20261031-goal_mode.md#team_structure) |
| `continues` | string | 否 | 要续接原 ACP 会话的前置任务 id（同批或之前编排的任务），执行者必须相同，用于要用到那个任务上下文的**新**工作，见 [ADR：热会话续接](../decisions/20261118-session_continuation.md)。验证没通过后的返工不新建任务，用 [`retry`](#retry_tool) |

成功时返回已写入看板的任务；失败时返回全部错误，一个任务都不启动。

<a id="orchestration_validation"></a>
#### 校验规则

`validate_orchestration` 一次检查全部问题：

- `tasks` 必须是非空数组。
- `id` 格式合法，且不与看板上已有的任务或同批任务重复。
- `title` 和 `instructions` 不能为空。
- `assignee` 必须是协作者。
- 依赖必须存在，不能依赖自己，同批任务之间不能成环。
- 每个任务至少有一条验收标准。
- `owns` 是工作目录内的相对路径，不能是绝对路径，不能含 `..`。`.` 和多余的 `/` 去掉（`src/./a.rs`、`src//a.rs` 都是 `src/a.rs`）；比较两个路径是否重叠时不分大小写，macOS 默认的文件系统里 `src/Utils.rs` 和 `src/utils.rs` 是同一个文件。
- `deps` 中重复的 id 只算一次。
- 校验和写入看板在同一把锁里依次进行：同时提交的两份编排先后校验，不会让同一个 id 进看板两次。
- 可能同时执行的两个任务（彼此都不在对方的上游，比较对象是同批任务和看板上未结束的任务）`owns` 不能重叠：同一路径，或一个是另一个所在的目录。
- `verifies` 指向的任务存在、不是它自己、执行者不同；验证任务不能写 `owns`；Janus 把被验证的任务加入它的依赖，加入后不能成环。
- `continues` 指向的任务存在、不是它自己、执行者与当前任务相同；验证任务（带 `verifies`）不能写 `continues`；Janus 把 `continues` 指向的任务加入依赖，加入后不能成环。

`owns`、`verifies` 和 `continues` 的检查在 `teamwork::check` 中，前面的基本检查都通过后才执行。

通过校验的任务按固定策略执行：最多尝试 `MAX_ATTEMPTS`（2）次，需要结构化结果。任务能否修改文件由执行者的 Agent 权限模式决定，编排中没有读写字段，见[权限交给 Agent 原生模式](../decisions/20261031-agent_native_permissions.md)。

<a id="wait"></a>
### `wait`

```json
{ "timeout_sec": 120 }
```

取回看板上的新消息。新消息中有需要负责人处理的（与[看板推送](../domains/20261031-goal_mode.md#board_push)相同的那些：提问、失败、阻塞、未解决的停滞、阻塞类写回、冲突、拆分请求、负责人派出子任务后改了文件、带痕迹问题或验证未通过的完成、用户的回答）、有任务完成（`task.succeeded`）或 Run 被取消时立即返回（`ends_board_wait`）；否则通过事件通知（`Run.board_wake`）挂起等待，这类事件到来时毫秒级唤醒返回，最多等待 `timeout_sec` 秒（1 到 180，默认 120）。只是告知的消息（`[开始]`、`[进展]`、`[备注]`、`[认领]`、`[尝试失败]`、`[等用户]`、负责人自己回答或取消留下的记录）不单独唤醒负责人，留到下一次返回时一起带上，或在超时时返回，不会丢。看板上没有未结束的任务时直接返回；等待超时且仍有任务在执行时，附带每个运行中任务的实时心跳（当前阶段、最近工具、已运行时长、已改动文件数）和等待启动的任务数。

返回的消息：

| 标记 | 来源事件 | 内容 |
| --- | --- | --- |
| `[开始]` | `attempt.started` | 任务、执行者、第几次尝试 |
| `[完成]` | `task.succeeded` | 摘要、验收总数和通过数、证据方法计数（测试 / 命令 / 检查 / 推理判断 / 未核实 / 未说明，见[证据方法](20261031-events.md#evidence_methods)）、只提醒不阻断的项、逐条验收（✓ / ✗、证据方法、标准、证据）、执行者的其他证据、独立验证的判定（验证任务已结束时）、风险、产物路径，以及结果和工作目录对不上的「痕迹核对」（`data.traceGaps`，见[工作目录里的痕迹](../domains/20261031-goal_mode.md#traces)）。超过限额的部分删去，并提示用 `task_detail` 查看，见[完成消息的限额](#inline_budget) |
| `[验证未通过]` | 验证任务的 `task.succeeded`（`verdict` 为 `rejected` 或 `inconclusive`） | 验证者完成了独立核查并判定需要修改或证据不足；提示判断问题出在哪个任务，用 `retry` 返工（`from` 指向这个验证，`session` 选 `continue` 或 `new`），返工完成后这个验证自动重新核对；换人或另开一项工作时才用 `orchestrate`。如有受阻的旧下游，消息列出其 ID，可用 `cancel` 取消不再需要的下游。仅对已完成且未通过的验证调用 `cancel` 时，工具返回错误并保留原判定 |
| `[尝试失败]` | `attempt.failed` | 失败原因，还会重试 |
| `[验证没通过]` | 验证任务的 `task.failed`（`reason: "verification"`） | 验证者补过一次仍缺少有效证据或结构不合要求；提示用 `retry` 让验证重新做，或按它发现的问题用 `retry` 让被验证的任务返工，或用 `cancel` 取消验证，不能用 `accept` |
| `[没通过验收]` | `task.failed`（`reason: "verification"`） | 协作者在原会话补过一次，仍有标准没核对、没证据或自认没达到，逐条列出；提示用 `accept`、`retry` 或 `cancel` 处理 |
| `[失败]` | `task.failed`（`reason: "attempts"`） | 用完尝试次数，需要负责人决定 |
| `[用户介入]` | 用户对协作者会话的 `user.message`、`control.taken`、`control.released`、`session.interrupted` | 用户直接在协作者的会话里发了消息、接管、交还、打断或让它以当前结果结束；只告知，不提前唤醒 `wait`。提醒负责人以用户的意思为准，不要用 `reply` 或 `retry` 改回去 |
| `[负责人改了文件]` | `lead.edited` | 负责人派出子任务后又改了文件；提醒它只做管理，改代码交给对应的子任务，这些改动会写进交付风险 |
| `[负责人用了资源库工具]` | `lead.routed` | 负责人派出子任务后经 MCP 路由调用了资源库的工具（每个工具记一次）；提醒它资源库的工具只用来查看，有副作用的操作交给子任务，这次调用会写进交付风险 |
| `[无法开始]` | `task.blocked` | 依赖失败，处理好依赖后会自动继续；或依赖的独立验证判定 `rejected` / `inconclusive`（`data.verdict`），提示负责人用 `retry` 返工，验证复审通过后任务自动开始，不再需要时取消它 |
| `[停滞]` | `task.stalled` | 协作者很久没有动静，连续重复同一个调用，或连续重复 2 步 / 3 步交替调用序列；提示继续等、`reply`、`retry` 或 `cancel` |
| `[用户已回答]` | `question.answered`（不是负责人回答的） | 用户在会话或应用中直接回答了协作者的提问，负责人不要再回答 |
| `[用户决定]` | `question.answered`（`ask_user` 的问题） | 用户对负责人所提问题的回答 |
| `[进展]` `[阻塞]` `[备注]` | `board.posted` | 协作者写回的内容 |
| `[请求拆分]` | `task.split_requested` | 协作者发现任务过大，提交拆分原因、已完成部分和建议子任务列表，等待负责人编排或回复 |
| `[冲突]` | `task.conflict` | 两个同时执行的任务改了同一批文件，或负责人直接修改了正在执行的任务负责 / 正在改的文件（`data.byLead: true`），提示负责人确认分工 |
| `[越界]` | `task.conflict`（`data.owned: true`） | 任务改了另一个可能同时执行的任务负责的文件，已提醒它停下，提示负责人确认分工 |
| `[认领]` | `task.claimed` | 协作者认领了要改的文件 |
| `[提问]` | `question.asked` | 问题和选项，需要用 `reply` 回答 |
| `[等用户]` | `approval.requested`、`input.requested` | 协作者在等用户审批或填写 |

除 `[用户决定]` 外，只有带任务 id、且任务在看板上的事件才会返回。

负责人的 Agent 支持插话时，需要负责人处理的消息还会直接推送进它的会话，推送过的消息算作已读，不再由 `wait` 返回，见[看板推送](../domains/20261031-goal_mode.md#board_push)。

<a id="inline_budget"></a>
#### 完成消息的限额

`[完成]` 消息让负责人能决定下一步，完整结果留在 `task_detail` 中，长 Run 不会把负责人的上下文占满：摘要最多 300 个字符，每条验收的标准 60 个、证据 160 个字符，证据、风险和提醒各列前 3 条（每条 160 个字符）并注明总数；逐条验收全部列出，但每条整体截断到同一限额。有删节时末尾提示「完整结果用 janus.task_detail 查看」。交给下游任务的上游摘要同样最多 300 个字符。

### `reply`

```json
{ "task": "T2", "text": "用 alpha 作为名字" }
```

| 情况 | 行为 |
| --- | --- |
| 任务有等待中的提问 | 作为回答发回协作者的会话（`question.answered`，`via: "lead"`） |
| 任务正在执行，没有提问 | 以「负责人回复：」开头立即送达：Agent 支持插话时插入当前这一轮，否则打断当前这一轮后作为新一轮发送；用户接管着这个会话时排队，交还托管时送达。见[消息的流转](20261031-events.md#message_flow) |
| 任务还没开始 | 消息保留到该协作者下一次开始工作 |
| 任务已经结束（完成、失败或已取消） | 返回错误，提示用 `retry` 让它回到原会话返工，或新建任务。这样消息不会被带进这个协作者之后的其他任务 |
| 任务不存在或 `text` 为空 | 返回错误 |

<a id="retry_tool"></a>
### `retry`

```json
{ "task": "T1", "session": "continue", "from": "V1", "note": "可选，负责人这一轮的判断", "instructions": "可选，新的完整说明", "accept": ["可选，新的验收标准"] }
```

让一个已经结束的任务再做一次，重新给满尝试次数：失败、已取消、被负责人取消的任务，或者已完成但需要返工的任务（例如独立验证判定没通过）。还没结束的任务返回错误，补充指示用 `reply`。

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `session` | 是 | `continue`：回到这个任务自己上一次的 ACP 会话，上下文都在；`new`：新开会话。不填或填别的值返回错误。上下文超过 75%、Agent 不支持 `loadSession` 或加载失败时，`continue` 回退为新会话；这个任务从来没开过会话时也新开，返回结果当场说明，见 [ADR：热会话续接](../decisions/20261118-session_continuation.md) |
| `from` | 否 | 一个已经给出判定的独立验证任务。它的判定、没通过的标准和证据、交接说明和风险原样进入下一次尝试的提示，并记一条 `context.handoff`。被重试的任务依赖 `from` 时返回错误 |
| `note` | 否 | 负责人对这一轮的补充 |
| `instructions`、`accept` | 否 | 替换任务说明和验收标准；`accept` 不能是空数组 |

记为 `task.reopened`（`reason: "lead.retry"`，`data.session`，以及可选的 `data.from`、`data.note`、`data.instructions`、`data.accept`），恢复时按它们重建任务。回到原会话时，提示只有验证意见、负责人的说明、改过的说明、上次失败的原因和验收标准；新开会话时是完整的任务提示再附上这些。

这个任务已完成的独立验证，以及 `from`，都回到待执行并在它完成后重新核对（`task.reopened`，`reason: "target.reworked"`，`data.target` 是被重试的任务；`from` 验证的不是它时，把它加入 `from` 的依赖）。复审回到验证者自己的会话，先核对上一轮指出的问题，再做回归。已经用了旧结果的下游（依赖它的任务，与 `amend` 用同一段逻辑 `Takers`）不会被重做或停下，由负责人决定：正在执行的立即收到一条负责人消息「上游子任务 T1 正在返工……」（与 `reply` 相同的送达方式），返回结果中列出它们，并提醒它们可能和返工改同一批文件、不再需要时用 `cancel` 停下；已经基于旧结果完成的也列在返回结果中，需要时在返工后同样用 `retry` 让它们返工；还没开始的自动等返工完成，交接时拿到新结果。

被它阻塞的任务在它成功后自动继续；因取消它而被连带取消的任务（`cancel` 的 `data.dependency` 指向它）一并恢复（`task.reopened`，`reason: "upstream.retry"`），负责人点名取消的任务不恢复。见 [ADR：返工由负责人用 `retry` 发回原任务](../decisions/20261119-rework_in_original_session.md)。

<a id="accept_tool"></a>
### `accept`

```json
{ "task": "T1", "reason": "我打开页面核对过，移动端触控那一条不影响这次的目标" }
```

接受一个没通过验收核对的任务的结果：用它最后提交的结构化结果把任务标记为完成（`task.succeeded`，`actor` 为 `lead`，`data.acceptedBy: "lead"`），没达到的部分和 `reason` 记为风险。只对 `task.failed` 的 `reason` 为 `verification` 的任务有效，对验证任务（带 `verifies`）无效：验证没通过要靠 `retry` 返工后重新验证，或者用 `cancel` 留下取消的理由（`teamwork::accept_refused`）。

<a id="amend_tool"></a>
### `amend`

```json
{ "task": "T4", "text": "改用经典 8 邻域规则，3D 只用于呈现" }
```

修订一个已完成任务的结论（`result.amended`），工作目录不动、任务不重跑。负责人推翻协作者的结论时用它，让下游以同一个结论为准；工作本身要改时用 [`retry`](#retry_tool) 返工。两者都改变了下游用过的结果，找出下游并通知、列出的逻辑相同（`Takers`）：

- 正在执行的下游任务立即收到一条负责人消息（与 `reply` 相同的送达方式）。
- 还没开始的下游任务在交接时拿到修订：任务说明的上游结果中附「负责人修订了这个结论，以修订为准：…」，`context.handoff` 的 `data.amendments` 列出修订。
- 已经基于旧结论完成的下游任务列在返回结果中，由负责人决定是否 `retry`。

只能修订已完成的任务；任务被重试后，之前的修订作废。

<a id="cancel_tool"></a>
### `cancel`

```json
{ "tasks": ["T3"], "reason": "这部分不做了，写进交付风险" }
```

取消任务：还没开始的不再开始，执行中的会话被停止，依赖它们的任务一并取消（都记为 `task.skipped_by_decision`，`actor` 为 `lead`，连带取消的在 `data.dependency` 记录原因）。已完成的任务不受影响。取消后可以用 `retry` 恢复，连带取消的下游会随它恢复。

<a id="task_detail"></a>
### `task_detail`

```json
{ "task": "T2" }
```

按 id 返回一个任务的全部信息：执行者和状态、说明、用量、验收标准、负责的文件、验证对象、续接会话的前置任务、上游和下游任务（带状态）、完整结果（验证判定、给下游的交接说明、逐条验收及其证据方法、全部证据、风险、验收总数与通过数和方法计数、只提醒不阻断的项）、独立验证这个任务的验证任务及其判定（两者分开展示）、负责人的修订、最近一次没通过验收或尝试失败的原因、改过的文件、产物，以及看板上的进展、阻塞、拆分提议、提问、回答和冲突（含负责人改文件的冲突）。负责人可以顺着上下游的 id 继续查看相关任务。任务不存在时返回错误。

用量段（`task_lines`）在说明之后、验收标准之前，给出这个任务的总量、费用、墙钟时长（含「其中等待用户」）、token 构成、上下文快照，每个尝试一行（编号、执行者、结局、token、结束原因、用时，包括失败、验证没通过、已过期但仍计入和已取消的尝试），以及每个成员的 token 和按模型的分布（`task_bill`，例如「成员 实现者：2,000 tokens · 模型 gpt-6-astra 1,500、gpt-6.1-sol 500」）。任务还没有会话时写「用量：未开始（子任务 T2 还没有会话）」，不等于「未上报」。用量缺失时这些工具照常返回，不报错、不阻塞任务。

<a id="ask_user_tool"></a>
### `ask_user`

```json
{ "question": "部署到哪个环境？", "why": "需要用户的账号", "options": ["测试", "生产"], "recommend": "测试" }
```

把只有用户能做的决定交给用户：写 `question.escalated`（`actor` 为 `lead`，没有任务，`data.from` 为 `lead`），应用在「需要你处理」中显示。工具立即返回，不等待；用户回答后，`wait` 返回 `[用户决定]`。负责人会话结束时，未回答的问题被撤回。`question` 和 `why` 必填。技术选型和实现方式不应使用这个工具，见[谁来做决定](../domains/20261031-goal_mode.md#decision_ownership)。

<a id="member_tools"></a>
## 协作者工具

`who` 为任务 id 时，`tools/list` 返回 `board_post`、`claim`、`peers` 和 `request_split`。负责人调用协作者工具返回「没有这个工具」：负责人用 `owns` 分配文件、用 `orchestrate` 拆分任务。

### `board_post`

```json
{ "kind": "blocker", "text": "缺少测试数据，先用样例继续" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `kind` | 否 | `progress`（默认）、`blocker` 或 `note` |
| `text` | 是 | 写到看板的内容，最多 8000 个字符（`POST_MAX_CHARS`）。长内容写进文件，在消息里给出路径 |

写入 `board.posted` 事件后立即返回，不等待回答。需要负责人做决定才能继续时，协作者应在结构化结果的 `question` 字段提问并结束本轮。

<a id="claim"></a>
### `claim`

```json
{ "paths": ["docs", "README.md"] }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `paths` | 是 | 相对工作目录的文件或目录，目录包含其下所有文件；规则与 `owns` 相同，绝对路径和 `..` 被拒绝；一次最多 100 个（`CLAIM_MAX_PATHS`），文件多时认领所在的目录 |

开始改负责范围以外的文件前认领它们（`teamwork::claim`）。不是自己负责的路径并入任务的 `owns`，写 `task.claimed`（`data.paths` 为新认领的路径），到任务结束为止有效；全部已归自己负责时返回提示，不写事件。拒绝的情况：路径归另一个可能同时执行的未结束任务负责（返回负责的任务，要求写 blocker 请负责人协调）；调用者是验证任务。规则见[团队结构](../domains/20261031-goal_mode.md#team_structure)。

<a id="peers"></a>
### `peers`

```json
{ "task": "T1" }
```

不带 `task` 时返回看板上的其他任务：状态、未结束任务负责的文件、和调用者的关系（你的上游、依赖你、和你改了同一批文件），正在执行的任务改过的文件，已完成任务完成后又被改过的文件，以及最近 5 条其他任务写回看板的内容。带 `task` 时返回那个任务的全部信息，与负责人的 [`task_detail`](#task_detail) 相同，例如上游任务的完整证据和负责人的修订。

<a id="request_split"></a>
### `request_split`

```json
{
  "reason": "涉及解析器与代码生成两个独立子系统，单次改动过大",
  "completed": "已完成 AST 定义",
  "subtasks": [
    { "title": "实现解析器", "owns": ["src/parser.rs"], "accept": ["单测通过"] },
    { "title": "实现代码生成", "owns": ["src/codegen.rs"], "accept": ["单测通过"] }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `reason` | 是 | 为什么需要拆分 |
| `completed` | 否 | 当前已经完成的部分 |
| `subtasks` | 是 | 建议拆出的子任务列表（1 到 8 项，`SPLIT_MAX_SUBTASKS`），每项含必填 `title`，可选 `owns`（路径校验规则与 `orchestrate` 相同）和 `accept` |

协作者发现当前任务远超预期范围时，向负责人提交结构化拆分提议：写入 `task.split_requested` 事件并触发看板唤醒与推送，由负责人决定是否用 `orchestrate` / `cancel` 重新编排，或用 `reply` 指示继续。验证任务（带 `verifies`）不能调用 `request_split`。协作者在提交拆分提议后若需停下等负责人调整编排，可在结果 `question` 中说明；伴有拆分提议的提问不计入连续 4 轮普通提问上限（总暂停硬上限为 8 轮）。

<a id="loop_tools"></a>
## 值班的工具

[值班](../domains/20261121-loops.md) 的会话连到同一个 `janus` 端点（`/mcp/{run}/{token}/lead`），端点见到 `kind` 为 `loop` 的 Run 时给出下面的工具，不给看板工具；看板工具名调用返回「没有这个工具」。`initialize` 的说明也换成值班的。

| 工具 | 参数 | 结果 |
| --- | --- | --- |
| `dispatch` | `goal`、`key`（必填），`source_url` | 在值班的工作区新建目标 Run，进[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)，`origin` 为 `loop`。工作区已经有这个 `key` 的 Run 时不新建，返回已有的 Run 和状态 |
| `dispatches` | `status`（可选） | 这个值班派出的 Run（处于这个状态的，最新的 50 个）：id、状态、key、目标第一行，已交付的带交付摘要。没有派过和没有这个状态的分开说 |
| `ask_user` | 同负责人的 [`ask_user`](#ask_user_tool) | 问题进收件箱，不阻塞；回答以 `answer` 唤醒值班，问题和回答写在那次醒来的提示里 |
| `save_state` | `text`（最多 4000 个字符） | 替换值班记下的状态（`loop.state_saved`），新会话的系统层带上它 |
| `set_name` | `name` | 给值班起名（第一行，最多 40 个字符），只能起一次；已经有名字时返回错误。还没有名字时醒来的提示会请它起 |
| `next_wake` | `after_seconds`（60 到 86400，超出时取边界）、`reason` | 约这一轮结束后再醒一次，原因显示给用户；时间表照旧。时间表在那之前就会到点时不约，告诉它时间表的下一次；不在醒来的一轮里或值班暂停时返回错误 |

`dispatch`、`ask_user`、`save_state`、`set_name`、`next_wake` 标为非破坏性操作，`dispatches` 标为只读。

<a id="acceptance_criteria"></a>
## 验收标准

每个任务都必须有验收标准（`accept`），它是执行者验证自己工作的依据。Janus 不替执行者运行任何验证命令，设计取舍见 [ADR：按验收标准自行验证](../decisions/20261101-criteria_over_commands.md)。

- **负责人写标准**：写结果和行为，例如「点击格子能翻开并显示周围雷数」「新增测试覆盖空输入并通过」，而不是某条具体命令。需要特定的验证方式时，写进标准或说明，作为要求而不是唯一的检查。
- **执行者自己验证**：任务说明要求执行者结束前逐条验证，方式由它判断（运行测试、启动程序看实际表现、读代码推理、对比输出），在结构化结果的 `checks` 中按顺序逐条写明 `passed`、`evidence` 和可选的 `method`。`method` 是 `test`（运行自动化测试）、`command`（运行命令或脚本）、`inspection`（检查代码、文件、界面或实际状态）、`reasoning`（推理或自我判断）或 `unverified`（证据缺失或暂时无法核实），只说明依据的类型，不代替证据。标准本身不合理或当前环境无法验证时，在 `question` 中请负责人调整。
- **Janus 核对结构**：每条标准都有对应的 check、有证据、没有自认未达到的、给出方法时是允许的值，才算通过，见[验证](../domains/20261031-run_lifecycle.md#verification)。旧结果没有方法时显示「未说明」并继续按原规则核对；`reasoning`、`unverified` 和没有方法只产生提醒，不自动判失败。
- **独立核对由负责人负责**：执行者的证据是它自己的说法。负责人说明要求负责人自己核对关键结果，改了代码的目标在结束前安排独立评审。

修改这些规则时，同步更新 `orchestrate` 工具中 `accept` 的描述、任务说明（`task_prompt`）和负责人说明（`goal_brief`）中的验收标准一节。
