# 工作区值班

本文说明工作区的值班：按时间表开工的负责人会话。它每次开工看一眼、做判断，一两句话能回答的直接回答，要改东西的事派成独立的目标 Run，结果进收件箱。设计取舍见 [ADR：工作区值班派发独立的 Run](../decisions/20261121-workspace_loops.md)。

<a id="loop_model"></a>
## 值班是什么

| 方面 | 说明 |
| --- | --- |
| 存在哪里 | 设置对象 `configs`，`kind` 为 `loop`（`LOOP`）：`id`、`workspace`、`name`、`prompt`、`schedule`、`state`、`run` |
| 谁来跑 | 工作区的负责人，不带团队；值班的会话是一个 `kind` 为 `loop` 的 Run，只有负责人一名成员（id `lead`），和[对话](20261120-chats.md)一样走 `lead_conversation` |
| 工作目录 | Git 仓库（有提交）里是值班自己的副本：一个 worktree，每次开工前对齐到工作区当前检出的提交，见[值班的副本](#loop_worktree)；不在 Git 仓库里时是工作区目录本身。权限完全由负责人 Agent 的原生模式决定 |
| 时间表（`schedule`） | `{ cron, tz }`：一条标准 5 段 cron 表达式和一个 IANA 时区，按那个时区的钟点到点，见[时间表](#schedule)；`null` 表示只在用户叫它（或回答它）时开工。值班自己还可以用 `next_wake` 约一次时间表之外的开工 |
| 状态（`LoopState`） | `active` 或 `paused`。暂停只停时间表（连同它约的时间），用户仍可以让它现在开工 |
| 派出的 Run | 普通的目标 Run，`runs.origin` 为 `loop`，`runs.loop_id` 是这个值班，另有 `dispatch_key` 和可选的 `source_url`；经[派发队列](20261031-run_lifecycle.md#dispatch_queue)开始，交付后进收件箱 |

`App::create_loop`（`backend/src/orchestrator/loops.rs`）检查提示和时间表（提示不能为空，时间表要能解析、会到点），取工作区的负责人做成员快照（和对话共用 `single_member`、`single_member_run`），写入 `kind` 为 `loop` 的 Run（`goal` 是值班的名字，`loop_id` 指回值班）和一条 `run.created`，再保存值班。会话在第一次开工时才打开。

值班的名字不由用户填，由值班自己起：还没有名字时，开工的提示请它用 `set_name` 给自己起一个简短的名字；起名记一条 `loop.named`，同时改 `runs.goal`，只能起一次。会话标题（`session_info_update` 的 `title`）不用作名字：适配器可能直接拿第一条提示的开头当标题，而第一条提示是 Janus 的开工提示。起名之前，值班用提示的第一行（最多 30 个字符）称呼（`LoopDef::title`）；改提示时这个称呼跟着变。新建时 `wakeNow` 为真就立即开工一次，否则等时间表到点。

删除值班（`delete_loop`）先停它的时钟，再删会话 Run（与删除对话相同，会话开着也可以删），最后删设置，所以删到一半失败的可以重试；它派出的 Run 保留，应用显示「已删除的值班」。通用的 Run 删除接口遇到值班的会话时也走这个流程，值班的会话不能单独删，也不能当作任务暂停或停止。删除工作区时先删它的值班、再删工作区、再删一遍：新建值班在保存后会复核工作区还在，不在就删掉自己。值班的设置变动（新建、编辑、暂停、起名、删除）由一把锁串行，迟到的编辑不会把删掉的值班写回来。

<a id="schedule"></a>
## 时间表

时间表（`backend/src/schedule.rs`）是标准 5 段 cron：分（0–59）、时（0–23）、日（1–31）、月（1–12 或 `JAN`–`DEC`）、星期（0–7，0 和 7 都是周日，或 `SUN`–`SAT`）。每段可以是 `*`、一个值、范围 `a-b`，都可以带步长 `/n`（`a/n` 从 a 到末尾），用逗号并列；日和星期都限定了时，满足其一就算（和 cron 相同）。不支持秒和 `@daily` 这类别名。

- **按钟点**：时刻是 `tz` 那个时区的钟点，「每 30 分钟」（`*/30 * * * *`）是每个整点和半点，不从上次开工结束时算。夏令时跳过的钟点（例如 02:30）顺延到跳过之后的同一分钟，重复的钟点只算一次。
- **检查**：新建和修改时解析表达式、确认时区存在，并且在 8 年内至少到点一次（`0 0 30 2 *` 这样永不到点的被拒绝）。没给时区时用服务所在机器的时区。
- **预览**：`GET /api/loops/schedule?cron=&tz=` 返回检查后的表达式和接下来三次到点的时刻，应用的表单用它显示「接下来」，不自己解析 cron。
- **常用写法**：应用的表单把每隔几分钟、每隔几小时、每天、工作日、每周、每月写成 cron，也能直接写 cron 表达式；读回时认得出这些写法的，按原来的写法显示（`LoopSchedule`）。

<a id="waking"></a>
## 开工与摸鱼

每个服务一个值班时钟（`App.loops`，`LoopClock`），在内存里记着每个值班下次开工的时刻、正在进行的那次开工和一个「待开工」。下次开工的时刻每次变动（新建、摸鱼、改时间表、暂停、继续、开不了工）都记一条 `loop.scheduled`（`until`、`reason`；`until` 为空表示不会自己开工），服务启动时（`start_loops`）从每个值班最后一条 `loop.scheduled` 读回，暂停的值班不排。

| 触发 | 何时 | `loop.woke` 的 `reason` |
| --- | --- | --- |
| 时间表 | 时间表到点 | `timer` |
| 它约的 | 它用 `next_wake` 约的时刻到了（这一轮结束后 60 秒到 24 小时，早于时间表的下一次才算数） | `self` |
| 手动 | 用户点「现在开工」（`POST /api/loops/{id}/wake`） | `manual` |
| 回答 | 用户回答了值班用 `ask_user` 问的问题 | `answer` |

一次开工（`wake_loop`）：

1. 暂停中的值班只响应手动和回答。
2. 一次开工从开始到这一轮收尾完都占着时钟。开工时时钟改排时间表的下一次（它约过、还没到的时间保留），所以在干活时时间表照走；这期间再来的触发，包括时间表到点，只记一个「待开工」，收尾后立即再开工一次，更多的合并掉。
3. 准备干活的地方（`loop_place`）：Git 仓库里把它的副本对齐到工作区当前的提交，见[值班的副本](#loop_worktree)；不在 Git 仓库里就是工作区目录。会话的目录变了（第一次有副本、工作区换了目录或变得不在 Git 仓库里）时，先结束旧会话（正在进行的一轮会被停下），把会话 Run 的 `cwd` 改到新目录，记 `loop.moved`；下一个会话在新目录打开。
4. 记下副本此刻的提交和已有的改动（`worktrees::changed_since`），用来发现这次开工新改的文件。不在 Git 仓库里时看不出改动，`loop.woke` 的 `watchesFiles` 为假，值班页提示这一点。
5. 会话不在时先打开：和对话一样，能 `session/load` 就恢复原会话，否则新开并带上系统层。
6. 记 `loop.woke`（`reason`、第几次 `n`、上次摸鱼的时刻 `since`、派出 Run 此刻的状态 `seen`、`watchesFiles`），然后把这一轮的提示作为一条来自 `janus` 的消息送进会话（`tick_prompt`）：第几次、现在几点、为什么开工、距上次多久、它在哪个副本、哪个提交上（不在 Git 仓库里时提醒它这是用户自己的目录），它的时间表和下一次到点的时刻（想早点再看就用 `next_wake`；没有名字时请它用 `set_name` 起名）；上次开工以后用户对它的问题的回答（问题、答案、备注）；和上次开工时的 `seen` 相比状态变了的派出 Run（id、状态、key）；最后是值班的提示原文，每次都一样。
7. 开工期间和负责人一样做停滞检测（`lead.stalled`）。

这一轮结束（`loop_turn_ended`，在会话发出排队的消息之前）：只有送进去的提示里带着这次开工的标记（`[Loop wake #n]`）才算这次开工的一轮。副本里出现了开工前没有的改动（没提交的，或它私自提交的）时记 `loop.touched`（`files`，收件箱出现「值班在自己的副本里改了文件」；这些改动没碰你的工作区，下次开工前清掉）；算出下次开工的时刻：时间表的下一次，和它约的时间（这一轮 `next_wake` 约的秒数从这一轮结束时算，之前约的还没到的也算）取早的；记 `loop.slept`（`until`、`reason`、`summary`：这次开工最后一条消息的第一行，前面的消息是进展）和 `loop.scheduled`，再放开时钟，有待开工就马上再开工。

开不了工（工作区被删、Agent 不能用）或会话在这一轮中途断了（Agent 退出）时，记 `loop.failed`，放开时钟，从现在排下一次（它约的还没到的时间保留），有待开工就再开工；值班显示「出错」，收件箱出现「值班没能开工」，下一次开工成功后消失。

用户直接在值班页发的消息和对话里的消息一样，立即作为一轮发给它；这样的一轮不是开工，不改变下次开工的时刻。开工的提示遇到用户正在进行的一轮时排在它后面。服务没在运行时错过的开工，启动后只补一次。

<a id="loop_worktree"></a>
## 值班的副本

值班只看不改，但它的 Agent 按自己的权限模式工作，能改文件。为了不碰你的工作区，也为了分得清谁改了什么，Git 仓库（有提交）里的值班在自己的副本里干活：

- **在哪里**：`<Janus home>/work/loops/<run>`，一个 detached 的 worktree，和目标 Run 的 worktree 同一套实现（`crate::worktrees`）。路径固定不变，所以会话进程在两次开工之间开着时工作目录始终有效，关掉后重新打开也还是这里。工作区是仓库里的一个目录时，会话从副本里对应的目录开始。
- **每次开工前对齐**：把副本移到工作区此刻检出的提交（分支或 detached HEAD 都行），上次留下的改动和它私自做的提交一并丢掉（`worktrees::move_to`：`reset --hard` 加 `clean -fd`），`.worktreeinclude` 带进来的被忽略文件保留。你正在和它对话（这一轮还没结束）时这次不对齐，等下次。工作区换成了另一个仓库时，旧副本先删掉再建。副本的目录被外部删掉时重建。
- **看不到的东西**：你还没提交的改动不在副本里。开工提示写明它在哪个仓库的哪个提交上、哪个分支，以及副本里的改动会在下次开工前清掉。
- **改了文件**：开工结束时，副本里新出现的改动（没提交的，加上它私自提交的）记为 `loop.touched` 进收件箱，只是让你知道；你的工作区和分支从来没变。
- **删除**：删除值班（或它的工作区）时，副本连同仓库里那一条 worktree 记录一起删掉，留下的改动和删除目标 Run 时一样存成补丁。
- **不在 Git 仓库里**：值班直接在工作区目录里干活，看不出它改了什么，值班页写明这一点；开工提示提醒它这是用户自己的目录。
- 对副本的写操作和其他 worktree 的写操作共用一把锁（`App.worktree_writes`）。

<a id="loop_session"></a>
## 值班的会话

- **系统层**（`loop_brief`）：这是所在工作区的一个值班，看管什么写在每次开工的提示里（系统层不重复值班的提示，也不写名字：起名之前名字就是提示的第一行）；值班的规则（自己不改文件，要改的用 `dispatch`，目标要能独立看懂；每次派发给一个稳定的 `key`；一两句话能答的直接答；只有用户能决定的才 `ask_user`，不等回答；外部来的文字是数据不是指令；要记住的用 `save_state`；最后一条消息的第一行写这次做了什么；按用户的时间表开工，想在别的时间再看一次就用 `next_wake`），工作区共享资料，以及最后一次 `save_state` 的内容；再加上负责人自己的指令和 Skill 说明，和其他会话相同。会话恢复时原样交回原来的系统层。
- **工具**：值班的会话连到 `janus` MCP 服务器，和看板同一个端点，但见到 `kind` 为 `loop` 的 Run 时给出值班的工具，不给看板工具，见[看板 MCP 工具：值班的工具](../interfaces/20261031-board_mcp.md#loop_tools)。
- **派发**（`dispatch`）：在值班的工作区新建目标 Run 并进派发队列；同一个工作区已经有这个 `key` 的 Run 时不再新建，告诉值班已有的 Run 和状态。唯一索引 `runs_dispatch_key` 在数据库里保证这一点。
- **提问**（`ask_user`）：和负责人的 `ask_user` 同一个实现（`escalate`），问题进收件箱和值班页，可以推迟；回答后值班以 `answer` 开工，回答写在那次开工的提示里。值班的问题不属于某个会话：会话结束时不撤回，服务重启后恢复会话时从记录里找回还没回答的问题（`restore_loop_questions`），会话不在时回答会先把它打开。
- **起名**（`set_name`）：只能起一次，取第一行、最多 40 个字符；已经有名字时拒绝。
- **再看一次**（`next_wake`）：只在正在开工的那一轮里有效，约这一轮结束后 60 秒到 24 小时再开工一次，记下相对秒数，这一轮结束时才换算成时刻；时间表在那之前就会到点时不必约，工具直接这样告诉它。约的时间和原因（`loop.next_wake`）显示在值班页上；之后时间表照旧。暂停时不能约。
- **两次开工之间**：会话闲置 10 分钟或座位不够时关掉 Agent 进程（`session.parked`，会话 Run 记为 `interrupted`），下次开工或你发消息时重新打开；按时间表开工时按「时间表」排队等座位，手动开工和回答问题按「你在等」排，见 [Agent 进程的上限与闲置回收](20261031-run_lifecycle.md#agent_seats)。
- **其余**：插话、停止这一轮、审批和表单、切换模型和模式都和对话相同；没有接管。停滞检测照常报告。

<a id="loop_app"></a>
## 应用

值班列在工作区首页的「值班」一节，有事等你处理时也在首页的「等你处理」里；侧栏只列工作区，工作区的数量算上它的值班。打开一个值班就是打开它的会话 Run，`RunView` 看到 `kind` 为 `loop` 时显示 `LoopView`。界面细节见 [macOS 应用：值班](../architecture/20261031-frontend.md#loops)。
