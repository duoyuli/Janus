# 协作三方：负责人、协作者和编排器

> 上级索引：[领域文档](index.md)

本文列出一次 Run 中三方各自能做什么：负责人和协作者通过看板 MCP 调用的工具，以及编排器（Janus 自己）在后台自动做的事。它是一张总览，每一项只写一句用途，参数和校验规则见[看板 MCP 工具](../interfaces/20261031-board_mcp.md)，流程细节见 [Run 生命周期](20261031-run_lifecycle.md)和[目标模式与共享看板](20261031-goal_mode.md)。

两个 Agent 都另有各自的原生工具（读写文件、执行命令），由 Agent 自己的权限模式决定能做什么，Janus 不另加限制，见 [Agent、角色与工作区](20261031-agents_and_roles.md#permission_modes)。用户自己的操作（暂停、停止、接管、发消息、审批、验收）见[用户操作](20261031-run_lifecycle.md#user_actions)。

<a id="division"></a>
## 分工

三方的分工按「判断」和「执行」划分：

- **负责人**做判断：拆成哪些子任务、交给谁、结果算不算数、哪项要返工、用原会话还是新会话、什么要问用户。
- **协作者**做子任务，按验收标准自己验证，交回结构化结果；遇到超出权限的决定，问负责人。
- **编排器**只做机械的部分，以及执行负责人已经声明的结构（依赖、独立验证、负责的文件）。它不替负责人做判断：例如独立验证判定没通过时，不自动返工，由负责人决定。这条分工的来由见 `LESSONS.md` 的 L-25 和 [ADR：返工由负责人用 `retry` 发回原任务](../decisions/20261119-rework_in_original_session.md)。

在这条分工上，还有几条规则（见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)）：

- 目标小到一个人一轮能做完时，负责人自己做；一旦派出第一个子任务，它只做管理，不再改工作目录里的文件，也不接手做不下去的子任务。
- 独立验证不强制：负责人可以派协作者验证，也可以自己核对；自己核对不单独记录，交付时由它在摘要里交代。
- 负责人只看到协作者的名字和职责，按职责选人。
- 协作者之间不直接沟通，一切经过负责人（星形）；看板工具 `board` 让协作者看到别人做了什么。
- 团队在 Run 中固定，缺什么能力由负责人告诉用户。
- 用户可以直接介入协作者的会话，负责人会在看板上读到。

<a id="lead"></a>
## 负责人

负责人用 `/goal` 推进目标（见[负责人会话](20261031-goal_mode.md#lead_session)），通过 8 个看板工具管理团队。

| 用途 | 工具 | 做什么 |
| --- | --- | --- |
| 看 | [`board`](../interfaces/20261031-board_mcp.md#task_detail) | 不传 `task`：协作者（名字和职责）和看板上所有子任务的状态；传 `task`：一个子任务的完整说明、结果、证据、验证结论、修订、改过的文件和问答 |
| | [`wait`](../interfaces/20261031-board_mcp.md#wait) | 取看板新消息；有子任务完成或需要它处理的事时立即返回，否则最多等 180 秒 |
| 派活 | [`orchestrate`](../interfaces/20261031-board_mcp.md#orchestrate) | 提交一组子任务：执行者、依赖、验收标准，可选 `owns`（负责的文件）、`verifies`（独立验证哪个子任务）、`continues`（接着哪个子任务的会话） |
| 跟进进行中的子任务 | [`reply`](../interfaces/20261031-board_mcp.md#lead_tools) | 回答协作者的提问，或给正在执行的协作者补充指示 |
| 处理结束的子任务 | [`retry`](../interfaces/20261031-board_mcp.md#retry_tool) | 让结束的子任务再做一次：失败、取消的，或已完成但要返工的。`session` 必填（回到原会话或新开会话），可带 `from`（依据哪个独立验证的意见）和 `note` |
| | [`amend`](../interfaces/20261031-board_mcp.md#amend_tool) | 修订一个已完成子任务的结论，不重跑，下游以修订为准；或接受一个没通过验收核对的结果，没达到的部分记为风险。对独立验证任务无效 |
| | [`cancel`](../interfaces/20261031-board_mcp.md#cancel_tool) | 取消不再需要的子任务，依赖它的一起取消 |
| 找用户 | [`ask_user`](../interfaces/20261031-board_mcp.md#ask_user_tool) | 把只有用户能做的决定交给用户；不等待，回答出现在 `wait` 里 |

派出子任务后，读文件、跑测试、看 diff 照常；改了工作目录里的文件，编排器会报告（见下文「编排器」）。

负责人在这些工具之外还会：

- 读到推送进它当前这一轮的看板消息（[看板推送](20261031-goal_mode.md#board_push)）。
- 用最后的回复写交付摘要，可以附上建议写入工作区共享资料的条目（[交付](20261031-goal_mode.md#delivery_in_goal_mode)）。

`retry` 和 `amend` 都会改变下游用过的结果：`amend` 只改结论、不动工作目录，`retry` 让执行者重做工作。两者对已经用了旧结果的下游处理相同：正在执行的会收到通知，已经完成的列给负责人。

<a id="collaborator"></a>
## 协作者

协作者在自己的 ACP 会话中做一个子任务，协作约定在会话的系统层中（[协作者的约定](20261031-goal_mode.md#collaborator_rules)）。它有 4 个看板工具，其中两个用来交结果和提问。

| 用途 | 工具或字段 | 做什么 |
| --- | --- | --- |
| 报告 | [`board_post`](../interfaces/20261031-board_mcp.md#member_tools) | 把进展、阻塞或需要负责人注意的事写到看板，不停下来 |
| 看别人 | [`board`](../interfaces/20261031-board_mcp.md#peers) | 看其他子任务的状态、负责的文件和改过的文件；传 `task` 看某个子任务的完整结果和修订 |
| 交结果 | [`submit`](../interfaces/20261031-board_mcp.md#submit) | `summary`、`handoff`（给下游的交接说明）、逐条 `checks`（标准、是否通过、证据、方法）、`evidence`、`risks`；独立验证任务另填 `verdict`（`approved`、`rejected` 或 `inconclusive`）。格式不对当场退回；有标准没达到时提醒一次可以修好再交。交上后结束这一轮，子任务才算交了 |
| 提问 | [`ask`](../interfaces/20261031-board_mcp.md#ask) | 需要负责人做决定才能继续时提问并结束这一轮；回答作为下一轮发回同一个会话。子任务太大时附上拆分提议（`split`），负责人立即收到；验证任务不能提。要改负责范围以外的文件，也先问负责人 |

`board_post` 的阻塞不会让协作者停下，`ask` 会；需要等负责人决定时用 `ask`。审批和表单请求是 Agent 自己发起的，由编排器交给用户，见下文。

<a id="orchestrator"></a>
## 编排器

编排器没有给 Agent 调用的工具，下面这些是它在后台自动做的事。

| 方面 | 自动做什么 | 详情 |
| --- | --- | --- |
| 调度 | 依赖都完成、执行者空闲、未超过并发上限时启动子任务；依赖失败时下游标为无法开始，处理好后自动恢复；独立验证判定没通过时，挡住判定之前编排的下游 | [任务调度](20261031-run_lifecycle.md#scheduling) |
| 会话 | 每次尝试启动一个 ACP 进程，注入模型、权限模式、Skill、MCP 和协作约定；按需用 `session/load` 续接原会话（`continues`、`retry` 的 `continue`、复审），上下文超过 75% 或加载失败时新开（`retry` 的 `continue` 遇到超过 75% 当场拒绝，由负责人改用 `new`）；尝试结束即关闭进程 | [一次尝试](20261031-run_lifecycle.md#attempt) |
| 提示 | 拼出任务说明、验收标准、上游结果和交接说明、同时进行的子任务、上次失败的原因；独立验证任务另附被验证任务的 diff、改动文件和弱证据；回到原会话时只发新的内容 | [一次尝试](20261031-run_lifecycle.md#attempt) |
| 核对结果 | `submit` 时当场检查格式：每条标准都有回答和证据、方法合法、验证任务的判定合法，不合格就退回；有自认不通过的，第一次提醒可以修好再交。这一轮结束时没交结果的提醒一次，仍没交就算这次尝试失败；交上的结果仍有不通过的标准就标为失败交给负责人。不运行验证命令 | [验证](20261031-run_lifecycle.md#verification) |
| 失败重试 | 进程退出、超时这类失败，还有次数时自动在新会话重试（每个子任务最多 2 次） | [重试、返工与失败](20261031-run_lifecycle.md#retry) |
| 停滞检测 | 很久没有动静，或连续重复同一个调用（含 2 步、3 步交替）时，往看板报「[停滞]」；只报告，不打断 | [停滞检测](20261031-run_lifecycle.md#watchdog) |
| 文件痕迹 | 记录每个子任务和负责人改过的文件；两个子任务改同一个文件、改了别人负责的文件时立即报告；完成时把结果和实际改动对账；保存每个子任务的 diff；告诉下游哪些文件在上游完成后又被改过 | [工作目录里的痕迹](20261031-goal_mode.md#traces) |
| 消息流转 | 需要负责人处理的消息：负责人在 `wait` 时唤醒它，没在等时推送进它当前这一轮；协作者的提问交给负责人，负责人不在岗时转给用户 | [看板推送](20261031-goal_mode.md#board_push)、[提问的流转](20261031-goal_mode.md#question_routing) |
| 负责人的越界 | 派出子任务后负责人改了文件：每个文件第一次被改时推送「[负责人改了文件]」，交付时单独列出负责人自己改的文件；不阻止，权限由 Agent 原生模式决定 | [负责人的职责](20261031-goal_mode.md#lead_role) |
| 用户介入 | 用户直接在协作者的会话里发消息、接管、交还、打断或让它以当前结果结束时，在负责人的看板上记「[用户介入]」，随下一次 `wait` 送到 | [共享看板](20261031-goal_mode.md#board_flow) |
| 交给用户 | Agent 的审批请求和表单只交给用户，负责人不能代为批准 | [审批和表单](20261031-goal_mode.md#user_requests_in_goal_mode) |
| 执行声明过的结构 | `retry` 时恢复因它被取消的下游；返工时让它的独立验证复审，并通知、列出已经用了旧结果的下游 | [重试、返工与失败](20261031-run_lifecycle.md#retry) |
| 收尾 | 负责人的目标一直不自己结束时问它是否完成；没有子任务在跑、负责人也结束时生成交付，标出改了文件却没有独立验证的子任务（只陈述事实） | [目标不自己结束时](20261031-goal_mode.md#goal_settle)、[交付条件](20261031-run_lifecycle.md#delivery_conditions) |
| 记录与恢复 | 每件事写成事件；服务重启后从事件重建看板，中断的尝试和负责人都用原会话续接，负责人另外收到重启时的看板状况 | [中断与恢复](20261031-run_lifecycle.md#recovery) |

其中「没达到的标准提醒再交一次」「没交结果提醒一次」和「失败后自动重试」是编排器自己决定再给一次机会，但只看格式、自报的结论和进程状态，不评判结果的好坏，属于机械的部分。
