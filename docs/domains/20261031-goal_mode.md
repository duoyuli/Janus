# 目标模式与共享看板

本文说明目标模式下的协作规则：负责人怎样启动和了解团队，负责人与协作者怎样通过共享看板传递任务、进展、阻塞和提问，以及负责人结束后未完成的事项怎样处理。看板工具的参数和校验规则见[看板 MCP 工具](../interfaces/20261031-board_mcp.md)，Run 的整体状态机见 [Run 生命周期](20261031-run_lifecycle.md)。

<a id="lead_role"></a>
## 负责人的职责

负责人是工作区中被指定为负责人的角色，在 Run 中的成员 id 固定为 `lead`。它：

- 用 `/goal` 推进用户的目标。目标小到一个人一轮能做完时，自己从头做到尾，不派子任务。
- 需要时把一部分工作编排给协作者。是否协作、交给谁、怎么拆，都由负责人判断，Janus 不强制规划。
- **派出第一个子任务后只做管理**：拆任务、读看板、判断、核对和交付，不再改工作目录里的文件，也不接手做不下去的子任务（改用 `retry`、换人、`ask_user` 或取消并写进交付风险）。读文件、跑测试、看 diff 照常。Janus 不禁止它改文件（权限由 Agent 原生模式决定），但从这时起它对每个文件的第一次改动都记为 `lead.edited`：作为「[负责人改了文件]」推送给负责人，重启后从事件恢复；交付时负责人自己改的文件单独列出（`leadEdits`），报告要写明怎么核对的。经 MCP 路由调用资源库的工具同样处理：每个工具第一次调用记为 `lead.routed`（「[负责人用了资源库工具]」），交付时列为风险，因为这些调用可能改了文件或对外做了事，而 Agent 上报的编辑里看不到。见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。
- 在协作者完成后自行核对结果，确认目标达成后结束。

只有开启了「可以担任负责人」（角色字段 `lead`）并且绑定了 Agent 的角色能做负责人；Agent 只有 Claude Code 和 Codex，两者都提供 `/goal`。保存工作区时检查（`save_workspace`），创建 Run 时为每个成员构建运行环境（`spec_for`），没有 Agent 的负责人在这里报错。应用的角色编辑和工作区设置也只允许这样的角色担任负责人：没有开启「可以担任负责人」的数字员工不显示「负责人」选项。

<a id="lead_session"></a>
## 负责人会话

`App::goal` 启动负责人会话并进入调度循环，`App::lead_goal` 负责会话本身：

1. 为负责人生成看板令牌，记录当前 diff 作为基线（之后的 diff 产物只包含 Run 期间的改动）。
2. Claude Code 负责人：在它的隔离配置 `~/.janus/data/agents/<id>/config/.claude.json` 中把工作目录标记为已信任，因为 Claude Code 只在受信任的工作区运行 `/goal`。不修改用户自己的 Claude 配置。
3. 启动 ACP 子进程，打开会话，接入看板 MCP 服务（`janus`），按角色设置会话控制项。
4. 注入说明（见[负责人知道什么](#lead_brief)）：负责人说明（连同用户留给负责人的消息）在前、资源库 Skill 目录的位置（有 Skill 时）居中、用户的长期要求在后，放进系统层。Claude Code 通过 `session/new` 的 `_meta.systemPrompt.append`；Codex 通过适配器进程的 `CODEX_CONFIG.developer_instructions`，它在适配器启动前就要确定，所以留言在会话打开后才标为送达（`peek_notes`、`take_peeked_notes`）。见 [ACP 集成](../interfaces/20261031-acp_integration.md#standing_instructions)。
5. 发送 `/goal <目标>`。目标超过 3800 个字符时截断。
6. 如果回复表明 Agent 不支持或拒绝 `/goal`，负责人以失败结束。
7. Codex 在提示返回后可能继续工作。Janus 读取 `session_info_update` 中的目标状态（记为 `goal.status` 事件），状态为 `active` 时继续跟随会话；目标一直不自己结束时，见[目标不自己结束时](#goal_settle)。
8. 一轮结束后，如果有用户排队的消息，把它们发给负责人继续；如果用户接管了会话，等待用户消息或交还。

系统层中的负责人说明（`channel` 为 `system`，会话页标为「团队协作指令」）、用户的长期要求（`instructions`，标为「数字员工的指令」）、`/goal` 和后续提示都作为 `session.prompt` 事件记录，负责人会话页可以展开查看。负责人调用 `orchestrate`、`wait`、`reply` 或 `board` 时，Janus MCP 入口会记录 `tool.started` 和 `tool.completed`，长时间的 `wait` 会先显示等待状态。

编排器重启后从中断处继续时，负责人的会话不按上面的步骤新开：能加载就加载原会话、不再发 `/goal`，见 [Run 生命周期](20261031-run_lifecycle.md#recovery)。

第一个目标结束时，结果记为「完成」（附最后一条回复），会话保持打开，成为交付后的对话；会话异常结束时记为「异常」（附错误）。目标结束和会话关闭是两回事：交付后的消息仍发进同一个会话，只有用户取消、会话出错或 Agent 退出时会话才关闭。用户取消 Run 时不记结果。

<a id="goal_settle"></a>
### 目标不自己结束时

有的 Agent 不会自己结束目标。Claude Code 只有在它自己的检查确认条件达成时才清除目标，这个检查可能不运行（例如接到自定义接入点、没有它使用的小模型）。这时负责人说完「已完成」就停下了，目标却一直是 `active`，Run 不会交付（真实运行中发现）。

所以跟随会话期间，负责人这一轮已经返回、没有正在执行的工具调用、会话安静超过 `goal_settle`（90 秒）时，Janus 直接问负责人（`goal_settle.rs`，记为 `session.prompt`，`channel: "goal_check"`）：

- 回复第一行是 `GOAL_DONE`：负责人确认目标已完成。Janus 用 `_session/goal`（`action: "clear"`）清除 Agent 的目标，记一条 `goal.status`（`actor` 为 `janus`，`data.by` 为 `janus`），目标结束。交付摘要取负责人的这条回复，去掉开头的标记。负责人会话不关闭，在同一个原生会话里等下一条消息，见[交付](#delivery_in_goal_mode)。
- 其他回复：负责人说明还差什么，继续推进，Janus 接着跟随。一段跟随中最多问 3 次，之后交给[停滞检测](20261031-run_lifecycle.md#watchdog)报告给用户。

<a id="lead_brief"></a>
## 负责人知道什么

负责人对团队的全部了解来自负责人说明（`goal_brief`，按 Run 的语言给出，见[注入的语言](#prompt_language)），`board` 工具（不带 `task`）会重复其中的协作者名单，并列出看板上的任务状态，不含用量。说明按负责人做事的时间顺序分节，参考的内容（协作工具、共享资料）放在最后，一条规则只在一节里说，见 [ADR：Janus 只注入协作规则](../decisions/20261125-collaboration_only_injection.md)：

1. **角色**：负责达成用户的目标；先判断小到自己能做完就自己做，否则派给协作者。
2. **协作者**：每人一行（`team_lines`），只有 id、名字和职责。负责人按职责决定派给谁，不看协作者用的 Agent、模型和权限模式：

   ```text
   - <id>：<name> · 职责：<description>
   - <id>: <name> · Responsibilities: <description>
   ```

3. **工作目录**：路径，大家都直接在这里工作、改动立即可见；然后按情况一句（`workdir_brief`）：Run 的 worktree（detached HEAD，依赖和构建产物不在里面，交付时 Janus 提交并合并回用户的分支，不要切换分支、不要在用户的仓库里运行 git）、Git 仓库，或不在 Git 仓库中。
4. **派活**：子任务说明写全背景、要做的事、负责什么、不能碰什么；验收标准写结果和怎样认出它，不写步骤；紧密耦合的放一个子任务，其余按文件、模块或问题切开，互不依赖的同时做，共用的定义先定下来；一个协作者实例一次只做一个子任务，会改同一批文件的用依赖排开。
5. **派出之后**：只做管理，不再改工作目录里的文件，资源库只用来查看，改了的文件 Janus 写到看板上并在交付中列为风险；派出的工作绝不自己接手；读看板跟进，需要负责人处理的消息会推进它的会话（[看板推送](#board_push)），先处理会卡住别人的；协作者提问后等回答；交的结果有标准没达到时，Janus 提醒执行者可以修好再交一次，仍没达到的由负责人决定接受、返工还是取消。
6. **交付**：目标达成才结束；最终回复以「结论」开头，需要用户决定时加「需要你决定」，然后写改了什么、怎样核对的、还有什么没做，交付标出的没有独立验证的子任务逐个说明；值得长期保留的事实写在「建议更新共享资料」一节（英文是「Suggested Updates to Shared Context」）；交付后的轮次也这样结尾。最后一条是提交和推送（`commit_rule`）：只有用户要求时才 commit、push、部署或发布，只做到要求的程度；Run 在 worktree 中时还写明提交和合并就是交付，推送前先 `git rebase <分支>` 再 `git push origin HEAD:<分支>`，见 [ADR：用户要求时 Agent 提交、推送和部署](../decisions/20261123-commit_push_on_request.md)。见[交付](#delivery_in_goal_mode)。
7. **谁来做决定**：见[谁来做决定](#decision_ownership)。
8. **协作工具**：看板 MCP 的工具一行一个，只说它是做什么的（`orchestrate`、`wait`、`board`、`reply`、`retry`、`cancel`、`amend`、`ask_user`，以及团队记忆的 `recall`、`remember`；`amend` 一行同时写明它也用来接受没完全达标但可以接受的结果），注明详细用法和限制在各工具自己的说明里。它是一份参考，放在流程之后；其他各节只写流程，不再提工具名。
9. **工作区共享资料**：只在工作区有共享资料时出现，标题里写明它的规则（用户维护、协作者都能看到、已有的事实直接用、和本次目标冲突时以目标为准），下面是正文，见[工作区共享资料](20261031-agents_and_roles.md#workspace_brief)。

说明之后依次是：从中断处继续时的恢复说明（看板上之前的任务及其状态、和用户最近的对话）、团队记忆一节、留给负责人的消息、用户的长期要求（数字员工的指令）。负责人和协作者能用的 Skill、MCP 不写进说明：它们通过各自的 ACP 会话参数交付，由 Agent 自己加载，见[资源库](20261116-resource_library.md#delivery)。

<a id="prompt_language"></a>
## 注入的语言

Janus 写给 Agent 的文字都有中文和英文两版：系统层的说明、提示、插话、看板消息、MCP 工具的说明和返回、生成的 `janus-skills`。用哪一版看 Run 的语言（`Run.lang`，`backend/src/lang.rs` 的 `Lang`），写法是 `tr!(lang, "中文", "English")`。只给应用和用户看的文字（事件标题、接口的错误信息、日志）不在其中。

- **语言从哪里来**：应用把界面实际用的语言（「跟随系统」换算成中文或英文）用 `PUT /api/language` 告诉服务端：每次连上全局事件流时，以及用户在「设置 › 通用」换语言时。服务端存为一项设置（`configs` 的 `language` 类，一行），没有时是中文。
- **固定在 Run 上**：Run 创建时（目标排队时、对话、值班和整理开始时）把当时的语言写进快照（`config.lang`），之后不变，换语言只影响之后创建的 Run，进行中的任务不会半路换语言。数据版本 24 给以前的 Run 记为中文。
- **读回 Agent 写的标题**：交付的标题按 Run 的语言要求，解析时两种都认（`LeadReport::of`）。
- 数字员工指令、Provider 自定义提示词、共享资料、用户消息和历史对话保留原文，不翻译。

<a id="board_flow"></a>
## 共享看板

负责人和协作者之间没有直接对话，所有协作信息都经过看板：

| 方向 | 方式 |
| --- | --- |
| 负责人 → 看板 | `orchestrate` 提交编排。Janus 先校验，全部通过后任务写入看板（`orchestration.accepted`）并按依赖执行；有任何错误则整份编排不执行（`orchestration.rejected`） |
| 协作者 → 看板 | 执行中用 `board_post` 写回进展、阻塞和备注；做完用 `submit` 交结果（含可选 `handoff` 和验证判定 `verdict`）；需要负责人决定时用 `ask` 提问并结束这一轮，任务过大时在提问里附上拆分提议 |
| 看板 → 负责人 | `wait` 事件驱动唤醒取回新消息：有任务完成或需要负责人处理时立即返回，任务开始、进展等只是告知的消息随下一次返回带上（超时时附运行中任务的实时心跳），`board` 查看全部状态，带 `task` 时按 id 查看一个任务的全部信息；需要负责人处理的消息还会推送进它的会话，见[看板推送](#board_push) |
| 看板 → 协作者 | `board` 查看其他任务的状态、关系、负责和改过的文件、完成后又被改过的文件和完整结果；和别的任务改了同一个文件、或改了别的任务负责的文件时收到提醒，见[同时改同一个文件](#conflicts) |
| 工作目录 → 负责人和协作者 | Janus 从工具调用和 Git 读回每个任务留下的改动，用来限定 diff、核对结果、标出可能过期的结论，见[工作目录里的痕迹](#traces) |
| 负责人 → 协作者 | `reply` 回答提问，或给正在执行的协作者补充指示（立即送达） |
| 负责人 → 任务 | `retry` 重做或返工（选择会话，可带验证意见）、`amend` 修订已完成任务的结论或接受没通过验收核对的结果、`cancel` 取消 |
| 负责人 → 用户 | `ask_user` 交出只有用户能做的决定 |

看板没有单独的存储，它就是 Run 的事件日志。`wait` 从负责人上次读到的 `seq` 继续，把与任务相关的事件格式化成消息返回（`board_entry`）。负责人能看到的事件类型见[看板 MCP 工具](../interfaces/20261031-board_mcp.md#wait)。

可以多次提交编排，后提交的任务可以依赖之前的任务。看板任务的 id 在整个 Run 内唯一。工具说明提醒负责人：一次调用的内容太长会被模型的单次输出上限截断，Agent 在本地就拒绝这份坏掉的参数，整份编排作废、Janus 收不到；子任务多或说明长时分几次提交，工作目录里已有的资料在说明里写路径，不整段抄进去。不建议另写说明文件：在 Git 仓库上，它会随交付合并进用户的分支，派出子任务后再写还会记为负责人改了文件。

用户可以绕过负责人，直接在协作者的会话里发消息、接管、交还、打断或让它以当前结果结束（无论这时 Agent 是否在跑一轮，结束都记为 `session.interrupted`，`data.finish` 为 `true`）。负责人管着看板，所以这些介入以「[用户介入]」写进它的看板：只告知，不提前唤醒 `wait`，随下一次返回送到，并提醒负责人以用户的意思为准（`user_intervention`）。用户发给负责人自己的消息和负责人会话中的操作不在此列。见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。

<a id="board_push"></a>
### 看板推送

负责人只有调用 `wait` 才读看板，而它可以自己动手做事。它做别的事情时，协作者的提问只能停着等，失败和停滞也没人处理。所以需要负责人处理的消息会直接推送进负责人正在进行的这一轮（`push_board`），设计取舍见 [ADR：需要负责人处理的看板消息推送进负责人的会话](../decisions/20261102-board_push.md)：

- **触发**：写入以下事件时（`needs_lead`）：`question.asked`、`task.failed`、`task.blocked`、没有 `resolved` 的 `task.stalled`、`kind` 为 `blocker` 的 `board.posted`、`task.conflict`、`task.split_requested`、`lead.edited`、`lead.routed`、带痕迹核对问题（`data.traceGaps` 不为空）或独立验证判定为 `rejected` / `inconclusive` 的 `task.succeeded`，以及用户的回答（`ask_user` 问题的回答，或用户在会话中直接回答协作者）。
- **合并**：触发后等 2 秒（`PUSH_SETTLE`），把负责人上次读到之后看板上的全部消息（格式与 `wait` 相同）合成一条，以「[Janus 看板推送]」（英文 Run 为「[Janus board push]」）开头，通过[插话](../interfaces/20261031-acp_integration.md#steering)插入负责人的这一轮，并把游标移到最后一条。推送过的消息不再由 `wait` 返回。
- **条件**：负责人的 Agent 声明了插话、会话正在进行、负责人没有在 `wait` 中，并且负责人在看板上（第一个目标完成前，或交付后正在处理一条消息，见[提问的流转](#question_routing)）。不支持插话的负责人不推送：推送只能排队到这一轮结束，在此期间 `wait` 反而看不到这些消息。推送只插话，插不进去时排队到这一轮结束，不打断负责人。
- **记录**：推送记为 `session.prompt`（`channel: "board"`），负责人会话中显示为「看板推送」；送达和读到的时刻记在 `message.routed`、`message.delivered` 中。

<a id="conflicts"></a>
### 同时改同一个文件

负责人和协作者都直接在这个 Run 的工作目录（Git 仓库上是它自己的 worktree）中工作，并行的任务可能改到同一个文件。Janus 从工具调用中识别改动（`record_edits`）：

- 协作者完成一次 `edit`、`delete` 或 `move` 类型的工具调用时，从 ACP 的 `locations`（没有时取输入中的 `file_path`、`path` 等）得到文件，转成相对工作目录的路径，记在这个任务名下（`tool.call` 的 `data.paths`）。
- 另一个正在执行的任务也改过其中的文件时，写 `task.conflict` 给负责人（`wait` 中的「[冲突]」，并触发看板推送）；双方协作者的 Agent 支持插话时，各收到一条以「[Janus]」开头的通知，说明对方在改哪些文件、改之前先读最新内容、分工不清时写 blocker。同一对任务的同一个文件只报告一次。
- 其中的文件归另一个可能同时执行的未结束任务负责（`owns`，见[团队结构](#team_structure)）时，不等对方也改，立即写 `task.conflict`（`data.owned: true`，`wait` 中的「[越界]」）；只有越界的一方收到「[Janus]」通知，要求它不再改这些文件，需要时写 blocker。上游或下游任务的文件、已结束任务的文件不算越界。同一个任务对同一个负责方的同一个文件只报告一次。
- 负责人自己的会话完成文件修改工具调用时，同样以类型化的 `Actor::Lead`（与名为 `lead` 的看板任务严格区分）记入痕迹（`record_lead_edits`）：若改到了正在执行的协作者任务 `owns` 负责或正在修改的文件，立即写 `task.conflict`（`data.byLead: true`，`data.other: "lead"`）并向支持插话的协作者发出提醒；若改到了已完成任务的文件，下游交接和 `board` 的任务详情中标出「负责人 改」。还没开始的任务负责的文件不算冲突：负责人先落盘共享契约再扇出（契约先行）正是这样做的，任务开始后会读到改动。记录来自事件，编排器重启后由 `resume_run` 重建。
- 每个任务改过的文件可以用负责人和协作者的 `board` 查看。

<a id="team_structure"></a>
### 团队结构：负责的文件和独立验证

负责人和协作者都直接在同一个工作目录中工作。冲突检测（见上节）只能在两个任务已经改了同一个文件之后报告；独立核对也不能只靠执行者自己的证据。所以编排可以声明两种结构，Janus 在 `orchestrate` 时校验（`teamwork::check`），规则见[校验规则](../interfaces/20261031-board_mcp.md#orchestration_validation)：

- **负责的文件（`owns`）**：任务负责修改的文件或目录。可能同时执行的任务（彼此都不在对方的上游）`owns` 不能重叠，否则整份编排被拒绝，负责人要用依赖串行或重新划分。协作者的任务提示会列出它负责的文件，要求只改这些，要改别的文件先问负责人。负责范围只由负责人在编排中定下，协作者没有扩大它的工具，见 [ADR：精简 Agent 的协作工具](../decisions/20261125-fewer_agent_tools.md)。Janus 不阻止它改别的文件：权限由 Agent 原生模式决定，改了另一个任务负责的文件会立即报告为「[越界]」，完成时还会在痕迹核对中列出。
- **拆分提议（`ask` 的 `split`）**：协作者发现任务横跨多个独立子系统或远超单次尝试可完成的范围时，在提问时附上拆分原因、已完成部分和建议子任务列表；提议当场写成 `task.split_requested` 送到负责人那里，由负责人判断是否重新编排或用 `reply` 指示继续；验证任务不能提拆分，见 [`ask`](../interfaces/20261031-board_mcp.md#ask)。
- **热会话续接（`continues`）**：负责人判断一项**新**工作适合接着同一协作者某个子任务的上下文做时，可声明 `continues` 指向那个子任务；首次尝试在上下文占用不超过 75% 且 Agent 支持 `loadSession` 时直接加载那个子任务的会话，免去重新阅读代码库，否则自动回退新建会话，见 [ADR：热会话续接](../decisions/20261118-session_continuation.md)。会话属于子任务，不属于协作者：同一个协作者可以有多个会话（例如一个做后端、一个做前端），独立领域的工作新开会话。验证没通过后的返工不新建子任务，见下文。
- **独立验证（`verifies`）**：一个任务声明它验证另一个任务。验证者必须是另一个协作者，Janus 自动让它依赖被验证的任务，不能写 `owns` 或 `continues`。它的任务提示附上被验证任务的验收标准、专属 diff 产物路径、实际改动文件、痕迹核对异常、弱证据条目提醒、风险（`teamwork::VerifiedContext`）和文件在被验证任务提交之后有没有变（见[证据复用](#evidence_reuse)），要求不改文件、不替执行者修问题，逐条核对验收标准、写明做了什么和看到了什么，并用 `verdict` 给出 `approved`、`rejected` 或 `inconclusive` 判定。
- **验证未通过**：验证者给出具体证据并报 `verdict: "rejected"` / `"inconclusive"`（或 `passed: false`）时，验证任务自身正常完成（`task.succeeded`），负责人在看板上读到「[验证未通过]」；验证者交的结果格式不对时，`submit` 当场退回，不会进入看板。`amend` 不能改验证任务的判定和结论。Janus 不自动返工：负责人判断问题出在哪个子任务，用 `retry` 把它发回原来的执行者（`from` 指向这个验证，`session` 选回到原会话或新开会话），验证意见原样交过去；返工完成后，这个验证在自己的会话中复审，见[重试、返工与失败](20261031-run_lifecycle.md#retry)。换人或另开一项工作时才用 `orchestrate`；旧的下游任务不再需要时，用 `cancel` 取消并写明理由。已完成的验证在复审前保留原判定；判定之前就编排好、依赖验证任务的任务不会开始（`blocked`，见[任务调度](20261031-run_lifecycle.md#scheduling)），复审通过后自动开始。未通过确认或取消的验证任务在交付的 `acceptance.verifications` 里 `passed` 为 `false`，每一个都列为被验证任务的风险，另一个验证任务的通过不会抵消它。

- **结论只对它看过的那一版有效**：被验证的任务有了新结果时（返工完成，或负责人用 `amend` 接受了没通过验收核对的结果），在这之前已经给出结论的验证自动重新打开，在新结果上复审；验证正在执行时被验证的任务返工了，它完成后看被验证的任务：还在返工，或者在它开始之后才有新结果，它也重新打开，等新结果出来再复审（`recheck_verifications`）。所以交付里的判定总是针对最终那一版，旧判定留在事件日志里，审计页可以回看。重开记为 `task.reopened`（`reason: "target.reworked"`），重启后照样重建。

`owns`、`verifies` 和 `continues` 是编排数据（`orchestration.accepted` 的任务字段），拆分提议是 `task.split_requested` 事件，都不增加任务状态，恢复时随任务定义和事件日志一起重建。

<a id="evidence_reuse"></a>
### 证据复用

同一套检查在同样的文件上跑出的结果相同。2026-11-15 至 11-24 的记录中，另一个成员刚跑过、中间没有改过文件，同一套检查又被重跑了 48 次，验证、验收和返工占子任务时间的 41%。所以 Janus 记下每份结果是在什么文件上做出来的，告诉后来的人这些文件变没变，由他们决定还要跑什么，Janus 不跳过也不禁止任何检查。

- **记下文件状态**：Git 工作目录中，协作者提交结果时（`result.submitted`，随后 `task.succeeded`）记下 `data.files`（`git::FilesState`）：当前提交（`head`），和每个与它不同或未跟踪的文件的 SHA-256（`files`，删除的记为 `deleted`，被忽略的不算）。只读文件，不往仓库里写任何东西；改动超过 2000 个文件时不记。重启后从事件读回（`TaskResult.files`）。
- **告诉验证者**：独立验证开始时，Janus 拿现在的文件状态和被验证任务提交结果时的比较（`teamwork::FilesSince`），写进它的任务提示：完全相同时，说明它的证据描述的就是现在的文件，`checks` 里写明哪些采信了它的证据；之后有变化时，列出变了的文件（最多 12 个）和提交是否变了，说明它的证据只对没受影响的条目有效。补跑什么由验证者自己决定。
- **告诉负责人**：验证任务完成时，看板的「[完成]」条目多一行「核对时的文件和 T1 提交结果时相同」，或「…不同（改了 …）」，比较的是两份结果各自记下的文件状态。负责人据此判断是否还要自己核对。
- **约定**：协作者的约定只写明文件没变时别人的证据仍然描述这些文件、可以引用。「重的检查做完时跑一次」「复查只运行证据没覆盖的部分」这些做法写在默认数字员工（PMO、通用数字员工、研发工程师、质量工程师、产品经理）的指令里。

<a id="traces"></a>
### 工作目录里的痕迹

协作者都在同一个工作目录中工作，各自做了什么，工作目录里本来就有记录。Janus 把能从工作目录读出来的事实直接读出来，不靠协作者自己汇报；看板只放读不出来的东西：动手前的承诺（`owns`）、意图和裁决。实现在 `traces` 模块：

- **记录**：每个任务改过的文件，和每个文件最后由哪个任务在哪个 `seq` 改的，来自工具调用（见[同时改同一个文件](#conflicts)）。
- **diff 只含自己的文件**：任务完成时保存的 diff 产物限定在它负责和改过的文件（`traces::scope`，路径按字面匹配）。未跟踪的新文件没有 `diff-index` 条目，用 `git diff --no-index /dev/null <文件>` 把内容和新增行记进同一个 diff，文件列表末尾仍列出它们的名字。两样都没有记录（例如只用命令改文件、又没有 `owns`）时才是整个工作目录的 diff，并在说明中写明可能含其他任务的改动；这时工作目录和上一个任务结束时一样就不保存。
- **整个任务的 diff**：任务的 diff 只含这个任务，负责人自己动手改的文件不在任何一个任务的 diff 里。负责人每一轮结束时（`record_run_changes`），Janus 把工作目录相对 Run 开始时（`baseRef`）的全部改动，包括 Run 里做的提交和未跟踪的新文件，存成一份 `run_diff` 产物，和上次的一样就不存；这就是验收时会带回源分支的内容。交付时它排在交付物的第一个，应用的「改动」页签也把它放在最上面。
- **结果与痕迹对账**：任务完成时，Janus 拿它负责的文件、改过的文件和工作目录相对 `HEAD` 的改动（`git diff-index --name-only HEAD` 加未跟踪文件）对账（`traces::gaps`），不一致的地方写进 `task.succeeded` 的 `data.traceGaps`：验证任务改了文件；改了负责范围以外的文件；负责的文件在工作目录里没有任何改动（不是 Git 仓库时，改为没有改这些文件的工具调用）。没有 `owns` 的任务只核对验证者。带 `traceGaps` 的完成消息在「[完成]」下多一行「痕迹核对」，并触发看板推送；`board` 的任务详情也列出，交付时每个任务的 `acceptance.traceGaps` 同样保留。负责人用 `retry` 重做或 `amend` 更正结论。
- **可能过期的结论**：任务完成后，它改过的文件又被别的任务改了，它的结论描述的是旧内容。下游任务的提示中，每个上游任务除了结果摘要，还列出它改过的文件和完成后又被谁改过（`context.handoff` 的 `data.files`、`data.stale`），要求以工作目录的现状为准；负责人和协作者的 `board` 中同样标出。

<a id="collaborator_board"></a>
### 协作者接入看板的条件

协作者的会话在 Agent 于 `initialize` 中声明 `mcpCapabilities.http` 为 `true` 时接入看板工具。Codex 和 Claude Code 都声明支持，它们的协作者总会接入看板；Agent 不声明时不接入，照常执行任务，通过结构化结果和提问回报。

<a id="collaborator_rules"></a>
### 协作者的约定

协作者怎样与 Janus 协作的固定约定（`collaborator_rules`）放在系统层，按 Run 的语言给出，排在用户的长期要求之前，整个会话都有效。和负责人说明一样按做事的顺序分节，一条规则只说一次：

- **工作方式**：直接在工作目录中工作，不改工作目录之外的文件；Janus 会拿结果和实际改过的文件对账；只在子任务说明要求时 commit、push 或部署，并且只做到说明要求的程度；Janus 说文件没变时，别人在这些文件上做出的证据仍然有效，可以引用，见[证据复用](#evidence_reuse)。
- **需要决定时**：缺少超出授权的决定时，向负责人提问（`ask`）并结束这一轮。
- **完成时**：用 `submit` 交结果，逐条写明验收标准是否达到和证据；没达到的说明原因，标准不合理时请负责人修改；怎样验证不在约定里，由数字员工的指令决定。交上后结束这一轮。字段和核对见[交结果和提问](20261031-run_lifecycle.md#structured_result)，约定里不再有 JSON 样例。
- **协作工具**：看板 MCP 的 `submit`、`ask`（子任务远超预期时附上拆分提议）、`board_post`、`board` 和团队记忆的 `recall`、`remember` 一行一个，只说它是做什么的，详细用法在各工具的说明里。

第一条提示（`task_prompt`）先写这次的子任务，再写它所处的环境：子任务的 id、标题和说明，验收标准，紧接着是团队结构段（负责的文件，或独立验证要核对什么、被验证任务的改动和文件状态、怎样给出判定）；然后是总目标、工作目录（Run 在 worktree 中时附一句说明，独立验证者的那句更短）、最多尝试几次、工作区共享资料；最后是上游任务的结果、同时进行的任务、上一次失败的原因和用户的留言。会话打开时，约定记为 `session.prompt`（`channel` 为 `system`）。

<a id="decision_ownership"></a>
## 谁来做决定

一次 Run 里有两类决定，处理方式不同：

| 类型 | 例子 | 谁决定 | 应用中 |
| --- | --- | --- | --- |
| 执行中的选择 | 做法、方案取舍、协作者在任务中的提问、失败任务怎么处理 | 负责人 | 看板「待处理」中标「负责人处理」，不需要用户操作 |
| 影响整个目标的决定 | 需求有多种理解且结果明显不同；需要用户的账号、凭据、付费或外部资源；用户没有要求过的不可逆或影响工作目录之外的操作（用户在目标里要求的提交、推送、部署照做） | 用户 | 「待处理」卡片，看板「待处理」中标「等你拍板」 |

负责人说明写明了这条分界，负责人用 `ask_user` 交出第二类决定，交出后继续做不依赖它的工作。审批和表单请求始终属于用户，见[审批和表单](#user_requests_in_goal_mode)。用户直接回答了协作者的提问时，负责人在 `wait` 中看到「用户已回答」，不再给出不同的答案。负责人要推翻协作者已经给出的结论时，用 `amend` 修订，下游任务以修订为准，避免前后两个结论同时在看板上生效。

<a id="question_routing"></a>
## 提问的流转

1. 协作者用 `ask` 提问，这一轮结束时问题转给负责人，任务停下等待（`question.asked`）。
2. 负责人在 `wait` 中读到 `[提问]`，用 `reply` 回答（`question.answered`，`via: "lead"`）。
3. 回答作为下一轮提示发回协作者原来的会话，协作者继续完成任务。

负责人在场时，提问不打扰用户。以下情况提问转给用户（`question.escalated`，由 `escalate_open_questions` 处理）：

- 负责人不在看板上，而协作者还在等回答：第一个目标完成后负责人空闲、等用户的下一条消息，或负责人会话已经结束（异常中断、Agent 退出）。
- 负责人不在看板上时出现的新提问。

交付后负责人仍在同一个会话中：用户发来消息（包括用 `/goal` 设置新目标）后，负责人处理这条消息的这一轮里重新在看板上，这期间编排的任务提问照常交给它、照常推送；这一轮结束、负责人又空闲时，仍没有回答的提问转给用户（`LeadState::on_duty`）。

负责人自己用 `ask_user` 交出的提问，到它离开看板（目标完成、交付后这一轮结束）时还没有回答的，被撤回（`decision.withdrawn`，`withdraw_lead_questions`）：负责人已经不等这个回答继续做完了，之后的回答也不会推给空闲的负责人。用户还想补充什么，直接给负责人发消息。值班的提问不撤回，回答会唤醒它，见[工作区值班](20261121-loops.md)。

只转交仍然有效的提问：任务正在执行、提问之后没有开始新的尝试、还没有被回答或转交过。用户也可以直接在协作者的会话页回答，先到的回答生效，负责人会在看板上收到「用户已回答」。

<a id="user_requests_in_goal_mode"></a>
## 审批和表单

协作者和负责人发出的审批请求（`session/request_permission`）和表单请求（`elicitation/create`）始终交给用户。负责人只能在看板上看到「等用户」，不能代为批准。这是有意的设计：权限决定属于用户。

<a id="failures_in_goal_mode"></a>
## 失败处理

- 验证任务没通过时不能用 `amend` 放行，见[团队结构](#team_structure)。
- 委派任务失败（`task.failed`）不会让 Run 停下等用户，应用也不弹出「等你拍板」卡片。负责人在 `wait` 中读到 `[失败]` 或 `[没通过验收]`（逐条列出没达到的标准），核对后用 `retry`（选择回到原会话还是新开会话，可改说明和验收标准）、`amend`（结果可以接受时接受它）或 `cancel` 处理；消息只写事实，这些选择写在负责人说明和工具说明里。被失败任务阻塞的任务在它处理好后自动继续，不需要重新编排。
- 协作者很久没有动静，或连续重复同一个调用时，负责人在 `wait` 中读到 `[停滞]`（见[停滞检测](20261031-run_lifecycle.md#watchdog)），由负责人判断继续等、用 `reply` 指出问题、`retry` 还是 `cancel`。Janus 不会自动打断它。
- 负责人自己很久没有动静或原地打转时，报告给用户（`lead.stalled`），应用在「待处理」中显示「负责人可能卡住了」，用户可以给负责人发消息、打断并接管或者继续等。
- 负责人会话在目标完成之前异常结束（Agent 进程退出、服务商报错、连接中断），Janus 等 `RETRY_AFTER`（30 秒）后让它回到自己的会话继续（`lead.failed` 的 `data.next` 为 `reopen`），走和服务重启后同一条恢复路径：能 `session/load` 就加载原会话，第一条提示写明会话为什么断了、协作者一直在继续、现在看板上每个子任务的状况，不重发 `/goal`；加载不了就新开会话，负责人说明里写明这是新会话。这期间协作者照常工作。重新打开后它没做任何事（说话、调用工具、编排）又断了，或者 Agent 拒绝了 `/goal`（`GoalRefused`），就不再重开（`next` 为 `stop`）：没有任务还在执行时 Run 失败，等用户「从中断处继续」，见 [Run 生命周期](20261031-run_lifecycle.md#recovery) 和 [ADR：断掉的会话回到原处继续](../decisions/20261125-resume_after_failure.md)。

<a id="delivery_in_goal_mode"></a>
## 交付

负责人的目标结束、没有任务还在执行或可以启动时，Run 交付：

- **一轮**：交付审的是这一轮，即上一次交付之后发生的事（第一次交付是从目标开始的全部）。这一轮的子任务是上一次交付之后有过事件的任务，新编排的和被发回返工的都算；之前轮次的子任务留在它们自己的交付里，不再重复列出。见 [交付的审阅](../architecture/20261031-frontend.md#review)。
- **负责人的报告**：取负责人最后一条回复（`lead_report`：这一轮里最后一段连续的 `agent.message`，之前边做边说的话不算；确认目标时开头的标记去掉），所有交付路径都一样：目标结束、交付后对话里的一轮、处理冲突的一轮。报告按标题切成几节（`LeadReport`，标题不分级别、粗体和冒号）：「结论」（`Conclusion`）一两句放在 `headline`，「需要你决定」（`Needs Your Decision`）的条目放在 `decisions`，共享资料建议一节的条目放在 `briefSuggestions`，其余整篇放在 `summary`，不截断，长文由应用折叠。负责人说明要求最后一条回复按这个结构写：先「结论」，有要用户决定的事时再列最多三个问题（从协作者的风险里挑出用户必须处理的），然后是改了什么、怎么核对的、哪些没做，只写结果不写过程；交付后对话里改了东西的一轮也这样结尾。
- **合并结果**：`merge` 写明结果怎样到了用户那里：`state` 是 `merged`（已合并）、`nothing`（没有新的改动）、`resolving`（冲突，第一次交给负责人解决）、`conflict`（负责人解决过仍然冲突，用户点验收再交给它）、`blocked`（用户那边挡住，例如有重叠的未提交改动、分支被改写）或 `inPlace`（不是 Git 目录，改动直接在工作目录里）；`note` 是给人看的一句话：合并到了哪个分支的哪个提交、没有新的改动，或者没能合并的原因（见[工作目录](20261031-run_lifecycle.md#workspace_model)）。之后给 Agent 读的交付（重新打开的负责人、值班、团队记忆的整理）是结论、报告和这句话连在一起（`delivery_text`）。
- **这一轮改了什么**：`changed` 列出这一轮改的文件。worktree 中的 Run 在合并之前，取 worktree 相对上次合并（第一次是任务开始时）的改动，包括提交和未跟踪的文件（`unmerged_files`）；不是 Git 目录时，取负责人和这一轮子任务的编辑工具调用里的文件。`leadEdits` 是负责人这一轮自己改的文件（`Traces::lead_edited_since`），它们没有经过子任务的验收和独立验证。
- 共享资料建议的条目由用户决定是否写入工作区，见[工作区共享资料](20261031-agents_and_roles.md#workspace_brief)。
- 证据从这一轮各任务的结构化结果汇总：`evidence` 保留每个任务的全部证据（不再只取第一条），`acceptance` 按任务给出验收标准总数、通过数、证据方法计数、逐条 `checks`、没说明/推理判断/未核实提醒、独立验证的结论（`verifications`）、改了文件却没有独立验证（`unverified`，只陈述事实，不说「未经确认」：负责人可能自己核对过）、痕迹核对（`traceGaps`）和这个任务自己报告的风险（`risks`），见[证据方法](../interfaces/20261031-events.md#evidence_methods)。
- `risks` 只放 Janus 查出来的事：独立验证没有通过、被取消或没有执行时，被验证的任务多一条「结论没有得到确认」；失败、已取消、被负责人取消、因依赖失败没有执行的任务；负责人派出子任务后自己调用了资源库工具。任务自己报告的风险只在它的 `acceptance` 条目里，不再复制一份，所以同一条风险不会出现两次。
- 负责人的说明要求：交付前每个改了文件的子任务都要核对过，可以是它安排的独立验证，也可以是它自己的检查；对标了 `unverified` 的子任务和它自己改的文件，报告要写明是怎么核对的（跑了什么、读了什么、看到了什么）。Janus 不记录负责人自己的核对，用户对照报告判断，见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。
- 负责人会话异常结束时不交付，Run 失败，见[失败处理](#failures_in_goal_mode)。
- 交付后负责人会话保持打开，成为常规对话：用户可以直接写下一轮任务，或用 `/goal` 设置新的目标。再次完成目标时再次交付。负责人处理消息期间编排的任务，提问和看板推送与第一个目标相同，见[提问的流转](#question_routing)。服务重启后，第一次发消息会重新打开会话并带上简要上下文。

设计取舍见 [ADR：负责人以 /goal 推进目标](../decisions/20261031-goal_mode_lead.md) 和 [ADR：通过 MCP 看板协作](../decisions/20261031-board_over_mcp.md)。
