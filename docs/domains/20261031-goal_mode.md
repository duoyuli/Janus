# 目标模式与共享看板

本文说明目标模式下的协作规则：负责人怎样启动和了解团队，负责人与协作者怎样通过共享看板传递任务、进展、阻塞和提问，以及负责人结束后未完成的事项怎样处理。看板工具的参数和校验规则见[看板 MCP 工具](../interfaces/20261031-board_mcp.md)，Run 的整体状态机见 [Run 生命周期](20261031-run_lifecycle.md)。

<a id="lead_role"></a>
## 负责人的职责

负责人是工作区中被指定为负责人的角色，在 Run 中的成员 id 固定为 `lead`。它：

- 用 `/goal` 推进用户的目标。目标小到一个人一轮能做完时，自己从头做到尾，不派子任务。
- 需要时把一部分工作编排给协作者。是否协作、交给谁、怎么拆，都由负责人判断，Janus 不强制规划。
- **派出第一个子任务后只做管理**：拆任务、读看板、判断、核对和交付，不再改工作目录里的文件，也不接手做不下去的子任务（改用 `retry`、换人、`ask_user` 或取消并写进交付风险）。读文件、跑测试、看 diff 照常。Janus 不禁止它改文件（权限由 Agent 原生模式决定），但从这时起它对每个文件的第一次改动都记为 `lead.edited`：作为「[负责人改了文件]」推送给负责人，重启后从事件恢复，交付时列为风险。经 MCP 路由调用资源库的工具同样处理：每个工具第一次调用记为 `lead.routed`（「[负责人用了资源库工具]」），交付时列为风险，因为这些调用可能改了文件或对外做了事，而 Agent 上报的编辑里看不到。见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。
- 在协作者完成后自行核对结果，确认目标达成后结束。

只有开启了「可以担任负责人」（角色字段 `lead`）并且绑定了 Agent 的角色能做负责人；Agent 只有 Claude Code 和 Codex，两者都提供 `/goal`。保存工作区时检查（`save_workspace`），创建 Run 时为每个成员构建运行环境（`spec_for`），没有 Agent 的负责人在这里报错。应用的角色编辑和工作区设置也只允许这样的角色担任负责人：没有开启「可以担任负责人」的数字员工不显示「负责人」选项。

<a id="lead_session"></a>
## 负责人会话

`App::goal` 启动负责人会话并进入调度循环，`App::lead_goal` 负责会话本身：

1. 为负责人生成看板令牌，记录当前 diff 作为基线（之后的 diff 产物只包含 Run 期间的改动）。
2. Claude Code 负责人：在它的隔离配置 `~/.janus/agents/<id>/home/.claude.json` 中把工作目录标记为已信任，因为 Claude Code 只在受信任的工作区运行 `/goal`。不修改用户自己的 Claude 配置。
3. 启动 ACP 子进程，打开会话，接入看板 MCP 服务（`janus`），按角色设置会话控制项。
4. 注入说明（见[负责人知道什么](#lead_brief)）：负责人说明（连同用户留给负责人的消息）在前、用户的长期要求在后，放进系统层。Claude Code 通过 `session/new` 的 `_meta.systemPrompt.append`；Codex 通过适配器进程的 `CODEX_CONFIG.developer_instructions`，它在适配器启动前就要确定，所以留言在会话打开后才标为送达（`peek_notes`、`take_peeked_notes`）。见 [ACP 集成](../interfaces/20261031-acp_integration.md#standing_instructions)。
5. 发送 `/goal <目标>`。目标超过 3800 个字符时截断。
6. 如果回复表明 Agent 不支持或拒绝 `/goal`，负责人以失败结束。
7. Codex 在提示返回后可能继续工作。Janus 读取 `session_info_update` 中的目标状态（记为 `goal.status` 事件），状态为 `active` 时继续跟随会话；目标一直不自己结束时，见[目标不自己结束时](#goal_settle)。
8. 一轮结束后，如果有用户排队的消息，把它们发给负责人继续；如果用户接管了会话，等待用户消息或交还。

系统层中的负责人说明（`channel` 为 `system`）、用户的长期要求（`instructions`）、`/goal` 和后续提示都作为 `session.prompt` 事件记录，负责人会话页可以展开查看。负责人调用 `orchestrate`、`wait`、`reply` 或 `team` 时，Janus MCP 入口会记录 `tool.started` 和 `tool.completed`，长时间的 `wait` 会先显示等待状态。

第一个目标结束时，结果记为「完成」（附最后一条回复），会话保持打开，成为交付后的对话；会话异常结束时记为「异常」（附错误）。目标结束和会话关闭是两回事：交付后的消息仍发进同一个会话，只有用户取消、会话出错或 Agent 退出时会话才关闭。用户取消 Run 时不记结果。

<a id="goal_settle"></a>
### 目标不自己结束时

有的 Agent 不会自己结束目标。Claude Code 只有在它自己的检查确认条件达成时才清除目标，这个检查可能不运行（例如接到自定义接入点、没有它使用的小模型）。这时负责人说完「已完成」就停下了，目标却一直是 `active`，Run 不会交付（真实运行中发现）。

所以跟随会话期间，负责人这一轮已经返回、没有正在执行的工具调用、会话安静超过 `goal_settle`（90 秒）时，Janus 直接问负责人（`goal_settle.rs`，记为 `session.prompt`，`channel: "goal_check"`）：

- 回复第一行是 `GOAL_DONE`：负责人确认目标已完成。Janus 用 `_session/goal`（`action: "clear"`）清除 Agent 的目标，记一条 `goal.status`（`actor` 为 `janus`，`data.by` 为 `janus`），目标结束。交付摘要取负责人的这条回复，去掉开头的标记。负责人会话不关闭，在同一个原生会话里等下一条消息，见[交付](#delivery_in_goal_mode)。
- 其他回复：负责人说明还差什么，继续推进，Janus 接着跟随。一段跟随中最多问 3 次，之后交给[停滞检测](20261031-run_lifecycle.md#watchdog)报告给用户。

<a id="lead_brief"></a>
## 负责人知道什么

负责人对团队的全部了解来自英文说明（`goal_brief`），`team` 工具会重复其中的协作者名单，并列出看板上的任务状态，不含用量。说明包含：

- 负责人的职责和自主权，以及「不要为了协作而协作」。
- 工作目录，以及负责人和协作者都直接在这里工作、改动立即彼此可见。
- 协作者名单，每人一行（`team_lines`），只有名字和职责。负责人按职责决定派给谁，不看协作者用的 Agent、模型和权限模式：

  ```text
  - <id>: <name> · Responsibilities: <description>
  ```

- 工作目录是不是 Git 仓库。
- 十个看板工具的用法，以及完成消息只有摘要、细节用 `task_detail` 查看。
- 看板推送：需要负责人处理的消息会以「[Janus 看板推送]」开头插入它的会话，推送过的不再出现在 `wait` 里；收到后先处理会卡住别人的事。见[看板推送](#board_push)。
- 谁来做决定，见[谁来做决定](#decision_ownership)。
- 怎么写验收标准、执行者怎么验证、证据方法（`test`、`command`、`inspection`、`reasoning`、`unverified`，见[证据方法](../interfaces/20261031-events.md#evidence_methods)）、没通过验收时怎么处理，与[验收标准](../interfaces/20261031-board_mcp.md#acceptance_criteria)一致；执行者的证据是它的说法，`reasoning`、`unverified` 和没有方法的项只是提醒，关键结果由负责人自己核对。
- 团队怎么组织（`teamwork::lead_guide`）：先估计规模，能干净切开的工作才分出去；多模块并行编码前契约先行（共享数据结构、接口签名或路由先由前置任务或负责人落盘）；每个任务写清负责什么、不能碰什么、做到什么算完成，并用 `owns` 声明负责的文件；协作者发现任务过大可用 `request_split` 提议拆分；重要改动安排独立验证（负责人只看到协作者的名字和职责，按职责选人），验证未通过时判断问题在哪个任务，用 `retry` 返工（`from` 指向验证，每次选择回到原会话还是新开会话），验证会自动复审；新工作要用到某个任务的上下文时用 `continues`，一个协作者可以有多个会话，独立领域的工作新开会话；看板上的「[认领]」「[越界]」和完成消息里的「痕迹核对」是什么意思，以工作目录的现状为准。见[团队结构](#team_structure)和[工作目录里的痕迹](#traces)。
- 协作要点：任务说明要写全（协作者看不到负责人的对话）；同一协作者实例的任务会排队；会改同一批文件的任务要用依赖串行，两个任务同时改了同一个文件时看板上会出现「[冲突]」；派出子任务后负责人不再改工作目录里的任何文件，也不接手做不下去的子任务，要调整就 `reply`，要重做就 `retry`，要换人就 `cancel` 后重新编排，谁都做不了时 `ask_user`；提问用 `reply` 回答；协作者完成后要自行核对；不要 `git commit`、push 或部署。
- 工作区共享资料的用法：已有的事实不再调研、不再问用户，与本次目标冲突时以本次目标为准；结束时把值得长期保留的新事实写在「Suggested Updates to Shared Context」一节。工作区有共享资料时，正文附在说明末尾，见[工作区共享资料](20261031-agents_and_roles.md#workspace_brief)。
- 负责人和协作者配置的 Skill、MCP 不写进 `goal_brief` 或 `team_lines`（它们通过各自的 ACP 会话参数交付，见[资源库](20261116-resource_library.md#delivery)）。角色指令和 Provider 的自定义提示词也不在说明里，按 [用户的长期要求](../interfaces/20261031-acp_integration.md#standing_instructions) 单独注入。
- 从中断处继续时，看板上之前的任务及其状态。

<a id="board_flow"></a>
## 共享看板

负责人和协作者之间没有直接对话，所有协作信息都经过看板：

| 方向 | 方式 |
| --- | --- |
| 负责人 → 看板 | `orchestrate` 提交编排。Janus 先校验，全部通过后任务写入看板（`orchestration.accepted`）并按依赖执行；有任何错误则整份编排不执行（`orchestration.rejected`） |
| 协作者 → 看板 | 执行中用 `board_post` 写回进展、阻塞和备注，用 `claim` 认领要改的文件，任务过大时用 `request_split` 提议拆分；结束时返回结构化结果（含可选 `handoff` 和验证判定 `verdict`）；需要负责人决定时在结果中提问并停下 |
| 看板 → 负责人 | `wait` 事件驱动唤醒取回新消息：有任务完成或需要负责人处理时立即返回，任务开始、进展等只是告知的消息随下一次返回带上（超时时附运行中任务的实时心跳），`team` 查看全部状态，`task_detail` 按 id 查看一个任务的全部信息；需要负责人处理的消息还会推送进它的会话，见[看板推送](#board_push) |
| 看板 → 协作者 | `peers` 查看其他任务的状态、关系、负责和改过的文件、完成后又被改过的文件和完整结果；和别的任务改了同一个文件、或改了别的任务负责的文件时收到提醒，见[同时改同一个文件](#conflicts) |
| 工作目录 → 负责人和协作者 | Janus 从工具调用和 Git 读回每个任务留下的改动，用来限定 diff、核对结果、标出可能过期的结论，见[工作目录里的痕迹](#traces) |
| 负责人 → 协作者 | `reply` 回答提问，或给正在执行的协作者补充指示（立即送达） |
| 负责人 → 任务 | `retry` 重做或返工（选择会话，可带验证意见）、`accept` 接受只是验证没通过的结果、`amend` 修订已完成任务的结论、`cancel` 取消 |
| 负责人 → 用户 | `ask_user` 交出只有用户能做的决定 |

看板没有单独的存储，它就是 Run 的事件日志。`wait` 从负责人上次读到的 `seq` 继续，把与任务相关的事件格式化成消息返回（`board_entry`）。负责人能看到的事件类型见[看板 MCP 工具](../interfaces/20261031-board_mcp.md#wait)。

可以多次提交编排，后提交的任务可以依赖之前的任务。看板任务的 id 在整个 Run 内唯一。

用户可以绕过负责人，直接在协作者的会话里发消息、接管、交还、打断或让它以当前结果结束（无论这时 Agent 是否在跑一轮，结束都记为 `session.interrupted`，`data.finish` 为 `true`）。负责人管着看板，所以这些介入以「[用户介入]」写进它的看板：只告知，不提前唤醒 `wait`，随下一次返回送到，并提醒负责人以用户的意思为准（`user_intervention`）。用户发给负责人自己的消息和负责人会话中的操作不在此列。见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。

<a id="board_push"></a>
### 看板推送

负责人只有调用 `wait` 才读看板，而它可以自己动手做事。它做别的事情时，协作者的提问只能停着等，失败和停滞也没人处理。所以需要负责人处理的消息会直接推送进负责人正在进行的这一轮（`push_board`），设计取舍见 [ADR：需要负责人处理的看板消息推送进负责人的会话](../decisions/20261102-board_push.md)：

- **触发**：写入以下事件时（`needs_lead`）：`question.asked`、`task.failed`、`task.blocked`、没有 `resolved` 的 `task.stalled`、`kind` 为 `blocker` 的 `board.posted`、`task.conflict`、`task.split_requested`、`lead.edited`、`lead.routed`、带痕迹核对问题（`data.traceGaps` 不为空）或独立验证判定为 `rejected` / `inconclusive` 的 `task.succeeded`，以及用户的回答（`ask_user` 问题的回答，或用户在会话中直接回答协作者）。
- **合并**：触发后等 2 秒（`PUSH_SETTLE`），把负责人上次读到之后看板上的全部消息（格式与 `wait` 相同）合成一条，以「[Janus 看板推送]」开头，通过[插话](../interfaces/20261031-acp_integration.md#steering)插入负责人的这一轮，并把游标移到最后一条。推送过的消息不再由 `wait` 返回。
- **条件**：负责人的 Agent 声明了插话、会话正在进行、负责人没有在 `wait` 中，并且负责人在看板上（第一个目标完成前，或交付后正在处理一条消息，见[提问的流转](#question_routing)）。不支持插话的负责人不推送：推送只能排队到这一轮结束，在此期间 `wait` 反而看不到这些消息。推送只插话，插不进去时排队到这一轮结束，不打断负责人。
- **记录**：推送记为 `session.prompt`（`channel: "board"`），负责人会话中显示为「看板推送」；送达和读到的时刻记在 `message.routed`、`message.delivered` 中。

<a id="conflicts"></a>
### 同时改同一个文件

负责人和协作者都直接在这个 Run 的工作目录（Git 仓库上是它自己的 worktree）中工作，并行的任务可能改到同一个文件。Janus 从工具调用中识别改动（`record_edits`）：

- 协作者完成一次 `edit`、`delete` 或 `move` 类型的工具调用时，从 ACP 的 `locations`（没有时取输入中的 `file_path`、`path` 等）得到文件，转成相对工作目录的路径，记在这个任务名下（`tool.call` 的 `data.paths`）。
- 另一个正在执行的任务也改过其中的文件时，写 `task.conflict` 给负责人（`wait` 中的「[冲突]」，并触发看板推送）；双方协作者的 Agent 支持插话时，各收到一条「[Janus 提醒]」，说明对方在改哪些文件、改之前先读最新内容、分工不清时写 blocker。同一对任务的同一个文件只报告一次。
- 其中的文件归另一个可能同时执行的未结束任务负责（`owns` 或认领，见[团队结构](#team_structure)）时，不等对方也改，立即写 `task.conflict`（`data.owned: true`，`wait` 中的「[越界]」）；只有越界的一方收到「[Janus 提醒]」，要求它不再改这些文件，需要时写 blocker。上游或下游任务的文件、已结束任务的文件不算越界。同一个任务对同一个负责方的同一个文件只报告一次。
- 负责人自己的会话完成文件修改工具调用时，同样以类型化的 `Actor::Lead`（与名为 `lead` 的看板任务严格区分）记入痕迹（`record_lead_edits`）：若改到了正在执行的协作者任务 `owns` 负责或正在修改的文件，立即写 `task.conflict`（`data.byLead: true`，`data.other: "lead"`）并向支持插话的协作者发出提醒；若改到了已完成任务的文件，下游交接和 `task_detail` 中标出「负责人 改」。还没开始的任务负责的文件不算冲突：负责人先落盘共享契约再扇出（契约先行）正是这样做的，任务开始后会读到改动。记录来自事件，编排器重启后由 `resume_run` 重建。
- 每个任务改过的文件可以用 `task_detail` 和 `peers` 查看。

<a id="team_structure"></a>
### 团队结构：负责的文件和独立验证

负责人和协作者都直接在同一个工作目录中工作。冲突检测（见上节）只能在两个任务已经改了同一个文件之后报告；独立核对也不能只靠执行者自己的证据。所以编排可以声明两种结构，Janus 在 `orchestrate` 时校验（`teamwork::check`），规则见[校验规则](../interfaces/20261031-board_mcp.md#orchestration_validation)：

- **负责的文件（`owns`）**：任务负责修改的文件或目录。可能同时执行的任务（彼此都不在对方的上游）`owns` 不能重叠，否则整份编排被拒绝，负责人要用依赖串行或重新划分。协作者的任务提示会列出它负责的文件，要求只改这些，需要改别的文件时写 blocker 或提问。Janus 不阻止它改别的文件：权限由 Agent 原生模式决定，改了另一个任务负责的文件会立即报告为「[越界]」，完成时还会在痕迹核对中列出。
- **认领（`claim`）**：协作者开始改 `owns` 以外的文件前，可以自己认领（`teamwork::claim`），写 `task.claimed`，看板上是「[认领]」。认领的文件并入它的 `owns`，到任务结束为止有效：对越界检测、`peers` 和之后的编排校验都和 `owns` 一样。已归另一个可能同时执行的未结束任务负责的文件不能认领，返回负责的任务；验证任务不能认领。设计取舍见 [ADR：协作者认领文件，Janus 读回工作目录里的痕迹](../decisions/20261113-claims_and_traces.md)。
- **拆分提议（`request_split`）**：协作者发现任务横跨多个独立子系统或远超单次尝试可完成的范围时，可用 `request_split` 提交拆分原因、已完成部分和建议子任务列表（`task.split_requested`），由负责人判断是否重新编排或用 `reply` 指示继续；验证任务不能请求拆分。
- **热会话续接（`continues`）**：负责人判断一项**新**工作适合接着同一协作者某个子任务的上下文做时，可声明 `continues` 指向那个子任务；首次尝试在上下文占用不超过 75% 且 Agent 支持 `loadSession` 时直接加载那个子任务的会话，免去重新阅读代码库，否则自动回退新建会话，见 [ADR：热会话续接](../decisions/20261118-session_continuation.md)。会话属于子任务，不属于协作者：同一个协作者可以有多个会话（例如一个做后端、一个做前端），独立领域的工作新开会话。验证没通过后的返工不新建子任务，见下文。
- **独立验证（`verifies`）**：一个任务声明它验证另一个任务。验证者必须是另一个协作者，Janus 自动让它依赖被验证的任务，不能写 `owns` 或 `continues`。它的任务提示附上被验证任务的验收标准、专属 diff 产物路径、实际改动文件、痕迹核对异常、弱证据条目提醒和风险（`teamwork::VerifiedContext`），要求不改文件、不替执行者修问题，读改动、运行测试或复现行为，逐条给出实际执行的命令和输出，并用 `verdict` 给出 `approved`、`rejected` 或 `inconclusive` 判定。
- **验证未通过**：验证者给出具体证据并报 `verdict: "rejected"` / `"inconclusive"`（或 `passed: false`）时，验证任务自身正常完成（`task.succeeded`），不走无意义的自我修复轮，负责人在看板上读到「[验证未通过]」；验证者自身结构不合要求用完修复轮时为「[验证没通过]」。`accept` 对验证任务无效。Janus 不自动返工：负责人判断问题出在哪个子任务，用 `retry` 把它发回原来的执行者（`from` 指向这个验证，`session` 选回到原会话或新开会话），验证意见原样交过去；返工完成后，这个验证在自己的会话中复审，见[重试、返工与失败](20261031-run_lifecycle.md#retry)。换人或另开一项工作时才用 `orchestrate`；旧的下游任务不再需要时，用 `cancel` 取消并写明理由。已完成的验证在复审前保留原判定；判定之前就编排好、依赖验证任务的任务不会开始（`blocked`，见[任务调度](20261031-run_lifecycle.md#scheduling)），复审通过后自动开始。未通过确认或取消的验证任务在交付的 `acceptance.verifications` 里 `passed` 为 `false`，每一个都列为被验证任务的风险，另一个验证任务的通过不会抵消它。

`owns`、`verifies` 和 `continues` 是编排数据（`orchestration.accepted` 的任务字段），认领是 `task.claimed` 事件，拆分提议是 `task.split_requested` 事件，都不增加任务状态，恢复时随任务定义和事件日志一起重建。

<a id="traces"></a>
### 工作目录里的痕迹

协作者都在同一个工作目录中工作，各自做了什么，工作目录里本来就有记录。Janus 把能从工作目录读出来的事实直接读出来，不靠协作者自己汇报；看板只放读不出来的东西：动手前的承诺（`owns`、认领）、意图和裁决。实现在 `traces` 模块：

- **记录**：每个任务改过的文件，和每个文件最后由哪个任务在哪个 `seq` 改的，来自工具调用（见[同时改同一个文件](#conflicts)）。
- **diff 只含自己的文件**：任务完成时保存的 diff 产物限定在它负责和改过的文件（`traces::scope`，路径按字面匹配）。未跟踪的新文件没有 `diff-index` 条目，用 `git diff --no-index /dev/null <文件>` 把内容和新增行记进同一个 diff，文件列表末尾仍列出它们的名字。两样都没有记录（例如只用命令改文件、又没有 `owns`）时才是整个工作目录的 diff，并在说明中写明可能含其他任务的改动；这时工作目录和上一个任务结束时一样就不保存。
- **结果与痕迹对账**：任务完成时，Janus 拿它负责的文件、改过的文件和工作目录相对 `HEAD` 的改动（`git diff-index --name-only HEAD` 加未跟踪文件）对账（`traces::gaps`），不一致的地方写进 `task.succeeded` 的 `data.traceGaps`：验证任务改了文件；改了负责范围以外的文件；负责的文件在工作目录里没有任何改动（不是 Git 仓库时，改为没有改这些文件的工具调用）。没有 `owns` 的任务只核对验证者。带 `traceGaps` 的完成消息在「[完成]」下多一行「痕迹核对」，并触发看板推送；`task_detail` 也列出，交付时每个任务的 `acceptance.traceGaps` 同样保留。负责人用 `retry` 重做或 `amend` 更正结论。
- **可能过期的结论**：任务完成后，它改过的文件又被别的任务改了，它的结论描述的是旧内容。下游任务的提示中，每个上游任务除了结果摘要，还列出它改过的文件和完成后又被谁改过（`context.handoff` 的 `data.files`、`data.stale`），要求以工作目录的现状为准；`task_detail` 和 `peers` 中同样标出。

<a id="collaborator_board"></a>
### 协作者接入看板的条件

协作者的会话在 Agent 于 `initialize` 中声明 `mcpCapabilities.http` 为 `true` 时接入看板工具。Codex 和 Claude Code 都声明支持，它们的协作者总会接入看板；Agent 不声明时不接入，照常执行任务，通过结构化结果和提问回报。

<a id="collaborator_rules"></a>
### 协作者的约定

协作者怎样与 Janus 协作的固定约定（`collaborator_rules`）放在系统层，使用英文，排在用户的长期要求之前，整个会话都有效。

- 结束前逐条验证验收标准，在结果的 `checks` 中写明是否达到、证据和证据方法。
- 直接在工作目录中工作，不 commit、push、部署，不改工作目录之外的文件。Run 在 worktree 中时，任务提示还说明这是一个新的目录：依赖和构建产物要按项目自己的方式准备，改了依赖就重新安装，验收时由 Janus 统一提交。
- 看板工具的用法（接入看板时）。
- 缺少超出授权的决定时，在结果的 `question` 中提问。
- 结构化结果的格式，见[结构化结果](20261031-run_lifecycle.md#structured_result)。

第一条提示（`task_prompt`）只有这一次的任务：目标、共享资料、任务和验收标准、工作目录、上游任务的结果、同时进行的任务、上一次失败的原因，以及团队结构段和用户的留言。会话打开时，约定记为 `session.prompt`（`channel` 为 `system`）。

<a id="decision_ownership"></a>
## 谁来做决定

一次 Run 里有两类决定，处理方式不同：

| 类型 | 例子 | 谁决定 | 应用中 |
| --- | --- | --- | --- |
| 执行中的选择 | 技术选型、实现方式、方案取舍、协作者在任务中的提问、失败任务怎么处理 | 负责人 | 看板「待处理」中标「负责人处理」，不需要用户操作 |
| 影响整个目标的决定 | 需求有多种理解且结果明显不同；需要用户的账号、凭据、付费或外部资源；不可逆或影响工作目录之外的操作 | 用户 | 「需要你处理」卡片，看板「待处理」中标「等你决定」 |

负责人说明写明了这条分界，负责人用 `ask_user` 交出第二类决定，交出后继续做不依赖它的工作。审批和表单请求始终属于用户，见[审批和表单](#user_requests_in_goal_mode)。用户直接回答了协作者的提问时，负责人在 `wait` 中看到「用户已回答」，不再给出不同的答案。负责人要推翻协作者已经给出的结论时，用 `amend` 修订，下游任务以修订为准，避免前后两个结论同时在看板上生效。

<a id="question_routing"></a>
## 提问的流转

1. 协作者在结构化结果中提问，任务停下等待（`question.asked`）。
2. 负责人在 `wait` 中读到 `[提问]`，用 `reply` 回答（`question.answered`，`via: "lead"`）。
3. 回答作为下一轮提示发回协作者原来的会话，协作者继续完成任务。

负责人在场时，提问不打扰用户。以下情况提问转给用户（`question.escalated`，由 `escalate_open_questions` 处理）：

- 负责人不在看板上，而协作者还在等回答：第一个目标完成后负责人空闲、等用户的下一条消息，或负责人会话已经结束（异常中断、Agent 退出）。
- 负责人不在看板上时出现的新提问。

交付后负责人仍在同一个会话中：用户发来消息（包括用 `/goal` 设置新目标）后，负责人处理这条消息的这一轮里重新在看板上，这期间编排的任务提问照常交给它、照常推送；这一轮结束、负责人又空闲时，仍没有回答的提问转给用户（`LeadState::on_duty`）。

只转交仍然有效的提问：任务正在执行、提问之后没有开始新的尝试、还没有被回答或转交过。用户也可以直接在协作者的会话页回答，先到的回答生效，负责人会在看板上收到「用户已回答」。

<a id="user_requests_in_goal_mode"></a>
## 审批和表单

协作者和负责人发出的审批请求（`session/request_permission`）和表单请求（`elicitation/create`）始终交给用户。负责人只能在看板上看到「等用户」，不能代为批准。这是有意的设计：权限决定属于用户。

<a id="failures_in_goal_mode"></a>
## 失败处理

- 验证任务没通过时不能 `accept`，见[团队结构](#team_structure)。
- 委派任务失败（`task.failed`）不会让 Run 停下等用户，应用也不弹出「等你决定」卡片。负责人在 `wait` 中读到 `[失败]` 或 `[没通过验收]`（逐条列出没达到的标准），核对后用 `retry`（选择回到原会话还是新开会话，可改说明和验收标准）、`accept`（结果可以接受）或 `cancel` 处理，也可以自己做。被失败任务阻塞的任务在它处理好后自动继续，不需要重新编排。
- 协作者很久没有动静，或连续重复同一个调用时，负责人在 `wait` 中读到 `[停滞]`（见[停滞检测](20261031-run_lifecycle.md#watchdog)），由负责人判断继续等、用 `reply` 指出问题、`retry` 还是 `cancel`。Janus 不会自动打断它。
- 负责人自己很久没有动静或原地打转时，报告给用户（`lead.stalled`），应用在「需要你处理」中显示「负责人可能卡住了」，用户可以给负责人发消息、打断并接管或者继续等。
- 负责人会话异常结束，且没有任务还在执行时，Run 失败。「从中断处继续」会恢复看板上的任务并重启负责人，见 [Run 生命周期](20261031-run_lifecycle.md#recovery)。

<a id="delivery_in_goal_mode"></a>
## 交付

负责人的目标结束、没有任务还在执行或可以启动时，Run 交付：

- 摘要取负责人最后一条 `agent.message`，去掉末尾的 JSON 块和共享资料建议一节，最长 2000 个字符，后面附上改动在哪里：非 Git 目录是「改动直接在工作目录中，Janus 没有提交」；worktree 中的 Run 说明改动在它的 worktree 里还没有提交，验收时 Janus 提交到 `janus/<run>` 分支。
- 共享资料建议一节的条目单独放在 `briefSuggestions` 中，由用户决定是否写入工作区，见[工作区共享资料](20261031-agents_and_roles.md#workspace_brief)。
- 证据和风险从看板上各任务的结构化结果汇总：`evidence` 保留每个任务的全部证据（不再只取第一条），`acceptance` 按任务给出验收标准总数、通过数、证据方法计数、逐条 `checks`、没说明/推理判断/未核实提醒、独立验证的结论（`verifications`）、改了文件却没有独立验证（`unverified`，只陈述事实，不说「未经确认」：负责人可能自己核对过）、痕迹核对（`traceGaps`）和这个任务的风险，见[证据方法](../interfaces/20261031-events.md#evidence_methods)。独立验证没有通过、被取消或没有执行时，被验证的任务多一条「结论没有得到确认」的风险；失败、已取消、被负责人取消、因依赖失败没有执行的任务也列为风险。
- 负责人的说明要求：交付前每个改了文件的子任务都要核对过，可以是它安排的独立验证，也可以是它自己的检查；对标了 `unverified` 的子任务，交付摘要要写明它是怎么核对的（跑了什么、读了什么、看到了什么）。Janus 不记录负责人自己的核对，用户对照摘要判断，见 [ADR：负责人派出子任务后只做管理](../decisions/20261119-lead_manages_after_delegating.md)。
- 负责人会话异常结束时不交付，Run 失败，见[失败处理](#failures_in_goal_mode)。
- 交付后负责人会话保持打开，成为常规对话：用户可以直接写下一轮任务，或用 `/goal` 设置新的目标。再次完成目标时再次交付。负责人处理消息期间编排的任务，提问和看板推送与第一个目标相同，见[提问的流转](#question_routing)。服务重启后，第一次发消息会重新打开会话并带上简要上下文。

设计取舍见 [ADR：负责人以 /goal 推进目标](../decisions/20261031-goal_mode_lead.md) 和 [ADR：通过 MCP 看板协作](../decisions/20261031-board_over_mcp.md)。
