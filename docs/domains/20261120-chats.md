# 对话

本文说明「对话」：用户选一名数字员工，把它当作单个 Agent 直接交互。对话是 `kind` 为 `chat` 的 Run，会话、消息、请求和用量的规则都沿用 Run 的那一套，本文只写它与目标 Run 不同的地方。设计取舍见 [ADR：和一名数字员工的对话是一种 Run](../decisions/20261120-chats_as_runs.md)。

<a id="chat_model"></a>
## 对话是什么

| 方面 | 目标 Run | 对话 |
| --- | --- | --- |
| 类型（`runs.kind`） | `goal` | `chat` |
| 团队 | 工作区的负责人和协作者 | 选中的一名数字员工，成员 id 是主会话固定的 `lead`；不要求开启「可以担任负责人」，只要绑定了 Agent |
| 工作目录 | 工作区目录或它的 worktree（`work/runs/<run id>`） | 新建的 `<Janus home>/work/chats/<run id>`，创建时为空 |
| 看板、编排、交付、验收 | 有 | 没有 |
| 开始 | 目标作为 `/goal` 发给负责人 | 会话立即打开，注入系统层后等用户先说 |
| 标题（`runs.goal`） | 目标 | 第一条消息；之前为空，应用显示「和 … 的新对话」 |
| 列表 | `GET /api/runs`、工作区的任务记录 | `GET /api/runs?kind=chat`、应用的「对话」页 |

`App::create_chat`（`backend/src/orchestrator/chat.rs`）依次执行：

1. 数字员工必须存在并绑定了 Agent，Agent 的运行环境完整（`spec_for`）。任何一项不满足都返回错误，不创建任何东西。
2. 把数字员工做成成员快照（`role_member`，和工作区团队共用）：Agent、模型、推理强度、会话控制项、指令，以及当时的整个资源库。Skill 复制到成员的资源包，和目标 Run 一样。
3. 新建工作目录，写入 Run（`kind` 为 `chat`，`goal` 为空，快照只有 `team`），记录 `run.created`（`data.kind` 为 `chat`，`data.role` 是数字员工的 id 和名字）。
4. 立即通过 ACP 启动 Agent、打开会话（见下节），注入系统层，然后记一条 `agent.status`（`turn` 为 `idle`）等用户先说。会话还在打开时发来的消息先留着，会话打开后作为第一轮发出（`message.routed`，`delivery` 为 `prompt`）。
5. 用户发出的第一条消息成为对话的标题（`title_chat` 写入 `runs.goal`；只附了图片时记为「看看这些图片」），之后的消息不再改它。

对话的数字员工经 MCP 路由和 Skill 路由拿到资源库，和目标 Run 的成员一样。它的令牌只对 MCP 路由有效：看板端点（`/mcp/{run}/{token}/lead`）见到对话一律拒绝，所以它不能编排任务，也不能冒充负责人。

<a id="chat_session"></a>
## 会话

对话的会话由 `lead_conversation` 运行，和交付后负责人的对话是同一个循环（`backend/src/orchestrator/lead.rs`）。与负责人不同的是：

- **系统层**：只有数字员工自己的指令，即用户的长期要求（Agent 设置里的自定义提示词和数字员工的指令），和其他会话的注入方式相同，见 [ACP 集成](../interfaces/20261031-acp_integration.md#standing_instructions)。Janus 的协作说明（团队、看板、负责人怎么派工、怎么验证）只给 Agent Team，对话里不注入；资源库的 Skill 和其他会话一样由 Agent 从资源包里自己加载 `janus-skills`，系统层不提它（见 [Skill 路由](20261116-resource_library.md#skill_router)）。重新打开时，能 `session/load` 就原样交回原会话打开时的系统层（`recorded_system`），之前的对话本来就在会话里，不再注入任何东西，也不记新的 `session.prompt`，见[恢复会话时的系统层](../interfaces/20261031-acp_integration.md#reload_system_layer)。唯一的例外：会话没法 `session/load`、要新开时，系统层带上最近 12 条对话，让它接着之前的话说（`chat_brief`，按 Run 的语言写中文或英文）；还没送到 Agent 的消息不算在内，它是新会话的第一条提示，不重复交给 Agent（`recent_exchanges`）。这段对话记成 `channel` 为 `history` 的 `session.prompt`，会话页标为「之前的对话」，和「数字员工的指令」分开显示。
- **没有看板和交付**：不接看板 MCP，不推送看板消息，一轮结束不交付。每一轮结束后记一条 `agent.status`（`turn` 为 `idle`），表示在等下一条消息；这是对话的常态，不进「待处理」，也不进收件箱。
- **斜杠命令照常**：消息原样发给 Agent，`/goal` 这类 Agent 自己的命令照常生效，目标状态照常跟随，但不会交付。
- **状态**：会话打开后 Run 是 `running`。服务重启时和其他 Run 一样记为 `interrupted`；会话异常结束（例如 Agent 进程退出、打不开会话）时记一条 `run.failed`，状态是 `failed`。会话闲置 10 分钟或座位不够时会被关掉 Agent 进程（`session.parked`，见 [Agent 进程的上限与闲置回收](20261031-run_lifecycle.md#agent_seats)），同样记为 `interrupted`。这几种状态下，用户发出的下一条消息会重新打开会话（`resume_run` 对对话总是按对话恢复，只有 `cancelled` 不能继续）：能 `session/load` 就恢复原会话，否则新开会话并带上最近的对话。应用不显示「从中断处继续」。
- **会话中的操作**：插话、排队、停止这一轮、切换模型和模式、审批和表单、图片、`@` 文件引用，都和负责人的会话相同，见[用户操作](20261031-run_lifecycle.md#user_actions)。对话没有接管：停止这一轮（`interrupt`）只取消这一轮，记为「停止 … 这一轮」，会话接着等下一条消息，不转为人工接管。对话里 Agent 的审批和表单出现在收件箱里。
- **删除**：对话的会话打开时也可以删除，不需要先停止。删除时先停止写入事件，再关闭会话（还在打开的会话看到删除标记后自己停下，不再建日志；资源库服务器不再启动），等正在建的日志文件建完（`Run.files`），然后删除它在 `data/chats/<run>/`（资源包、附件）、`work/chats/<run>/`、`logs/chats/<run>/` 下的一切、Agent 自己留下的会话记录和数据库中的记录。对话和任务只在目录上分开，数据模型、接口和会话循环都是同一套，见 [HTTP API](../interfaces/20261031-http_api.md#run_delete)。

<a id="chat_app"></a>
## 应用

- **侧栏**：收件箱下面依次是「团队」（所有工作区，任务记录在各自的首页）和「对话」两组，在同一个滚动区里。「对话」标题旁的「+」新建对话（也可以用菜单「文件 › 新对话」⌥⌘N 或菜单栏图标菜单的「新对话」），下面每个对话一行，和工作区的样式相同：数字员工名字首字的描边小方块、标题（第一条消息，之前是「和 … 的新对话」），会话开着时行尾一个绿色小圆点，有事等你处理时是数量；数字员工、状态和时间在悬停提示里。所有对话都能列出：按页读取（`RunPager`，见 [HTTP API](../interfaces/20261031-http_api.md#run_list)），滚动到最后一个时读下一页；右键可以删除。
- **新建对话**（`ChatsView`，`UI/ChatsView.swift`）：版式和工作区首页一致：顶部是「新对话」标题和一句说明，下面是数字员工卡片，和「设置 › 数字员工」一样按分组排列、每组标出组名（只有一个分组时不标），一行两张（名字、最多三行职责；选中的卡片描边并略带底色；没有绑定 Agent 或 Agent 没有测试通过的不能选，写出原因），卡片右下方是「和 … 开始对话」按钮（↩），左边提示可以双击卡片直接开始。点卡片选中，点按钮开始；双击卡片直接开始。开始后立即打开会话并进入对话，没有输入框，也不显示 Agent、模型和权限。上次选的数字员工记在本机（`janus.chatRole`），它不能运行时选第一个能运行的。
- **一个对话**：打开对话和打开 Run 一样（`Screen.run`），`RunView` 看到 `kind` 为 `chat` 时显示 `ChatView`：上面是数字员工的头像、名字、Agent、模型和权限模式，右侧是工作目录（点按在 Finder 中显示），下面是和工作台负责人对话同一个会话卡片（`ChatCard`）。没有工作台、审计和团队页签，工具栏只有文档、导出事件日志和删除对话。
- **输入框**（`chatSession`）：会话在等消息（包括刚开始、会话还在打开）时只有「发送」；数字员工正在处理时显示「正在处理」，按钮只有「停止这一轮」（⌘.）和「插话」，没有接管；有的模型会先长时间思考、没有任何输出，标题旁的「N 秒没有新输出」说明它仍在工作。会话已关闭时写「发送后重新打开和 … 的会话」，发送即重新打开。对话中用户发出的消息就是这一轮的提示，不再重复显示「继续提示」。
- **状态推导**：`run.created` 带 `kind: chat` 时 `RunInfo.chat` 为真；对话的会话打开（带 `session` 的 `agent.status`）时状态回到 `running`；对话的数字员工不显示为负责人，头像和颜色取它的角色。
