# 团队记忆

本文说明工作区的团队记忆：工作区里各个 Run 的 Agent 记下、之后的 Run 读到的笔记，以及负责人定期整理它们。它在共享资料下面一层：共享资料是用户写的、必须遵守的规则，团队记忆是 Agent 写的、可以被推翻的笔记。设计取舍见 [ADR：工作区的团队记忆由 Agent 写、记来源、定期整理](../decisions/20261123-team_memory.md)。

<a id="memory_model"></a>
## 笔记是什么

| 方面 | 说明 |
| --- | --- |
| 存在哪里 | SQLite 的 `memories` 表（数据版本 22），一个工作区一组；删除工作区时一并删掉 |
| 一条笔记 | `id`、`workspace`、`kind`、`title`（最多 80 个字符）、`hook`（索引里那一行，最多 150 个字符）、`body`（最多 4000 个字符）、`created_at`、`updated_at` |
| 类型（`MemoryKind`） | `fact`（事情是怎样的）、`decision`（选了什么、为什么）、`pitfall`（踩过的坑和怎么避开）、`howto`（怎么做一件事）；界面上叫事实、决定、坑、做法 |
| 来源 | 最后一次写它的是谁：`run_id`（哪个 Run）、`who`（成员 id，用户改的是 `user`、没有 Run）、`author`（成员的名字，用户是「你」）。读出时带上那个 Run 的目标和状态（`runGoal`、`runStatus`） |
| 上限 | 一个工作区最多 300 条（`NOTES_MAX`），满了只能更新已有的，或等整理 |

笔记和 Run 一样不跨工作区：会话只能读写自己 Run 所属工作区的笔记，别的工作区的 id 当作不存在。对话（`kind` 为 `chat`）不属于工作区，没有团队记忆。

实现在 `backend/src/orchestrator/memory.rs`（规则、工具、注入、整理）和 `backend/src/db/memories.rs`（存储）。

<a id="memory_write"></a>
## 写笔记

目标 Run 的负责人和每个协作者、值班的会话都能用 `janus.remember` 写一条笔记，或带 `id` 更新一条已有的；用法见[看板 MCP 工具：团队记忆的工具](../interfaces/20261031-board_mcp.md#memory_tools)。写入立即生效，之后打开的会话就能读到；在 Run 里记一条 `memory.saved`（`id`、`title`、`kind`、`created`），全局事件流发 `memory` 通知。

- **写什么**：注入的说明要求只写之后的 Run 还得重新弄清、又不能从代码直接看出的事（怎么构建、运行、测试；一个坑和怎么避开；为什么这样做；东西在哪），一个主题一条，已有那个主题的笔记就更新它，不新增近似的一条。仓库里已经写着的、只和这次任务有关的不写。
- **外部内容只留指针**：issue、网页、工具输出这类外部来的文字不抄进笔记，最多留链接。
- **不保存凭据**：标题、摘要或正文里像凭据的内容（私钥头、`sk-`、`ghp_`、`github_pat_`、`xoxb-`、`AKIA` 等）直接拒绝（`looks_secret`），Janus 的数据库不存凭据。
- **不能删**：只有整理会话有 `forget`；负责人和协作者调用它得到「没有这个工具」。用户可以在应用里删。

<a id="memory_read"></a>
## 读笔记

工作区的每个会话打开时，系统层在共享资料之后附上团队记忆一节（`memory_section`）：怎么用这些笔记，以及笔记的索引，每条一行（`id · 类型 · 标题 — 摘要`），按最近修改排序，最多 200 行（`INDEX_MAX`），更多的写明数量、请它用 `janus.recall` 搜。负责人的目标会话、交付后的对话、协作者每个任务的会话和值班的会话都有这一节；整理会话的那一节是全部笔记的索引。

- **是笔记，不是规则**：说明写明共享资料、本次目标和用户的话优先；笔记可能过时，用之前先对照代码。要团队必须遵守的事，由用户加进共享资料。
- **按需读全文**：索引只有一行，正文用 `janus.recall` 按 `id` 读，或按词搜（每个词都要出现在标题、摘要或正文里，最多 10 条）。
- **被取消的 Run 写的笔记不给之后的 Run**：`runStatus` 为 `cancelled` 的笔记不进索引、也搜不到；整理时它们标着「来自被取消的 Run」，没有之后的 Run 证实就删掉。
- **索引是打开会话那一刻的**：会话进行中别人新写的笔记不会出现在它的系统层里，但 `recall` 读得到。

<a id="dream"></a>
## 整理

整理是工作区负责人的一个会话，只做一轮：合并同一主题的笔记、改正被后来的 Run 推翻的、删掉过时或没用的、把相对日期改成绝对日期、让索引保持一行一条。它是 `kind` 为 `dream` 的 Run（应用里叫「整理团队记忆」），只有负责人一名成员，在 Janus home 里自己的空目录（`work/dreams/<run>`）中，不在工作区目录里，所以不改工作区的文件。

- **何时开始**：一个目标 Run 交付时（`run_delivered`），同一工作区自上次整理开始以来交付或验收的目标 Run 有 5 个以上（`DREAM_AFTER_RUNS`），上次整理在 24 小时以前（`DREAM_EVERY_MS`），没有正在进行的整理，而且有笔记，就自动开始；用户也可以在工作区页点「现在整理」（`POST /api/workspaces/{id}/memories/consolidate`）。同一工作区同时只有一次整理，再请求返回 409；没有笔记时返回 400。
- **它知道什么**：系统层（`dream_brief`）是整理的做法和全部笔记的索引；开始的提示（来自 `janus`）列出上次整理以来交付的 Run：id、日期、目标和交付摘要。
- **它能做什么**：`janus` 端点见到 `kind` 为 `dream` 的 Run 时只给 `recall`、`remember` 和 `forget` 三个工具，看板和值班的工具都没有。`forget` 必须写原因，记一条 `memory.forgotten`（`id`、`title`、`reason`）。
- **一轮结束**：这一轮结束时（`dream_turn_ended`）记一条 `memory.consolidated`：`saved`、`forgotten` 是这一轮改写和删除的条数，`summary` 是最后一条消息的第一行；Run 改为已交付，会话关闭，不能继续对话，要再整理就重新开始一次。会话中途断了时 Run 为失败，已经改的笔记保留。

<a id="memory_review"></a>
## 用户怎么看、怎么改

- **工作区页**：右栏共享资料下面是「团队记忆」卡片，每条笔记一行（类型、标题，悬停看摘要和谁在哪个 Run 里写的），默认 5 条，可以展开全部；标题旁的「?」说明团队记忆怎么工作；有笔记时右上角有「现在整理」，正在整理时是「整理中」（点开是整理页），有过整理时底部显示「上次整理：<时刻>」。界面细节见 [macOS 应用：团队记忆](../architecture/20261031-frontend.md#team_memory)。
- **改一条**：点开一条笔记可以改类型、标题、摘要和正文（`PUT /api/memories/{id}`），改过的笔记来源变成「你」；也可以删除（`DELETE /api/memories/{id}`）。
- **加入共享资料**：笔记表单里的「加入共享资料…」把这条笔记作为一行（`标题：正文`）加进共享资料的表单，用户保存后它就成了每个 Run 都要遵守的规则，见[工作区共享资料](20261031-agents_and_roles.md#workspace_brief)。
- **整理的结果**：整理交付后收件箱出现「团队记忆整理好了」，打开是整理页：改了几条、删了几条、它的总结，以及这一轮的全部工具调用；看过后标记为已处理。没完成的整理显示「团队记忆没整理完」。

<a id="native_memory"></a>
## Agent 自带的记忆

Claude Code 有自己的 auto memory，按工作目录分别保存；Janus 里每个 Run 在自己的 worktree、每个对话在自己的新目录，这些记忆在下一个 Run 里读不到，还会把同一工作区的知识分散到很多目录。所以 Janus 启动 Claude Code 时设置 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`（只在启动环境里，不写它的配置文件），团队的知识只放在团队记忆里。Codex 的 memories 默认关闭，Janus 不打开它。
