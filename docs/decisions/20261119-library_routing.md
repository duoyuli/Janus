# ADR：资源库默认给所有数字员工，经 MCP 路由和 Skill 路由提供

- 状态：已采纳（accepted），记录于 2026-11-19；同日按逻辑推导修订第 3、5 条和取舍（见文末「修订记录」）。
- 修订：[ADR：资源库统一管理 Skill 和 MCP，在会话启动时注入](20261116-launch_time_resources.md) 中「角色选择资源、Run 创建时固定、会话启动时逐项注入」的部分：现在只有收口的资源这样注入，其余经路由提供。会话启动时注入、不写 Agent 配置文件的原则不变。
- 相关文档：[资源库](../domains/20261116-resource_library.md)、[Agent、角色与工作区](../domains/20261031-agents_and_roles.md)、[安全边界](../operations/20261031-security.md#library)、[研究：magpie 的资源库](../research/20261116-magpie_library.md)、[研究：动态数字员工与资源装配](../research/20261117-dynamic_digital_workers.md)。

## 背景

此前数字员工的能力由角色勾选的 Skill 和 MCP 决定：缺一种能力，就要建一个专门的数字员工，或者在 Run 开始前改角色。2026-11-19 讨论下一阶段的「能力动态路由」时，用户参考了 [yetone/magpie](https://github.com/yetone/magpie) 的两个开关：MCP 路由（每个 Agent 只拿到一个服务器，背后的服务器由 magpie 代为运行，工具多时按需查找）和 Skill 路由（每个 Agent 只拿到一个 Skill，它列出背后的 Skill 和路径，按需读取）。magpie 路由的是勾选给某个 Agent 的资源；用户的方向更进一步：每个数字员工默认能用整个资源库，团队里只需要一个通用的数字员工。

## 决策

1. **默认给所有人，个别收口**：资源库里的每个资源有一个属性：给所有数字员工，或者只给选中它的数字员工（收口）。默认 Skill 给所有人、MCP 收口，用户在资源库里放开某个 MCP。不考虑旧数据的过渡：升级时每个资源按这个默认值填写，角色原来的选择不保留。
2. **收口的资源照旧直接注入**：角色编辑器的「资源」只用来选收口的资源；选中的收口资源像以前一样在 Run 创建时固定、在会话启动时注入（Skill 进资源包，MCP 进 `mcpServers`）。
3. **MCP 路由**：Janus 在自己的 HTTP 服务上为每个 Run 提供一个 MCP 端点，令牌和 `who` 的规则与看板相同。每个会话拿到这一个端点，代替逐个注入给所有人的 stdio 服务器。（实现时修订：路由只接命令启动的 stdio 服务器；http、sse 服务器不在本机起进程，路由省不下什么，还要给 Janus 加 HTTP 客户端，所以给所有人的 http、sse 服务器照旧直接注入每个会话。）背后的服务器**每个会话一份**：同一个 Run 里负责人和每个子任务（`who`）各有自己的进程，和服务器直接交给 Agent 时一样互不干扰。会话打开时就在后台启动，工作目录是这个 Run 的工作目录（Git 仓库上是它的 worktree），环境和 Agent 一样隔离；列工具有时间上限，没就绪的服务器先不列出，继续在后台启动。服务器跟着会话：会话关闭、Run 停止、取消或失败时按进程组结束，服务器派生的子进程一起结束。工具名要放进模型的工具名长度上限：算上 Agent 加的前缀，过长或清理过字符的名字截短并带上哈希，调用时按完整名字查找。Claude Code 和 Codex 自己会按需搜索 MCP 工具，所以路由列出完整的工具列表；`initialize` 的说明列出背后有哪些服务器、各自做什么。每次调用记一条事件：调用者、子任务、服务器、工具、耗时和错误，不记参数。
4. **Skill 路由按数量切换**：给所有人的 Skill 不超过 10 个时，照旧全部放进资源包直接注入；超过 10 个时，资源包里只放一个 `janus-skills`，它的 `SKILL.md` 列出每个 Skill 的描述和文件路径，Agent 判断用得上时再读对应的 `SKILL.md`。
5. **负责人也拿到两个路由**：它可以自己完成小目标；派出子任务后，资源库里的工具只用来查看（读、查询、检查），有副作用的操作交给子任务。Janus 不拦截，但派出子任务后负责人每调用一个新的路由工具，看板上记一条提醒，交付时列为风险，和「派出后改了文件」同样处理：Janus 判断不了一次调用有没有副作用，所以只记事实，由负责人和用户判断。
6. **自定义命令的 Agent**：声明了 HTTP MCP 能力的，和 Claude Code、Codex 一样拿到 MCP 路由；没有声明的，给所有人的服务器逐个注入。自定义命令没有 Skill 入口，拿不到 Skill。（实现时修订：原来写的是自定义命令一律不变，但路由只看 Agent 是否支持 HTTP MCP，没必要按 Agent 类型区分。）
7. **通用数字员工**：新增一个默认数字员工「通用数字员工」；新建工作区的预设改为负责人加通用员工（3 个实例），前提是通用员工已经绑定 Agent。（实现时修订：原来还写了「首次启动创建的默认工作区」，但 Janus 首次启动不创建工作区，只有新建工作区的预设。）研究员、产品经理、研发工程师、质量工程师保留，需要时加进工作区。

## 取舍

- **默认全开而不是逐项勾选**：一个通用员工就能处理各种子任务，不需要为了一种工具加人或改角色；代价是工具人人可用，所以给有副作用的 MCP 留了收口，并且 MCP 默认收口。
- **每个会话一套后端，而不是每个 Run 或全服务共用**：依赖项目目录的 stdio 服务器在每个 Run 的 worktree 里才对；浏览器、终端、数据库连接这类有状态的服务器，两个会话共用一个进程会互相干扰，而服务器直接交给 Agent 时本来就是每个会话一份。进程数和以前一样，换来不会用错目录、也不会串状态。
- **不做 Janus 自己的工具搜索**：Claude Code 和 Codex 自带工具搜索；magpie 的 `find_tools` / `call_tool` 是给没有工具搜索的 Agent 的，Janus 只支持这两个内置 Agent。
- **Skill 按数量切换**：少量 Skill 直接注入，体验最好，也能在 Agent 原生的 `/` 菜单里点名；多了才用一条描述代替全部，省提示词。
- **只提醒、不拦截负责人对工具的使用**：一个 MCP 调用有没有副作用 Janus 判断不了，拦截会误伤查看类的调用；但不留痕会让「派出后只做管理」失去依据，所以和改文件一样记在看板上。

## 后果

- 资源（`Item`）增加「给谁」的字段，数据迁移按默认值填写；资源库界面突出「给所有数字员工」和两个路由，角色编辑器的「资源」只列收口资源。
- 有凭据的 MCP 服务器改由 Janus 进程启动（工作目录是 Run 的工作目录），不再由 Agent 进程启动。环境和 Agent 一样隔离：每个资源一个隔离目录，只加上资源保存的值，不继承 Janus 进程的环境和用户的主目录（实现时修订：最初的实现直接继承了 Janus 进程的环境）；值仍只在启动时从 `secrets/library/` 读取，不进快照和事件。这扩大了 Janus 进程本身运行的第三方代码范围，安全文档的「资源库」一节相应更新。
- Skill 路由让 Agent 读取 Janus 目录下资源包里的文件；默认的权限模式不需要确认，严格的权限模式会询问。
- 负责人说明增加「派出后资源库工具只用来查看」；负责人只看到协作者的名字和职责这一点不变（所有员工能力相同）。

## 修订记录

2026-11-19，实现后按原有流程（创建 Run、打开会话、子任务执行、负责人派出后、停止、交付）逐步推导，修订如下：

- 第 3 条：后端从「同一个 Run 共用」改为每个会话一份；会话打开时预先启动，列工具有时间上限；服务器跟着会话结束（会话关闭、Run 停止、取消、失败），按进程组结束；工具名限长并带哈希。原因：共用进程会让有状态的服务器在会话之间串状态；按需启动在第一次下载包时会超过 Agent 等待 MCP 的时间；不按进程组结束会留下 `npx` 派生的孤儿进程；最初按「闲置 10 分钟」停止，推导后发现它会在会话中途停掉浏览器这类有状态的服务器，而服务器交给 Agent 时本来就活到会话结束，所以改为跟着会话。
- 第 5 条：从「不加检测」改为看板提醒。原因：路由工具写的文件不在 Agent 上报的编辑里，负责人派出后经路由做的修改原本完全看不到。
- 资源包里的 Skill 要用文件系统的克隆复制：给所有人的 Skill 每个成员一份，普通复制会让每个 Run 的磁盘占用随成员数成倍增长。实现时核实，Rust 的 `fs::copy` 在 APFS 上已经用 `fclonefileat` 克隆（20 份 1 GiB 的复制用时 8 毫秒、不占磁盘），不需要改代码。
- 命令启动的 MCP 服务器在资源库里新建、修改或导入时预先启动一次（可以慢，最多 10 分钟），让 `npx`、`uvx` 下载的包落在它的隔离目录里，Run 里的启动就能在 Agent 给的时间内完成，列工具的 8 秒上限因此够用；准备结果显示在资源库，启动不了的配置当场可见。
- 删除资源时从各数字员工的选择里一并去掉，并先停掉各 Run 里它的服务器；修改资源的值时停掉正在运行的服务器，下次用到时带着新值启动。
- 已知限制，不改行为：经 MCP 工具写的文件不在 Agent 上报的编辑里，文件认领、越界提醒和交付痕迹看不到它们；验证子任务也能用所有给所有人的 MCP，「只检查不改文件」靠指令和 Agent 的权限模式保证。
