# ADR：Agent 进程按座位限量，闲着的会话关掉进程

- 状态：已采纳（accepted），记录于 2026-11-22。
- 相关文档：[Run 生命周期：Agent 进程的上限与闲置回收](../domains/20261031-run_lifecycle.md#agent_seats)、[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)、[配置](../interfaces/20261031-configuration.md#settings)、[对话](../domains/20261120-chats.md)、[值班](../domains/20261121-loops.md)。

## 背景

每个 ACP 会话是一对常驻进程：适配器和 Agent。实测一个闲着的 Codex 会话约占 250 MB 内存（适配器约 89 MB，Codex 约 166 MB），Claude Code 在同一量级。已有的两道上限只管「同时做多少事」：`max_running_runs` 限制在做的目标 Run（默认 8），`max_concurrent_attempts` 限制单个 Run 里的协作者（默认 3）。没有管到的：

- 闲着的会话从不关：已交付、已验收的目标 Run 的负责人，每个打开过的对话，两次开工之间的值班，都一直开着，直到服务重启、取消或手动停止。预览环境里一个值班摸鱼 1 小时 44 分钟，进程一直在。
- 对话和值班不计入任何上限。
- 没有全局总数：8 个目标 Run 同时在做时，最坏是 8 个负责人加 24 个协作者，再叠加闲着的会话。

## 决策

1. **闲置回收**：会话一轮结束后闲着超过 10 分钟（`IDLE_AFTER`），且 Run 里没有别的事需要它时，关掉它的 Agent 进程。适用于对话、两次开工之间的值班、目标已完成且没有任务在跑的目标 Run 的负责人；目标还在做、这一轮没结束、人工接管中的都不关。下一条消息或开工用已有的恢复路径重新打开，能加载原会话就加载。
2. **全局座位**：所有 ACP 进程共用一组座位，默认 12 个（`JANUS_MAX_AGENT_SESSIONS` / `max_agent_sessions`，1 到 64），实际不少于 `max_running_runs + 1`。座位由进程持有，进程被关掉或释放时还回，没有哪条路径会漏还。
3. **满了时**：先请闲得最久的可关会话让出，新会话等空位并写明在等；空出的座位先给你在等的，再给按时间表来的，最后给协作者，同一类按先后。谁在等由会话本身决定：协作者的会话算协作者，负责人的会话算它所在的这次打开（对话和你的消息算你在等，排到的目标和值班按时开工算时间表）。
4. 关掉的对话和值班会话记为 `interrupted`（和服务重启后一样，界面显示已关闭），目标 Run 状态不变；记一条 `session.parked` 说明原因。

## 取舍

- **与按内存自动算上限相比**：固定数加配置项简单可预期，用户可以自己调；不同 Agent 的占用差别大，按内存推算也只是估计。
- **与只做闲置回收相比**：回收只处理闲着的进程，十几个对话或值班同时在一轮里时仍没有上限；座位兜底。
- **与只做座位相比**：只限量不回收，闲着的会话会把座位占满，正在干活的反而要等。
- **代价**：关掉后再发消息要多等几秒启动；加载不了原会话的 Agent 带上之前的对话新开会话。暂停中的目标 Run 的负责人仍占着座位，暂停的多了，协作者可能要等到你继续或停止它们。

## 后果

- 新增 `seats.rs` 和 `orchestrator/parking.rs`；`AgentPhase` 多一个 `waiting_for_seat`，事件多一种 `session.parked`。
- 不改存储的数据，不需要迁移。
