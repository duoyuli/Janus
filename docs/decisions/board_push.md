# ADR：需要负责人处理的看板消息推送进负责人的会话

- 状态：已采纳（accepted），记录于 2026-11-02。补充 [ADR：通过 MCP 看板协作](board_over_mcp.md) 中「长轮询与推送相比」的取舍，不取代它。
- 相关文档：[目标模式与共享看板](../domains/goal_mode.md#board_push)、[看板 MCP 工具](../interfaces/board_mcp.md#wait)、[ACP 集成](../interfaces/acp_integration.md#steering)、[ACP 适配器管理](../architecture/adapters.md#catalog)。

## 背景

用户把 Janus 定位为「一次完成一个复杂目标的 Agent 团队」，并对照 DeepSeek Harness 团队的 Super-agent 架构文章讨论了改进方向。文章指出：主会话只能按轮次推进时，正在执行长操作的主会话看不到新事件；把耗时操作改成异步、把事件作为新消息推回会话，才能让交互不被阻塞。

Janus 的负责人只有调用 `janus.wait` 时才读看板。负责人允许自己动手做事，它在跑测试、改代码的时候，协作者的提问只能停着等，失败和停滞也没人处理；而一个复杂目标里的任务耦合紧密，一个提问没人回答，卡住的往往是整条依赖链。

同时，用户发现会话里的「插话」很慢：消息要等这一轮结束才送达，数据库中有一条发给负责人的消息等了约 5 分钟。原因是当时使用的 Codex 和 Claude Code 适配器版本太旧，没有插话能力。

## 决策

1. Codex 和 Claude Code 的适配器改用支持插话的版本（现在为官方 npm 包，见[适配器清单](../architecture/adapters.md#catalog)）。
2. 看板上出现需要负责人处理的事件（协作者的提问、任务失败、无法开始、停滞、阻塞、两个任务改了同一个文件或越界、结果和工作目录对不上、用户的回答）时，Janus 等 2 秒收集同一批事件，然后把负责人上次读到之后的全部看板消息作为一条消息插入负责人正在进行的这一轮，并把它们算作已读。
3. 只推送给支持插话的负责人。负责人正在 `wait` 时不推送，`wait` 会把同样的消息交给它。
4. `wait` 保留，作为负责人没事可做时等待进展的方式。

## 取舍

- **与只用长轮询相比**：负责人做别的事情时也能及时处理会卡住别人的事；代价是推送会打断负责人的思路，负责人说明要求它先处理会卡住别人的事，再回到手上的工作。
- **只推送给支持插话的负责人**：不支持插话时，推送只能排队到这一轮结束，而推送已经把这些消息算作已读，负责人在这期间调用 `wait` 反而看不到它们。所以这种负责人保持只靠 `wait`。
- **不打断负责人**：推送只用插话，不像负责人回复协作者那样在插不进去时打断这一轮。负责人的这一轮通常就是整个目标，打断的代价太大。
- **适配器来源（2026-11-15 前的做法）**：当时为插话从仓库构建适配器，比从 npm 安装慢，需要开发依赖和构建步骤；适配器后来改为官方 npm 包，见 [ADR：使用官方 ACP 适配器](official_acp_adapters.md)。

## 后果

- 负责人说明中写明推送的格式和含义；推送记为 `session.prompt`（`channel: "board"`），在负责人会话中显示为「看板推送」。
- 同一机制也用于给协作者发冲突提醒（只发给支持插话的协作者）。
- 新增或修改需要负责人处理的事件类型时，同时决定它是否触发推送（`needs_lead`）。
- 2026-11-02 用真实的 Codex 负责人和 DeepSeek over Claude Code 协作者验证：协作者写回阻塞 2 秒后推送进正在执行 `sleep 90` 的负责人会话；用户插话 Codex 立即读到，Claude Code 在当前工具调用结束后约 4 秒读到。
- 2026-11-15：适配器改为官方 npm 包，插话改用 `_session/steering`，见 [ADR：使用官方 ACP 适配器](official_acp_adapters.md)。本决策的推送规则不变。
