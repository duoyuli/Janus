# ADR：交付时把结果合并回分支

- 状态：已采纳（accepted），记录于 2026-11-23。
- 部分取代：[ADR：验收时把结果合并回任务开始时的分支](20261120-merge_back_on_accept.md) 中合并的时机：结果在每次交付时带回，验收只在交付没能带回时再合并；合并的做法（提交、变基到最新的分支、只快进、关掉钩子、什么情况下不动）不变。
- 修订：[ADR：验收冲突交给负责人解决](20261123-lead_resolves_accept_conflicts.md)：交付时的冲突同样交给负责人，同一个冲突只自动交一次，命令改为 `git rebase <分支现在的提交>`，没做完的变基、合并也交给负责人；[ADR：用户要求时 Agent 提交、推送和部署](20261123-commit_push_on_request.md) 的第 4 条「从 worktree 推送」：推送前先在 worktree 里变基到最新的分支。
- 相关文档：[Run 生命周期](../domains/20261031-run_lifecycle.md#workspace_model)、[交付条件](../domains/20261031-run_lifecycle.md#delivery_conditions)、[事件](../interfaces/20261031-events.md)、[安全边界](../operations/20261031-security.md#workspace_access)。

## 背景

Git 仓库上的 Run 在 Janus 自己的 worktree 里工作，原来只有用户点验收，结果才回到用户的分支。2026-11-23 的审计发现，用户看到的是「Agent 改了代码，我的分支上却没有」：

- 用户对负责人说「提交一下」「合并到 main」，负责人只能提交在 detached 的 worktree 里，回复「已提交」，用户在自己的目录里看不到。
- 用户要求推送时，负责人从 worktree 推 `HEAD:main`，远端有了，本地 main 还没有；之后验收如果要变基，本地和远端就分叉了。
- 验收之后负责人按要求做的提交不会再次交付：判断「验收后又有了改动」只看未提交的文件，一个提交让工作区干净，Run 停在「已验收」。验收之后的一轮被服务重启打断时，worktree 还会被移除，提交跟着丢掉。
- 负责人解决验收冲突后分支又前进了，下一次验收仍从任务起点重放，把 worktree 并入的分支提交再重放一遍；负责人的变基做到一半时验收，冲突标记会被提交上去。

先尝试过加一个负责人工具 `janus.merge`，让它在用户要求时触发合并。用户的意见是「如无必要，勿增实体」，并指出「只有点验收才合回去」本身就别扭：验收是对结果的判断，合回分支是一次 Git 操作，两者被绑在了一起。调研 Codex 和 Claude Code 的源码（Codex `c983e8d171`）得到：

- 两者都没有给模型合并回原分支的工具。Codex 的 worktree 由宿主程序创建，带回本地是应用的功能（桌面应用的 Handoff、命令行的 `codex apply`）；Claude Code 的 `EnterWorktree` / `ExitWorktree` 只管会话的目录和退出时保留还是删除。改文件归模型，动 Git 元数据归宿主。
- Codex 的 `workspace-write` 沙箱把 linked worktree 的 `.git` 指针和它指向的 gitdir 设为只读（`codex-rs/protocol/src/permissions.rs`），也不让写用户的仓库目录。在沙箱模式下，Agent 在 Janus 的 worktree 里 `git commit`，或在用户目录里 `git merge`，都会失败。

## 决策

1. **交付时合并**：Run 每次交付（目标完成，以及交付之后对话里的一轮又改了文件或做了提交），Janus 都把结果带回创建时检出的分支：提交剩下的改动（说明是目标的第一行），分支前进过就先变基，再快进（`App::merge_at_delivery` → `worktrees::accept`，和验收同一个流程）。带回了提交时记 `run.merged`（`actor` 为 `janus`），交付摘要写明合并到了哪个提交。验收只表示用户认可、结束这次交付；交付没能带回的，验收时再合并。
2. **冲突交给负责人，只交一次**：交付时变基冲突，或 worktree 里有没做完的变基、合并等操作，用户的目录和分支不动，照常交付，并把冲突和确切的命令（`git rebase <分支现在的提交>`）交给负责人；它这一轮结束时再次交付并合并。它没解决时，再次交付只说明仍然冲突，不再自动交给它（`lead.merge_handed_back`），避免来回打转；用户点验收时再交给它一次。用户那边挡住（未提交的改动会被覆盖、分支被删除或改写）时，交付摘要说明原因，用户处理后点验收再合并。
3. **「有没有新东西」按提交比较**：交付或验收之后，对话中的一轮结束时有未提交的改动，或 worktree 的 `HEAD` 不再是上次合并带到的提交（`worktrees::moved_on`），就再次交付并合并。服务启动时，有这样改动的已验收 Run 保留 worktree、再次交付并合并，不移除。
4. **只重放分支没有的提交**：变基用 `git rebase <分支现在的提交>`，前提是任务的起点（或上次合并带到的提交）同时在分支和 worktree 的历史里，所以重放的只是任务自己的提交。整个 Run 的 diff 也从这里算起（`worktrees::fork_point`），就是下一次交付要带回的改动。
5. **推送和发布**：负责人说明写明，用户要提交或合并时把工作做完、交付，交付时就进了用户的分支；要推送或发布时，先在 worktree 里 `git rebase <分支>`（冲突在这里解决，再跑检查），再推 `HEAD`，交付时用户的分支快进到同一个提交，本地和远端一致。负责人不在用户的仓库目录里运行 git，也不在 worktree 里切换分支；沙箱不让它提交时，留给交付时由 Janus 提交。

## 取舍

- **交付时合并，而不是验收时合并**：代码进分支的时机和用户点不点验收无关，和不用 worktree 时 Agent 直接改用户目录的体验一致；用户说「提交」「合并」，交付时就已经在分支上了，无人值守的「提交到 main 再发布」也能完成。代价是代码先进分支、后被核对，不满意时让负责人改或自己 `git revert`。
- **不加合并工具**：两个参照产品都没有；交付时合并已经覆盖了用户要求合并的场景，宿主执行也不受 Agent 沙箱的限制。
- **冲突只自动交一次**：负责人解决不了时不让它和交付来回打转；之后由用户决定继续对话还是点验收再试。

## 后果

- 新事件 `run.merged`，应用把它显示为「交付时合并到你的分支」，交付卡片和「团队与权限」写「交付时合并到 …」或「已合并到 …」。
- `worktrees::Conflict` 不再带任务提交的起点；`worktrees::Unfinished` 表示 worktree 里有没做完的操作。
- 安全边界中，快进用户的分支从「用户验收时」变为「每次交付时」，包括[值班](../domains/20261121-loops.md)派出、没有人看着的任务，写成明确接受的风险，见[安全边界](../operations/20261031-security.md#workspace_access)。
