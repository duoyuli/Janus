# ADR：通过 MCP 看板协作

- 状态：已采纳（accepted），记录于 2026-10-30。
- 相关文档：[目标模式与共享看板](../domains/goal_mode.md#board_flow)、[看板 MCP 工具](../interfaces/board_mcp.md)、[ADR：主控以 /goal 推进目标](goal_mode_lead.md)。

## 背景

目标模式下，主控决定调用协作者时，用户希望它生成一套编排，并且编排要代码化：先验证编排，再执行编排。执行过程中要解决信息怎样在主控和协作者之间传递，用户提出用共享的协作看板：调用协作者时把任务写到看板上；协作者遇到阻塞或其他情况时写回看板；还要解决看板上的信息怎样回到主控。

## 决策

1. Janus 内置一个 MCP 服务器（streamable HTTP，JSON 响应），在主控和支持 HTTP MCP 的协作者会话中以 `janus` 的名字接入。
2. 主控的工具：`orchestrate`（提交编排，先完整校验，有任何错误则整份不执行）、`wait`（长轮询读取看板新消息，最多 45 秒）、`reply`（回答提问或补充指示）、`team`（查看团队和任务状态）。协作者的工具：`board_post`（写回进展、阻塞、备注）。
3. 看板不另建存储，就是 Run 的事件日志；`wait` 按游标读取与任务相关的事件。
4. 协作者需要主控决定时，在结构化结果中提问并结束本轮，回答发回同一会话。主控结束后仍未回答的提问转给用户。
5. 审批和表单请求始终交给用户，主控只能看到「等用户」。
6. 每个 Run 用随机令牌区分；工具带只读或非破坏性标注，避免 Codex 对看板调用请求用户审批。

## 取舍

- **MCP 与解析主控输出文本相比**：编排是结构化参数，可以一次返回全部校验错误；主控可以在执行中多次提交编排、主动读取进展。代价是依赖 Agent 对 HTTP MCP 的支持。
- **长轮询与推送相比**：服务端不需要维护到 Agent 的推送通道；主控需要反复调用 `wait`，没有新消息时会占用它的轮次。
- **Pi 等只支持 stdio MCP 的 Agent 不接入**：它们照常执行，但不能在执行中途写回看板，只能通过结果和提问回报。
- **主控不代批审批**：保证权限决定始终在用户手里，代价是协作者等用户时，主控只能等待。

## 后果

- 看板消息的格式（`board_entry`）和事件类型绑定，新增事件类型时要决定是否让主控看到。
- 2026-11-02 起，需要主控处理的消息在主控支持插话时还会直接推送进它的会话，长轮询仍然保留，见 [ADR：需要主控处理的看板消息推送进主控的会话](board_push.md)。
- 真实运行中发现并修复的问题（Pi 拒绝 HTTP MCP、Codex 对看板调用请求审批、主控结束后提问无人回答）都已体现在上述决策中。
