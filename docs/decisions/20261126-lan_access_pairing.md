# ADR：手机在局域网里扫码配对后访问 Janus

- 状态：已采纳（accepted），记录于 2026-11-26，方案由用户在 2026-11-26 选定（「局域网 + 扫码配对」）。扩大了信任边界（合并前检查第 5 条）。
- 相关文档：[安全边界：网络暴露](../operations/20261031-security.md#network_exposure)、[安全边界：配对的设备](../operations/20261031-security.md#paired_devices)、[HTTP API：设备与手机访问](../interfaces/20261031-http_api.md#devices)、[ADR：由事件推导的状态只在服务端算](20261126-backend_owns_derived_state.md)。

## 背景

用户要做一个和 Mac 应用功能对齐的 Web 版本，并且要能在手机上用。在此之前，Janus 服务没有鉴权，只监听 `127.0.0.1`，所以只有本机的应用能用。手机要连上服务，就只能对局域网开放，而一个没有鉴权的服务一旦对局域网开放，局域网里的任何设备都能读写设置、运行记录，并启动 Agent。

即使只在本机，浏览器也是新的客户端：浏览器里打开的任何网站都能向 `127.0.0.1` 发请求（CSRF）。网站还可以把自己的域名解析到 `127.0.0.1`（DNS 重绑定），浏览器会把这个页面当成和服务同源。原先只有两个返回凭据的接口防住了这两种情况，见 [ADR：MCP 服务器的值在编辑器里能看能改](20261119-mcp_values_visible.md)。

## 威胁模型

- **局域网里的其他设备**：同一个 Wi-Fi 或有线网中的电脑和手机，可以直接访问 Mac 的局域网地址和端口。
- **同一网络上的嗅探**：局域网上的通信是明文 HTTP，同一个网络中能抓包的人可以看到请求和设备令牌（例如开放的咖啡馆 Wi-Fi、被入侵的路由器）。
- **浏览器里的其他网站**：用户在配对过的浏览器里打开的其他网站，可以发起跨站请求（CSRF），也可以用 DNS 重绑定把自己的域名指向 Janus。
- **不在范围内**：同一用户下本机的其他进程。它们本来就能读 Janus home 里的 `0600` 文件，见[适用范围](../operations/20261031-security.md#scope_limits)。

## 决策

1. **默认关闭，由 Mac 上的用户打开**：在 Mac 应用的「设置 › 手机访问」里打开开关后，服务才额外监听局域网。开关存在服务端（`configs` 中一行 `lan_access`），没有这一行就是关。只有本机应用能拨这个开关，已配对的设备不能，这样一台设备不能把 Janus 开放给它所在的网络。
2. **同一个端口，监听所有接口**：局域网监听绑定 `0.0.0.0:<Janus 的端口>`，和 `127.0.0.1` 上的监听并存。macOS 把连接交给绑定得最具体的地址，所以本机发出的请求仍然到回环监听，从局域网监听进来的请求全部来自网络。关掉开关时停止接受连接，关闭空闲连接，并结束已经打开的事件流。
3. **扫码配对，每台设备一个令牌**：
   - 本机应用取一个配对码，显示成二维码，同时显示链接 `http://<局域网地址>:<端口>/pair/<码>`。配对码一次有效，5 分钟内过期，由 10 个字母组成（约 50 位）。
   - 连续错 5 次，所有还开着的配对码一起作废，要在 Mac 上重新显示一个。
   - 设备用配对码换到一个 32 字节的随机令牌，放在 cookie `janus_device` 里（`HttpOnly`、`SameSite=Strict`、`Path=/`，有效期 400 天）。Janus 只保存令牌的 SHA-256，每台设备一个 `0600` 文件，放在 `data/secrets/devices/`，令牌不进数据库，也不进备份。
4. **除本机应用外，每个请求都要设备令牌**：
   - 本机应用照旧放行，条件是：从回环监听进来、对方地址是回环地址、`Host` 是回环名字、请求不带 `Origin` 和 `Sec-Fetch-Site`。
   - 其他所有 `/api/*` 请求都要带有效的设备 cookie，包括本机浏览器发出的、局域网监听收到的，以及自称来自本机的；没有就返回 401。
   - 例外只有两个：Web 客户端的静态文件，它们里面没有用户的数据；配对用的 `POST /api/devices/claim`。
   - 浏览器发出的修改类请求，`Origin` 必须和 `Host` 一致。
   - 看板和 MCP 路由的端点只在回环监听上提供，局域网监听上返回 404。
5. **决定谁能进来的只给本机应用**：本机环境和「试命令」、取配对码、拨开关，已配对的设备也不能做，返回 403。MCP 的值和 Agent 的环境变量起初也只给本机应用，2026-11-26 用户决定配对的设备也能读，见 [ADR：MCP 的值和 Agent 的环境变量也给配对的设备](20261126-credentials_to_paired_devices.md)。
6. **吊销**：本机应用可以取消任何设备的配对；已配对的设备只能取消自己的配对，用于退出登录。取消后，这台设备的令牌立即失效，它打开的事件流也随即断开。

## 为什么不用 HTTPS 自签名证书

- 手机浏览器不信任自签名证书，每台设备都要先手动安装并信任一个根证书，在 iOS 上还要到设置里分两步打开。这比扫码难得多，而且一个由 Janus 生成、被手机完全信任的根证书，本身就是一个高价值目标：私钥一旦泄露，就能伪造任何网站。
- 局域网 IP 会变，证书要随之重签，或者签成通配。
- 用户需要加密时，有更好的现成办法：Tailscale 或 VPN 在网络层加密。Tailscale 的地址（`100.x`）也在局域网监听的范围里，配对链接会一并列出。

## 取舍

- **明文局域网**：在不可信的网络（公共 Wi-Fi）上，抓包的人可以拿到设备令牌，冒充这台设备。这一点明确接受，对策如下：
  - 默认关闭。
  - 应用里写明只在可信的网络上打开，在外面用 Tailscale 或 VPN。
  - 不用时关掉开关。
  - 怀疑令牌泄露时，在 Mac 上取消那台设备的配对。
- **配对过的设备几乎什么都能做**：创建任务、回答审批、改设置，和 Mac 应用一样，因为 Web 版的目标就是和 Mac 应用对齐。包括读编辑器里的凭据；例外是本机环境，以及拨开关、生成配对码。
- **cookie 不限定端口**：浏览器给 `127.0.0.1` 的 cookie 也会带到同一主机的其他端口。只有本机上别的服务读请求头时才会看到它；本机进程不在威胁模型内。
- **同端口监听依赖 macOS 的绑定语义**：Linux 不允许在回环监听旁边再绑定同端口的通配地址。Janus 只在 macOS 上运行，所以只有 macOS 上的测试检查真实的绑定。

## 后果

- 本机的浏览器第一次打开 Web 版时也要配对，可以用应用里的「在浏览器中打开」，它会带上一个配对码。
- 新的接口：`/api/devices*`、`/api/lan-access`。全局事件流多一个 `devices` 通知。
- 新的凭据位置 `data/secrets/devices/<id>.json`。删除 Janus home 时会一起删掉；不需要数据升级，因为以前没有这类数据。
