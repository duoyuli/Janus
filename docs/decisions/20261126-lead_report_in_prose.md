# ADR：负责人的交付报告和目标确认仍写在回复里

- 状态：已采纳（accepted），记录于 2026-11-26。界定 [ADR：协作者用工具交结果和提问](20261125-hand_in_with_tools.md) 和 `AGENTS.md`「需要 Agent 交回结构化的东西时给工具」这条约定的范围：它管协作者交给 Janus 的结果和提问，不管负责人写给用户的报告。
- 相关文档：[目标模式中的交付](../domains/20261031-goal_mode.md#delivery_in_goal_mode)、[目标不自己结束时](../domains/20261031-goal_mode.md#goal_settle)、[工作区共享资料](../domains/20261031-agents_and_roles.md#workspace_brief)、[ADR：减少重复的 Agent 工具](20261125-fewer_agent_tools.md)。

## 背景

2026-11-26 的架构治理指出两处从负责人的回复正文里读东西：交付时 `LeadReport::of` 按标题把负责人最后一条回复拆成「结论」「需要你决定」「建议更新共享资料」三节；负责人的 `/goal` 一直不自己结束时，Janus 问它是否完成，回复第一行是 `GOAL_DONE` 就清除目标（`goal_settle`）。协作者交结果已经改成工具，这两处看起来是同一类问题。

## 决策

1. 负责人的交付报告仍是它最后一条回复的正文。三个标题只是帮应用分块显示：标题按 Run 的语言写在负责人说明里，两种语言的标题都认；找不到某一节时，那一节为空，整段回复照样作为交付摘要，交付不受影响。
2. 目标确认仍用回复第一行的 `GOAL_DONE`。它只在 Agent 自己的目标检查不运行时才用到（例如 Claude Code 接自定义端点、没有它用来判断的小模型），认不出时负责人继续工作，问过几次后由看门狗告诉用户，不会误判为完成。
3. 不给负责人加交报告或确认完成的工具。

## 取舍

- **报告是写给人看的**：协作者的结果要被 Janus 逐条核对（验收标准、证据方法、判定），格式错了会让任务失败，所以必须用工具当场校验。负责人的报告是给用户读的文字，Janus 不核对它，拆分失败的代价只是少分一块显示。
- **工具要有必要**：加一个「交报告」或「目标完成」的工具，负责人就多一步必须记住的操作，忘了调用时交付反而卡住；[ADR：减少重复的 Agent 工具](20261125-fewer_agent_tools.md) 刚把负责人的工具减到八个。`GOAL_DONE` 是给某个 Agent 局限打的补丁，等 Agent 的目标检查在各种端点下都能运行时直接删掉，不值得为它加一个长期的工具。
- **约定的边界写清楚**：「需要 Agent 交回结构化的东西时给工具」指 Janus 要据此做判断、改状态的交接。负责人报告的分节只影响显示；`GOAL_DONE` 会改变状态，但只在补丁路径上，且认不出时的结果是安全的（继续等）。

## 后果

- `LeadReport`、`take_section`（`backend/src/orchestrator/report.rs`）和 `goal_settle` 保留，代码注释指向本 ADR。
- 以后若 Janus 需要据负责人的报告做判断（例如按「需要你决定」自动生成待处理决定），先改成工具，再做这个功能。
