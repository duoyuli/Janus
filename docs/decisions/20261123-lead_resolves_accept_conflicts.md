# ADR：验收冲突交给负责人解决

- 状态：已采纳（accepted），记录于 2026-11-23。
- 取代：[ADR：验收时把结果合并回任务开始时的分支](20261120-merge_back_on_accept.md) 第 4 条中的「变基冲突」一项，和取舍中的「冲突时失败，而不是交给负责人解决」。
- 相关文档：[Run 生命周期](../domains/20261031-run_lifecycle.md#workspace_model)、[交付条件](../domains/20261031-run_lifecycle.md#delivery_conditions)、[Run 操作](../interfaces/20261031-http_api.md#run_actions)、[安全边界](../operations/20261031-security.md#workspace_access)。

## 背景

验收时源分支有了新提交、和任务的改动冲突，原来的做法是验收失败，弹一句「任务的结果在提交 X，可以在你的目录里用 git merge X 自己合并」，任务停在「已交付」。用户指出这样不合适：用户要自己理解冲突、在自己的目录里合并，合并到一半就留下一个没完成的合并；冲突应该由 Agent 处理，处理完向用户说明，而不是停在那里。

2026-11-23 就出了这样的情况：一个改团队记忆位置的任务和 main 上新写的 change log 在 `CHANGELOG.md` 的同一处冲突，用户照提示在自己的目录里执行 `git merge`，留下了没完成的合并。

## 决策

1. **冲突交给负责人**：验收时变基冲突，Janus 仍先中止变基，用户的目录和分支都不动，任务的结果留在 worktree 的提交里（`worktrees::Conflict` 带上分支、分支现在的提交、任务提交的起点、结果所在的提交和冲突的文件）。验收操作不再返回错误，而是以 Janus 的名义给负责人发一条消息（`conflict_prompt`），Run 仍是「已交付」。负责人的会话不在时，消息在重新打开的会话里送达。
2. **负责人在 worktree 里解决**：消息给出确切的命令 `git rebase --onto <分支现在的提交> <任务提交的起点>`，要求逐个读冲突文件两边的改动、按两边的意图合在一起、不直接丢掉任何一边，拿不准时用 `ask_user` 问用户；完成变基后跑相关检查；不改源分支本身，也不把它 merge 进来。
3. **说明后再次交付**：负责人最后用几句话告诉用户哪些文件冲突、各自怎么合的、跑了什么检查。处理这条消息的一轮结束时，Run 再次交付（`LeadState.redeliver`）；用户再验收时，源分支已经在结果的历史里，直接快进。
4. **其他失败仍交给用户**：用户目录里未提交的改动或同名的未跟踪文件会被覆盖、源分支被删除或被回退改写、detached HEAD 移动了、worktree 不在了，这些都涉及用户自己的目录和分支，仍然验收失败并说明原因，由用户处理。

## 取舍

- **负责人解决，而不是 Janus 自动选一边**：冲突的两边都是有意的改动，只有读懂两边才能合对；负责人有任务的上下文，用户需要时它会问。
- **变基，而不是合并提交**：和验收本身一样保持线性历史，任务的提交重放到源分支的最新提交上，验收仍然只是快进。
- **不改用户的目录**：负责人只在任务自己的 worktree 里操作，用户的目录和分支在用户再次验收前保持原样。

## 后果

- `POST /api/runs/{id}/actions` 的 `accept` 遇到变基冲突时返回成功，事件里多一条 Janus 发给负责人的 `user.message`；处理它的一轮结束后有一条新的 `run.delivered`。
- 负责人在 worktree 里运行的 `git rebase` 是 Agent 自己的操作，按它的权限模式执行，仓库的钩子是否运行由 Git 和 Agent 决定；Janus 自己的 Git 写操作范围不变。
