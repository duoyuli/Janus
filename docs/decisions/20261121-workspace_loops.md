# ADR：工作区值班派发独立的 Run

- 状态：已采纳（accepted），记录于 2026-11-21。
- 相关文档：[工作区值班](../domains/20261121-loops.md)、[派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)、[看板 MCP 工具：值班的工具](../interfaces/20261031-board_mcp.md#loop_tools)、[HTTP API：值班](../interfaces/20261031-http_api.md#loops)、[macOS 应用：值班](../architecture/20261031-frontend.md#loops)、[安全边界：工作区值班](../operations/20261031-security.md#loops)、[ADR：所有目标 Run 经过一个派发队列](20261121-dispatch_queue.md)、[ADR：和一名数字员工的对话是一种 Run](20261120-chats_as_runs.md)。

## 背景

Janus 要从「一次 Run 的多 Agent 协作」变成常驻的工作台：把 issue、定时检查这类信号变成做完的工作，人只通过收件箱参与。Run 是一次性的执行单元，没有能一直在岗、按时查看外部变化的东西。用户和 Claude 在 2026-11-20 讨论后定下了方向，2026-11-21 定下了方案里留给用户的几项：派出的 Run 自动开始，用户手动提交的目标也排队，去掉时间和费用上限，槽位默认 8。

## 决策

1. **值班是工作区里的一段提示加一张时间表**：时间表是一条标准 5 段 cron 加时区，按钟点开工；也可以不设时间表，只在叫它时开工。值班自己可以用 `next_wake` 约一次时间表之外的开工（比如等 CI 跑完再看），时间表照旧，约的时间和原因显示给用户。由工作区的负责人来跑，不带团队。（2026-11-21 修订：原来的「固定间隔、自定节奏、只手动」三选一按实现方式分，用户看不出下次几点开工，也表达不了「工作日 9 点」；「自定节奏」是给 Agent 的能力，不该是用户的设置。）
2. **值班的会话是 `kind` 为 `loop` 的 Run**：和对话一样只有一名成员、走 `lead_conversation`，会话、消息、审批、恢复都复用对话的一套；会话一直续用，打不开时新开并带上最近的往来。值班的设置存为 `configs` 中 `kind` 为 `loop` 的对象。
3. **一次醒来就是这个会话的一轮**：Janus 以 `janus` 的名义发一条提示（第几次、为什么醒、派出的 Run 有什么变化、值班的提示原文）。醒着时再来的唤醒合并成一次，等这一轮结束；服务停掉期间错过的醒来，启动后只补一次。
4. **下次醒来的时刻记在事件里**：每次变动记一条 `loop.scheduled`，服务启动时从最后一条读回，内存里只有时钟。
5. **值班自己不改东西，要改的派成独立的 Run**：`dispatch` 新建目标 Run，经派发队列开始，结果进收件箱，不回到值班，Run 结束也不唤醒它；值班下次醒来时自己查（`dispatches`，以及醒来提示里的变化）。Run 之间没有依赖。
6. **派发按 key 去重**：同一工作区一个 key 只有一个 Run，由数据库唯一索引保证；Run 记下 `origin`、`loop_id`、`dispatch_key`、`source_url`。
7. **提问不阻塞**：值班的 `ask_user` 进收件箱，回答以 `answer` 唤醒它，问题和回答写在那次醒来的提示里；问题不随会话结束撤回。
8. **派出即开始**：没有每个值班的确认开关，没有「等你开始」的状态。
9. **叫「值班」，名字由它自己起**：中文界面和中文文档叫「值班」，按时间表「开工」、干完「摸鱼」；英文界面和代码里叫 Loop，wake / sleep。新建时不填名字，第一次开工时请它用 `set_name` 给自己起名，起名之前用提示的第一行。（2026-11-21 修订：原来取会话标题当名字，但 Codex 拿第一条提示的开头当标题，名字成了「[Loop wake #1] …」。）

## 取舍

- **复用对话的会话，而不是每次醒来新开会话**：续用保留判断的前后文，和 Claude Code 的 `/loop` 一致；状态（`save_state`、派发记录）都在记录里，新开会话时也能接上。代价是会话越来越长，由 Agent 自己压缩。
- **值班在自己的副本里，不在工作区目录里**：Git 仓库里值班有一个 worktree，路径固定，每次开工前对齐到工作区当前的提交，留下的改动清掉；`git`、`gh` 在副本里一样能用。代价是它看不到用户还没提交的改动，多占一份磁盘。（2026-11-21 修订：原来值班就在工作区目录里，靠开工前后比较目录来发现它改的文件，用户或其他程序同时在这个目录里改的文件都被算到值班头上，值班还按用户的回复派出了撤回这些改动的任务。）不在 Git 仓库里时仍在工作区目录里，看不出改动。
- **用户直接发给值班的消息立即作为一轮发出**：和对话一致，不攒到下次醒来；这一轮不算醒来，不改下次醒来的时刻。
- **暂停只停时间表，不关会话**：暂停时仍可手动唤醒；会话进程在醒来之间不关闭，P0 不做进程的停放。
- **不做**：值班对象、全局 webhook 路由、Run 之间的依赖、带团队的值班、Run 结束唤醒值班、按 token 或时长的预算。webhook 提前唤醒、按来源的信任规则、PR 交付、代你验收的收件箱值班留到之后，各自先写 ADR。

## 后果

- `RunKind` 新增 `loop`，`RunOrigin` 新增（`user`、`loop`）；数据版本 19 给 `runs` 加 `origin`、`loop_id`、`dispatch_key`、`source_url` 和唯一索引。
- 看板端点见到值班的会话时给出值班的工具；全局事件流多一种 `loop` 通知。
- 应用的工作区首页和侧栏列出值班，打开值班是它的会话页；收件箱多「值班改了工作区的文件」「值班没能醒来」两类事项。
- 删除工作区时删除它的值班；删除值班时保留它派出的 Run。
