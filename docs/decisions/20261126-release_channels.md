# ADR：稳定版和测试版（RC）两个发布渠道

- 状态：已采纳（accepted），记录于 2026-11-26。
- 相关文档：[CI 与发布：发布渠道](../operations/20261101-ci_release.md#channels)、[macOS 应用：更新渠道](../architecture/20261031-frontend.md#update_channels)、[ADR：应用内增量更新](20261102-in_app_updates.md)、[安全边界：本机运行器](../operations/20261031-security.md#local_runner)。

## 背景

每次合并到 main 都按日期发版，开了自动更新的应用几分钟内就装上。还不完善的功能因此马上到了所有用户手里。用户要求分成两个渠道：日常版本走稳定渠道，还在测试的分支单独打标签发到 RC 渠道，应用里可以选跟随哪一个。

## 决策

1. **稳定版**：标签 `v<年>.<月>.<日>[.<序号>]`，只能打在 main 的提交上，发布为 GitHub 的正式 Release，也就是 `releases/latest`。
2. **测试版（RC）**：标签 `v<年>.<月>.<日>[.<序号>]-rc.<序号>`，打在任意分支上（约定叫 `rc/<名字>`），发布为 prerelease。`releases/latest` 不返回 prerelease，所以跟随稳定渠道的应用，包括这次之前装的所有版本，都看不到 RC。
3. **版本顺序**：`2026.11.27-rc.1` < `2026.11.27-rc.2` < `2026.11.27`。RC 的版本号必须比最新的稳定版新，否则 RC 渠道收不到它。
4. **应用内的渠道**：「设置 › 通用 › 更新」选「稳定版」或「测试版（RC）」，记在本机，默认稳定版。RC 渠道取最近的发布里版本最新、能安装的那个，所以也会收到更新的稳定版。
5. **从 RC 切回稳定版不降级**：留在当前的 RC 构建上，等出现比它新的稳定版再升过去。
6. **发布说明**：RC 也写在 `CHANGELOG.md` 里，小节名是它的版本号（`## 2026.11.27-rc.1`）。这些改动随稳定版发布时，把对应的 RC 小节合并进稳定版那一节。
7. **数据迁移**：改了数据迁移的 RC 必须建在最新的 main 之上，迁移的版本号接在 main 后面，合并回 main 时也不能变（合并前检查第 13 条）。Release 工作流机械检查前一半。
8. **CI**：推送 `rc/**` 分支也运行 CI，Release 照旧等这个提交的「CI result」通过才发布。

## 取舍

- **用 prerelease 区分，不另建更新源**：GitHub 的 `releases/latest` 本来就跳过 prerelease，已经装好的旧版本不用任何改动就不会收到 RC；不需要再维护一份渠道清单。
- **不降级**：数据迁移只能往前走，旧版服务遇到更新过的数据库会拒绝启动（`migrations.rs`）。自动降级等于让 Janus 打不开；留在 RC 上等下一个稳定版，代价只是多用几天测试版。
- **RC 的迁移必须跟着 main**：RC 用户的数据库已经按 RC 的含义升到了某个版本号。main 上同一个版本号如果是别的迁移，RC 用户升到稳定版时这个迁移会被当成已经跑过而跳过，数据就坏了。
- **RC 也写 change log**：版本按日期走，RC 小节合并进正式版那一节就是这一版完整的说明，不另起一套说明的来源。

## 后果

- `Updater` 按渠道取版本（`Updater.Channel`、`fetchNewest`），版本比较认得 RC（`isNewer`、`isCandidate`），RC 的版本号在界面上标「测试版」。
- `.github/scripts/release-channel.sh` 判断标签属于哪个渠道、能不能发布；RC 发布为 prerelease，发布说明开头写明只有 RC 渠道会更新到它。
- 推送 `rc/**` 分支会触发 CI，包括本机运行器这条腿，能推分支的只有维护者。
