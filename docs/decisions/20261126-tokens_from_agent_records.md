# ADR：token 用量以 Agent 自己的会话记录为准

- 状态：已采纳（accepted），记录于 2026-11-26。
- 相关文档：[事件：会话记录](../interfaces/20261031-events.md#usage_records)、[用量口径](../interfaces/20261031-events.md#usage_accounting)、[ACP 集成：会话中能看到什么](../interfaces/20261031-acp_integration.md#session_view)、[安全边界：Agent 运行环境隔离](../operations/20261031-security.md#agent_isolation)。

## 背景

用量账本的 token 原来只来自 `session/prompt` 的返回：一轮正常结束时才有数字，进行中的一轮显示 0，崩溃、超时或被杀掉的一轮永远丢失。实际数据中，一个正在进行的 Claude Code 会话在自己的会话记录里已有 17,492,792 token，账本里是 0；已经结束的会话两边完全一致，说明口径没错，错在时机和覆盖面。

之前有一个补救：尝试异常结束且这一轮没有上报 token 时，从 Claude Code 的会话记录里补一条这一轮的汇总（`source: "native_log"`）。它只覆盖协作者尝试、只覆盖 Claude Code、只在结束时补，负责人和对话的会话仍会丢，进行中仍是 0。

## 决策

1. **token 以 Agent 自己的会话记录为准**：Claude Code 的 `projects/<项目>/<会话>.jsonl`（含子 Agent 的记录）和 Codex 的 `sessions/…/rollout-…-<会话>.jsonl`，只读 Janus 隔离的 Agent 配置目录（`data/agents/<id>/config`），不读用户自己的 `~/.claude`、`~/.codex`。
2. **读数写成事件**：账本必须是事件日志的纯函数，回放、重启和历史 Run 得到同样的数字，所以编排器把读到的值记为 `session.usage`（`source: "records"`、`session`、`turnEnded`、按模型的累计 `models`），不让账本自己去读文件。
3. **一轮进行时每 20 秒、结束时再一次**：有变化才记；结束时无论正常返回、出错、超时、被打断还是进程退出都记一次。读取位置和去重表在内存里跨轮复用，每次只读新追加的完整行。
4. **累计值按增量归属，复用费用的做法**：和费用读数一样，按原生会话和模型取相邻读数的增量，归入后一次读数的任务、尝试和时段（`SessionReadings`）。
5. **不重复计数**：有会话记录读数的原生会话，`session/prompt` 返回的 token 照常记下但不再计入账本；没有读数的会话照旧按每轮的返回计。去掉 `native_log` 补救，它的旧事件仍按一轮的 token 读。

## 取舍

- **为什么不在账本里读文件**：账本由事件推出，文件会被删除（删除 Run 时一并删）、会变；写成事件后历史数字不再依赖文件还在不在。
- **为什么不只在结束时读**：结束时读能补上崩溃的一轮，但进行中的长轮次（负责人跟随 `/goal` 可能持续数小时）仍显示 0。20 秒的间隔让数字及时，读的只是新追加的部分，开销很小。
- **为什么记累计值而不是增量**：服务重启后内存里的读取位置没了，从头再读得到的累计值与之前的一致，账本取差即可；记增量就要求读取状态在重启后仍准确。
- **和返回值的差别**：Claude Code 的会话记录不含不写进记录的辅助调用（例如生成会话标题），比 `_meta.quota.model_usage` 略少，实际数据中约少万分之一；模型名取响应里的 `message.model`。换来的是进行中和异常结束的轮次不再丢失，差别远小于丢失的量。

## 后果

- Run 页、看板和交付的用量在一轮进行中就逐步增长，崩溃的一轮也计入；会话在第一轮结束前显示了 token 就算已上报。
- 有会话记录的会话，轮次按 `turnEnded: true` 的读数计。
- 升级前开始、升级后续接的会话，第一次读数带着整个会话到那时为止的累计值，之前按返回值计入的 token 改为归在这次读数上，总量基本不变。
- 新增运行时如果也把用量写在自己的记录里，在 `agent_records` 加一种读法即可；没有记录的 Agent 自动沿用返回值。
