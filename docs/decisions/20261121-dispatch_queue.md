# ADR：所有目标 Run 经过一个派发队列

- 状态：已采纳（accepted），记录于 2026-11-21。
- 相关文档：[Run 生命周期：派发队列](../domains/20261031-run_lifecycle.md#dispatch_queue)、[创建 Run](../domains/20261031-run_lifecycle.md#create_run)、[HTTP API](../interfaces/20261031-http_api.md#run_actions)、[配置](../interfaces/20261031-configuration.md#settings)、[ADR：工作没有时间和费用上限](20261121-no_work_limits.md)。

## 背景

工作区要加值班：按节奏醒来，把要改的事派成独立的 Run。没有人看着时，Run 的数量本身需要上限，否则一次分拣几十个 issue 就会同时拉起几十个负责人和更多协作者。原来的并发上限 `max_concurrent_attempts` 只管一个 Run 内部同时运行的子任务，跨 Run 没有任何限制。用户已经决定：工作不设时间和费用上限，限制只来自机器资源这类真实约束。

## 决策

1. **一个服务一个派发队列，跨工作区，先进先出**：同时在做的目标 Run 不超过 `max_running_runs`（`JANUS_MAX_RUNNING_RUNS`，默认 8，范围 1 到 32）。只有 `planning`、`running` 且没暂停的目标 Run 占槽位。
2. **用户在工作区首页提交的目标也进队列**：用户的目标就是一次手动派发，和值班派出的一起排队；有空位时立即开始并在返回前准备好，体验和以前一样。
3. **排队的 Run 只有记录**：新状态 `queued`，第一条事件是 `run.queued`。worktree、团队和资源库快照、基线都在开始时才确定，所以排队期间对工作区的修改会被采用；工作区被删除或 Agent 不能用时，Run 开始时记为 `failed`。
4. **队列不另存**：就是状态为 `queued` 的 Run 按创建时间排序，重启后原样保留；排位在读取时计算（`queuePosition`）。
5. **排队的 Run 只能立即开始或取消**：`start` 不等空位直接开始，`cancel` 让它不再开始，也可以删除；其余操作返回 409。

## 取舍

- **在开始时而不是创建时拍快照**：排了很久的 Run 应该用最新的团队和代码基线开始，而不是创建那一刻的。代价是创建时看到的团队不一定是最后用的团队，应用在排队页写明这一点。
- **暂停让出槽位**：暂停的 Run 不再启动新任务，留着槽位会让队列空等。继续时不抢回：可能短暂超过槽位数，新 Run 等到有空位。
- **不区分优先级**：用户的目标和值班的派发同样先进先出；要插队时用「立即开始」，由用户决定。「从中断处继续」和给中断的任务发消息也是用户直接要求开始，同样不等空位。
- **进队、离队都是一个事务**：记录和事件一起写，带条件的更新只领仍在排队的 Run，避免并发的补位、立即开始、取消和删除互相踩；服务开始监听后才补位。准备没完成就停了的 Run 回到队列原位，因为它没有快照可以恢复。
- **等人的 Run 暂不让出槽位**：Run 停在等审批或回答时进程仍开着，仍占槽位。关进程、让出槽位、处理后优先恢复（停放）留到之后。

## 后果

- `RunStatus` 新增 `queued`，可以转到 `planning`、`cancelled`、`failed`；准备没完成的 `planning` 和没能开始的 `failed` 可以回到 `queued`。服务重启时排队的 Run 不记为中断。
- 应用的任务记录和任务页写出排位，排队的任务页只有目标、说明、「取消任务」和「立即开始」。
- 产品端到端测试的服务用 32 个槽位，避免并行场景互相排队；`queue` 场景用一个槽位单独验证。
