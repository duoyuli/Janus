# ADR：事件是唯一事实来源

- 状态：已采纳（accepted），记录于 2026-10-30，决策早于本记录。
- 相关文档：[架构概览](../architecture/overview.md#principles)、[事件参考](../interfaces/events.md)、[macOS 应用](../architecture/frontend.md#event_derivation)、[Run 生命周期](../domains/run_lifecycle.md#recovery)。

## 背景

Janus 的一个 Run 同时涉及多个长时间运行的 Agent 会话、用户的审批和回答、编排器的调度决定。界面需要实时显示这些状态，编排器重启后要能从中断处继续，事后还要能回放和审计一个 Run 是怎样走到交付的。

## 决策

1. 只有编排器改变 Run 和任务的状态，每次变化都先作为事件追加到 SQLite 的 `events` 表，再广播给界面。
2. 事件只追加，不修改。`text` 给人看，程序逻辑只读 `type` 和 `data`。
3. 界面不保存业务状态，由 `derive` 从事件推导。
4. 恢复 Run 时，团队从 `runs.config` 快照重建，任务状态从事件重建。目标模式的看板就是事件日志本身，`wait` 按 `seq` 游标读取。
5. 需要等待处理的事项在 `data.key` 中带唯一键，回答、撤回、转交都按键关联。

## 取舍

- **与独立状态表相比**：不需要维护事件和状态表之间的一致性，回放和导出天然完整；代价是每次读取都要遍历事件，Run 很长时界面推导和恢复会变慢。目前接受。
- **一致性要求落在三处推导逻辑上**：应用的 `derive` / `boardFacts`、看板 `board_entry`、恢复 `resume_run` 各自解释事件。新增或修改事件类型时必须同时检查这三处，否则会出现界面、主控和恢复看到的状态不一致。
- **少量运行时状态不在事件中**：等待者（`waiters`）、活动会话和看板令牌只在内存中，重启后由恢复流程重新建立。

## 后果

- 导出 NDJSON 即可得到 Run 的完整记录。
- 界面断线或缓冲溢出时，重新读取全部事件即可恢复，不需要额外的同步协议。
- 修改事件格式时要考虑旧 Run：旧事件不会被改写，推导逻辑需要兼容。
