# ADR：和一名数字员工的对话是一种 Run

- 状态：已采纳（accepted），记录于 2026-11-20。
- 相关文档：[对话](../domains/20261120-chats.md)、[数据模型](../architecture/20261031-data_model.md#sqlite_tables)、[HTTP API](../interfaces/20261031-http_api.md#chats)、[安全边界](../operations/20261031-security.md#workspace_access)、[macOS 应用](../architecture/20261031-frontend.md#screens)。

## 背景

用户要在应用里直接和某一名数字员工对话：选一个数字员工，把它当作单个 Agent 来交互，交互页面和工作区里负责人的对话对齐甚至复用，单 Agent 的交互能力尽量完整。对话用临时目录，每次生成一个 id，放在用户目录下。

Janus 已经有一条完整的单会话路径：Run 交付或验收后，负责人的会话保留为常规对话（`lead_conversation`）。它支持插话、排队、打断、接管、审批和表单、图片、`@` 文件、斜杠命令、切换模型和模式、用量，并且能在服务重启后用 `session/load` 恢复。界面上，`ChatCard` 是负责人对话和每个子任务会话共用的会话视图。

## 决策

1. **对话是 `kind` 为 `chat` 的 Run**：`runs` 表加 `kind` 列（`goal` 或 `chat`，数据版本 12），事件、事件流、操作接口、用量账本、删除都用 Run 现有的一套，不另建表和接口。只新增 `POST /api/chats` 和 `GET /api/runs?kind=chat`。
2. **数字员工占用 Run 的主会话**：对话的快照只有一名成员，就是选中的数字员工，成员 id 用主会话固定的 `lead`，会话走 `lead_conversation`。对话不接看板、不发 `/goal`、不交付，每一轮结束后等下一条消息；Agent 自己的 `/goal` 等斜杠命令照常转给它。
3. **工作目录在 Janus home**：每个对话新建 `<Janus home>/chats/<run id>` 作为工作目录，删除对话时一起删除。不放在用户主目录下，因为仓库规则要求运行时数据都在 Janus home，主目录下多出来的目录用户不知道何时可以删。
4. **没有看板，也不能借令牌碰看板**：对话的数字员工拿到的令牌对它的 MCP 路由有效，看板端点见到对话一律拒绝。
5. **对话没有工作区，不进任务列表**：对话的数字员工可以是任何绑定了 Agent 的数字员工，不要求「可以担任负责人」；任务列表和对话列表分开计数。
6. **点开就开会话，由用户先说**：新建对话只选数字员工，Janus 立即通过 ACP 启动 Agent、注入系统层，会话等用户的第一条消息；第一条消息成为对话的标题。
7. **会话没了就由下一条消息重新打开**：服务重启（`interrupted`）或会话异常结束（`failed`）后，对话不显示「从中断处继续」，用户直接发消息，能 `session/load` 就恢复原会话，否则新开会话并带上最近的对话。

## 取舍

- **复用 Run，而不是新建对话实体**：新建实体要重写事件存储、事件流、消息流转、请求卡片、用量和恢复，和 Run 的那一套必然分叉。代价是 Run 的代码里多了 `kind` 分支：恢复、删除、看板鉴权、列表和应用的几处推导。
- **成员 id 沿用 `lead`**：会话的键是枚举 `SessionKey::Lead`，主会话的全部机制都按它找；为对话另起一个键会复制这些分支。名字不代表对话的数字员工在带团队，应用按 Run 的类型显示它自己的名字和头像，不显示「负责人」。
- **工作目录是空的临时目录**：对话里的数字员工没有项目上下文，要改别处的文件得由用户指给它。需要在项目里工作时，仍然用工作区提交目标。

## 后果

- 对话里 Agent 的审批和表单出现在收件箱里；对话等下一条消息是常态，不算等你处理。
- 交付后负责人的对话也受益：重新打开的会话现在会生成 MCP 路由的令牌，资源库的工具在服务重启后的对话里也能用。
- 删除一个开着会话的对话不需要先停止。
