# ADR：验收时把结果合并回任务开始时的分支

- 状态：已采纳（accepted），记录于 2026-11-20。
- 取代：[ADR：Git 仓库上的每个任务在自己的 worktree 中运行](20261119-run_worktrees.md) 的第 6 条（验收时提交到 `janus/<run-id>` 分支）和第 7 条中「从 `janus/<run-id>` 重建 worktree」；[ADR：worktree 写入用户仓库的边界](20261119-worktree_trust_boundary.md) 中验收和重建两行，以及「不改用户当前检出的分支和工作目录里的文件」。
- 相关文档：[Run 生命周期](../domains/20261031-run_lifecycle.md#workspace_model)、[安全边界](../operations/20261031-security.md#workspace_access)、[数据模型](../architecture/20261031-data_model.md#migrations)。

## 背景

2026-11-19 起，Git 仓库上的每个任务在自己的 worktree 中运行，验收时 Janus 把结果提交到 `janus/<run-id>` 分支，合并由用户决定。用户指出：Janus 主打对用户无干扰、不破坏用户的开发环境，多出一个要自己合并的分支，就要用户理解 worktree、分支和合并，认知成本反而高了。

参考的做法：Claude Code 的 `--worktree` 建 `worktree-<名字>` 分支，不自动合并，没有改动时退出就删除；Codex 应用的 worktree 处于 detached HEAD、不建分支，结果通过用户点击的 Handoff 回到本地目录，分支可选。两者都不在用户不知情时改用户的目录，Git 操作由工具自己完成。

## 决策

1. **结果回到任务开始的地方**：创建 Run 时记下工作目录当时检出的分支（`runs.config.worktree.branch`；处于 detached HEAD 时为 `null`）。验收时 Janus 在 worktree 里提交全部改动，再把这个提交带回这个分支，不建 `janus/` 分支。验收是用户明确的操作，作用和 Codex 的 Handoff 相同。
2. **线性历史**：源分支没动过时直接快进；任务期间源分支有了新提交（用户自己提交，或另一个任务先合并），先在任务的 worktree 里把任务的提交变基到最新的源分支上，再快进。每次验收在源分支上是一个提交，没有合并提交。
3. **只快进，不在用户目录里合并**：源分支检出在用户的目录（或用户的其他 worktree）时，在那里执行 `git merge --ff-only`，文件随分支一起更新；没有检出在任何地方时只移动分支（`git update-ref`，带旧值比较）。
4. **失败时什么都不动**：下面几种情况验收失败，任务保持「已交付」，用户的目录和分支保持原样，结果留在 worktree 的提交里，错误信息给出提交号，由用户自己合并：
   - 变基冲突：变基中止，用户目录里不会出现冲突标记。
   - 用户目录里有未提交的改动，和任务改的文件重叠（包括未跟踪的同名文件）：Git 拒绝快进，错误信息列出这些文件，请用户先提交或暂存。和任务无关的未提交改动不受影响。
   - 源分支已被删除。
5. **detached HEAD**：任务开始时工作目录处于 detached HEAD，验收时如果工作目录仍在原来的提交上（或 Janus 上次验收移动到的提交上），把它快进到结果；工作目录移动过或已经检出了分支，按第 4 条失败。
6. **不运行钩子**：Janus 对仓库的所有写操作都带 `-c core.hooksPath=/dev/null`，包括创建 worktree、提交、变基和快进，`post-checkout`、`post-commit`、`post-merge`、`post-rewrite` 也不运行。
7. **继续已验收的任务**：worktree 被移除后再继续，从最后一次验收带回的提交（`risk.accepted` 的 `data.commit`）重建；从未带回过结果时从起点重建。
8. **旧数据**：数据版本 10 给已有的 worktree 中的 Run 补上 `branch`：取升级时工作目录检出的分支，前提是这个分支的历史包含 Run 的起点（这样变基只重放任务自己的提交）；否则为 `null`。

## 取舍

- **自动合并，而不是留一个分支**：用户不需要知道 worktree 和分支，验收后结果就在自己的目录里；代价是 Janus 会改用户检出的分支和目录里的文件，所以只在验收这个明确的时刻、只用快进来做。
- **冲突时失败，而不是交给负责人解决**：用户选择由自己处理冲突；任务保持「已交付」，用户可以合并提交，也可以继续对话让负责人调整后再验收。
- **变基，而不是合并提交**：历史保持线性，一次验收一个提交；任务的提交本来就只是验收时 Janus 做的一次提交，变基不会丢失有意义的历史。
- **不自动暂存用户的改动**：`stash` 再恢复可能在用户的文件里留下冲突标记，违背「不破坏用户的开发环境」。
- **旧 Run 按当前分支推断**：创建时的分支没有记录，只能推断；要求分支包含起点，避免把无关的提交重放到别的分支上。推断不出时让用户自己合并，不猜。

## 后果

- `risk.accepted` 的 `data` 是 `repo`、`branch`（源分支，detached 时为 `null`）和 `commit`（带回的提交，没有新改动时为 `null`）；`run.created` 的 `data.worktree.branch` 是源分支。
- 交付摘要、负责人说明和任务提示说明验收时合并回哪个分支；应用的交付页和「团队与权限」页显示「验收时合并回 X」或「已合并到 X」。
- 安全文档的「工作目录访问」一节增加：验收时 Janus 会快进用户检出的分支和目录里的文件。
- 已经存在的 `janus/<run-id>` 分支不再使用，Janus 不删除它们，由用户决定去留。
