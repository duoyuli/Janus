# ADR：返工由负责人用 `retry` 发回原任务，会话由负责人每次选择

- 状态：已采纳（accepted），记录于 2026-11-19。
- 取代：[ADR：基于 `session/load` 复用前置任务会话](20261118-session_continuation.md) 的第 2 条（`retry` 的布尔参数 `continue_session`）和「验证没通过后派修复子任务」的用法；该 ADR 的 `continues`、75% 回退和能力检查仍然有效。
- 相关文档：[Run 生命周期](../domains/20261031-run_lifecycle.md#retry)、[目标模式与共享看板](../domains/20261031-goal_mode.md#team_structure)、[看板 MCP 工具](../interfaces/20261031-board_mcp.md#retry_tool)、[事件](../interfaces/20261031-events.md)、[macOS 应用](../architecture/20261031-frontend.md#session_view)。

## 背景

2026-11-19 本机的一个 Run（`rmwn8huoj`）里，研发者完成 T1，质量工程师的独立验证 T2b 判定 `rejected`。负责人按当时的说明派了修复子任务 T3（`continues: T1`）和新的验证子任务 T4；T4 又判定 `rejected`，于是再派 T5 和 T6b。一个需求最后展开成 8 个子任务。

`session/load` 本身是成功的：T3、T5 和 T1 用的是同一个 ACP 会话，Agent 也记得之前的上下文。用户看到的却是「同一个数字员工又开了一个新会话」，原因在任务模型：

- 被验证的任务停在「完成」，`retry` 只接受失败或已取消的任务，`reply` 拒绝已经结束的任务，负责人只能新建子任务。
- 验证意见要由负责人改写进新任务的说明（T3 的提示有 4965 个字），验证者自己的结论、证据和建议没有直接交给执行者。
- 续接靠负责人记得写 `continues`；续接后又发一遍完整的任务说明；会话卡片按任务划分，新任务的会话从空白开始。
- 每一轮都要新建验证任务，从头全量验收。

讨论中还确认了两点：看板由负责人全权管理，「要不要返工、返工哪一项」是判断，应当由负责人做，Janus 不自动返工；一个数字员工可以同时有多个会话（例如一个做后端、一个做前端），会话属于一项工作，不属于数字员工，复用与否要按情况判断。

## 决策

1. **判断归负责人，执行归 Janus**：验证判定没通过时，负责人读看板，判断问题出在哪个子任务，用 `retry` 把它发回原来的执行者。Janus 只做机械的部分：重新打开任务、选择会话、把验证意见交过去、改完后让验证重新核对。这与现有分工一致：Janus 自动做的只有机械恢复（进程失败后的自动重试、结果缺证据时在原会话补一次）和执行负责人已经声明的结构（按 `deps` 调度、`retry` 恢复连带取消的下游）。
2. **`retry` 可以重开已完成的任务**：任务状态增加「完成 → 待执行」这一条转移，只由负责人的 `retry` 触发。返工不新建子任务，任务 id、会话卡片和尝试编号都延续。
3. **`session` 必填**：`retry` 的 `session` 取 `"continue"`（回到这个子任务自己上一次的会话）或 `"new"`（新开会话），不填或填别的值直接报错。不设默认值，是因为负责人是模型，常会省略可选参数，一省略就落到默认会话；必填让它每次都判断「这次要不要原来的上下文」。上下文超过 75%、Agent 不支持 `loadSession` 或加载失败时，`continue` 仍按原 ADR 回退为新会话。`continues` 保留，用于负责人判断某项**新**工作适合接着另一个子任务的会话做。
4. **`from` 直接交接验证意见**：`retry` 可以带 `from`，指向一个已经给出判定的独立验证子任务。它的判定、没通过的标准和证据、交接说明和风险原样进入返工提示，并写一条 `context.handoff`；负责人只在 `note` 里写自己的判断。被返工的任务不能依赖 `from`，否则复审会等在返工前面。
5. **复审跟着结构走**：验证任务声明了 `verifies`，被验证的任务一返工，原来的判定就过期了。所以返工时，这个任务所有已完成的独立验证，加上 `from`，都回到待执行，并依赖被返工的任务（`from` 验证的不是它时，把它加进 `from` 的依赖，记在事件里，重启后重建）。复审默认回到验证者自己的会话：验证要独立于执行者的思路，不必独立于自己上一轮的判断；在自己的会话里复审，它知道上一轮指出了什么，先核对这些问题，再做回归。验收标准仍然逐条回答，没受返工影响的可以写明沿用上一轮的证据。
6. **回到原会话时只发新的内容**：会话里已经有任务说明和之前的工作，所以返工提示只有验证意见、负责人的说明、更新过的说明（如果改了）、上次失败的原因和验收标准；新开会话时才发完整的任务说明，再附上这些内容。

## 取舍

- **不自动返工**：自动返工省一个负责人回合，但验证意见可能和用户中途收窄的范围冲突（这个 Run 的 T2 就是这样被取消的），问题也可能出在上游任务。哪个任务返工、要不要返工，只有读过看板的负责人能判断。
- **一个 `retry`，不另加 `rework`**：失败重试和完成后返工，本质都是「让这个子任务再做一次」，区别在任务状态和会话选择。会话用必填参数表达，状态由 Janus 判断，两个工具反而容易用错。
- **复审复用验证者的会话**：可能让验证者沿用上一轮的思路。用两点控制：提示要求先核对上一轮的问题再做回归、所有标准仍逐条给证据；上下文超过 75% 时新开会话。
- **不保留常驻进程**：继续沿用「尝试结束即关闭 ACP 进程、需要时 `session/load`」，理由见原 ADR。

## 后果

- `janus.retry` 的参数：`task`、`session`（必填）、`from`、`note`、`instructions`、`accept`；去掉 `continue_session`。看板上「[验证未通过]」的处理建议、`accept` 的拒绝说明和负责人说明改成用 `retry` 返工。
- `task.reopened` 的 `data.reason` 增加 `target.reworked`（验证任务因被验证的任务返工而复审，`data.target` 是被返工的任务）；`lead.retry` 带 `data.session`，可带 `data.from`、`data.note`，不再有 `data.continueSession`。事件不迁移：旧 Run 中重试后尚未开始的任务，重启后按新会话处理。
- `attempt.started` 增加 `data.reopen`，记录这次尝试为什么开始（负责人的重试及其会话和 `from`，或复审及其 `target`）。应用在尝试的标题行写明「接着原会话」「按 V1 的意见返工」「T1 返工后复审」等，返工在同一个会话卡片里接着显示。
- 任务状态在服务端用 `Reopen`、`SessionChoice`、`ReopenReason` 三个枚举表达，不读字符串判断。不改表结构，不扩大信任边界。
