# ADR：多 Agent 协作的分工：负责人派出子任务后只做管理

- 状态：已采纳（accepted），记录于 2026-11-19，同日实施。第 3、4、7、11、12 条维持当时的行为；其余各条的落地见文末「实施」。
- 相关文档：[协作三方：负责人、协作者和编排器](../domains/20261119-collaboration_roles.md)、[目标模式与共享看板](../domains/20261031-goal_mode.md)、[Run 生命周期](../domains/20261031-run_lifecycle.md)、[2026-11-19 Agent Team 协作问题梳理](../review/20261119-collaboration_issues.md)、[ADR：返工由负责人用 `retry` 发回原任务](20261119-rework_in_original_session.md)。

## 背景

2026-11-19 落地返工之后，用户和 Agent 逐项梳理了多 Agent 协作的分工，一次一个问题，每个问题给出选项和建议，由用户决定。起点是三方各能做什么（见[协作三方](../domains/20261119-collaboration_roles.md)），依据包括当天的协作问题梳理（CO-01 至 CO-09）和本机 Run 的基线数据：负责人的 token 占 43%，有文件改动的子任务只有约 63% 安排了独立验证。

贯穿各条结论的原则沿用返工 ADR 和 `LESSONS.md` 的 L-25：判断归负责人，编排器只做机械的部分和执行负责人声明过的结构，编排器能确定的事实摆到明面上，由人或负责人判断。

## 决策

1. **负责人的角色按是否派出子任务切换**：目标小、一个人能做完时，负责人自己做；一旦派出第一个子任务，它就只做管理（拆任务、读看板、判断、交付），不再改工作目录里的文件。
2. **靠提示和检测，不靠权限**：权限由 Agent 原生模式决定（[ADR](20261031-agent_native_permissions.md)），Janus 不在派出后把负责人切成只读。负责人说明写明这条边界；派出后负责人对工作目录的任何改动都记下来，在看板上提醒负责人，并写进交付风险。跑测试、读文件、看 diff 这类只读操作照常。
3. **确认结果不强制独立验证**：负责人可以派一个协作者独立验证，也可以自己验证。
4. **负责人自己验证不留单独记录**：核对过程留在负责人的会话里，交付时由它根据上下文写进交付摘要。
5. **交付按事实标出没有独立验证的子任务**：改了文件、没有独立验证的子任务，交付页标「没有独立验证」，不写「未经确认」；负责人的交付摘要必须交代这些子任务是怎么核对的。
6. **负责人只看到协作者的名字和职责**：不显示 Agent、模型、权限模式、用量和资源。负责人说明和文档中「优先换模型交叉验证」的要求删除，因为负责人看不到模型，这条无法执行（CO-03 按此关闭）。
7. **星形结构**：协作者之间不直接沟通，所有事交给负责人，由负责人派给对应的协作者；`peers` 保留，协作者可以看到别人做了什么。
8. **团队在 Run 中固定**：缺人时，负责人用 `ask_user` 说明缺什么能力、要用在哪个子任务上，不把子任务硬派给不合适的人。负责人申请、用户批准后在 Run 中加人，放到下一阶段，和资源库的能力动态路由一起设计（CO-05）。
9. **负责人不接手失败的子任务**：派出后，子任务做不下去时，负责人只能 `retry`（原会话或新会话）、取消后派给别人、`ask_user`，或取消并写进交付风险。
10. **用户插手协作者的会话要让负责人知道**：用户对协作者插话、接管、交还、让它以当前结果结束时，看板记一条「[用户介入]」，随负责人下一次唤醒送到，不单独打断负责人。
11. **同一个目录上的多个 Run 暂不处理**：不提醒，也不互斥（CO-07）。以后计划用 git worktree 解决，届时另写 ADR 取代[任务直接在工作目录中运行](20261031-in_place_workspaces.md)。
12. **负责人的上下文完全交给 Agent 自己**：Janus 不在上下文接近上限时重开负责人会话，也不额外要求负责人在对话里记下核对结论。

## 取舍

- **派出后只管理，而不是始终动手或始终只管理**：小目标不必为一处改动另开会话；一旦有了团队，负责人改文件会和协作者冲突、让痕迹对账和返工的归属变模糊，它的上下文也会越来越大。
- **检测而不禁止**：不违反「权限由 Agent 原生模式决定」，越界也能被看到；代价是只能事后发现。
- **不强制验证、不记负责人的确认**：独立验证的成本和必要性由负责人判断；交付只陈述 Janus 能确定的事实，负责人的核对由它自己在摘要里交代，用户对照着看。
- **负责人看不到模型**：避免它按模型名字而不是按职责派活；放弃了跨模型交叉验证这个质量手段。
- **星形结构**：协作者之间商量接口会绕过负责人的判断，`owns` 和接口约定可能被改掉而负责人不知道；代价是多一次转达。
- **固定团队、不管同目录多 Run**：都留给后续阶段的结构性方案（资源库的动态路由、git worktree），不先做临时的提醒或锁。
- **不接手、上下文交给 Agent**：规则一有例外，模型就会常用它；返工用 `continue` 回到原会话的成本已经很低。上下文管理和权限、Skill、MCP 一样，用 Agent 原生的机制。

## 后果

- 第 3、4、7、11、12 条维持现状，不改代码。
- 现状文档和[协作三方](../domains/20261119-collaboration_roles.md)已按这些规则更新。

## 实施

- 第 1、2、8、9 条：负责人说明、团队组织说明和默认 PMO 的指令写明「派出后只做管理、不接手、缺人时告诉用户」；派出后负责人对每个文件的第一次改动记为 `lead.edited`，推送给负责人、重启后恢复、交付时列为风险，负责人的对话中显示一行提醒；看板「[失败]」「[停滞]」不再建议负责人自己做。见[负责人的职责](../domains/20261031-goal_mode.md#lead_role)。
- 第 5、6 条：交付的每个任务条目带 `unverified`（已完成、改了文件、没有独立验证），应用在逐条验收、概览和复制的摘要中标「没有独立验证」；负责人说明要求交付摘要交代这些子任务怎么核对；删掉「优先换模型交叉验证」。见[交付](../domains/20261031-goal_mode.md#delivery_in_goal_mode)。
- 第 10 条：用户对协作者会话的消息、接管、交还、打断和以当前结果结束，在负责人的看板上记为「[用户介入]」，随下一次 `wait` 送到。见[共享看板](../domains/20261031-goal_mode.md#board_flow)。
