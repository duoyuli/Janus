# ADR：ACP 适配器按需安装，按版本存放

- 状态：已采纳（accepted），记录于 2026-10-30。
- 相关文档：[ACP 适配器管理](../architecture/adapters.md)、[部署方案](../operations/deployment.md#upgrade)、[ADR：用户数据、依赖和日志都放在 Janus home](user_home_layout.md)。

## 背景

早期安装 Janus 时，要按文档手动执行四组 `npm install` 或 `git clone`，把全部适配器装进仓库。用户要求：ACP 适配器应该让用户按需下载加载，而不是一次性全部装好；适配器以后还会更新升级，这些都要处理好。

## 决策

1. 代码中维护一份适配器清单：每个内置运行时对应一个适配器，以及它的来源（npm 包或 GitHub 仓库）。
2. 第一次检查用到某个适配器的 Agent 时自动安装；用户也可以在页面上手动安装。
3. 每个版本装在自己的目录中，`current` 符号链接指向当前版本。安装先在临时目录完成并确认入口文件存在，再原子地切换 `current`。
4. 页面提供检查更新、升级和切回已安装版本；保留当前版本和上一个版本，更老的自动清理。
5. 会话从解析后的版本目录启动，升级不影响正在运行的会话。
6. Git 来源没有发布版本，用 `<package.json 版本>-<提交>` 作为版本号，检查更新时比较默认分支的最新提交。

## 取舍

- **与预先全部安装相比**：只下载用到的适配器，Janus 本身保持精简；代价是第一次检查某个 Agent 时要等下载和构建（Pi 需要编译 TypeScript），并且需要网络。
- **与原地覆盖升级相比**：按版本存放占用更多磁盘（每个适配器最多两份），换来升级失败不破坏现有版本、可以立即回滚、不影响运行中的会话。
- **Git 来源只能装最新提交**：没有 tag 时无法可靠地列出可选版本；需要固定版本时，以后可以在清单中加入提交号。

## 后果

- 新增一种内置运行时，需要在 `ADAPTERS` 中登记它的适配器，并在 `spec_for` 中通过 `for_base` 使用。
- 适配器的安装环境是 Janus 进程自己的环境（`npm`、`git`、网络代理设置），不是 Agent 的隔离环境。
