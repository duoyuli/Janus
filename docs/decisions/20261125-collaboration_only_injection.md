# ADR：Janus 只注入协作规则，做事方法写在数字员工的指令里

- 状态：已采纳（accepted），记录于 2026-11-25。取代 [ADR：按验收标准自行验证](20261101-criteria_over_commands.md) 的第 5 条（负责人自己核对关键结果、改了代码的目标安排独立评审），以及 [ADR：Skill 路由是一份按需查找的目录](20261120-skill_catalog.md) 的第 1 条（系统层指路）。第 5 条中「MCP 服务器都不返回 `instructions`」和「负责人说明和协作者约定各有一节协作工具」被 [ADR：MCP 路由照 magpie 只给三个工具](20261126-mcp_router_three_tools.md) 取代（2026-11-26）：`instructions` 是服务器的自我介绍，不是注入系统层的提示词，Janus 的每个 MCP 服务器都在其中列出工具，各说明里的「协作工具」一节删除。
- 相关文档：[目标模式与共享看板](../domains/20261031-goal_mode.md#lead_brief)、[协作者的约定](../domains/20261031-goal_mode.md#collaborator_rules)、[默认角色](../domains/20261031-agents_and_roles.md#product_launch_roles)、[验收标准](../interfaces/20261031-board_mcp.md#acceptance_criteria)。

## 背景

Janus 要做通用的智能体团队，不只做编码。但它注入每个会话的说明里写着编码团队的做法：负责人说明要求「每个改了文件的子任务都要核对」「重要改动安排独立验证」「小改动一个执行者加一次检查」「并行编码前先定数据结构和路由」，验收标准举的是扫雷和测试的例子；协作者约定和验证者提示要求「跑测试、启动程序、读代码」，「整套测试只跑一次」。这些说明对所有数字员工都生效，用户写的律师、编辑或分析师也会照着编码的方法做事。

## 决策

1. Janus 注入的说明只写协作机制：看板工具、编排与校验、负责的文件和认领、痕迹核对、结构化结果的格式（逐条 `checks`、证据方法、`verdict`）、提问的流转、交付的格式、共享资料和团队记忆、Git worktree 与提交规则。
2. 怎样做事、怎样验证、流程多重、什么时候安排独立验证，写在数字员工的指令里。能力的泛化靠建不同的数字员工，不靠改 Janus。
3. 默认数字员工接过原来写在 Janus 里的做法：PMO 要求交付前每个改了文件的子任务都核对过，验收标准写可观察的结果；通用数字员工和研发工程师写验证方式和「重的检查只跑一次」；质量工程师写明 checks 要给出实际执行的命令和输出。
4. 注入的说明保持精简：机制只说一次，不重复工具描述里已有的内容。
5. **不写 MCP 的用法，只给一节工具简介**：Janus 只按 ACP 格式在 `session/new` 的 `mcpServers` 里挂上服务器，工具由 Agent 自己加载。工具怎么用、有什么限制只写在各工具的说明里，看板、值班、记忆整理和资源库路由的 MCP 服务器都不返回 `instructions`。负责人说明和协作者约定各有一节「协作工具」，一个工具一行，只说它是做什么的：两种 Agent 都按需加载 MCP 工具（开局只有工具名或命名空间），这一节让 Agent 知道有哪些工具、用到时去看说明。其他各节只写流程，不再穿插工具名。值班和团队记忆的说明里没有工具用法。
6. **Skill 由 Agent 自己加载**：资源库的 Skill 仍只经一个路由 Skill `janus-skills`，Agent 按自己的 Skill 机制（Claude Code 的插件、Codex 的 `.agents/skills`）加载它，什么时候读由它的描述决定。系统层不再写「先读 janus-skills 的 SKILL.md」那句话（`skills_note` 删除）。

## 取舍

- **与 Janus 统一要求核对相比**：用户自建的负责人如果不写核对的要求，就不会再被 Janus 要求核对。交付仍标出改了文件却没有独立验证的子任务，负责人要在摘要里交代怎样核对的，用户能看到缺口。
- **工具说明是唯一来源，简介只当索引**：一个工具的用法只写一处，说明和工具描述不会各说各的。最初完全不提工具，但 Claude Code 开局只加载工具名和服务器的 `instructions`、Codex 只列命名空间，负责人可能想不到去找 `orchestrate` 和 `wait`；所以加回一行一个的简介，不写用法。
- **不写 Skill 的位置**：Agent 的 Skill 列表超出预算时可能只剩名字，`janus-skills` 的描述就看不到了。这时 Agent 和用户自己装的 Skill 一样受预算限制，不再由 Janus 另外指路；`janus-skills` 的描述把「什么时候读」写在最前面。
- **不按领域分说明**：没有在 Janus 里为不同领域准备不同的说明。领域只是数字员工的指令和资源库里的 Skill、MCP，Janus 不需要知道。

## 后果

- 负责人说明、`collaborator_rules`、验证者提示和 `FilesSince` 的提示都不再提测试、程序和代码，改成和领域无关的说法。负责人说明和协作者约定按做事的顺序重新分节，一条规则只说一次；`teamwork::lead_guide` 并入负责人说明的「派活」一节后删除。
- 默认数字员工的指令随版本更新（`sync_seeds`），用户没改过的自动换成新文本，不需要迁移。
- `SystemPart::Skills` 和 `session.prompt` 的 `skills` 通道去掉；看板工具的描述补上原来写在说明里的限制（例如 `accept` 不能越过没通过的独立验证、`wait` 不再带回推送过的消息）。
