# ADR：数字员工按分组管理，用文件导入导出，招聘顾问写文件交付

- 状态：部分被取代（superseded），记录于 2026-11-25。2026-11-26 起，第 5 条（招聘顾问把文件写进对话目录、对话提示导入）和取舍「文件而不是工具」已被 [ADR：招聘顾问在对话里用工具交出数字员工，用户确认后创建](20261126-propose_employees_in_chat.md) 取代；分组、数字员工文件、导入和不开管理 MCP 仍然有效。 第 3 条（导入）和随之而来的取舍、`/api/roles/import*` 接口已被 [ADR：不做从文件导入数字员工](20261126-no_role_import.md) 取代（2026-11-26）。
- 相关文档：[角色](../domains/20261031-agents_and_roles.md#roles)、[分组](../domains/20261031-agents_and_roles.md#role_groups)、[数字员工文件](../domains/20261031-agents_and_roles.md#role_files)、[对话](../domains/20261120-chats.md#chat_app)、[安全边界](../operations/20261031-security.md#role_files)、[ADR：Janus 只注入协作规则](20261125-collaboration_only_injection.md)。

## 背景

Janus 要成为通用的 Agent Team 工作台，就要容纳各行各业的数字员工：「换一个领域就是换一组数字员工」。数字员工原来只能在编辑器里一个一个建，名字、职责、指令都要自己写，还要逐个选 Agent、模型和权限；设置页把所有人平铺在一个列表里。用户提出两件事：给数字员工分类、分组；让别的 Agent 能按用户的需求创建数字员工。

## 决策

1. **分组**：数字员工多一个字段 `group`（分组名，空表示不分组，最多 40 个字）。一人只属于一个组，不做多标签。分组只给应用用来管理：设置页按组列出，可以整组改名、整组改用一个 Agent、整组导出；新建或编辑工作区时可以按组选人。负责人说明和任何会话都不提分组。默认数字员工分在「产品上线」「通用」「对话」三组。
2. **数字员工文件**：一人一个 Markdown 文件，开头 `---` 之间是 `id`、`name`、`desc`、`group`、`color`、`init`、`lead`，之后是指令全文；旁边可以有同名的 `.png` 当头像。默认数字员工（`backend/roles/`）、导入和导出用同一种格式、同一个解析（`RoleFile`）。Claude Code 的 subagent 文件（`name`、`description`、正文）照样能读：`description` 只取第一段作职责，`tools`、`model` 和非 `#` 开头的颜色不读，因为它们是 Agent 自己的设置。
3. **导入**：用户在应用里选一个文件夹或一个文件，服务读出其中的数字员工文件（文件夹名作为没写分组的文件的分组），逐个列出、可以查看指令，用户勾选、给这一批选一个 Agent 后才保存。同名的默认不勾选；导入永远不覆盖已有的人，id 被占用时另取 `-2`、`-3`。导入时服务按路径重新读文件，不接受应用传来的内容。
4. **不开管理 MCP**：不给外部 Agent 一个能直接新建、改写数字员工的接口。终端里的 Claude Code、Codex 本来就擅长写文件，写出数字员工文件、用户导入，已经满足「让别的 Agent 创建数字员工」。
5. **招聘顾问**：加一位默认数字员工「招聘顾问」（`recruiter`，在「对话」组）。它在对话里和用户聊清楚要做的事，按 Janus 团队的运作方式设计人选，把文件写进对话自己的目录。对话每一轮结束时，应用看一眼目录里有没有数字员工文件，有就在对话上方提供「导入数字员工…」，打开的就是第 3 条的导入表单。没有给对话加新工具。

## 取舍

- **指令会成为系统提示**：数字员工的指令在之后每一次会话里都作为系统提示注入。让 Agent 直接写入，等于让它给以后的 Agent 定长期规则，而且一条错误的指令会一直起作用。所以和共享资料一样，Agent 只提出（写文件），用户逐个看过、勾选后才保存。这也是不开管理 MCP 的主要原因：那需要一个长期有效、能改写所有人系统提示的凭据，属于扩大信任边界，而文件已经够用。
- **文件而不是工具**：按「如无必要，勿增实体」，招聘顾问交付用文件，不加 `propose_roles` 这类工具。文件同时服务手写、导出再导入、社区的 subagent 合集和终端里的 Agent，一条路径覆盖所有来源；以后如果在对话里确认卡片的体验明显更好，再评估工具。
- **单选分组**：分组的主要用途是「一个行业或场景的一套班子」，单选足够，按组整组操作也才有明确含义。通用数字员工这类跨团队的人放在「通用」组，工作区按组选人后可以再手动加。
- **Agent、模型和权限不进文件**：它们属于用户这台机器上的设置，导入时由用户给整批选 Agent，模型和权限取 Agent 的默认值，导入后可以逐个改。
- **不自动更新导入的人**：导入后的数字员工就是用户自己的，来源文件再改不会同步过来，没有记录来源，也没有「来源有更新」。要更新就再导入一次，或者直接编辑。

## 后果

- 数据版本 25 给每个数字员工加 `group`（默认数字员工取它所在的组，其余为空），数据版本 26 给已有数据加上招聘顾问。
- 新增 `agents/role_files.rs`（文件的读写、扫描、导入、整组操作）和共用的 `front_matter.rs`（Skill 的 `SKILL.md` 也用它读元数据）。
- 新接口：`POST /api/roles/import/scan`、`POST /api/roles/import`、`GET /api/roles/{id}/file`、`POST /api/role-groups/rename`、`POST /api/role-groups/bind`。
- 服务读取用户选择的本机文件夹，和资源库「从文件夹复制」Skill 相同的信任边界，限制见[安全边界](../operations/20261031-security.md#role_files)。
