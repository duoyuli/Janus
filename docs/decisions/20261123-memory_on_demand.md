# ADR：团队记忆按需检索，不放进会话的说明

- 状态：已采纳（accepted），记录于 2026-11-23。
- 取代：[ADR：工作区的团队记忆由 Agent 写、记来源、定期整理](20261123-team_memory.md) 的第 4 条「索引常驻、正文按需」，以及后果中「每个工作区会话的系统层多了团队记忆一节」里关于索引的部分。
- 相关文档：[团队记忆：读笔记](../domains/20261123-team_memory.md#memory_read)、[看板 MCP 工具：团队记忆的工具](../interfaces/20261031-board_mcp.md#memory_tools)、[安全边界：团队记忆](../operations/20261031-security.md#team_memory)。

## 背景

团队记忆上线时，每个工作区会话的系统层都附上笔记的索引（每条一行，最多 200 行），正文按需用 `janus.recall` 读。用户指出：记忆不应该每次都带进去，应该按需检索。索引会随笔记增多变长，每个会话都背着一份大多与本次任务无关的列表；工作区页也因此把团队记忆和共享资料说成了「每个任务都会带上的上下文」，两者的定位被混在一起。

同时，`janus.recall` 的搜索要求每个词都出现，换个说法、中文不分词时就搜不到，撑不起「按需检索」；它还会搜到被取消的 Run 写的笔记，和文档说的不一致。

## 决策

1. **说明里不放笔记**：工作会话（负责人、协作者、值班）的系统层只写团队记忆的用法：这个工作区有多少条笔记（被取消的 Run 写的不算），开始工作前、遇到本来要自己查清的事（怎么构建、运行、测试，一个坑，为什么这样做，东西在哪）时用 `janus.recall` 检索；笔记是笔记不是规则；怎样写笔记。没有笔记时也说明可以检索，因为同一个 Run 里别人可能正在写。
2. **检索按相关程度排序**：`recall` 带 `query` 时，查询拆成词（按空格和标点；中文这类不用空格的、超过两个字的词再拆成相邻两字），每个词在标题里出现记 3 分、在摘要里记 2 分、在正文里记 1 分，有一个词命中就算，按分数从高到低、同分按最近修改，返回前 5 条全文。带 `id` 读那一条。两者都不带时列出笔记目录（`id`、类型、标题、摘要，最近修改的在前，最多 50 条），供需要时浏览。
3. **工作会话检索不到被取消的 Run 写的笔记**：检索和目录都排除它们；整理会话照旧能看到，并标着「来自被取消的 Run」。
4. **整理会话仍拿到全部索引**：整理的工作就是逐条判断全部笔记，它的系统层照旧列出索引。整理说明改为让每条笔记好检索：标题和摘要用别人会搜的词点明主题。
5. **工作区页的说法跟着改**：团队记忆卡片的「?」说明笔记不会放进每个任务的说明，Agent 需要时检索。

## 取舍

- **由 Agent 检索，而不是 Janus 按任务自动挑几条注入**：自动挑选仍然是每次都带进去，只是带得少，挑错了 Agent 也不知道还有别的；Agent 知道自己卡在哪，按需检索更准。代价是 Agent 可能不去搜，所以说明里写明什么时候该搜。
- **关键词打分，不用向量检索**：笔记最多 300 条、每条很短，按词打分足够，不需要嵌入模型和额外的服务；原 ADR 的「不做向量检索」不变。拆相邻两字是为了让不分词的中文也能用别的说法搜到。

## 后果

- 工作会话的系统层不再随笔记数量变长；Agent 看到的笔记都是它自己检索来的。
- `recall` 的工具说明、整理说明和 e2e 的团队记忆场景都按新的行为写。
