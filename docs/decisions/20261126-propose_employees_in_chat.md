# ADR：招聘顾问在对话里用工具交出数字员工，用户确认后创建

- 状态：已采纳（accepted），记录于 2026-11-26。取代 [ADR：数字员工按分组管理，用文件导入导出，招聘顾问写文件交付](20261125-role_files.md) 的第 5 条和取舍「文件而不是工具」；分组、数字员工文件、导入和「不开管理 MCP」仍按那份 ADR。
- 相关文档：[对话里提议的数字员工](../domains/20261120-chats.md#proposed_employees)、[角色](../domains/20261031-agents_and_roles.md#roles)、[对话的工具](../interfaces/20261031-board_mcp.md#chat_tools)、[接口](../interfaces/20261031-http_api.md#proposed_employees)、[安全边界](../operations/20261031-security.md#role_files)、[ADR：协作者用工具交结果和提问](20261125-hand_in_with_tools.md)。

## 背景

招聘顾问原来把设计好的数字员工写成 Markdown 文件放进对话目录，应用每一轮结束时扫描目录，再提示「导入数字员工…」。用户试用后认为最终产物是一堆文本文件不对：聊完之后，招聘顾问应当直接用工具交出这一批人，用户在对话里确认就创建。用户选定了两点：保存前要在对话里确认（看过指令、选 Agent、勾选）；这个工具只给招聘顾问，不给所有对话。用户同时要求由事件推导的状态在后端计算，应用只展示。

## 决策

1. **能力开关**：数字员工多一个字段 `hires`（「可以在对话里提议数字员工」），默认数字员工里只有招聘顾问打开（默认角色文件写 `hires: true`，只有默认角色读这个键）。用户在数字员工编辑器里开关。导入的文件和对话提议的人都不能打开它：它只由用户给。Run 快照的成员记下创建时的值（`Member::hires`）。
2. **工具**：成员打开了 `hires` 的对话，主会话拿到 `janus` MCP 服务器，只有一个工具 `propose_employees`（调用者 `Caller::Hiring`，没有团队记忆）。其他对话仍然没有这个服务器，令牌对了也返回错误。参数是一组数字员工（名字、职责、分组、颜色、头像字、是否负责人、指令），当场按数字员工文件的规则核对（`RoleFile::checked`），不合格的整批退回并说明第几位、哪里不对。
3. **提议存在事件里**：工具把这一批写成对话的 `roles.proposed` 事件（存在 SQLite），用户创建或不要时写 `roles.created` / `roles.declined`，带上提议事件的 `seq`。对话「还没处理的提议」只有最新一条，由服务端从事件算出（`open_proposal`），应用读 `GET /api/runs/{id}/proposal` 展示。不新建表：提议只属于这个对话，事件日志就是它的记录。
4. **确认**：对话上方显示「某某提议了 N 位数字员工」，「查看并创建…」打开和文件导入同一个表单（逐个看指令、勾选、给这一批选 Agent），保存时调 `POST /api/runs/{id}/proposal`，服务端从事件读回这一批再创建，不接受应用传来的内容；「不用了」调 `POST /api/runs/{id}/proposal/decline`。同一批只能处理一次，新的一批替换还没处理的那一批。
5. **去掉写文件的路径**：招聘顾问的指令改为用工具交出；对话不再扫描目录、不再提示导入文件。从文件导入仍在「设置 › 数字员工 › 导入…」。

## 取舍

- **工具而不是文件**：用户明确要工具。按「需要 Agent 交回结构化的东西时给工具」，参数由工具的 schema 约束、交的时候当场核对，不靠 Agent 写对 front matter；对话目录里也不再留一堆只为导入写的文件。文件导入仍服务手写、导出再导入和 subagent 合集。
- **确认而不是直接保存**：指令会成为这些数字员工以后每次会话的系统提示，所以仍然由用户逐个看过、勾选后才保存，这一点和文件导入相同。工具只把提议记下，创建只能由用户经本机接口触发。
- **按数字员工开关，而不是所有对话都有**：大多数对话（老友、通用数字员工）不需要创建数字员工，给它们这个工具只会多一个被误用的入口。按 id 判断「是不是招聘顾问」是从 id 读出身份，所以写成字段；用户自己的数字员工需要时也能打开。
- **不新建表**：提议和对话同生同灭，删除对话时随事件一起删；服务端从事件算出状态，和团队记忆、交付等其他由事件推导的状态一致。

## 后果

- 数据版本 27：数字员工加 `hires`（招聘顾问为 `true`，其余 `false`），Run 快照的成员加 `hires`（已有的为 `false`）。
- 新事件 `roles.proposed`、`roles.created`、`roles.declined`；新接口 `GET`/`POST /api/runs/{id}/proposal`、`POST /api/runs/{id}/proposal/decline`。
- 对话第一次可能拿到 `janus` MCP 服务器：信任边界扩大到「打开了 `hires` 的对话可以提议数字员工」，提议本身不改变任何设置，见[安全边界](../operations/20261031-security.md#role_files)。
- 应用的对话页只读服务端给的提议，不再扫描目录；导入表单多一种来源（`RoleImport.chat`）。
