<a id="agent_isolation"></a>
## Agent 运行环境隔离

每个 Agent 子进程的环境由 Janus 完整构造（`spec_for`、`sandbox_env`），不继承 Janus 自身进程的环境：

- 只从宿主继承 `PATH`、语言环境、`TERM`、`USER`、`LOGNAME`、`SHELL`、`TZ` 和 `SSH_AUTH_SOCK`。
- `HOME` 和 XDG 目录指向 `~/.janus/data/agents/<id>/home`，`TMPDIR` 指向 `~/.janus/tmp/agents/<id>`（每次启动 Janus 时清空），Agent 查找 `~/...` 时落在自己的目录里：那里是用户目录的镜像，只挡 Agent 自己的配置和用户列出的路径。
- Agent 的配置目录（`CODEX_HOME`、`CLAUDE_CONFIG_DIR`）是 `~/.janus/data/agents/<id>/config`。用户自己的 `~/.codex`、`~/.claude` 不会被读取或修改。
- 用户在 Agent 设置中填写的环境变量不能覆盖上面这些由 Janus 控制的变量。
- [MCP 路由](../domains/20261116-resource_library.md#mcp_router)启动的服务器也一样（`sandbox_vars`）：每个资源一个隔离的 `HOME` `~/.janus/data/library/servers/<资源 id>/` 和 `TMPDIR` `~/.janus/tmp/servers/<资源 id>/`，只多出资源自己保存的值，这些值同样不能覆盖 Janus 控制的变量。

完整的变量清单见[配置](../interfaces/20261031-configuration.md#agent_env)。

隔离的 `HOME` 镜像用户目录，只挡一份清单，见下一节[本机环境](#host_env)。

例外：Claude Code 做负责人时，Janus 在它的隔离配置 `~/.janus/data/agents/<id>/config/.claude.json` 中把工作目录标记为已信任。这只修改 Janus 为该 Agent 创建的配置，不修改用户自己的 Claude 配置。

<a id="host_env"></a>
## 本机环境

每个 Agent 和 MCP 服务器的隔离 HOME 是用户目录的镜像（`host_env.rs`），见 [ADR](../decisions/20261122-mirror_host_home.md)：

- 用户目录下的每一项以符号链接放在同一位置，`Library`、`Library/Application Support`、`.config`、`.local`、`.cache` 和含有被挡路径的目录逐项镜像。启动 Agent 或 MCP 服务器时镜像一遍；「挡住的路径」改动时立即作用于所有已有的隔离 HOME。
- 挡住的路径：一份可编辑的清单，全局一份，默认是常见 Agent 自己的配置（指令、Skill、MCP、登录）和高危数据（云服务凭据、GPG、kubeconfig、密码管理器、浏览器、邮件和信息），用户可以删减和添加；没改过时跟着默认清单更新。Janus home 在用户目录里时一直挡着。`~/.Trash` 不链接。
- Agent 能读写用户目录里没挡住的一切，包括登录钥匙串（`~/Library/Keychains`）：工具刷新令牌、写缓存都写到用户自己的文件。这没有扩大 Agent 实际能读的范围：隔离 HOME 本来就挡不住用完整路径的读取，它只决定工具默认去哪里找。配置目录隔离的 Claude Code 在钥匙串可见时仍是未登录状态，不会用上用户自己的 Claude 登录。
- `~/.ssh` 默认不挡：OpenSSH 按系统账户找用户目录，不看 `$HOME`。`SSH_AUTH_SOCK` 传给 Agent，Agent 能用用户的 ssh-agent 里的密钥。
- Janus 只删自己建的、指向用户同一路径的链接，从不删用户的文件；隔离 HOME 里原有的同名内容改名为 `<名字>.janus-own` 留着，那个路径被挡住时放回。
- `GET/PUT /api/host-env` 和 `POST /api/host-env/try`（以本机用户和 Agent 的方式各跑一条命令）只回答本机的应用（规则同 `GET /api/connections/{id}/env`），网页发来的请求得到 403：它们列出用户目录的内容、决定 Agent 能用到什么、运行用户给的命令。

<a id="local_config_import"></a>
## 复制本机配置

选择「复制本机配置」时，只复制与模型接入有关的内容：

| 运行时 | 保留的配置项 |
| --- | --- |
| Codex | `model`、`model_provider`、`model_providers`、`model_reasoning_*`、`model_verbosity`、`model_context_window`、`model_auto_compact_token_limit`、`model_catalog_json`（引用的模型目录一并复制）、`openai_base_url`、`service_tier` |
| Claude Code | `model`，以及 `settings.json` 中配置模型接入点的 `env` 项 |

指令文件、hooks、插件、MCP、Skill、权限和沙箱策略都不复制。

凭据来源：

- 运行时自己的凭据文件（例如 `auth.json`）。
- Claude Code 在 macOS 钥匙串中的登录信息，通过 `security` 命令读取。
- 用户登录 shell 中导出的凭据变量：标准变量，以及配置文件中引用的变量（Codex 的 `env_key`）。Janus 以交互式登录 shell 读取环境，与新开终端看到的一致。

应用中的预览（`/api/local-config`）只列出会复制的文件和变量名，不显示值。

<a id="secrets"></a>
## 凭据保存

| 内容 | 位置 | 权限 |
| --- | --- | --- |
| Agent 的凭据字段、复制来的凭据变量和 Claude 手动设置的私有变量 | `~/.janus/data/secrets/agents/<id>.json`（目录 `0700`） | `0600` |
| 资源库 MCP 服务器的环境变量和 HTTP header 值 | `~/.janus/data/secrets/library/<资源 id>.json`（目录 `0700`） | `0600` |
| Agent 自己的登录状态（如 Codex 的 `auth.json`、Claude Code 的 `.claude.json`） | `~/.janus/data/agents/<id>/config/` | Agent 自己决定 |
| Janus home | `~/.janus/` | `0700` |

- SQLite、Run 快照、事件和设置接口只记录凭据字段和变量的名字（`secretsSet`、`importedEnv`、`envKeys`、`headerKeys`，以及资源库的 `vars[].set`），不返回值。MCP 的值在打开会话时读取，放进 `mcpServers` 交给 Agent。
- 返回值的接口只有两个：`GET /api/library/mcp/{id}/values` 供应用的 MCP 编辑器显示和修改资源库 MCP 服务器的值，`GET /api/connections/{id}/env` 供 Agent 编辑器显示环境变量的全部值（令牌也在，本地优先，见 [ADR：Agent 的环境变量在编辑器里全部显示](../decisions/20261121-agent_env_visible.md)）。两个接口它只回答本机的应用：`Host` 必须是回环地址（`127.0.0.1`、`localhost`、`[::1]`），带 `Origin` 或 `Sec-Fetch-Site` 的请求（浏览器里网页发出的）返回 403，所以网页（包括把自己的域名改绑到 `127.0.0.1` 的网页）读不到这些值。同一用户的其他进程本来就能读 `0600` 的值文件，不受这个限制影响。Agent 的其他凭据（Codex 的 API Key、Claude 订阅的 OAuth Token、复制来的凭据变量）不经任何接口返回。见 [ADR：MCP 服务器的值在编辑器里能看能改](../decisions/20261119-mcp_values_visible.md)。
- 登录日志返回给应用前，凭据值替换为 `<secret>`。
- 切换认证方式时，新方式用不到的凭据被删除。

Claude 的环境变量编辑器可以接收凭据。常用模型、推理强度、压缩窗口等参数及普通 HTTP(S) 服务地址保存在连接设置中。含用户信息、查询参数或片段的服务地址和其他非空变量均按私有值保存。SQLite 和设置接口在 `env` 中用 `null` 标记这些名字，只有本机应用经 `GET /api/connections/{id}/env` 读到值。旧版曾手动粘贴到环境变量框中的私有值会在数据版本 13 迁出，升级前的数据库备份仍含旧数据。

Codex 的自定义 API 密钥用独立的 API Key 字段填写。Codex 高级设置中的环境变量会作为普通配置保存并返回。

<a id="setup_ids"></a>
## 设置对象的 id

Agent、角色、工作区和资源库中的 id 会成为 Janus home 中目录和文件的名字（`data/agents/<id>/`、`data/secrets/agents/<id>.json`、`data/secrets/library/<id>.json`、`data/library/sources/<id>/` 等，全部来自 `Layout`），由 `check_id` 校验：只能用小写字母、数字和 `-`，以字母或数字开头，最长 40 个字符。保存时校验客户端给出的 id，删除 Agent、角色和拼出资源库的路径前也会校验，所以接口请求不能让 Janus 在这些目录之外写入或删除文件。

<a id="workspace_access"></a>
## 工作目录访问

- Git 仓库（有提交）上的每个任务在自己的 worktree（`<Janus home>/work/runs/<run>`）中运行，运行期间不改用户的目录，每次交付时（以及交付时没能合并、用户验收时）把结果快进到用户的分支和目录（见下）；同一个任务内的子任务共用这个 worktree，并行的子任务可能修改同一批文件。非 Git 目录中任务直接在用户选择的目录中运行，改动立即生效，同一目录上的多个任务也可能修改同一批文件（创建时只提醒）。
- Janus 自己会写用户仓库的 Git 数据，只限于：创建和锁定 worktree（`.git/worktrees/`），移除时只删 Janus 自己那一条（`git worktree remove --force --force`），不 `prune` 整个仓库；交付（或验收）时在 worktree 里提交、必要时把这个提交变基到最新的源分支，再把创建 Run 时检出的分支快进到结果：分支检出在用户的目录时在那里 `git merge --ff-only`，用户目录里的文件随之改变，否则只移动分支；移除 worktree；数据升级移动 Janus home 的目录时，用 `git worktree repair` 改写原仓库和 worktree 之间的两处链接。所有写操作都带 `-c core.hooksPath=/dev/null`，不运行仓库的钩子（钩子可能是 Agent 写进去的）；所有对用户目录和副本的 git 调用（读和写）都关掉仓库的文件系统监视程序（`core.fsmonitor`，也是仓库配置里会执行的程序），不等终端输入（`GIT_TERMINAL_PROMPT=0`），也不继承 Janus 启动环境里指向别处的 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE`、`GIT_CONFIG_PARAMETERS` 这类变量（`git::command`，资源库从 Git 来源拉取时也经过它）。仓库自己配置的过滤器（clean、smudge）和 LFS 照常运行，副本才完整，这是明确接受的风险。worktree 里有没做完的变基、合并等操作时什么都不提交。变基冲突时，Janus 中止变基，把冲突交给负责人在 worktree 里解决（负责人运行的 `git rebase` 是 Agent 自己的操作，按它的权限模式执行），解决后再次交付，见 [ADR：验收冲突交给负责人解决](../decisions/20261123-lead_resolves_accept_conflicts.md)。快进会覆盖用户未提交的改动或没纳入版本管理的同名文件（包括被忽略的 `.env`）、源分支被删除或被回退改写时，不合并（验收时返回失败），用户的目录和分支不变，不会留下半合并的状态，也不自动暂存用户的改动。不推送，不改源分支以外的分支，不删除分支；没有配置提交身份时验收报错，不替用户编造身份。见 [ADR：worktree 写入用户仓库的边界](../decisions/20261119-worktree_trust_boundary.md)、[ADR：验收时把结果合并回任务开始时的分支](../decisions/20261120-merge_back_on_accept.md) 和 [ADR：交付时把结果合并回分支](../decisions/20261123-merge_back_on_delivery.md)。
- **交付时合并是明确接受的风险**：Agent 写的代码在用户核对之前就进了用户的分支和目录，验收只是事后的认可，和不用 worktree 时 Agent 直接改用户目录一样。Janus 只让分支前进（快进），不推送，不覆盖用户未提交的改动；用户不满意时让负责人修改，下一次交付再合并，或者自己 `git revert`。[值班](../domains/20261121-loops.md)派出的任务没有人看着，交付时同样合并进用户的分支。
- 创建 worktree 时，原仓库 `.worktreeinclude` 列出的被忽略文件（例如 `.env`）会复制进 worktree，供任务的 Agent 读取。这些文件由用户自己列出；Janus 不复制其他被忽略的文件，也不跟随符号链接。
- 一个 Agent 能做什么由它自己的权限模式执行。Janus 不做操作系统级的文件、网络或终端限制，权限模式也不是 Janus 的强制安全策略。
- 数字员工没有选择权限模式时，Codex 以 Full access、Claude Code 以 Bypass permissions 运行：不经确认就能修改任意文件、执行命令和访问网络。需要审批的场景，在数字员工的「权限」中改选其他模式。Codex 的模式在启动时同时写进线程的审批和沙箱设置，`/goal` 的各轮也照它执行；2026-11-22 之前，Codex 负责人的 `/goal` 实际仍在工作目录沙箱里、需要时询问，比界面显示的模式更严。见 [ADR：Codex 和 Claude Code 默认不受限运行](../decisions/20261118-unrestricted_default_mode.md)。
- 负责人说明和协作者的约定要求 Agent 只在用户要求时提交、推送或部署（协作者按子任务说明），并且只做到要求的程度；没有要求时不做。这只是指令，不是强制，见 [ADR：用户要求时 Agent 提交、推送和部署](../decisions/20261123-commit_push_on_request.md)。Agent 在 worktree 里的提交随交付一起带回源分支；Agent 推送或部署时走的是它自己的凭据和权限模式。Janus 只在交付或验收时提交并快进源分支（见上），从不推送。
- 非 Git 目录没有 diff，也无法用 Git 回退。删除一个 worktree 中的 Run 时，没提交的改动存成补丁留在 `<Janus home>/data/deleted-runs/`；被忽略的文件（例如复制进来的 `.env`）不进补丁，补丁里不会有凭据，这些文件的改动随 worktree 删除。补丁存不下来（Git 索引被占用、磁盘写不进）时不删 worktree，删除失败并说明原因；原仓库不在了时整个 worktree 目录原样移到 `deleted-runs/<run>/`。
- [对话](../domains/20261120-chats.md)的工作目录是 Janus 新建的 `<Janus home>/work/chats/<run>`，不是用户的目录。它在 Janus home 里面，和 worktree 一样只是起点，不是边界：数字员工按自己的权限模式能读写的范围不变，默认的 Full access、Bypass permissions 下也能读到 Janus home 中的数据库和 `data/secrets/` 下的凭据，和在目标 Run 中一样。删除对话时这个目录连同里面的文件一起删除，不留补丁，删除前应用会说明。删除 Run 或对话时，它的会话在 Agent 配置目录里留下的会话记录（Claude Code 的 `projects/…/<会话>.jsonl`、Codex 的 `sessions/…`）也一起删除，删掉的对话不会在 Agent 自己的记录里留下全文。

<a id="loops"></a>
## 工作区值班与无人值守的派发

[工作区值班](../domains/20261121-loops.md) 按时间表自己醒来，没有人看着。它不新增网络监听、下载来源或凭据存放：值班的会话就是负责人的一个会话（Git 仓库里在它自己的副本中），能做的事和用户在对话里让负责人做的一样。下面几项是明确接受的风险：

- **值班自己改了文件**：系统层要求值班不改文件、要改的派成任务，但这只是指令，它按负责人的原生权限模式工作，默认不受限时能改文件。Git 仓库里值班在自己的副本（`work/loops/<run>` 的 worktree）里干活，改动碰不到用户的工作区和分支，开工结束时新出现的改动记为 `loop.touched` 进收件箱，下次开工前清掉；但它仍能用 `git push`、`gh` 这类命令直接改外部，副本拦不住。工作区不在 Git 仓库里时它直接在工作区目录里干活，Janus 看不出改动，也不提醒，值班页明确写出这一点（`watchesFiles` 为假）。需要更严时，给负责人这名数字员工选只读的权限模式（值班也就不能用 `gh` 之类的命令回写外部）。
- **派出即开始**：值班派出的任务直接进派发队列，空出位置就以工作区团队的权限模式开始，没有人确认。外部文字（issue、评论）只经值班用自己的话写进目标，系统层要求把外部文字当数据，但提示注入仍可能让值班写出不该做的目标。按来源决定信任（陌生人的 issue 只讨论、团队成员的才派发）留到之后写进代码。值班还能用同一个 key 再调用 `dispatch`，给自己派出、还在进行中的任务的负责人递话（写明来自值班，不冒充用户）；只限它自己派出的任务，别的值班和用户自己的任务收不到，风险和它写进目标的文字相同。
- **对外发言**：值班用自己的工具（例如 `gh issue comment`）在外部平台回复，不经 Janus，也不经用户确认；这和对话里负责人能做的相同。建议在值班的提示里写明只在任务验收后回复。
- **不停地醒、不停地派**：工作没有时间和费用上限，时间表最短每分钟到点一次，值班自己也能约一次 60 秒后再醒，派出的任务结束也会唤醒它。同时在做的任务受派发队列的槽位限制，停滞和原地打转照常报告，用户可以暂停或删除值班。

<a id="team_memory"></a>
## 团队记忆

[团队记忆](../domains/20261123-team_memory.md)让 Agent 写下的笔记被同一工作区之后的会话读到（笔记不在系统层里，会话需要时经 `recall` 检索到，见 [ADR：团队记忆按需检索](../decisions/20261123-memory_on_demand.md)），这扩大了信任边界：一个会话里写错的、或被外部文字诱导写下的内容，会被之后的 Run 读到。它不新增网络监听、下载来源或凭据存放，笔记只在 Janus 的 SQLite 里。对策和明确接受的风险：

- **只经工具写，按工作区隔离**：笔记只能经 `janus.remember` 写入，工具从会话的令牌找到 Run、从 Run 找到工作区，别的工作区的笔记读不到也改不了；对话没有团队记忆。只有整理会话能删除。
- **记来源**：每条记着最后写它的 Run、成员和时间，应用里显示；被取消的 Run 写的笔记不给之后的 Run。这是按来源判断可信度的基础，用户据此删掉可疑的笔记。
- **是笔记，不是规则**：注入的说明写明共享资料、本次目标和用户的话优先，笔记用之前先核对代码；要团队必须遵守的，只能由用户加进共享资料。
- **外部内容只留指针**：说明要求 issue、网页、工具输出这类外部文字最多留链接、不抄进笔记，整理时也一样；这只是指令，提示注入仍可能让 Agent 写下诱导性的笔记（记忆投毒，OWASP ASI06）。明确接受这一风险：笔记有来源、用户可以随时查看和删除，整理会在之后的 Run 推翻它时删掉。
- **不保存凭据**：像凭据的内容（私钥头和常见服务的令牌格式）拒绝写入；格式不常见的密钥认不出来，这一点也明确接受。
- **整理会话**：在 Janus home 自己的空目录里，只给记忆工具；但它按负责人的原生权限模式工作，仍能运行命令，和用户在对话里让负责人做的事相同。
- **Agent 自带的记忆**：Claude Code 的 auto memory 在 Janus 启动的会话里关闭（启动环境的 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`），不写它的配置文件，用户自己在 Janus 之外使用不受影响。

<a id="network_exposure"></a>
## 网络暴露

- HTTP 服务没有鉴权。默认只监听 `127.0.0.1:7878`。
- 把 `JANUS_ADDR` 改为非回环地址，会把设置、凭据名、运行记录、目录检查（`/api/inspect`）和全部控制接口暴露给能访问该地址的任何客户端。
- 看板 MCP 端点的 URL 带令牌，防止其他 Run 和本机其他进程误用；它不是面向网络的认证机制。令牌的随机密钥取自 `/dev/urandom`，读不到时负责人的会话不启动，不退回到可猜测的时间戳和进程号。
- `/api/file` 只返回任务的产物文件（`data/runs/<run>/artifacts/<task>/<文件>`，解析符号链接后判断），Janus home 中的数据库和凭据不能通过它读取。选择目录用系统的文件夹选择框，服务不提供目录浏览接口。
- 看板 MCP 的 URL 中的令牌由 Run 的随机密钥和 `who` 派生，每个会话只能以自己的身份访问看板，见[看板 MCP 工具](../interfaces/20261031-board_mcp.md#transport)。对话没有看板：对话中数字员工的令牌只对它的 MCP 路由有效（打开了 `hires` 的还能调用 `propose_employees`，见[数字员工文件](#role_files)），拿它访问看板端点返回 403，不能借看板编排任务或冒充负责人。

<a id="adapter_install"></a>
## 适配器安装

- 适配器来自 npm（`@agentclientprotocol/codex-acp`、`@agentclientprotocol/claude-agent-acp`）。Janus 不校验包的签名，信任边界与手动执行 `npm install` 相同。
- npm 安装带 `--ignore-scripts`，不执行包自带的安装和生命周期脚本。
- 安装命令在 Janus 进程自己的环境中运行（`PATH`、npm 配置、代理），不是 Agent 的隔离环境。
- 服务启动后和之后每 6 小时，Janus 对已安装的适配器自动执行 `npm view <包> version`，向 npm（或用户 npm 配置里的 registry）查询最新版本；查到比当前新的版本时，**不需要用户确认，直接安装并切换**，这是 2026-11-24 起新增的信任边界，见 [ADR：自动接受并安装适配器的新版本](../decisions/20261124-automatic_adapter_updates.md)和[自动检查与升级](../architecture/20261031-adapters.md#update_check)。
- 自动接受的代价由以下限制控制：安装仍带 `--ignore-scripts`，只执行适配器进程本身；每个版本装在自己的目录，切换前的版本保留，用户可以从「切回历史版本」切回并固定（固定后不再自动升级），坏版本不会删掉能用的旧版本；安装和升级的版本、命令和输出记在 `~/.janus/logs/adapters/<id>.log`。Janus 不校验包的签名，也不做安装后的启动探测或自动回滚，坏版本要由用户切回。
- 来源写在代码中，应用和接口不能指定其他来源。

<a id="library"></a>
## 资源库

规则见[资源库](../domains/20261116-resource_library.md)。

- **不碰 Agent 自己的配置**：资源只在会话启动时通过 `session/new` / `session/load` 的 `mcpServers`、`_meta` 和进程环境变量交给 Agent，不写用户的 `~/.claude`、`~/.codex`，也不写 Janus 隔离目录中的 Agent 配置。Agent 不读取用户自己的 Agent Skill 目录：Skill 只能在应用中新建、从用户选择的目录复制，或从 Git 来源导入。
- 扫描本机目录时，只在所选目录内发现 Skill，跳过符号链接、`.git` 和 `node_modules`。复制时再次核对候选路径，只复制每个 Skill 自己目录内的普通文件，跳过隐藏文件（例如 `.env`、`.git`）和 `node_modules`。符号链接的目标必须位于该 Skill 目录内。单个 Skill 最多包含 2000 个文件，总大小不超过 20 MB。
- **Git 来源是第三方内容**：只支持 GitHub 链接。Janus 只克隆和读取其中的 `SKILL.md`，不执行仓库中的任何文件，也不从仓库导入 MCP 服务器；扫描不跟随符号链接，克隆时不下载 Git LFS 内容、不弹出凭据输入。Skill 的内容会作为说明交给 Agent；是否可信，由用户在导入时判断。
- **精选库是第三方内容**：资源库的「推荐」列出 Janus 挑选、核对过的第三方 Skill 仓库和 MCP 服务器，列表随应用发布，显示时不访问网络。一键添加和用户自己粘贴链接、填写服务器相同：Skill 克隆仓库的默认分支，命令启动的服务器用 `npx -y <包>@latest` 或 `uvx <包>` 运行最新版本，都不锁版本，包或仓库被篡改时会拿到被篡改的内容。见 [ADR：资源库的精选库随应用发布](../decisions/20261119-library_catalog.md)。
- **资源包是副本**：Run 创建时 Skill 复制到成员自己的资源包。Codex 的 `additionalRoots` 会把资源包加入会话的文件访问范围，Agent 改动资源包只影响这个成员，不影响资源库和其他成员。
- **凭据**：填写或粘贴的配置中的值保存到 `data/secrets/library/`（`0600`）。删除资源时一并删除它的值。值只在 Janus 进程启动命令服务器或连接 URL 服务器时读取，不交给 Agent，不进 `session/new`、快照、事件和日志。
- **每项资源都给所有数字员工**：资源库里的每项资源对每个 Run 的负责人和所有协作者开放，不按角色划分，也不能收口。添加一个带凭据、有副作用的服务器（写数据库、发消息、花钱），就意味着所有数字员工都能调用它；不想让数字员工用的服务器，不要加进资源库。负责人派出子任务后只用来查看：Janus 不拦截，派出后的每个新工具记在看板上、交付时列为风险。见 [ADR：资源库的每项资源都给所有数字员工，只经两个路由提供](../decisions/20261120-library_routed_only.md)。
- **MCP 路由由 Janus 运行服务器**：命令启动的服务器不由 Agent 进程启动，而是由 Janus 进程在第一次调用时启动。它不继承 Janus 进程的环境：和 Agent 一样只拿到隔离环境（[Agent 运行环境隔离](#agent_isolation)，`HOME` 和 XDG 目录在 `~/.janus/data/library/servers/<资源 id>/`，跨 Run 保留；`TMPDIR` 在 `~/.janus/tmp/servers/<资源 id>/`；删除资源时一起删除）加上资源保存的值，工作目录是 Run 的工作目录。它看不到用户 shell 里的密钥和主目录下的文件（例如 `~/.ssh`），能读写的是 Run 的工作目录和自己的隔离目录。默认同一个 Run 的会话共用一个进程（标成「每个会话单独运行」的除外），在自己的进程组里，Run 停止时连同它派生的进程一起结束。经它写的文件不在 Agent 上报的编辑里，Janus 的文件归属和越界提醒看不到。路由端点只在本机监听地址上，令牌和 `who` 与看板相同；每次调用记一条 `mcp.routed` 事件，不记参数。
- **Janus 进程连接 URL 服务器**：HTTP、SSE 服务器不交给 Agent，由 Janus 进程（`orchestrator::mcp_client`，`reqwest`）连接用户填写的地址，带上资源保存的 header（例如 `Authorization`）。这是 Janus 主动发出的网络请求：目标只是资源库里填写的地址，TLS 用 macOS 系统的证书库，遵循系统代理，不跟随 SSE 服务器给出的、不同源的消息地址（header 会随每条消息发送）。服务器返回的内容作为工具结果交给 Agent，和 Agent 直接连接时一样不可信。Streamable HTTP 的会话在 Run 停止、闲置 10 分钟或修改资源时用 DELETE 结束。
- **Skill 路由**：Agent 按系统层给出的路径读 `janus-skills` 的目录，再按目录读取 Janus 目录下资源包里的文件。Janus 从工具调用里认出读了哪个 Skill 并记成 `skill.used`，只记 Skill 的名字和版本，不记调用的其他参数。

<a id="role_files"></a>
## 数字员工文件

规则见[数字员工文件](../domains/20261031-agents_and_roles.md#role_files)和[对话里提议的数字员工](../domains/20261120-chats.md#proposed_employees)，取舍见 [ADR：数字员工按分组管理，用文件导入导出](../decisions/20261125-role_files.md) 和 [ADR：招聘顾问在对话里用工具交出数字员工](../decisions/20261126-propose_employees_in_chat.md)。

- **指令是第三方内容**：对话里提议的指令之后会作为系统提示交给 Agent，一条恶意或错误的指令会在每次会话里起作用。所以提议要用户在表单里看过、勾选后才保存，从不覆盖已有的数字员工。Janus 不从文件导入数字员工，不读用户选的目录（[ADR](../decisions/20261126-no_role_import.md)）。Agent 不能直接新建或改写数字员工；Janus 没有给外部 Agent 管理数字员工的接口。
- **对话里的提议**：只有用户打开了 `hires` 的数字员工（默认只有招聘顾问）的对话能拿到 `janus` 服务器，令牌由对话的随机密钥派生，只对这个对话有效，只有 `propose_employees` 一个工具。工具只把提议记成对话的事件，不改任何设置；创建只能由本机应用调 `POST /api/runs/{id}/proposal`，服务端从事件读回这一批，不接受应用传来的内容。`hires` 只由用户在编辑器里打开，提议的人不能带上它，所以一个数字员工不能经由提议让别人也能提议。
- **导出由应用写**：服务只经 `GET /api/roles/{id}/file` 给出文件内容，写到哪里由应用在用户选的文件夹里决定，服务不向用户目录写文件。文件里没有 Agent、模型、会话控制项，也没有任何凭据。

<a id="app_updates"></a>
## 应用更新的来源

- 更新只来自 Info.plist 中 `JanusUpdateRepo` 指定的 GitHub 仓库的最新 Release（只有 CI 带版本号打包的发布写入它，本地打包不写，不会更新自己），通过 HTTPS 下载，每个部分都核对 `update.json` 中的 SHA-256。
- 当前应用用固定证书签名时，新版本必须满足当前应用的指定要求（同一个 bundle ID、同一张证书），否则拒绝安装。这挡住了被篡改的 Release 附件；能签出被接受的更新的只有持有签名证书的人，证书的 `.p12` 和 Actions secrets 要妥善保管。
- 当前应用是 ad-hoc 签名时没有签名者可以要求，只依靠 HTTPS 和 SHA-256，信任程度与手动下载 DMG 相同。2026.11.18.5 起发布用固定证书签名（私钥只在生成它的机器的 `~/.config/janus/signing/` 和仓库的 Actions secrets 中，不在 Janus home），从 ad-hoc 版本更新到它时仍按 ad-hoc 规则接受，之后只接受同一张证书签名的版本。
- 替换脚本只移动应用包、打开新应用，不使用管理员权限；应用所在目录不可写时放弃更新。
- 自动更新（默认打开，「设置 › 通用 › 更新」可以关掉）不经用户点击就安装新版本，安装前的来源、SHA-256 和签名者校验与手动更新完全相同，没通过就不装；它只在没有任务和对话在进行时重开应用，不打断进行中的工作。信任的仍是持有签名证书的人：证书泄露时，攻击者签出的版本在打开自动更新的机器上会被自动装上，而不是等用户点击，这是明确接受的风险，见 [ADR：自动更新](../decisions/20261123-automatic_updates.md)。

<a id="local_runner"></a>
## 本机运行器

维护者的 Mac 上常驻一个 GitHub Actions 自托管运行器（标签 `janus-local`），GitHub 的 macOS 运行器 5 分钟排不到时，CI 的应用测试和 Release 的打包改在它上面跑，见 [CI 与发布：本机运行器](../operations/20261101-ci_release.md#local_runner)和 [ADR](../decisions/20261124-local_runner_fallback.md)。这只涉及维护者的机器，使用 Janus 的人不受影响。

- 运行器以维护者自己的账户执行工作流，能读写这个账户能读写的一切，任务里还带着仓库的 Actions secrets（签名证书）。所以能让任务跑到它上面的人，等于能在这台机器上运行任意代码。
- 推送到 `main` 和标签的只有维护者；工作流里只有推送触发的运行才有本机这条腿。
- 仓库是公开的，Pull Request 可以改工作流文件、把任务指向自托管运行器。挡住它的是仓库设置：外部贡献者的工作流一律先审批（`all_external_contributors`），不批准就不会运行。**Agent 不批准外部贡献者的工作流运行**，也不把这项设置改松；需要运行外部 PR 的检查时，由人看过它对 `.github/` 的改动再决定。这是明确接受的风险：一次误批准就是在维护者的机器上执行别人的代码。
- 运行器从 `github.com/actions/runner` 的发布页下载，锁定版本并核对发布说明里的 SHA-256；它之后会自己更新（GitHub 要求运行器保持较新的版本）。
- 签名步骤在本机会新建临时钥匙串并改用户的钥匙串搜索列表，工作流的最后一步恢复列表并删除临时钥匙串。证书的 `.p12` 本来就在这台机器的 `~/.config/janus/signing/`，没有多出存放位置。
- 公开的任务日志带着运行器的工作目录，所以它装在 `/Users/Shared/janus-actions-runner`，路径里没有用户名；工具报错时打印的其他路径（例如 `~/.cargo`）仍可能出现在日志里。

<a id="data_upgrade"></a>
## 数据升级与备份

- 升级前的备份 `backups/janus-v*.db` 是 `janus.db` 的完整副本，内容与数据库相同：设置对象、Run 记录和事件，不含凭据（凭据不在数据库里）。目录在 Janus home（`0700`）之下，其他用户进不去；备份文件的权限与 `janus.db` 相同。只保留最近 5 份。
- 迁移只修改 `janus.db`，不读写用户的 Agent 配置和工作目录，不访问网络。
- 数据升级的端到端测试（`just e2e-upgrade`）从本仓库的 Git 标签用 `git archive` 取出旧版本源码并在临时目录构建，不下载发布产物；服务监听 `127.0.0.1` 上一个空闲端口，使用临时 Janus home，不碰用户的 `~/.janus` 和 7878 端口。
- 产品端到端测试（`just e2e-product`）同样只用临时 Janus home 和 `127.0.0.1` 上的空闲端口（应用自启服务的场景另选一个），替身适配器运行仓库中的 `fake_acp.py`，适配器的新版本检查问的是本机的替身 registry，不联网；应用的本地设置写进独立的 `JANUS_DEFAULTS_SUITE`，结束时删除。`--real` 的冒烟测试用独立的临时 home 和另一个空闲端口，只读地拷贝用户 Janus home（默认 `~/.janus`）中的 Codex 和 Claude Code Agent：设置经接口写入，凭据文件按文件复制（来源是旧布局时从 `agents/<id>/secrets.json`），「复制本机配置」再从同样的来源目录复制；从 npm 安装官方适配器（与配置检查相同的来源），结束时删除临时 home 中复制来的凭据，`--keep` 也不保留。

<a id="macos_permissions"></a>
## macOS 权限引导

- 「设置 › 通用 › macOS 权限」引导用户授予完整磁盘访问、应用程序管理和屏幕录制。仅检查当前 Janus 应用的权限；独立服务、其他终端或不同负责进程启动的 Agent 可能需要分别授权。系统权限与 Agent 原生权限模式分别生效，完整磁盘访问不绕过文件所有者权限、SIP 或 Agent 沙箱。
- 三项权限都由应用检测，状态只来自 macOS 对当前进程的回答，用户的操作不会被记成授权。屏幕录制用公开的预检查和申请接口，不在检查中截图。完整磁盘访问通过打开系统 TCC 数据库检测，打开后立即关闭，不读内容。应用程序管理用 TCC.framework 的私有函数 `TCCAccessPreflight` 只查询当前应用自己的状态；它不弹提示、不改任何授权，系统没有这个函数或答案无法识别时显示「测不出来」。
- 用户点击「一键开始授权」后逐项申请或打开系统设置，允许跳过。首次运行和安装标识变化后有未授权的项目时自动显示引导，不自动授予权限、不重置现有授权、不读取 TCC 数据库的内容或其他私人文件，也不改写其他应用来触发权限提示。
- 「重新打开 Janus」只是退出后用 `open` 重新打开当前应用包，不重置、不修改任何授权；删除系统设置中的旧授权记录由用户自己完成。
- `data/app/permissions.json` 位于 Janus home，只保存安装标识和是否处理过引导，不保存权限状态；记录不授予权限，也不向服务或 Agent 注入权限设置。源码运行不会对宿主终端发起权限申请。
- 决策、限制与依据见 [macOS 权限引导 ADR](../decisions/20261117-macos_permission_guidance.md)。

<a id="model_prices"></a>
## 模型价格的来源

- 价格只来自 `https://models.dev/api.json`，来源写在代码中（`backend/src/prices.rs`），接口不能指定其他地址。
- 下载用系统的 `curl`，只允许 HTTPS，限时 120 秒、限 64 MB，在 Janus 进程自己的环境中运行（`PATH`、代理）。内容只当 JSON 数据解析，不执行任何部分；每个价格必须是非负的有限数。
- 解析后的表写到 `~/.janus/cache/prices.json`，整体替换；下载或解析失败时保留原来的表。
- 价格只用于账单上的估算，标明不是账单；不写进事件，不影响调度、交付或 Agent 的会话。被篡改的价格最多让估算不对。决策见 [ADR：按 models.dev 的价格估算用量](../decisions/20261115-model_prices.md)。

<a id="scope_limits"></a>
## 适用范围

当前是单机、单用户模式，适合本地开发和实验。不提供多租户、远程执行、强隔离执行或生产级访问控制。在用于重要项目之前，先评估共享工作目录、无鉴权和缺少操作系统级沙箱这三项限制。
