# Agent 变更的经验教训

本仓库的代码由 Agent 修改和合并。本文记录定期清理中发现的问题：哪些改动不应该合并、哪些验证不够严密，以及合并前要做的检查。合并前检查规则同时写在仓库根目录的 `AGENTS.md` 中，Agent 每次会话都会加载；本文保留规则的来由、未解决项和清理记录。新增或修改规则时两处同步。每次清理在[清理记录](#cleanup_log)中追加一条。

<a id="checklist"></a>
## 合并前检查

满足以下全部条件才合并。不满足的项写进提交说明并说明原因，不能静默跳过。

1. `just test` 通过，并且新行为有测试。测试要走真实的鉴权、校验和持久化路径，不能直接读内部状态绕过它们（见 [L-03](#l03)）。
2. `cargo fmt --check` 和 `cargo clippy --all-targets -- -D warnings` 没有诊断，CI 中执行，本地用 `just lint`。新代码不新增 `#[allow(...)]`，确有必要时在旁边写明理由。
3. 一个提交只做一件事。提交说明里的条目超过三项、或者涉及互不相关的功能时，拆开提交（见 [L-04](#l04)）。
4. 源文件不超过 2000 行。新功能放进对应职责的模块；一个文件接近上限时先按职责拆成子模块（例如 `orchestrator/`、`agents/`），再加功能（见 [L-04](#l04)）。
5. 扩大信任边界的改动（新的下载来源、执行第三方脚本、新的网络监听、读写用户目录、改变凭据的存放）要先写 ADR，并更新[安全边界](security.md)（见 [L-05](#l05)）。
6. 已知的高影响审查问题（`docs/review/` 和本文的未解决项）要么在合并前修复，要么在[安全边界](security.md)中写成明确接受的风险。新功能不能排在未处理的高影响问题之前（见 [L-01](#l01)）。
7. 删掉不用的代码，不用 `let _ = x;`、`#[allow(dead_code)]` 或注释掉来「保留」它（见 [L-06](#l06)）。
8. 新功能和已有功能的流程相同时，提取共用函数，不复制代码（见 [L-07](#l07)）。
9. Run 和测试不得修改仓库内的文件，工作目录不指向仓库内部。
10. 状态和归属用类型表达：多选一的状态用枚举，不用字符串；属于谁、是哪一类，写成字段，不从键或 id 的形状（前缀、分隔符）读出来；能由已有状态推出的值不另存一份；运行状态由 `App` 持有，不放进进程级的全局变量，代码读 `App.cfg`，不读进程的配置（见 [L-08](#l08)）。

<a id="lessons"></a>
## 经验教训

<a id="l01"></a>
### L-01：审查发现没有跟进

2026-10-31 的[代码审查报告](../review/code_review_2026_10_31.md)列出 J-01 等 5 个高影响问题。之后 17 个提交都在加功能，到 2026-11-08 清理时 J-01（协作者把 MCP URL 中的 `who` 改成 `lead` 就能拿到负责人工具）仍未修复，报告也没有挂到任何索引下，后来的 Agent 读文档时看不到它。

教训：审查报告必须有去处。每个问题要么修复，要么在相关文档中写成接受的风险；报告本身要从索引可达。

<a id="l02"></a>
### L-02：质量门禁只在本地，不在 CI

CI 只运行 `cargo test`。`cargo fmt --check` 和 `cargo clippy -D warnings` 在 10-31 已经失败，之后没有人处理，诊断一直存在。门禁不在 CI 里，Agent 就不会在意它。

教训：想要守住的规则要放进 CI。和默认值不同的约定写进配置（例如 `backend/rustfmt.toml` 的行宽），不要留一个永远失败的检查。

<a id="l03"></a>
### L-03：测试绕过了要验证的边界

看板 MCP 的测试直接读出 Run 的令牌，再用任意 `who` 调用接口。测试因此证明「令牌对了就能用」，却从来没验证「协作者的 URL 不能冒充负责人」，J-01 一直被测试掩盖。

教训：鉴权类测试至少要有一个反例：拿低权限的凭据去请求高权限的操作，断言被拒绝。测试使用和真实客户端相同的方式获得凭据。

<a id="l04"></a>
### L-04：一次提交塞进多个功能，文件持续膨胀

`ceee92a` 一个提交包含插话、看板推送、编辑冲突检测、两个新工具、负责人卡住提醒和适配器来源切换，`orchestrator.rs` 一次增加 672 行，已到 6500 行。这样的提交无法逐项审查，回滚时也只能整体回滚；适配器来源变化这种安全相关的改动就混在功能里合并了。

教训：一个提交一个主题。文件超过 2000 行后，先拆分再加功能。

<a id="l05"></a>
### L-05：安全相关的改动混在功能提交里

同一个提交把 Codex 和 Claude Code 的适配器从 npm 发布版改为从 GitHub 默认分支的最新提交构建：不锁定提交，安装时包含开发依赖并执行构建脚本，运行在 Janus 进程自己的环境中。文档同步更新了，但没有 ADR，提交标题也看不出来。

教训：改变代码从哪里来、在什么环境执行，是信任边界的变化，要单独提交、写 ADR，并优先锁定到具体提交。当前状态记录在[未解决项](#open_items)。

<a id="l06"></a>
### L-06：用占位代码安抚编译器

测试中出现过 `let list = …; let _ = list;` 这种定义后立刻丢弃的变量，`Source::Npm` 在没有任何使用者后加上 `#[allow(dead_code)]` 保留。这类代码让读者以为它有用途。

教训：不用的代码直接删除，需要时从 Git 历史中找回。

<a id="l07"></a>
### L-07：复制整个模块而不是提取共用代码

`47eb897` 新增 MCP 资源库时，把 Skill 资源库的「检查远端提交」「浅克隆到临时目录」「替换检出目录」约 100 行逐行复制到 `mcp_sources.rs`，只改了函数名和字段名。之后修一处的 bug，另一处不会跟着修。

教训：第二次写同样的流程时就提取共用函数。新模块与已有模块结构相似时，先看能复用什么，再写新代码。

<a id="l08"></a>
### L-08：隐式状态：从字符串的形状读出归属

待处理的决定（提问、审批、表单）只存在一个以键为索引的表里，谁在等它从键的前缀读出：`q-<task>-<n>-` 和 `req-<task>-<n>-`。任务 id 可以带 `-`，任务 `api` 第 1 次尝试结束时，前缀 `q-api-1-` 也匹配任务 `api-1` 的问题 `q-api-1-1-1`，把别人的问题撤回；负责人回复 `api` 时按前缀 `q-api-` 找问题，可能回答成 `api-1` 的。负责人的会话和任务的会话共用同一个以字符串为键的表，名为 `lead` 的任务结束时会关掉负责人自己的会话。同一次检查里还发现：接管状态是三个由人手同步的布尔值，Run 的「已取消」标志和状态各存一份，负责人的状态散在五个字段里，Skill 库的路径读进程的配置而不是 `App` 的 home（测试会写进用户真实的 `~/.janus`），适配器任务和价格表是进程级全局变量，应用里的状态全是字符串（有一处判断的是根本不存在的 `created`）。

教训：归属和状态要写成类型和字段（`SessionKey`、`Pending.owner`、`Hold`、`LeadGoal`、`RunStatus`），由编译器检查；能推出的值不另存；`App` 持有自己的一切，测试的 `App` 才真正与用户的数据隔离。
