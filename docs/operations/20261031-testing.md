<a id="running_tests"></a>
## 运行

```sh
just test
```

等于 `cd backend && cargo test`。提交前再运行 `just lint`，执行与 CI 相同的 `cargo fmt --check` 和 Clippy 检查。

macOS 应用的测试见 [macOS 应用](#macos_app)。Web 客户端的类型检查和单元测试用 `just test-web`（Node 自带的 `node:test`，不需要服务和浏览器），浏览器测试见 [Web 端到端测试](#web_e2e)。

测试不访问网络，不调用真实 Agent，也不安装适配器：脚本化 Agent 装成 Codex 和 Claude Code 的替身适配器（`stand_in_adapters`），由 `python3` 代替 Node 启动。需要本机有 `git` 和 `python3`。

<a id="e2e"></a>
## 端到端验证

每个需求开发完成后运行 `just e2e`，它是合并前的必过门禁（`AGENTS.md` 合并前检查第 12 条）。它先单独构建一次 Web 客户端（`just web`：每次 cargo 编译都把 `web/dist` 嵌进服务，不能在别的步骤编译时改它，所以之后的步骤带 `JANUS_WEB_BUILT=1`，打包时不再构建）。五步互不依赖，`e2e/all.py` 让它们同时运行，各写各的日志（系统临时目录的 `janus-e2e-all-*`），每步结束时打印结果和用时，全部结束后打印产品和 Web 端到端测试的摘要、没通过那一步日志的最后 40 行和总结果；任何一步没通过，`just e2e` 就失败：

| 步骤 | 命令 | 验证什么 |
| --- | --- | --- |
| 1. 静态检查和后端测试 | `just lint && just test` | 格式和 Clippy（与 CI 相同），单元测试和进程内的流程测试（`flow_tests`），见[测试分布](#test_layout)；两者共用 Rust 的构建目录，所以在同一步里先后运行 |
| 2. 应用测试 | `just test-mac` | 应用的推导逻辑和视图，见 [macOS 应用](#macos_app) |
| 3. 产品端到端测试 | `just e2e-product` | 真实构建的服务和应用跑完每条用户旅程，见[产品端到端测试](#product_e2e) |
| 4. 数据升级测试 | `just e2e-upgrade` | 最近的发布版本写出的数据由当前版本升级，见[数据升级测试](#upgrade_tests) |
| 5. Web 端到端测试 | `just test-web` 和 `just e2e-web` | Web 客户端的类型检查和单元测试，再在嵌着它的真实服务上用 Chrome 按桌面和手机宽度核对页面，见 [Web 端到端测试](#web_e2e) |

`just e2e` 的参数交给第 3 步：

- 不带参数：从源码构建，替身 Agent 运行，结果确定，不访问网络，约 1 分钟（16 核的 Mac，代码已编译过；改了代码时多出编译的时间）。每个需求都跑。
- `--packaged`：测试 `just app` 打出的 `dist/Janus.app`（内置服务和 Node.js），能发现打包、签名和内置 Node 的问题。发布前必跑。
- `--real`：另加真实 Agent 的冒烟测试（`real` 场景）：负责人用本机负责人的 Agent（Codex 或 Claude Code），协作者用 Claude Code，需要网络，以及一个已经配好 Claude Code（负责人用 Codex 时还要 Codex）并通过配置检查的 Janus（默认 `~/.janus`，`--real-from <Janus home>` 指定其他的），会消耗 token（第一次运行约 5 分钟、135 万 token），视 Agent 发挥可能更久；它从一开始就和其他场景同时跑，所以整次验证的用时约等于它自己的用时。发布前，以及改了 ACP 集成、适配器、Agent 启动环境或负责人提示时必跑。

新功能改了用户可见的行为时，在产品端到端测试中新增或修改场景，见[编写场景](#e2e_scenarios)；Web 客户端画的页面在 `web/e2e/` 里加测试。e2e 只在本地运行，不在 CI 中运行。

<a id="product_e2e"></a>
## 产品端到端测试

`e2e/product.py`（`just e2e-product`）在真实的二进制上验证产品，覆盖 `flow_tests` 碰不到的部分：正式构建的适配器查找和 Node 启动（后端测试用 `python3` 运行替身适配器）、HTTP 接口、看板 MCP 端点、服务重启，以及应用从服务读到的状态。

运行方式：

1. 同时构建服务（`cargo build`）和应用（`swift build`）；`--packaged` 时运行 `frontend/scripts/package.sh --no-dmg`，使用 `dist/Janus.app` 中的 `janus-server`、应用和内置 Node.js。
2. 在系统临时目录创建 `janus-e2e-*`，其中有临时 Janus home、每个场景的 Git 工作目录和脚本化 Agent 目录。服务监听 `127.0.0.1` 上的一个空闲端口（每次运行由系统分配，所以两个任务各自的 worktree 里可以同时跑端到端测试），不碰用户的 `~/.janus` 和 7878 端口。
3. **替身适配器**：在临时 home 的 `cache/adapters/codex/9.9.9/` 和 `cache/adapters/claude/9.9.9/` 放入与官方 npm 包同名的包，`bin` 是一个 Node 脚本，它把标准输入输出交给 `backend/testdata/fake_acp.py`。Janus 照常用 Node 启动「Codex」和「Claude Code」，走的是正式的启动路径，Agent 的行为由脚本决定，不联网、不花钱。协作者也用 Claude Code 类型，经同一个替身适配器运行脚本化 Agent。
4. 启动应用，连接这个服务（`JANUS_HOME`、`JANUS_ADDR`），通过快照命令通道驱动（见 [macOS 应用](#macos_app)）。同时运行的场景各用一个应用（`Apps`，6 个，第一个之外的在 `setup` 运行时启动），一个场景留下的页面和表单不会碰到另一个；某个场景让它的应用退出了，下一个场景换一个新的。每个应用的本地设置写进自己的 `JANUS_DEFAULTS_SUITE`，结束时删除，不改用户自己的应用设置。
5. 按场景运行：自带服务的场景（`@scenario(own=True)`：`real`、`app-server`，以及要重启服务或用别的设置的 `queue`、`seats`、`restart`、`language`，它们经 `ctx.private` 拿到自己的 Janus home、服务和应用，`settings` 给应用另设本地设置）从一开始就在旁边运行；`setup` 最先在共用的服务上运行；其余场景各自建团队（Agent、数字员工、工作区、脚本化 Agent 目录），6 个同时运行。`setup-settings`、`setup-editors`、`setup-run` 只给 `setup` 做好的东西截图、和服务核对，所以也同时运行；它们声明 `needs="setup"`，只挑它们重跑时 `setup` 一起运行。测试里的应用默认用简体中文（`App` 写进本地设置的 `janus.language`），服务端给 Agent 的文字因此是中文，和机器的系统语言无关；`language` 场景另用英文。
6. 测试脚本扮演负责人的「大脑」：从脚本化 Agent 的 `calls.log` 读出负责人会话的看板地址，像 Agent 一样调用 `orchestrate`、`wait`、`reply`、`retry` 等工具；协作者的行为由 `script.json` 决定；用户的操作走 HTTP 接口，和应用发出的请求相同。
7. 每个场景结束时打开应用，等应用推导出的状态（`state` 命令写出的 Run 状态、任务状态、验证判定、收件箱、用量、资源库 Skill 的使用次数和改进提示）与服务记录的一致，再按页面截图，检查截图是真实窗口的尺寸且不是纯色：主窗口没有打开时，`shot` 截到的是菜单栏图标的小窗口，不能算画出来了。
8. 所有场景跑完后检查临时 Janus home 的顶层只有布局声明过的名字（`e2e/lib.py` 的 `HOME_TOP`，对应 `layout::TOP`），作为报告中单独的一项「Janus home」。
9. 报告写在 `janus-e2e-*/report/`：`report.md`（每个场景的检查项、用时和失败原因）、`janus.log`、`app.log`（另外几个应用是 `app-<n>.log`，自带服务的场景是 `janus-<场景>.log` 和 `app-<场景>.log`）和 `app/` 下所有应用的截图。没有 `--keep` 时删除报告以外的临时文件。新功能涉及的页面，开发者要亲自看一遍截图。

参数：`--only <场景>`（可重复）、`--list` 列出场景、`--no-app` 只测服务、`--keep` 保留临时 home 和工作目录、`--packaged`、`--real`、`--real-from`。有场景没通过时，最后一行给出只重跑这些场景的命令（带上同样的 `--packaged`、`--real`），构建是增量的，不用再等整套。

<a id="e2e_scenarios"></a>
### 场景

| 场景 | 覆盖 |
| --- | --- |
| `setup` | 服务的 meta、替身适配器、默认数字员工（产品研发组的 PMO 和 4 个专职角色、对话组的「老友」和「招聘顾问」，没有通用数字员工，只有这两个组）；非 PNG 的头像被拒绝；Agent 类型只有 Codex 和 Claude Code（添加自定义命令的 Agent 被拒绝）、两种 Agent 的配置检查和控制项；凭据不出现在设置接口中，Agent 编辑器经本机接口读到并显示全部环境变量的值（没有配对的网页和改绑的域名读不到，401）；没绑定 Agent 的数字员工不能做负责人；资源库的 Skill 和带值的 MCP（资源没有「给谁用」，收口和勾给数字员工的接口已删除，数字员工没有 `resources`）；协作者的 `session/new` 只有看板和 `janus-tools`，MCP 的地址和值都不在里面，也不进入 Run 记录和导出；命令服务器由 MCP 路由在 Run 的 worktree 里启动，HTTP 服务器（替身 `fake_mcp_http.py`）添加后预先连接并数出工具，经路由调用时带着保存的 header，经真实 HTTP 调用路由：`initialize` 的 `instructions` 列出各服务器和用途，`tools/list` 只有 `find_tools`、`call_tool`、`run_code`，空查询的 `find_tools` 列出全部工具（读完分页、不列只能以 task 方式调用的工具），按关键词找到的带说明和参数，经 `call_tool` 调用、名字写错时列出相近的工具，`run_code` 的脚本调用工具，直接 `tools/call` 未知工具返回 `-32602`，协作者的令牌不能冒充负责人，调用记 `mcp.routed`；工作区和目录检查；被使用的资源和数字员工不能删除；默认团队跑通一个带独立验证的目标 |
| `setup-settings` | `setup` 之后，应用读到的 Agent 状态和默认数字员工；设置的各页；自动更新默认开着、能关掉，测试中的应用不检查也不下载更新；资源库 MCP 标签的代码模式默认开，关掉再打开，每次应用状态（`mcp.codeMode`）都和服务端的 `mcpRouter.code` 一致 |
| `setup-editors` | `setup` 之后：新建 Claude 自定义 API 时「填入模板」带入服务给的模板；设置列表只有私有变量的名字，编辑器显示全部值；MCP 编辑器的表单、JSON、新建和精选；默认数字员工都带 256 像素的头像，换上自己的图得到裁好的 256 像素 PNG，移除后回到文字；数字员工和工作区编辑器，共享资料在单独的表单里编辑、不打开工作区设置 |
| `setup-run` | `setup` 之后：工作区页按新到旧列出它的任务记录，打开时键盘在目标输入框里，名称旁的共享资料和团队记忆写着有没有内容；`setup` 跑通的那个目标的各页 |
| `goal-codex` | Codex 负责人的完整目标：编排校验、看板令牌与 `who` 绑定（反例返回 403）、进展与提问、交付摘要、diff 产物经 Run 的文档和 diff 接口读取、读不到数据库、NDJSON 导出、SSE、用量账本、`expectedSequence` 与 `commandId`、验收、验收后继续对话；目标图片写进负责人说明 |
| `goal-claude` | Claude Code 负责人：看板推送经插话进入会话、推送过的消息不再由 `wait` 返回、交付后新的 `/goal`（期间协作者的提问仍推送给负责人）、再次交付、消息中的图片、非图片附件被拒绝；交付后这个 Run 在收件箱只有最新一次交付的「等你验收」一条，应用里忽略它后它离开收件箱，Run 仍是已交付 |
| `review` | 交付的审阅：负责人报告的「结论」和「需要你决定」切进 `headline`、`decisions`，其余整篇保留；交付带合并结果和这一轮改的文件，风险只放 Janus 查出来的；交付后停止被拒绝；交付后让负责人补一个文件，第二次交付只含这一轮（负责人自己改的文件，没有上一轮的子任务）。应用工作台的群消息（派工、开工、交结果、等你验收的交付）、T1 的话题和「@你」的件数与服务端 `group=1` 的视图逐条一致，打开 T1 的话题、跳到等你处理的消息后截图；不带 `group=1` 的视图里负责人的会话没有群消息。应用的交付卡片（`state` 的 `review`：阶段、是否给出验收按钮（`actions`）、轮次、结论、要你决定的事、改的文件、子任务、你的追加要求、需要你看的）和服务端逐项一致，收件箱只有第二次交付一条 |
| `usage` | 按模型上报、只报上下文、多轮相加；Run 账本、时间段账单和应用算出的用量一致 |
| `decisions` | 审批、表单、负责人 `ask_user` 到用户；在应用收件箱中就地审批；表单和回答回到 Agent；负责人结束后留下的提问转给用户；等用户时群标题下的耗时按秒推进、期间无新事件 |
| `failures` | 自动重试、依赖失败与重试后恢复、没通过验收由负责人接受、取消连带下游、验证者判定不通过不能放行、负责人用 `retry` 让任务按验证意见回到原会话返工（不选会话被拒绝）、验证在自己的会话中复审通过、返工时正在执行的下游收到通知并列给负责人、不合法的证据方法；应用中返工和复审在同一个会话卡片里接着显示 |
| `worktrees` | 同一个仓库上的两个任务各自在 worktree 里改同一个文件，互不干扰也不报冲突；`.worktreeinclude` 带上被忽略的 `.env`，未提交的改动不带进去并在创建前提醒；每次执行记下 Git 信息（分支、开始时的提交、worktree 路径），子任务页显示仓库、分支和提交，不显示副本的路径；交付时结果作为一个提交快进到工作区目录当前的分支（Janus 的 `run.merged`），交付摘要说明合并到了哪里，用户没提交的其他文件保留，不建 `janus/` 分支，应用显示已合并到哪个分支，之后验收不再提交；验收后负责人按要求提交的改动再次交付并合并；第二个任务改了同一个文件，交付时冲突交给负责人一次（没解决时再次交付说明仍然冲突，用户验收时再交给它一次），任务保持已交付，用户的分支不动，目录里没有半合并的状态；非 Git 目录上的任务直接在目录里运行，有任务在跑时创建前提醒 |
| `controls` | 暂停与继续、打断后人工接管并以当前结果结束、接管与交还（负责人在看板上读到「[用户介入]」）、切换控制项（空值被拒绝）、没有预算可追加、状态冲突（409）、取消、删除（删除后 Janus home 中没有留下名字带这个 Run id 的任何东西，删除 worktree 时有意保留的补丁除外） |

编写场景：

- 场景是 `e2e/scenarios/` 中带 `@scenario` 的函数，参数是 `ctx`（服务、应用和辅助函数）和 `c`（检查）。`c(条件, 说明)` 记一项检查，`c.must` 失败时中止场景。说明写成用户能理解的行为。
- 服务的 `npm_config_registry` 指向 `e2e/lib.py` 的替身 registry（`Registry`，`ctx.registry`），适配器的新版本检查不访问 npm：每个包的最新版本默认是替身适配器的版本，场景可以改（`ctx.registry.latest[包名]`），问过哪些包记在 `ctx.registry.asked`。它还为每个版本生成 npm tarball（`package/package.json` 和一个把 stdio 交给 `fake_acp.py` 的 `shim.js`，`dist` 带 `shasum` 和 `integrity`），所以自动升级的 `npm install` 走的是真实安装路径；场景可以用 `Registry.close()` 停掉它，让下一次真实安装失败，用来检查失败时的界面文案和日志。自带服务的场景要配一个自己的 `Registry`（`npm_config_registry=reg.url`），不要改共用 registry 的 `latest`，否则会影响共用服务上的其他场景。`--real` 的冒烟测试用自己的服务，从真实的 npm 安装。
- `ctx.team(...)` 建一个团队，`team.run(目标)` 提交目标，`run.orchestrate`、`run.read_board`、`run.finish` 扮演负责人，`run.act` 执行用户操作，`run.wait_event` 等事件，`ctx.ui` 核对应用的状态并截图。共用部分在 `e2e/lib.py` 和 `e2e/scenarios/__init__.py`。
- 每个场景用自己的团队名（同时也是 Agent、数字员工和工作区 id 的前缀），场景之间不共享 `FAKE_DIR`：负责人等待的 `lead-go` 文件对同一目录下的所有负责人生效。
- 鉴权和校验类的检查至少写一个反例（合并前检查第 1 条）。
- 新功能需要脚本化 Agent 的新行为时，扩展 `fake_acp.py` 并更新[脚本化 Agent](#fake_agent)。

## Web 端到端测试

`e2e/web.py`（`just e2e-web`）在真实构建的服务上验证 Web 客户端：

1. 构建 Web 客户端（`just web`；`--built` 时跳过，`just e2e` 已经构建过）和嵌着它的服务（`cargo build`）。
2. 在系统临时目录创建 `janus-web-e2e-*`，临时 Janus home、替身适配器和替身 npm registry 和产品端到端测试相同（`e2e/lib.py`），服务监听 `127.0.0.1` 上的空闲端口。
3. `prepare` 用 `e2e/scenarios` 的 `Ctx.team` 准备等用户处理的 Run：负责人带选项的提问（有快捷回答）、不带选项的提问（可以推迟）、另一个团队里已交付的目标（每个团队一个脚本化 Agent 目录：让负责人交付会让同一目录里的负责人都交付）；`web` 工作区里负责人记下的三条团队记忆和一个睡着的值班；工作区 `web-new`，它的 Agent 通过了配置检查，负责人交付每个目标，供浏览器提目标和开对话；一个供浏览器新建工作区的空目录；还有会话用的：一个回复过一次的对话，一个目标里三个子任务分别跑完一整个会话（思考、计划、带 diff 的调用）、请求审批、请求填表。；再用另一个团队准备一个派出子任务、写了文件、交付后等验收的目标（`reviewed`），给 Run 页用：有证据、diff、文档和时间线。这些 id 和路径经 `JANUS_WEB_DATA` 交给测试。
4. 运行 `web/e2e/` 的 Playwright 测试，用本机已装的 Chrome（`channel: "chrome"`，不下载浏览器）。五个项目依次运行：
   - `pair`：没配对的浏览器只看到配对说明、它自己的请求都是 401；错的配对码显示服务端的原因；再像 Mac 应用那样取一个配对码（Playwright 自己的请求不带 `Origin` 和 `Sec-Fetch-Site`，按本机程序放行），在 Chrome 里打开 `/pair/<码>` 配对，核对设备出现在服务端的列表里、配对码不能再用，把拿到的 cookie 存给后面的项目。
   - `phone`（390×844，触屏，手机的 UA）只看不改，`desktop`（1280×820）之后再点快捷回答、推迟和忽略，所以两边看到的是同一批 Run；两者都带 `pair` 存下的 cookie。
   - 两者都跑 `web.spec.ts`（收件箱、页签和侧栏、语言）和 `home.spec.ts`：工作区页（团队一行、共享资料和团队记忆的状态、工作区的问题、「等你处理」、值班、任务记录）、工作区列表在干活和已删除的标记、新对话的分组，都和服务端的返回逐项比较；各提一个目标并等它交付，各开一个对话并核对是和选的数字员工；团队记忆的条目和来源、加入共享资料的那一行；值班页和它的表单。改的操作只在 `desktop` 做：改一条笔记、删一条笔记、把值班改成每 2 小时、新建一个值班、从填的目录新建工作区，每一项都到服务端核对。会话（`session.spec.ts`）也是这样：手机在对话里用按钮发一条消息，桌面回答审批和表单。

   - `plain-http`：同一个服务换成 `janus.test` 这个名字（Chrome 用 `--host-resolver-rules` 指到 `127.0.0.1`），这不是安全上下文，和手机经局域网或 Tailscale 的明文 HTTP 地址一样（`crypto.randomUUID` 不存在）。在这个地址上重新配对，从对话的输入框发一条消息并等到回复，从收件箱点一个快捷回答，都到服务端核对。2026-11-27 手机上发消息没有反应，就是因为前面的项目都跑在算作安全上下文的 `127.0.0.1` 上。

   每个测试是新的浏览器上下文，从浏览器语言（中文）开始。测试读服务端数据都用 Playwright 自己的请求，这也核对了本机程序不配对仍然能用接口。
5. 每个页面的数据由 `window.__janus.state()` 读出（见 [Web 客户端](../architecture/20261126-web.md#state)），和服务端的返回逐项比较（收件箱的键、标题、说明、下一行、能否推迟、快捷回答；工作区页的待处理分组和任务记录；会话的行和它们的顺序在摘要、详细两档都和服务端排的一致，事件的一行是服务端写的那句，输入框的状态和按钮，`@` 的建议，停在输入框上方的审批和表单；Run 页的状态胶囊、标题、摘要行、交付的阶段、信号和数字、检查器三栏、成员、允许的操作，审计页的五条规则，团队页的说明，子任务页的执行轨迹、下游和验收数，diff 的文件，文档的长度，`run.spec.ts`）；换成英文后再和 `?lang=en` 的返回比较；点的操作用服务端的事件和收件箱核对。手机上另查侧栏收起、页签在、页签不低于 44 像素、下一级页面有返回。Run 页另查：服务端不允许的操作（进行中的目标不能删除）按钮带服务端的原因，桌面上点「验收」后服务端进入 `accepted`、页面收成服务端写的那一行；手机上 Run 页和子任务页没有元素超出屏幕（时间线、代码、表格在自己的框里滚动）。
6. 报告在 `janus-web-e2e-*/report/`：`playwright/`（HTML 报告，`npx playwright show-report <目录>` 打开，失败的测试带 trace）、`shots/`（每个页面桌面和手机各一张，收件箱另有深色），`janus.log`。新功能涉及的页面，开发者要亲自看一遍截图。

参数：`--keep` 保留临时 home，`--built` 跳过 Web 构建，`--` 之后的交给 `playwright test`（例如 `-- --project desktop`、`-- -g inbox`）。

## 数据升级测试

改了存储的数据（表、设置对象或 Run 快照的字段、默认数字员工）就要加迁移，见[数据升级](../architecture/20261031-data_model.md#migrations)。三层测试保证迁移写了、写对了：

1. **写入时的检查**：测试中每次 `put_config` 都按 `data_shape.rs` 登记的字段检查，缺字段或多字段直接失败。直接写设置对象的测试用 `agents::test_connection`、`agents::test_role` 生成完整的对象。
2. **单元测试**（`backend/src/migrations/tests.rs`，随 `just test` 运行）：
   - 新库从 0 升到最新、不备份；更新版本的数据被拒绝；预览不改动原库；字段步骤重复执行不再改动。
   - `backend/testdata/upgrade/v0.sql` 是 Janus 2026.11.18 真实写出的数据（由下面的端到端脚本导出），升级后先有备份，每个对象都符合当前结构，迁移不涉及的对象原样不变，再次打开不重复升级，迁移删掉的表（`leases`）不会被重新建出。
   - `the_data_shape_matches_its_snapshot`：表结构和登记的字段与 `backend/testdata/data_shape.json` 一致。结构变了而数据版本没变时失败，提示先加迁移；加了迁移后运行 `just data-shape` 更新快照。
   - 某个迁移处理的数据在 `v0.sql` 中没有（例如之后新增的设置类型）时，用端到端脚本从对应版本导出新的样本，放进 `backend/testdata/upgrade/` 并在测试中覆盖。
3. **端到端测试**（`just e2e-upgrade`，`just e2e` 的第 4 步）：`e2e/upgrade.py` 对最近 3 个发布标签（或 `--from <标签>` 指定的）逐个执行：
   - 用 `git archive` 取出这个标签的 `backend/`，在临时目录构建旧版服务；发布过的版本不会变，构建结果按提交号留在系统临时目录的 `janus-e2e-builds/` 里（不在仓库和用户目录里，先写旁边再改名，两次运行同时写也不会读到半个文件），之后的运行直接用，所以这一步平时约 5 秒，有新版本时才编译；在临时 Janus home 和一个空闲端口上启动，按应用的方式通过接口写入数据：两个 Agent 连接（2026.11.20 起的版本不再接受「自定义命令」，只建 Claude Code 一个）、绑定 Agent 的默认数字员工、改过指令的默认数字员工、自定义数字员工、工作区（有一次提交的 Git 仓库），再写入两个带那个版本成员快照的已交付 Run：一个直接在目录中运行，一个在这个仓库的 worktree 中运行、没有记录开始时的分支（成员按旧版本的数据版本取当时的格式：数据版本 23 起是 `connection`、`connection_name` 和 `runtime`，之前是 `runtime`、`kind` 和 `runtime_name`，见 `old_member`）。
   - 停掉旧版服务，`janus migrate --dry-run` 预览升级且不改动数据；再启动当前版本的服务，检查数据版本、备份（旧版本的数据已是最新时，检查不升级也不备份）、没改过的默认数字员工换成当前文本、改过的保留并提示、自定义数据和工作区不变、Run 快照成员已迁移、worktree 中的旧 Run 记下工作目录检出的分支、「保留我的」之后不再提示、升级后预览没有遗留问题、再次启动不重复升级、更新版本的数据被拒绝；Janus home 整理成新布局（数据库在 `data/`，凭据在 `data/secrets/`，Agent 的配置目录在 `data/agents/<id>/config`，顶层只有布局声明过的名字）。
   - 需要 Rust 工具链、`git` 和 `python3`，每个标签的构建要一两分钟。`--keep` 保留临时目录，`--dump-fixture <路径>` 把最旧标签写出的数据导出为样本 SQL。

## 脚本化 Agent

`backend/testdata/fake_acp.py` 是一个按脚本行事的 ACP Agent，声明支持 HTTP MCP。它装成 Codex 和 Claude Code 的替身适配器：后端测试的 `test_app` 在临时 Janus home 的 `adapters/<id>/9.9.9/` 下放一个与官方 npm 包同名的包，`bin` 指向这个脚本，并把运行适配器的程序（`Config::node`）设为 `python3`（`stand_in_adapters`）；端到端测试用一个 Node 脚本转给它，见[产品端到端测试](#product_e2e)。所以测试走的是正式的启动路径和 Claude Code、Codex 的系统层。`FAKE_DIR` 环境变量指向它的工作目录：

| 文件 | 作用 |
| --- | --- |
| `script.json` | 任务 id → 每次提示的结果列表，最后一个结果重复使用 |
| `calls.log` | Agent 记录收到的会话设置（`session/new` 的 `_meta` 和 `mcpServers`、`set_config_option`）和负责人收到的提示 |
| `lead-go` | 目标模式负责人在这个文件出现前一直工作，然后以文件内容作为最后回复结束 |
| `mute` | 存在时不回答 `initialize`，像启动时卡住的 Agent |
| `steer` | 存在时声明 `_session/steering`：一轮进行中收到的 steer 记入 `calls.log`（`steer <内容>`，带文件引用时另记 `links <路径>…`），回复 `injected` |
| `session-<会话 id>.json` | Agent 自己写的会话与任务、验收标准的对应关系：服务重启后用 `session/load` 加载的会话由新进程接手，仍知道自己在做哪个任务 |
| `content.json` | 演示内容：有这个文件时，Agent 照它说话和写文件，见下文的 `content` 结果和[界面截图](#screenshots) |

任务的结果像真实 Agent 一样交：从 `session/new` 或 `session/load` 的 `mcpServers` 记下 janus 服务器的地址，用 MCP 调用 `janus.submit` 交结果、`janus.ask` 提问（`calls.log` 记 `submit <任务> taken` 或 `refused`、`ask <任务>`）；交的结果被提醒有标准没达到、可以再交一次，而脚本里这个任务的下一步是 `ok` 时，它取出这一步，修好后再交一次。`script.json` 中可用的结果：`ok`、`fail`、`content`（照 `content.json` 做这个任务，见下文）、`cancelled`、`slow`、`busy-tool`（进行中的工具调用持续 2.5 秒）、`high-ctx`（上报 80% 上下文占用）、`handoff`（写文件并返回 `handoff`、`risks` 和 `reasoning` 方法）、`reject` / `approve`（返回带证据的 `verdict: "rejected"` / `"approved"`）、`write:<文件>`、`edit:<文件>`（写文件并上报一次带 `locations` 的 `edit` 工具调用，再忙 2 秒，让并行的任务重叠）、`permission`（发出带三个选项的 `session/request_permission`）、`elicit`（发出带表单的 `elicitation/create`）、`loop`（给出结果前连续 5 次发出相同的工具调用）、`loop2`（连续 4 轮交替发出 `Edit a.rs` 和 `cargo test`）、`ask`（用 `janus.ask` 提问并结束本轮，回答作为下一条提示）、`methods`（每条验收依次带 `test`、`command`、`inspection`、`reasoning`、`unverified` 五种证据方法，另有三条任务级证据）、`badmethod`（第一条验收写不合法的 `method: "vibes"`，`janus.submit` 必须当场退回）、`rich`（发出思考、计划、斜杠命令、一个先进行中再完成并带 diff 的工具调用、上下文用量，并自己切换模式；`session/prompt` 的返回带 token 用量）、`skill:<名字>`（像真实 Agent 用资源库 Skill：从 `session/new` 或 `session/load` 的 `_meta` 交来的资源包（Claude Code 的 `claudeCode.options.plugins`、Codex 的 `additionalRoots`）找到 `janus-skills` 的 `SKILL.md`，读目录，按目录写的位置读这个 Skill 的 `SKILL.md`，两次读取都上报为 `read` 工具调用，在 `calls.log` 记 `skill <名字> read`，目录里没有时记 `skill <名字> missing`）。默认声明 `loadSession: true`（`no-load` 文件关闭、`fail-load` 文件模拟加载报错），收到 `session/load` 时记入 `load <sid>`；`session/new` 和 `session/load` 都记一行 `layer <new 或 load> <sid> <系统层的 JSON 字符串>`，系统层取 `_meta.systemPrompt.append`，没有时取 `CODEX_CONFIG` 的 `developer_instructions`。用量场景（供只读的用量账本使用）：`usage`（上报三次上下文快照和一个 `cost`，`session/prompt` 的返回带主循环 1200 input / 300 output / 1500 total，以及 `_meta.quota.model_usage` 中主模型 1500 和一个子 Agent 500 两行）、`usage-quiet`（只报上下文快照，完全不上报 token）、`usage-turns`（第一轮 1000 token 后提问，回答后的一轮报 2500，两轮相加是 3500）、`records` / `records-crash`（像 Claude Code 一样在 `CLAUDE_CONFIG_DIR` 的 `projects/<工作目录>/<会话>.jsonl` 写会话记录：一个响应分两行写，取后一行是 480，子 Agent 的记录里另有 80；`records` 交结果并在返回里另报 1500，账本不能再计入；`records-crash` 在这一轮中途退出进程，像崩溃的 Agent）。系统层以「You are the Loop of the workspace」或「你是工作区「…」（…）的值班」开头的会话是工作区值班：每次开工的提示记 `loop prompt <JSON>`，回复「看过了：<第一行>」；以 `[me] ` 开头的是测试里以用户身份发的消息，回复「回复：<其余>」；提示里有 `[write <文件>]` 时先在工作区追加这个文件，有 `[hold]` 时一直等到 FAKE_DIR 中出现 `loop-go`（随即删掉）。系统层写有「consolidating this workspace's team memory」或「整理这个工作区的团队记忆」的会话是团队记忆的整理：提示记 `dream prompt <JSON>`，这一轮一直等到 FAKE_DIR 中出现 `dream-go`，以它的内容回复并删掉它，测试在这期间调用记忆工具。`session/set_mode` 记入 `calls.log`（`mode <id>`），一轮进行中收到的 `session/set_config_option` 也照常应用并记入（`set <id> <值>`），每轮提示里的文件引用也记入（`links <路径>…`）。负责人的会话在重启后被加载、收到 Janus 的恢复提示（以「[Janus] Janus restarted while you were working on this goal.」开头）时，记 `lead resumed <sid> <提示的 JSON 字符串>`，一直做到 FAKE_DIR 中出现 `lead-go`，再报告目标已清除并以它的内容回复。FAKE_DIR 中有 `goal-sticky` 文件时，负责人把 `/goal` 报告为进行中且从不清除，像检查不运行的 Claude Code；Janus 问它目标是否完成时回复 `GOAL_DONE` 加 `lead-go` 的内容，收到 `_session/goal` 时记入 `goal clear` 并报告目标已清除。

不是任务的提示里写着「[write <文件>]」时，在会话目录里追加这个文件，上报一次带 `locations` 的编辑工具调用（不是 Git 目录时 Janus 靠它知道负责人改了文件），然后结束这一轮（交付后让负责人补写文件）；同时写着「[commit]」时，先在会话目录里 `git add -A` 并提交（用户要求负责人提交）。`hold:<文件>` 一直工作到 `FAKE_DIR/<文件>` 出现，然后给出通过的验证结论（验证还在执行时被验证的任务返工）。

对话中的数字员工在系统层里看到对话说明（「talking with the user directly」）时在 `calls.log` 记 `chat brief <工作目录>`，之后每条提示都回复「回复：<提示>」。

作为目标模式负责人时，它在 `session/new`、`session/load` 的系统层（`_meta.systemPrompt.append`）里看到负责人说明时在 `calls.log` 记 `brief ok`（从中断处继续时记 `brief ok resumed`），再在收到 `/goal …` 后等待 `lead-go`。计数器保存在 `FAKE_DIR` 中，同一任务的多次尝试（不同进程）共用脚本进度；读和加一在文件锁里完成，同时运行的进程（例如两个配置检查共用 `count-unknown`）不会读到写了一半的计数。

`backend/testdata/fake_mcp.py` 是一个按 stdio 说 MCP 的替身服务器，给 [MCP 路由](../domains/20261116-resource_library.md#mcp_router)的测试用：每次启动在 `FAKE_MCP_LOG` 指向的文件里记一行 `start`（用来确认列工具时没有启动它），工具 `cwd` 回答它的工作目录，`echo` 原样返回 `text`，`roots` 反过来向客户端发 `roots/list` 并回答第一个根目录，`env` 回答 `HOME` 和指定的环境变量，`grow` 新增一个工具并发出 `notifications/tools/list_changed`，`quit` 回答后退出，`spawn` 启动一个 `sleep` 子进程并回答它的 pid，`hang` 一直不回答、被取消时（`notifications/cancelled`）在 `FAKE_MCP_CANCELLED` 指向的文件里记一行 `cancelled <原因>`，`task_only` 只能以 task 方式调用（`execution.taskSupport: required`）。工具列表分两页给出（`nextCursor`）；`FAKE_MCP_VERSION` 指定它在 `initialize` 中回答的协议版本。

`backend/testdata/fake_mcp_http.py` 是 HTTP 上的替身 MCP 服务器：在 `127.0.0.1` 的空闲端口上监听，第一行输出端口；`/mcp` 是 Streamable HTTP（`initialize` 给出 `Mcp-Session-Id`，工具调用用事件流回答，其他用 JSON），`/sse` 是旧的 SSE 传输（先给出消息地址，回复从事件流到达）。每个请求都要带 `Authorization: Bearer good`，否则返回 401。它把新会话（`init`）、被客户端结束的会话（`delete`）和打开的事件流（`sse`）记到第一个参数指向的文件；工具 `whoami` 回答收到的 `Authorization` 和 `MCP-Protocol-Version`，`expire` 忘掉当前会话，之后带着它的请求返回 404。

`content.json` 让 Agent 说出和写出像样的内容，给[界面截图](#screenshots)用，测试不用它。结果 `content` 按 `tasks.<任务 id>` 做这个任务：先给出 `thought`（思考）和 `plan`（计划），把 `files` 里的文件写进工作目录并上报带 diff 的编辑，上报 `context` 和 `cost`（上下文和费用），发出 `commands` 里的命令（最后一条在干活期间保持进行中），有 `permission` 时先请求审批，有 `hold` 时等 `FAKE_DIR` 里的这个文件出现，一共干 `seconds` 秒，最后交回结构化结果：`summary`、`handoff`、`evidence`、`risks`、`verdict` 原样写入，`checks` 按顺序给每条验收标准填证据、方法和是否通过，`tokens` 是这一轮的用量。负责人的目标以 `goals` 的某个键开头时，等 `FAKE_DIR/go-<key>` 出现，以这个目标的 `report` 结束并上报 `tokens` 和 `cost`，所以几个负责人可以共用一个 `FAKE_DIR`、各自结束。值班把会话标题定为 `loop_title`，醒来后回答 `loops.<提示的第一行>`，没有时回答 `loop_default`。

## 测试夹具

`flow_tests::harness(name, members, script)`（`harness_with` 另外改 `App` 的配置，例如停滞阈值、槽位数）：

- 在系统临时目录创建 `janus-flow-<name>-<pid>`，内含一个初始化过的 Git 仓库作为工作区。
- `App` 由 `served_app` 建出：它的路由在一个空闲的本地端口上提供，交给 Agent 的 MCP 地址指向那里，所以脚本化 Agent 像真实 Agent 一样经 HTTP 调用 janus 的工具。测试里模拟重启时也用 `served_app` 建新的 `App`，不用 `test_app`（它不监听端口，地址是默认的 `127.0.0.1:7878`）。
- 注册一个 Claude Code 类型的 `fake` Agent（经替身适配器运行脚本化 Agent），声明 `mode`（`read-only` / `ask` / `agent` / `full`）权限控制项。
- `members` 是 `(角色 id, 是否可写)` 列表，第一个是负责人；不可写的角色使用 `read-only` 模式。

辅助函数：`start`（创建 Run 并以负责人身份提交一份编排）、`finish_lead`（让脚本化负责人结束目标）、`act`（发送 Run 操作）、`tool`（以负责人或协作者身份调用看板工具）、`wait_until`（等待事件条件）、`events`、`has`、`status`。

<a id="test_conventions"></a>
## 约定

- 每个 `flow_tests` 测试给 `harness` 传唯一的 `name`。测试并行运行，名字相同的测试会共用并互相删除临时目录，造成随机失败。
- 测试结束时删除临时目录。
- 新增事件类型或改变流程时，在 `flow_tests` 中用脚本化 Agent 覆盖，不依赖真实 Agent。
- 真实 Agent 的验证由 `just e2e --real` 运行（见[端到端验证](#e2e)），不进入 `just test`。
- 需要等待 SwiftUI 布局或延后滚动的界面测试使用 `@MainActor async`，等待期间通过 `await Task.sleep` 让出主线程。同步 `@MainActor` 测试内反复调用 `RunLoop.main.run(until:)` 不能可靠执行排入主队列的工作，会在滚动修正执行前断言失败。`ChatScrollTests` 先验证主队列中的回调已执行，再检查打开位置、向上翻阅和跟随新消息；修复夹具时保留这些行为断言，并在 CI 的最低支持版本上验证。屏幕锁定时窗口服务器不给窗口显示周期，这个测试会明确跳过并说明原因，解锁后重跑。
- 注入滚动手势的窗口测试把窗口加入显示列表，以便在其他主线程测试运行时也获得显示周期；窗口透明且忽略真实鼠标事件，合成手势直接发送给滚动视图。结束时关闭窗口，避免真实输入或遗留窗口影响后续测试。

## macOS 应用

- `just test-mac`（`cd frontend && swift test`，只装了命令行工具时加上 `scripts/swift-test-flags.sh` 给出的宏插件路径）运行 `frontend/Tests/JanusTests` 中的 Swift Testing 测试：服务端 Run 视图、收件箱条目和审阅的解码（`RunStateTests`、`anEntryReadsBackAsServed`、`theServedReviewReadsBack`）、用量账本（读服务端账本的每个范围、缺失保持缺失、不认识的提醒略过、提醒按数字写成文字、实时 Run 的耗时按秒推进与结束 / 只读 / 回放时冻结、金额的美元写法，`UsageLedgerTests`；用量卡片和时间段账单在浅色与深色下的绘制，`SessionViewTests`）、JSON、Markdown 文档的解析、Plan 控制项过滤、资源库的读法（Skill 按服务端给的分组和目录顺序排、目录方式、使用情况后面接上次读的时间，`LibraryTests`）、新建工作区的预设（负责人所在分组里绑定了 Agent 的数字员工，`newWorkspacesStartWithTheLeadsGroup`）、和服务端同值的枚举逐项对照 `backend/src` 里的定义（Run 的类型和来源、Agent 阶段、会话提示的来由、消息的去向、Janus 的工具名、用户操作，`WireTests`）、英文翻译的每个中文键仍写在应用或服务端的源码里（`everyTranslatedStringIsStillUsed`）、收件箱按工作区分行（`Inbox.waiting`，`InboxTests`）、时间文案、用量数字和缺失状态、首页按原因合并的问题、审计日志按前缀分类和只编译一次的正则（`FormatTests`）、系统通知只发新事项（`notificationsAreForWhatIsNew`）、服务端排好的会话行加上用户的展开收起（拆出的最后一步在点开那一组时并回去）、会话旁边的计划、控制项、用量、待发送和请求的解码、输入框建议的按键（`ConversationTests`）、diff、文档清单和实时预览的解码、会话只在停在底部时跟随新内容（`ChatFollow`，`SessionViewTests`）、在真实窗口中用触控板手势往上翻后新回复不移动视图、回到底部后继续跟随、打开时停在最新处（`ChatScrollTests`），以及应用更新（`UpdaterTests`：版本号比较、只下载变化的部分、`update.json` 的读取、用 `codesign` 现场签一个最小应用包来检查签名校验、版本号不符和文件被改动后拒绝安装、替换脚本移入新版本失败且留下半个新应用时，旧应用完整放回原处并打开）。只装命令行工具时，`@Test` 宏插件在 `usr/lib/swift/host/plugins/testing` 下、不会自动加载，`just test-mac` 检测到这种情况会加上 `-plugin-path`；CI 的 macOS 运行环境自带 Xcode，直接运行 `swift test`。
- `MacPermissionsTests` 使用注入的系统接口，覆盖首次启动、同版重启、签名身份或 bundle ID 变化、全部已授权时不弹引导、逐项引导只在检测到授权后前进、拒绝和跳过、实时撤权、系统不给答案时的「测不出来」、系统设置打开失败、引导记录保存失败，以及源码运行不申请权限。测试不访问 TCC 数据库、不触发系统授权弹窗。界面验收使用隔离的应用包和 Janus home，通过快照命令检查权限页与首次引导，不与滚动交互测试并行渲染。
