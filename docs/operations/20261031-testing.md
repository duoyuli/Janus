# 测试

本文说明 Janus 的测试结构、每个需求完成后的端到端验证、测试用的脚本化 Agent 和编写新测试时的约定。运行环境见[运行手册](20261031-runbook.md)。

<a id="running_tests"></a>
## 运行

```sh
just test
```

等于 `cd backend && cargo test`。提交前再运行 `just lint`，执行与 CI 相同的 `cargo fmt --check` 和 Clippy 检查。

macOS 应用的测试见 [macOS 应用](#macos_app)。

测试不访问网络，不调用真实 Agent，也不安装适配器（脚本化 Agent 是自定义命令类型）。需要本机有 `git` 和 `python3`。

<a id="e2e"></a>
## 端到端验证

每个需求开发完成后运行 `just e2e`，它是合并前的必过门禁（`AGENTS.md` 合并前检查第 12 条）。依次执行以下步骤，任何一步失败即停止：

| 步骤 | 命令 | 验证什么 |
| --- | --- | --- |
| 1. 静态检查 | `just lint` | 格式和 Clippy，与 CI 相同 |
| 2. 后端测试 | `just test` | 单元测试和进程内的流程测试（`flow_tests`），见[测试分布](#test_layout) |
| 3. 应用测试 | `just test-mac` | 应用的推导逻辑和视图，见 [macOS 应用](#macos_app) |
| 4. 产品端到端测试 | `just e2e-product` | 真实构建的服务和应用跑完每条用户旅程，见[产品端到端测试](#product_e2e) |
| 5. 数据升级测试 | `just e2e-upgrade` | 最近的发布版本写出的数据由当前版本升级，见[数据升级测试](#upgrade_tests) |

`just e2e` 的参数交给第 4 步：

- 不带参数：从源码构建，替身 Agent 运行，结果确定，不访问网络，约 5 分钟。每个需求都跑。
- `--packaged`：测试 `just app` 打出的 `dist/Janus.app`（内置服务和 Node.js），能发现打包、签名和内置 Node 的问题。发布前必跑。
- `--real`：另加真实 Codex 负责人和 Claude Code 协作者的冒烟测试（`real` 场景），需要网络，以及一个已经配好 Codex 和 Claude Code 并通过配置检查的 Janus（默认 `~/.janus`，`--real-from <Janus home>` 指定其他的），会消耗 token（第一次运行约 5 分钟、135 万 token），视 Agent 发挥可能更久。发布前，以及改了 ACP 集成、适配器、Agent 启动环境或负责人提示时必跑。

新功能改了用户可见的行为时，在产品端到端测试中新增或修改场景，见[编写场景](#e2e_scenarios)。e2e 只在本地运行，不在 CI 中运行。

<a id="product_e2e"></a>
## 产品端到端测试

`e2e/product.py`（`just e2e-product`）在真实的二进制上验证产品，覆盖 `flow_tests` 碰不到的部分：正式构建的负责人规则（`cfg!(test)` 之外只有 Codex 和 Claude Code 能做负责人）、适配器查找和 Node 启动、HTTP 接口、看板 MCP 端点、服务重启，以及应用从服务读到的状态。

运行方式：

1. 构建服务（`cargo build`）和应用（`swift build`）；`--packaged` 时运行 `frontend/scripts/package.sh --no-dmg`，使用 `dist/Janus.app` 中的 `janus-server`、应用和内置 Node.js。
2. 在系统临时目录创建 `janus-e2e-*`，其中有临时 Janus home、每个场景的 Git 工作目录和脚本化 Agent 目录。服务监听 `127.0.0.1:7979`，不碰用户的 `~/.janus` 和 7878 端口。
3. **替身适配器**：在临时 home 的 `adapters/codex/9.9.9/` 和 `adapters/claude/9.9.9/` 放入与官方 npm 包同名的包，`bin` 是一个 Node 脚本，它把标准输入输出交给 `backend/testdata/fake_acp.py`。Janus 照常用 Node 启动「Codex」和「Claude Code」，走的是正式的启动路径，Agent 的行为由脚本决定，不联网、不花钱。协作者用同一个脚本化 Agent 作为自定义命令。
4. 启动应用，连接这个服务（`JANUS_HOME`、`JANUS_ADDR`），通过快照命令通道驱动（见 [macOS 应用](#macos_app)）。应用的本地设置写进单独的 `JANUS_DEFAULTS_SUITE`，结束时删除，不改用户自己的应用设置。
5. 按场景运行：`setup` 最先运行；其余场景各自建团队（Agent、数字员工、工作区、脚本化 Agent 目录），最多 4 个并行；会重启或替换服务的场景（`restart`、`app-server`、`real`）最后依次运行。
6. 测试脚本扮演负责人的「大脑」：从脚本化 Agent 的 `calls.log` 读出负责人会话的看板地址，像 Agent 一样调用 `orchestrate`、`wait`、`reply`、`retry` 等工具；协作者的行为由 `script.json` 决定；用户的操作走 HTTP 接口，和应用发出的请求相同。
7. 每个场景结束时打开应用，等应用推导出的状态（`state` 命令写出的 Run 状态、任务状态、验证判定、收件箱、用量）与服务记录的一致，再按页面截图，检查截图是真实窗口的尺寸且不是纯色：主窗口没有打开时，`shot` 截到的是菜单栏图标的小窗口，不能算画出来了。
8. 报告写在 `janus-e2e-*/report/`：`report.md`（每个场景的检查项和失败原因）、`janus.log`、`app.log` 和 `app/` 下的截图。没有 `--keep` 时删除报告以外的临时文件。新功能涉及的页面，开发者要亲自看一遍截图。

参数：`--only <场景>`（可重复）、`--list` 列出场景、`--no-app` 只测服务、`--keep` 保留临时 home 和工作目录、`--packaged`、`--real`、`--real-from`。

<a id="e2e_scenarios"></a>
### 场景

| 场景 | 覆盖 |
| --- | --- |
| `setup` | 服务的 meta、替身适配器、默认数字员工；三种 Agent 的配置检查和控制项；凭据不出现在接口中；自定义命令不能做负责人；资源库的 Skill 和带值的 MCP（值进入 `session/new`，不进入 Run 记录和导出）；工作区和目录检查；被使用的资源和数字员工不能删除；默认团队跑通一个带独立验证的目标；应用的设置各页、数字员工和工作区编辑器 |
| `goal-codex` | Codex 负责人的完整目标：编排校验、看板令牌与 `who` 绑定（反例返回 403）、进展与提问、交付摘要、diff 产物与 `/api/file` 的范围、NDJSON 导出、SSE、用量账本、`expectedSequence` 与 `commandId`、验收、验收后继续对话；目标图片写进负责人说明 |
| `goal-claude` | Claude Code 负责人：看板推送经插话进入会话、推送过的消息不再由 `wait` 返回、交付后新的 `/goal`（期间协作者的提问仍推送给负责人）、再次交付、消息中的图片、非图片附件被拒绝 |
| `usage` | 按模型上报、只报上下文、多轮相加；Run 账本、时间段账单和应用算出的用量一致 |
| `decisions` | 审批、表单、负责人 `ask_user` 到用户；在应用收件箱中就地审批；表单和回答回到 Agent；负责人结束后留下的提问转给用户；等用户时运行卡片的耗时按秒推进、期间无新事件 |
| `failures` | 自动重试、依赖失败与重试后恢复、没通过验收由负责人接受、取消连带下游、验证者判定不通过不能放行、不合法的证据方法 |
| `controls` | 暂停与继续、打断后人工接管并以当前结果结束、接管与交还、切换控制项（空值被拒绝）、追加预算、状态冲突（409）、取消、删除 |
| `sessions` | 思考、计划、斜杠命令、工具 diff、模式和用量；同时改同一文件的冲突；认领、`peers`、拆分请求；痕迹对账；`@` 文件搜索与引用 |
| `restart` | 服务重启：Run 记为中断、从中断处继续（新的看板令牌、已完成任务不重跑、原会话 `session/load` 续接）、回放已交付的 Run 时会话只读且草稿不发出、已交付的 Run 重启后继续对话（同时发来的两条消息只加载一次原会话，两条都送到负责人）、应用重新连上 |
| `app-server` | 没有服务在运行时应用自己启动服务（源码运行用 `JANUS_SERVER_BIN`，打包版用内置的），退出时停掉它 |
| `real`（`--real`） | 独立的 Janus home 和 `127.0.0.1:7981`；拷贝一份 `--real-from` 中的 Codex 和 Claude Code Agent（同样的设置，「复制本机配置」从同样的来源目录再复制一次，接口不返回的凭据按文件复制），Janus 从 npm 安装真实适配器；Codex 负责人带 Claude Code 协作者在 `examples/calc` 的副本上完成一个小目标，运行它的测试；用户决定按推荐项自动处理；结束时删除复制来的凭据 |

编写场景：

- 场景是 `e2e/scenarios/` 中带 `@scenario` 的函数，参数是 `ctx`（服务、应用和辅助函数）和 `c`（检查）。`c(条件, 说明)` 记一项检查，`c.must` 失败时中止场景。说明写成用户能理解的行为。
- `ctx.team(...)` 建一个团队，`team.run(目标)` 提交目标，`run.orchestrate`、`run.read_board`、`run.finish` 扮演负责人，`run.act` 执行用户操作，`run.wait_event` 等事件，`ctx.ui` 核对应用的状态并截图。共用部分在 `e2e/lib.py` 和 `e2e/scenarios/__init__.py`。
- 每个场景用自己的团队名（同时也是 Agent、数字员工和工作区 id 的前缀），场景之间不共享 `FAKE_DIR`：负责人等待的 `lead-go` 文件对同一目录下的所有负责人生效。
- 鉴权和校验类的检查至少写一个反例（合并前检查第 1 条）。
- 新功能需要脚本化 Agent 的新行为时，扩展 `fake_acp.py` 并更新[脚本化 Agent](#fake_agent)。

<a id="upgrade_tests"></a>
## 数据升级测试

改了存储的数据（表、设置对象或 Run 快照的字段、默认数字员工）就要加迁移，见[数据升级](../architecture/20261031-data_model.md#migrations)。三层测试保证迁移写了、写对了：

1. **写入时的检查**：测试中每次 `put_config` 都按 `data_shape.rs` 登记的字段检查，缺字段或多字段直接失败。直接写设置对象的测试用 `agents::test_connection`、`agents::test_role` 生成完整的对象。
2. **单元测试**（`backend/src/migrations/tests.rs`，随 `just test` 运行）：
   - 新库从 0 升到最新、不备份；更新版本的数据被拒绝；预览不改动原库；字段步骤重复执行不再改动。
   - `backend/testdata/upgrade/v0.sql` 是 Janus 2026.11.18 真实写出的数据（由下面的端到端脚本导出），升级后先有备份，每个对象都符合当前结构，迁移不涉及的对象原样不变，再次打开不重复升级，迁移删掉的表（`leases`）不会被重新建出。
   - `the_data_shape_matches_its_snapshot`：表结构和登记的字段与 `backend/testdata/data_shape.json` 一致。结构变了而数据版本没变时失败，提示先加迁移；加了迁移后运行 `just data-shape` 更新快照。
   - 某个迁移处理的数据在 `v0.sql` 中没有（例如之后新增的设置类型）时，用端到端脚本从对应版本导出新的样本，放进 `backend/testdata/upgrade/` 并在测试中覆盖。
3. **端到端测试**（`just e2e-upgrade`，`just e2e` 的最后一步）：`e2e/upgrade.py` 对最近 3 个发布标签（或 `--from <标签>` 指定的）逐个执行：
   - 用 `git archive` 取出这个标签的 `backend/`，在临时目录构建旧版服务；在临时 Janus home 和 `127.0.0.1:7979` 上启动，按应用的方式通过接口写入数据：两个 Agent 连接、绑定 Agent 的默认数字员工、改过指令的默认数字员工、自定义数字员工、工作区，再写入一个带那个版本成员快照的已交付 Run（成员按旧版本的数据版本取当时的格式）。
   - 停掉旧版服务，`janus migrate --dry-run` 预览升级且不改动数据；再启动当前版本的服务，检查数据版本、备份（旧版本的数据已是最新时，检查不升级也不备份）、没改过的默认数字员工换成当前文本、改过的保留并提示、自定义数据和工作区不变、Run 快照成员已迁移、「保留我的」之后不再提示、升级后预览没有遗留问题、再次启动不重复升级、更新版本的数据被拒绝。
   - 需要 Rust 工具链、`git` 和 `python3`，每个标签的构建要一两分钟。`--keep` 保留临时目录，`--dump-fixture <路径>` 把最旧标签写出的数据导出为样本 SQL。

<a id="fake_agent"></a>
## 脚本化 Agent

`backend/testdata/fake_acp.py` 是一个按脚本行事的 ACP Agent，作为 `custom` 类型的 Agent 启动，声明支持 HTTP MCP。`FAKE_DIR` 环境变量指向它的工作目录：

| 文件 | 作用 |
| --- | --- |
| `script.json` | 任务 id → 每次提示的结果列表，最后一个结果重复使用 |
| `calls.log` | Agent 记录收到的会话设置（`session/new` 的 `_meta` 和 `mcpServers`、`set_config_option`）和负责人收到的提示 |
| `lead-go` | 目标模式负责人在这个文件出现前一直工作，然后以文件内容作为最后回复结束 |
| `steer` | 存在时声明 `_session/steering`：一轮进行中收到的 steer 记入 `calls.log`（`steer <内容>`，带文件引用时另记 `links <路径>…`），回复 `injected` |
| `session-<会话 id>.json` | Agent 自己写的会话与任务、验收标准的对应关系：服务重启后用 `session/load` 加载的会话由新进程接手，仍知道自己在做哪个任务 |

`script.json` 中可用的结果：`ok`、`fail`、`cancelled`、`slow`、`busy-tool`（进行中的工具调用持续 2.5 秒）、`cancel-usage`（收到 `session/cancel` 后在返回值中附带 `usage`）、`high-ctx`（上报 80% 上下文占用）、`handoff`（写文件并返回 `handoff`、`risks` 和 `reasoning` 方法）、`reject` / `approve`（返回带证据的 `verdict: "rejected"` / `"approved"`）、`write:<文件>`、`edit:<文件>`（写文件并上报一次带 `locations` 的 `edit` 工具调用，再忙 2 秒，让并行的任务重叠）、`permission`（发出带三个选项的 `session/request_permission`）、`elicit`（发出带表单的 `elicitation/create`）、`loop`（给出结果前连续 5 次发出相同的工具调用）、`loop2`（连续 4 轮交替发出 `Edit a.rs` 和 `cargo test`）、`ask`（以提问结束本轮，回答作为下一条提示）、`methods`（每条验收依次带 `test`、`command`、`inspection`、`reasoning`、`unverified` 五种证据方法，另有三条任务级证据）、`badmethod`（第一条验收写不合法的 `method: "vibes"`，核对必须拒绝）、`rich`（发出思考、计划、斜杠命令、一个先进行中再完成并带 diff 的工具调用、上下文用量，并自己切换模式；`session/prompt` 的返回带 token 用量）。默认声明 `loadSession: true`（`no-load` 文件关闭、`fail-load` 文件模拟加载报错），收到 `session/load` 时记入 `load <sid>`。用量场景（供只读的用量账本使用）：`usage`（上报三次上下文快照和一个 `cost`，`session/prompt` 的返回带主循环 1200 input / 300 output / 1500 total，以及 `_meta.quota.model_usage` 中主模型 1500 和一个子 Agent 500 两行）、`usage-quiet`（只报上下文快照，完全不上报 token）、`usage-turns`（第一轮 1000 token 后提问，回答后的一轮报 2500，两轮相加是 3500）。`session/set_mode` 记入 `calls.log`（`mode <id>`），一轮进行中收到的 `session/set_config_option` 也照常应用并记入（`set <id> <值>`），每轮提示里的文件引用也记入（`links <路径>…`）。FAKE_DIR 中有 `goal-sticky` 文件时，负责人把 `/goal` 报告为进行中且从不清除，像检查不运行的 Claude Code；Janus 问它目标是否完成时回复 `GOAL_DONE` 加 `lead-go` 的内容，收到 `_session/goal` 时记入 `goal clear` 并报告目标已清除。

作为目标模式负责人时，它先确认说明（`calls.log` 记 `brief ok`），再在收到 `/goal …` 后等待 `lead-go`。计数器保存在 `FAKE_DIR` 中，同一任务的多次尝试（不同进程）共用脚本进度。

## 测试夹具

`flow_tests::harness(name, members, script)`：

- 在系统临时目录创建 `janus-flow-<name>-<pid>`，内含一个初始化过的 Git 仓库作为工作区。
- 注册一个 `fake` Agent，声明 `mode`（`read-only` / `ask` / `agent` / `full`）权限控制项。
- `members` 是 `(角色 id, 是否可写)` 列表，第一个是负责人；不可写的角色使用 `read-only` 模式。
- 测试构建下 `Runtime::leads` 允许 `custom` 类型做负责人，以便脚本化 Agent 担任负责人。

辅助函数：`start`（创建 Run 并以负责人身份提交一份编排）、`finish_lead`（让脚本化负责人结束目标）、`act`（发送 Run 操作）、`tool`（以负责人或协作者身份调用看板工具）、`wait_until`（等待事件条件）、`events`、`has`、`status`。

<a id="test_conventions"></a>
## 约定

- 每个 `flow_tests` 测试给 `harness` 传唯一的 `name`。测试并行运行，名字相同的测试会共用并互相删除临时目录，造成随机失败。
- 测试结束时删除临时目录。
- 新增事件类型或改变流程时，在 `flow_tests` 中用脚本化 Agent 覆盖，不依赖真实 Agent。
- 真实 Agent 的验证由 `just e2e --real` 运行（见[端到端验证](#e2e)），不进入 `just test`。
- 需要等待 SwiftUI 布局或延后滚动的界面测试使用 `@MainActor async`，等待期间通过 `await Task.sleep` 让出主线程。同步 `@MainActor` 测试内反复调用 `RunLoop.main.run(until:)` 不能可靠执行排入主队列的工作，会在滚动修正执行前断言失败。`ChatScrollTests` 先验证主队列中的回调已执行，再检查打开位置、向上翻阅和跟随新消息；修复夹具时保留这些行为断言，并在 CI 的最低支持版本上验证。屏幕锁定时窗口服务器不给窗口显示周期，这个测试会明确跳过并说明原因，解锁后重跑。
- 注入滚动手势的窗口测试把窗口加入显示列表，以便在其他主线程测试运行时也获得显示周期；窗口透明且忽略真实鼠标事件，合成手势直接发送给滚动视图。结束时关闭窗口，避免真实输入或遗留窗口影响后续测试。
