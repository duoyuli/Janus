<a id="running_tests"></a>
## 运行

```sh
just test
```

等于 `cd backend && cargo test`。提交前再运行 `just lint`，执行与 CI 相同的 `cargo fmt --check` 和 Clippy 检查。

macOS 应用的测试见 [macOS 应用](#macos_app)。

测试不访问网络，不调用真实 Agent，也不安装适配器：脚本化 Agent 装成 Codex 和 Claude Code 的替身适配器（`stand_in_adapters`），由 `python3` 代替 Node 启动。需要本机有 `git` 和 `python3`。

<a id="e2e"></a>
## 端到端验证

每个需求开发完成后运行 `just e2e`，它是合并前的必过门禁（`AGENTS.md` 合并前检查第 12 条）。依次执行以下步骤，任何一步失败即停止：

| 步骤 | 命令 | 验证什么 |
| --- | --- | --- |
| 1. 静态检查 | `just lint` | 格式和 Clippy，与 CI 相同 |
| 2. 后端测试 | `just test` | 单元测试和进程内的流程测试（`flow_tests`），见[测试分布](#test_layout) |
| 3. 应用测试 | `just test-mac` | 应用的推导逻辑和视图，见 [macOS 应用](#macos_app) |
| 4. 产品端到端测试 | `just e2e-product` | 真实构建的服务和应用跑完每条用户旅程，见[产品端到端测试](#product_e2e) |
| 5. 数据升级测试 | `just e2e-upgrade` | 最近的发布版本写出的数据由当前版本升级，见[数据升级测试](#upgrade_tests) |

`just e2e` 的参数交给第 4 步：

- 不带参数：从源码构建，替身 Agent 运行，结果确定，不访问网络，约 5 分钟。每个需求都跑。
- `--packaged`：测试 `just app` 打出的 `dist/Janus.app`（内置服务和 Node.js），能发现打包、签名和内置 Node 的问题。发布前必跑。
- `--real`：另加真实 Codex 负责人和 Claude Code 协作者的冒烟测试（`real` 场景），需要网络，以及一个已经配好 Codex 和 Claude Code 并通过配置检查的 Janus（默认 `~/.janus`，`--real-from <Janus home>` 指定其他的），会消耗 token（第一次运行约 5 分钟、135 万 token），视 Agent 发挥可能更久。发布前，以及改了 ACP 集成、适配器、Agent 启动环境或负责人提示时必跑。

新功能改了用户可见的行为时，在产品端到端测试中新增或修改场景，见[编写场景](#e2e_scenarios)。e2e 只在本地运行，不在 CI 中运行。

<a id="product_e2e"></a>
## 产品端到端测试

`e2e/product.py`（`just e2e-product`）在真实的二进制上验证产品，覆盖 `flow_tests` 碰不到的部分：正式构建的适配器查找和 Node 启动（后端测试用 `python3` 运行替身适配器）、HTTP 接口、看板 MCP 端点、服务重启，以及应用从服务读到的状态。

运行方式：

1. 构建服务（`cargo build`）和应用（`swift build`）；`--packaged` 时运行 `frontend/scripts/package.sh --no-dmg`，使用 `dist/Janus.app` 中的 `janus-server`、应用和内置 Node.js。
2. 在系统临时目录创建 `janus-e2e-*`，其中有临时 Janus home、每个场景的 Git 工作目录和脚本化 Agent 目录。服务监听 `127.0.0.1` 上的一个空闲端口（每次运行由系统分配，所以两个任务各自的 worktree 里可以同时跑端到端测试），不碰用户的 `~/.janus` 和 7878 端口。
3. **替身适配器**：在临时 home 的 `cache/adapters/codex/9.9.9/` 和 `cache/adapters/claude/9.9.9/` 放入与官方 npm 包同名的包，`bin` 是一个 Node 脚本，它把标准输入输出交给 `backend/testdata/fake_acp.py`。Janus 照常用 Node 启动「Codex」和「Claude Code」，走的是正式的启动路径，Agent 的行为由脚本决定，不联网、不花钱。协作者也用 Claude Code 类型，经同一个替身适配器运行脚本化 Agent。
4. 启动应用，连接这个服务（`JANUS_HOME`、`JANUS_ADDR`），通过快照命令通道驱动（见 [macOS 应用](#macos_app)）。应用的本地设置写进单独的 `JANUS_DEFAULTS_SUITE`，结束时删除，不改用户自己的应用设置。
5. 按场景运行：`setup` 最先运行；其余场景各自建团队（Agent、数字员工、工作区、脚本化 Agent 目录），最多 4 个并行；会重启或替换服务的场景（`restart`、`app-server`、`real`）最后依次运行。
6. 测试脚本扮演负责人的「大脑」：从脚本化 Agent 的 `calls.log` 读出负责人会话的看板地址，像 Agent 一样调用 `orchestrate`、`wait`、`reply`、`retry` 等工具；协作者的行为由 `script.json` 决定；用户的操作走 HTTP 接口，和应用发出的请求相同。
7. 每个场景结束时打开应用，等应用推导出的状态（`state` 命令写出的 Run 状态、任务状态、验证判定、收件箱、用量、资源库 Skill 的使用次数和改进提示）与服务记录的一致，再按页面截图，检查截图是真实窗口的尺寸且不是纯色：主窗口没有打开时，`shot` 截到的是菜单栏图标的小窗口，不能算画出来了。
8. 所有场景跑完后检查临时 Janus home 的顶层只有布局声明过的名字（`e2e/lib.py` 的 `HOME_TOP`，对应 `layout::TOP`），作为报告中单独的一项「Janus home」。
9. 报告写在 `janus-e2e-*/report/`：`report.md`（每个场景的检查项和失败原因）、`janus.log`、`app.log` 和 `app/` 下的截图。没有 `--keep` 时删除报告以外的临时文件。新功能涉及的页面，开发者要亲自看一遍截图。

参数：`--only <场景>`（可重复）、`--list` 列出场景、`--no-app` 只测服务、`--keep` 保留临时 home 和工作目录、`--packaged`、`--real`、`--real-from`。

| `setup` | 服务的 meta、替身适配器、默认数字员工（含通用数字员工和「老友」，都带 256 像素的默认头像）；在应用里换上自己的头像得到裁好的 256 像素 PNG，非 PNG 被拒绝，移除后回到文字；Agent 类型只有 Codex 和 Claude Code（添加自定义命令的 Agent 被拒绝）、两种 Agent 的配置检查和控制项；凭据不出现在设置接口中，Agent 编辑器经本机接口读到并显示全部环境变量的值（网页和改绑的域名读不到）；没绑定 Agent 的数字员工不能做负责人；资源库的 Skill 和带值的 MCP（资源没有「给谁用」，收口和勾给数字员工的接口已删除，数字员工没有 `resources`）；协作者的 `session/new` 只有看板和 `janus-tools`，MCP 的地址和值都不在里面，也不进入 Run 记录和导出；命令服务器由 MCP 路由在 Run 的 worktree 里启动，HTTP 服务器（替身 `fake_mcp_http.py`）添加后预先连接并数出工具，经路由调用时带着保存的 header，经真实 HTTP 列工具（读完分页、不列只能以 task 方式调用的工具、说明以服务器名开头）、调用，未知工具返回 `-32602`，协作者的令牌不能冒充负责人，调用记 `mcp.routed`；工作区和目录检查；被使用的资源和数字员工不能删除；默认团队跑通一个带独立验证的目标；应用的设置各页、数字员工和工作区编辑器，共享资料在单独的表单里编辑、不打开工作区设置 |

| `failures` | 自动重试、依赖失败与重试后恢复、没通过验收由负责人接受、取消连带下游、验证者判定不通过不能放行、负责人用 `retry` 让任务按验证意见回到原会话返工（不选会话被拒绝）、验证在自己的会话中复审通过、返工时正在执行的下游收到通知并列给负责人、不合法的证据方法；应用中返工和复审在同一个会话卡片里接着显示 |

| `controls` | 暂停与继续、打断后人工接管并以当前结果结束、接管与交还（负责人在看板上读到「[用户介入]」）、切换控制项（空值被拒绝）、没有预算可追加、状态冲突（409）、取消、删除（删除后 Janus home 中没有留下名字带这个 Run id 的任何东西，删除 worktree 时有意保留的补丁除外） |
| `sessions` | 思考、计划、斜杠命令、工具 diff、模式和用量；同时改同一文件的冲突；认领、`peers`、拆分请求；痕迹对账；`@` 文件搜索与引用 |
| `adapter-updates` | ACP 适配器的新版本：服务启动后自动检查每个已安装的适配器；装的已是最新时不提醒、也不显示成适配器的任务；npm 上有新版本时标出可以升级，应用侧栏提醒；装的比 npm 上的还新时不算新版本；没有新版本后提醒消失 |
| `skills` | Skill 路由：负责人和协作者的系统层都写明 `janus-skills` 目录的位置；替身 Agent 照着读目录、在目录里找到 Skill 再读它的 `SKILL.md`；`janus-skills` 的描述写明何时读它并带上描述片段，目录逐行写着完整描述；读 Skill 记一条 `skill.used`，读目录不算；资源库记下读过它的会话数，描述太短的 Skill 带着 `short` 提示，目录方式是 `list`；应用里每个 Skill 的会话数和提示类别与服务端一致、提示写成界面语言的文字，路由说明按目录顺序（读过的在前）排、目录方式与服务端一致，并截图资源库的 Skill 页 |
| `chats` | 和一名数字员工对话：不存在的数字员工被拒绝；开始对话就打开会话、注入系统提示词，Agent 不先说话，第一条消息之前没有标题；第一条消息成为标题；对话是 `chat` 类型的 Run，在 Janus home 下新建的目录里，团队只有这名数字员工，没有看板 MCP，Agent 知道自己在单独对话；不进任务列表；对话列表按页读取（第二页接着第一页，不对的 cursor 被拒绝）；第二条消息在同一个会话里；带表格和代码块的 Markdown 回复在应用中按表格和代码块显示（`lastReply`），不是一段竖线和反引号；应用的对话页和对话首页；应用中默认 ⌘↩ 发送、↩ 只换行，改成「↩ 发送」后 ⇧↩ 换行不发送、↩ 把消息发给数字员工并得到回复，设置 → 通用的「发送消息」画出来了；对话的工作目录在 `work/chats/` 下，和任务分开；删除时工作目录、资源包和日志一起删除，Janus home 中没有留下名字带对话 id 的东西 |

| `queue`（串行） | 派发队列：用一个槽位重启服务；第一个目标直接开始，后两个排队且只有 `run.queued`；详情和列表带排位，应用的任务页和工作区页写出排位；排队的目标不能发消息（409）、取消后不再开始；暂停让出位置，下一个自动开始；「立即开始」越过槽位；另一个工作区的目标占着位置时这个工作区的目标也排队，停掉服务再启动后，在做的目标记为中断、排队的目标自动开始，应用里是进行中。其余场景的服务用 32 个槽位，互不排队 |
| `restart` | 服务重启：Run 记为中断、从中断处继续（新的看板令牌、已完成任务不重跑、原会话 `session/load` 续接）、回放已交付的 Run 时会话只读且草稿不发出、已交付的 Run 重启后继续对话（同时发来的两条消息只加载一次原会话，两条都送到负责人）、应用重新连上 |
| `app-server` | 没有服务在运行时应用自己启动服务（源码运行用 `JANUS_SERVER_BIN`，打包版用内置的），退出时停掉它 |
| `real`（`--real`） | 独立的 Janus home 和另一个空闲端口；拷贝一份 `--real-from` 中的 Codex 和 Claude Code Agent（同样的设置，「复制本机配置」从同样的来源目录再复制一次，接口不返回的凭据按文件复制），Janus 从 npm 安装真实适配器；Codex 负责人带 Claude Code 协作者在 `examples/calc` 的副本上完成一个小目标（目标里明确要求交给协作者实现并独立验证，否则负责人会按规则自己做完），运行它的测试，并确认负责人派出子任务后没有自己改文件；资源库里放一个给所有人的命令服务器（替身 `fake_mcp.py`）和 11 个 Skill（都给所有数字员工），确认真实的 Claude Code 经 `janus-tools` 调通了路由工具，负责人派出后若调用了资源库工具，交付风险里列出了它；两个 Agent 都把加载到的 Skill 列成会话命令（Codex 是 `$<名字>`，Claude Code 是 `janus:<名字>`），要求各自都有 `janus-skills`、且被它收起的 11 个 Skill 一个都不单独出现；另放一个 calc 项目测试写法的 Skill（`calc-test-conventions`），目标不点它的名、也不复述它的描述，检查真实 Agent 从目录里找到并读了它（`skill.used`），新测试照它的写法命名（`test_mod_…`）；用户决定按推荐项自动处理；结束时删除复制来的凭据 |

编写场景：

- 场景是 `e2e/scenarios/` 中带 `@scenario` 的函数，参数是 `ctx`（服务、应用和辅助函数）和 `c`（检查）。`c(条件, 说明)` 记一项检查，`c.must` 失败时中止场景。说明写成用户能理解的行为。
- 服务的 `npm_config_registry` 指向 `e2e/lib.py` 的替身 registry（`Registry`，`ctx.registry`），适配器的新版本检查不访问 npm：每个包的最新版本默认是替身适配器的版本，场景可以改（`ctx.registry.latest[包名]`），问过哪些包记在 `ctx.registry.asked`。`--real` 的冒烟测试用自己的服务，从真实的 npm 安装。
- `ctx.team(...)` 建一个团队，`team.run(目标)` 提交目标，`run.orchestrate`、`run.read_board`、`run.finish` 扮演负责人，`run.act` 执行用户操作，`run.wait_event` 等事件，`ctx.ui` 核对应用的状态并截图。共用部分在 `e2e/lib.py` 和 `e2e/scenarios/__init__.py`。
- 每个场景用自己的团队名（同时也是 Agent、数字员工和工作区 id 的前缀），场景之间不共享 `FAKE_DIR`：负责人等待的 `lead-go` 文件对同一目录下的所有负责人生效。
- 鉴权和校验类的检查至少写一个反例（合并前检查第 1 条）。
- 新功能需要脚本化 Agent 的新行为时，扩展 `fake_acp.py` 并更新[脚本化 Agent](#fake_agent)。

## 数据升级测试

改了存储的数据（表、设置对象或 Run 快照的字段、默认数字员工）就要加迁移，见[数据升级](../architecture/20261031-data_model.md#migrations)。三层测试保证迁移写了、写对了：

1. **写入时的检查**：测试中每次 `put_config` 都按 `data_shape.rs` 登记的字段检查，缺字段或多字段直接失败。直接写设置对象的测试用 `agents::test_connection`、`agents::test_role` 生成完整的对象。
2. **单元测试**（`backend/src/migrations/tests.rs`，随 `just test` 运行）：
   - 新库从 0 升到最新、不备份；更新版本的数据被拒绝；预览不改动原库；字段步骤重复执行不再改动。
   - `backend/testdata/upgrade/v0.sql` 是 Janus 2026.11.18 真实写出的数据（由下面的端到端脚本导出），升级后先有备份，每个对象都符合当前结构，迁移不涉及的对象原样不变，再次打开不重复升级，迁移删掉的表（`leases`）不会被重新建出。
   - `the_data_shape_matches_its_snapshot`：表结构和登记的字段与 `backend/testdata/data_shape.json` 一致。结构变了而数据版本没变时失败，提示先加迁移；加了迁移后运行 `just data-shape` 更新快照。
   - 某个迁移处理的数据在 `v0.sql` 中没有（例如之后新增的设置类型）时，用端到端脚本从对应版本导出新的样本，放进 `backend/testdata/upgrade/` 并在测试中覆盖。
3. **端到端测试**（`just e2e-upgrade`，`just e2e` 的最后一步）：`e2e/upgrade.py` 对最近 3 个发布标签（或 `--from <标签>` 指定的）逐个执行：
   - 用 `git archive` 取出这个标签的 `backend/`，在临时目录构建旧版服务；在临时 Janus home 和一个空闲端口上启动，按应用的方式通过接口写入数据：两个 Agent 连接（2026.11.20 起的版本不再接受「自定义命令」，只建 Claude Code 一个）、绑定 Agent 的默认数字员工、改过指令的默认数字员工、自定义数字员工、工作区（有一次提交的 Git 仓库），再写入两个带那个版本成员快照的已交付 Run：一个直接在目录中运行，一个在这个仓库的 worktree 中运行、没有记录开始时的分支（成员按旧版本的数据版本取当时的格式）。
   - 停掉旧版服务，`janus migrate --dry-run` 预览升级且不改动数据；再启动当前版本的服务，检查数据版本、备份（旧版本的数据已是最新时，检查不升级也不备份）、没改过的默认数字员工换成当前文本、改过的保留并提示、自定义数据和工作区不变、Run 快照成员已迁移、worktree 中的旧 Run 记下工作目录检出的分支、「保留我的」之后不再提示、升级后预览没有遗留问题、再次启动不重复升级、更新版本的数据被拒绝；Janus home 整理成新布局（数据库在 `data/`，凭据在 `data/secrets/`，Agent 的配置目录在 `data/agents/<id>/config`，顶层只有布局声明过的名字）。
   - 需要 Rust 工具链、`git` 和 `python3`，每个标签的构建要一两分钟。`--keep` 保留临时目录，`--dump-fixture <路径>` 把最旧标签写出的数据导出为样本 SQL。

<a id="fake_agent"></a>
## 脚本化 Agent

`backend/testdata/fake_acp.py` 是一个按脚本行事的 ACP Agent，声明支持 HTTP MCP。它装成 Codex 和 Claude Code 的替身适配器：后端测试的 `test_app` 在临时 Janus home 的 `adapters/<id>/9.9.9/` 下放一个与官方 npm 包同名的包，`bin` 指向这个脚本，并把运行适配器的程序（`Config::node`）设为 `python3`（`stand_in_adapters`）；端到端测试用一个 Node 脚本转给它，见[产品端到端测试](#product_e2e)。所以测试走的是正式的启动路径和 Claude Code、Codex 的系统层。`FAKE_DIR` 环境变量指向它的工作目录：

| 文件 | 作用 |
| --- | --- |
| `script.json` | 任务 id → 每次提示的结果列表，最后一个结果重复使用 |
| `calls.log` | Agent 记录收到的会话设置（`session/new` 的 `_meta` 和 `mcpServers`、`set_config_option`）和负责人收到的提示 |
| `lead-go` | 目标模式负责人在这个文件出现前一直工作，然后以文件内容作为最后回复结束 |
| `mute` | 存在时不回答 `initialize`，像启动时卡住的 Agent |
| `steer` | 存在时声明 `_session/steering`：一轮进行中收到的 steer 记入 `calls.log`（`steer <内容>`，带文件引用时另记 `links <路径>…`），回复 `injected` |
| `session-<会话 id>.json` | Agent 自己写的会话与任务、验收标准的对应关系：服务重启后用 `session/load` 加载的会话由新进程接手，仍知道自己在做哪个任务 |

`script.json` 中可用的结果：`ok`、`fail`、`cancelled`、`slow`、`busy-tool`（进行中的工具调用持续 2.5 秒）、`high-ctx`（上报 80% 上下文占用）、`handoff`（写文件并返回 `handoff`、`risks` 和 `reasoning` 方法）、`reject` / `approve`（返回带证据的 `verdict: "rejected"` / `"approved"`）、`write:<文件>`、`edit:<文件>`（写文件并上报一次带 `locations` 的 `edit` 工具调用，再忙 2 秒，让并行的任务重叠）、`permission`（发出带三个选项的 `session/request_permission`）、`elicit`（发出带表单的 `elicitation/create`）、`loop`（给出结果前连续 5 次发出相同的工具调用）、`loop2`（连续 4 轮交替发出 `Edit a.rs` 和 `cargo test`）、`ask`（以提问结束本轮，回答作为下一条提示）、`methods`（每条验收依次带 `test`、`command`、`inspection`、`reasoning`、`unverified` 五种证据方法，另有三条任务级证据）、`badmethod`（第一条验收写不合法的 `method: "vibes"`，核对必须拒绝）、`rich`（发出思考、计划、斜杠命令、一个先进行中再完成并带 diff 的工具调用、上下文用量，并自己切换模式；`session/prompt` 的返回带 token 用量）、`skill:<名字>`（像真实 Agent 用资源库 Skill：从系统层找到 `janus-skills` 的 `SKILL.md`，读目录，按目录写的位置读这个 Skill 的 `SKILL.md`，两次读取都上报为 `read` 工具调用，在 `calls.log` 记 `skill <名字> read`，目录里没有时记 `skill <名字> missing`）。默认声明 `loadSession: true`（`no-load` 文件关闭、`fail-load` 文件模拟加载报错），收到 `session/load` 时记入 `load <sid>`；`session/new` 和 `session/load` 都记一行 `layer <new 或 load> <sid> <系统层的 JSON 字符串>`，系统层取 `_meta.systemPrompt.append`，没有时取 `CODEX_CONFIG` 的 `developer_instructions`。用量场景（供只读的用量账本使用）：`usage`（上报三次上下文快照和一个 `cost`，`session/prompt` 的返回带主循环 1200 input / 300 output / 1500 total，以及 `_meta.quota.model_usage` 中主模型 1500 和一个子 Agent 500 两行）、`usage-quiet`（只报上下文快照，完全不上报 token）、`usage-turns`（第一轮 1000 token 后提问，回答后的一轮报 2500，两轮相加是 3500）。系统层写有「a Loop in the workspace」的会话是工作区值班：每次开工的提示记 `loop prompt <JSON>`，回复「看过了：<第一行>」；以 `[me] ` 开头的是测试里以用户身份发的消息，回复「回复：<其余>」；提示里有 `[write <文件>]` 时先在工作区追加这个文件，有 `[hold]` 时一直等到 FAKE_DIR 中出现 `loop-go`（随即删掉）。`session/set_mode` 记入 `calls.log`（`mode <id>`），一轮进行中收到的 `session/set_config_option` 也照常应用并记入（`set <id> <值>`），每轮提示里的文件引用也记入（`links <路径>…`）。FAKE_DIR 中有 `goal-sticky` 文件时，负责人把 `/goal` 报告为进行中且从不清除，像检查不运行的 Claude Code；Janus 问它目标是否完成时回复 `GOAL_DONE` 加 `lead-go` 的内容，收到 `_session/goal` 时记入 `goal clear` 并报告目标已清除。

不是任务的提示里写着「[write <文件>]」时，在会话目录里追加这个文件并结束这一轮（交付后让负责人补写文件）。`hold:<文件>` 一直工作到 `FAKE_DIR/<文件>` 出现，然后给出通过的验证结论（验证还在执行时被验证的任务返工）。

对话中的数字员工在系统层里看到对话说明（「talking with the user directly」）时在 `calls.log` 记 `chat brief <工作目录>`，之后每条提示都回复「回复：<提示>」。

作为目标模式负责人时，它在 `session/new`、`session/load` 的系统层（`_meta.systemPrompt.append`）里看到负责人说明时在 `calls.log` 记 `brief ok`（从中断处继续时记 `brief ok resumed`），再在收到 `/goal …` 后等待 `lead-go`。计数器保存在 `FAKE_DIR` 中，同一任务的多次尝试（不同进程）共用脚本进度；读和加一在文件锁里完成，同时运行的进程（例如两个配置检查共用 `count-unknown`）不会读到写了一半的计数。

`backend/testdata/fake_mcp.py` 是一个按 stdio 说 MCP 的替身服务器，给 [MCP 路由](../domains/20261116-resource_library.md#mcp_router)的测试用：每次启动在 `FAKE_MCP_LOG` 指向的文件里记一行 `start`（用来确认列工具时没有启动它），工具 `cwd` 回答它的工作目录，`echo` 原样返回 `text`，`roots` 反过来向客户端发 `roots/list` 并回答第一个根目录，`env` 回答 `HOME` 和指定的环境变量，`grow` 新增一个工具并发出 `notifications/tools/list_changed`，`quit` 回答后退出，`spawn` 启动一个 `sleep` 子进程并回答它的 pid，`hang` 一直不回答、被取消时（`notifications/cancelled`）在 `FAKE_MCP_CANCELLED` 指向的文件里记一行 `cancelled <原因>`，`task_only` 只能以 task 方式调用（`execution.taskSupport: required`）。工具列表分两页给出（`nextCursor`）；`FAKE_MCP_VERSION` 指定它在 `initialize` 中回答的协议版本。

`backend/testdata/fake_mcp_http.py` 是 HTTP 上的替身 MCP 服务器：在 `127.0.0.1` 的空闲端口上监听，第一行输出端口；`/mcp` 是 Streamable HTTP（`initialize` 给出 `Mcp-Session-Id`，工具调用用事件流回答，其他用 JSON），`/sse` 是旧的 SSE 传输（先给出消息地址，回复从事件流到达）。每个请求都要带 `Authorization: Bearer good`，否则返回 401。它把新会话（`init`）、被客户端结束的会话（`delete`）和打开的事件流（`sse`）记到第一个参数指向的文件；工具 `whoami` 回答收到的 `Authorization` 和 `MCP-Protocol-Version`，`expire` 忘掉当前会话，之后带着它的请求返回 404。

<a id="harness"></a>
## 测试夹具

`flow_tests::harness(name, members, script)`（`harness_with` 另外改 `App` 的配置，例如停滞阈值、槽位数）：

- 在系统临时目录创建 `janus-flow-<name>-<pid>`，内含一个初始化过的 Git 仓库作为工作区。
- 注册一个 Claude Code 类型的 `fake` Agent（经替身适配器运行脚本化 Agent），声明 `mode`（`read-only` / `ask` / `agent` / `full`）权限控制项。
- `members` 是 `(角色 id, 是否可写)` 列表，第一个是负责人；不可写的角色使用 `read-only` 模式。

辅助函数：`start`（创建 Run 并以负责人身份提交一份编排）、`finish_lead`（让脚本化负责人结束目标）、`act`（发送 Run 操作）、`tool`（以负责人或协作者身份调用看板工具）、`wait_until`（等待事件条件）、`events`、`has`、`status`。

<a id="test_conventions"></a>
## 约定

- 每个 `flow_tests` 测试给 `harness` 传唯一的 `name`。测试并行运行，名字相同的测试会共用并互相删除临时目录，造成随机失败。
- 测试结束时删除临时目录。
- 新增事件类型或改变流程时，在 `flow_tests` 中用脚本化 Agent 覆盖，不依赖真实 Agent。
- 真实 Agent 的验证由 `just e2e --real` 运行（见[端到端验证](#e2e)），不进入 `just test`。
- 需要等待 SwiftUI 布局或延后滚动的界面测试使用 `@MainActor async`，等待期间通过 `await Task.sleep` 让出主线程。同步 `@MainActor` 测试内反复调用 `RunLoop.main.run(until:)` 不能可靠执行排入主队列的工作，会在滚动修正执行前断言失败。`ChatScrollTests` 先验证主队列中的回调已执行，再检查打开位置、向上翻阅和跟随新消息；修复夹具时保留这些行为断言，并在 CI 的最低支持版本上验证。屏幕锁定时窗口服务器不给窗口显示周期，这个测试会明确跳过并说明原因，解锁后重跑。
- 注入滚动手势的窗口测试把窗口加入显示列表，以便在其他主线程测试运行时也获得显示周期；窗口透明且忽略真实鼠标事件，合成手势直接发送给滚动视图。结束时关闭窗口，避免真实输入或遗留窗口影响后续测试。

- `just test-mac`（`cd frontend && swift test`）运行 `frontend/Tests/JanusTests` 中的 Swift Testing 测试：事件推导、看板事实、用量账本（与后端共用的 `usage_cases.json`、每轮相加、按模型的上报、上下文快照不累计、缺失与 0、费用的累计与重置、负责人单列、尝试的结局、等待时间、回放位置、实时 Run 的耗时按秒推进与结束 / 只读 / 回放时冻结、提醒只读、金额的美元写法，`UsageLedgerTests`；用量卡片和时间段账单在浅色与深色下的绘制，`SessionViewTests`）、JSON、Markdown 文档的解析、Run 中 Markdown 文档的收集、负责人卡住和改了同一个文件的待处理事项、越界和结果对不上的待处理事项与认领（`tracesOpenOnTheBoardUntilTheLeadActs`）、插话被读到后不重复显示、Plan 控制项过滤、资源库条目的文案（来源、来源中已删除、缺少的值、按运行时的不支持原因、每项一行的警示；Skill 按目录顺序排、目录方式、使用情况和按类别写成文字的改进提示，`LibraryTests`）、新建工作区的预设（通用数字员工绑定 Agent 后是负责人加通用数字员工，`newWorkspacesStartWithTheLeadAndTheGeneralWorker`）、数字员工编辑器里给所有人的资源的概括（`theWorkerEditorSumsUpWhatEveryoneHas`）、收件箱（只取运行页标为等人处理的条目、已结束 Run 的验收与继续提醒、稍后处理到时间回来且会卡住 Agent 的事项不能推迟、选择题就地回答的按钮和文案，`InboxTests`）、时间文案、用量数字和缺失状态、首页按原因合并的问题、审计日志按前缀分类和只编译一次的正则（`FormatTests`）、diff 的解析和审阅意见合成的消息、系统通知只发新事项（`DiffTests`）、会话的计划、控制项、命令、用量的读取和输入框补全、用量的「本会话 / 上一轮」标签与 Run 累计分开、内联 diff 的行、Agent 回显的看板工具调用（`mcp.janus.*`、`mcp__janus__*`）不重复显示、会话只在停在底部时跟随新内容（`ChatFollow`，`SessionViewTests`）、尝试标题行写明在哪个会话和为什么开始（返工、复审，`attemptHeadersSayWhichSessionAndWhy`）、负责人的返工记为一条带会话选择和验证意见的决定并清掉复审前的旧判定（`aReworkIsTheLeadsDecisionAndClearsTheOldVerdict`）、在真实窗口中用触控板手势往上翻后新回复不移动视图、回到底部后继续跟随、打开时停在最新处（`ChatScrollTests`），以及应用更新（`UpdaterTests`：版本号比较、只下载变化的部分、`update.json` 的读取、用 `codesign` 现场签一个最小应用包来检查签名校验、版本号不符和文件被改动后拒绝安装、替换脚本移入新版本失败且留下半个新应用时，旧应用完整放回原处并打开）。只装命令行工具时，`@Test` 宏插件在 `usr/lib/swift/host/plugins/testing` 下、不会自动加载，`just test-mac` 检测到这种情况会加上 `-plugin-path`；CI 的 macOS 运行环境自带 Xcode，直接运行 `swift test`。
- `MacPermissionsTests` 使用注入的系统接口，覆盖首次启动、同版重启、签名身份或 bundle ID 变化、全部已授权时不弹引导、逐项引导只在检测到授权后前进、拒绝和跳过、实时撤权、系统不给答案时的「无法检测」、系统设置打开失败、引导记录保存失败，以及源码运行不申请权限。测试不访问 TCC 数据库、不触发系统授权弹窗。界面验收使用隔离的应用包和 Janus home，通过快照命令检查权限页与首次引导，不与滚动交互测试并行渲染。
- 查看界面：设置 `JANUS_SNAPSHOT_DIR` 后，应用每 0.7 秒读取一次 `<目录>/cmd`，逐行执行 `open inbox`、`open run:<id>`、`open home:<工作区>`、`open settings:<general|agents|roles|library|adapters|usage|permissions|updates>`（`permissions` 和 `updates` 打开「通用」并滚动到对应的一节；`library:skill`、`library:mcp` 打开资源库的 Skill 或 MCP 标签）、`page <board|audit|team|task:<id>|agent:<id>|replay:<seq>>`、`fold <usage|progress|risks|tasks|all|任务> <open|closed>`（展开或收起工作台的用量明细、运行级风险、进展时间线和逐条验收，用来截展开态）、`role <id>`、`agent-edit <id|new>`（打开某个 Agent 或新建 Agent 的编辑器）、`workspace <id>`、`mcp-edit <new|名字|catalog:<精选>> [json]`（在资源库的 MCP 标签打开新建、某个服务器或某个精选服务器预填好的编辑器，带 `json` 时打开 JSON 视图）、`close-sheet`（也关闭设置浮层）、`doc <路径>`（打开文档窗口）、`paste <图片路径>`（把图片交给当前窗口第一个输入框的粘贴处理，使用私有剪贴板）、`size <宽>x<高>`、`shot <名字>`、`snooze-first` / `wake-all`（把第一条可推迟的事项放一小时后 / 让所有推迟的事项回来）、`close-window`（关闭主窗口，检查只剩菜单栏图标）、`appearance <light|dark|system>`（只在应用内切换浅色或深色外观，不改系统设置）、`review <任务>`（打开这个任务最新 diff 的审阅窗口）、`window <标题开头>`（之后的 `shot` 截标题以它开头的窗口，不带参数时恢复默认）、`inbox-act <条目>:<按钮>`（按位置点收件箱里的就地回答按钮，走和点击相同的代码）、`density <detail|summary>`（切换会话的显示档位）、`draft <任务或 Agent> <文字>`（往会话的输入框里填文字，用来看斜杠命令和 `@` 文件的候选）、`send-key <commandReturn|return>`（像设置里那样选择发送键）、`press <return|shift-return|command-return>`（在当前窗口第一个输入框里按键，走和打字相同的处理）、`reload`（重新读取设置、资源库和 Run 列表，像重新打开应用一样；通过接口写入的设置随后出现在应用中）、`state <名字>`（把当前页面、收件箱（含每个事项的种类和就地按钮）、设置浮层、Dock 图标、应用读到的 Agent、数字员工、工作区和 Run 列表、发送键（`sendKey`），以及打开的 Run 中各会话输入框的草稿（`drafts`）、应用推导出的状态、任务状态、尝试次数、验证判定、待处理请求、各 Agent 阶段、用量、运行卡片此刻显示的耗时（`elapsedMs`），以及最后一条 Agent 消息画成的 Markdown 块（`lastReply`，例如 `["para", "table:仓库,分支", "code:bash"]`）写成 `<名字>.json`，产品端到端测试据此核对应用与服务一致），截图保存为 `<目录>/<名字>.png`。截的是应用自己的窗口，不需要屏幕录制权限；窗口服务器返回纯色图片时（例如没有屏幕录制权限或窗口不在当前桌面）改用视图自身渲染。配合 `JANUS_HOME` 和 `JANUS_ADDR` 指向一份数据副本使用，不影响正在运行的 Janus；这种模式下应用不自动检查更新，不访问 GitHub。应用启动时忽略 AppKit 保存的窗口状态（`$TMPDIR/<bundle id>.savedState`，与同一 bundle ID 的其他进程共用），测试实例退出时写下的状态不会让主窗口在下次启动时不出现。设置 `JANUS_DEFAULTS_SUITE` 时，应用的本地设置（收件箱的推迟、选中的工作区、外观、语言、显示档位等）写进以它命名的独立存储，不改用户自己的应用设置。
