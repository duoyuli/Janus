# 规则的来由

每条都是：发生了什么 → 规则。「分工」一节是多 Agent 协作里反复出现的问题，后面几节来自一次三天、约 160 个 PR 的生产运行（一个公开的 Web 应用，一个负责人会话带一组协作者）。想偏离某条原则，或拿不准它的边界时读这里。

## 分工

- 「验证没通过就自动返工」看起来顺理成章，但哪一项要返工、回原会话还是新开会话，取决于问题出在哪里，是读过看板之后的判断。→ 机械的事照做，判断留给负责人。
- 负责人派出子任务后自己接手改文件，这些改动没有经过任何验收。→ 派出之后只做管理；确实改了就单独列出并说明怎样核对的。
- 验收标准写成要执行的命令，协作者跑了命令就算完成。→ 标准写可观察的结果，协作者按标准自己验证并逐条给证据。
- 同一套检查在没变过的文件上被反复重跑，验证和返工占掉了近一半的时间。→ 记下文件状态，没变就引用已有的证据。
- 结果写在回复正文里，要从文字里猜哪条达到了。→ 结果有固定的结构，逐条对应验收标准，格式不对当场退回。
- 注入给协作者的说明越写越长，协作、做法和任务混在一起，互相矛盾。→ 协作约定、角色指令、子任务说明各写各的，一条规则只说一次。
- 给工作加时间上限，快做完的子任务被打断重来。→ 工作没有时间和费用上限；停滞只报告，由负责人判断。

## 授权

- 发布会话把支付 PR 上的门禁通过当成了发布的许可，整批已经准备推送，推送前被叫停。→ 通过是证据，不是授权；高风险的 PR 列在挂起清单里，只在记下用户原话之后单独发布。
- 一个界面 PR 包含了它的后端 PR 的提交（两次）。把后端 PR 的编号排除在一批之外，并不能把它的提交排除在外。→ 冻结一批之前，检查没有候选包含挂起的 head。
- 一次运行的授权（按批发布、快速回滚）被写成了通用规则。→ 授权记在这次运行的看板里，带出处和范围；示例不授予任何东西。
- 生产上的步骤被提出时，好像检查通过就等于批准。→ 每一项生产变更都点名确切的提交、SQL 或设置，并为这一项等用户的同意。
- 创建付费或账号级的资源可能被拒绝给 Agent。→ 放进用户的清单，附上要打开的页面；不绕过。

## 门禁与测试

- 一次门禁漏了准入路由的测试就通过了支付 PR，发布时更宽的检查发现 27 个失败。→ 边界改动加上每个调用方的测试。
- 一轮批量门禁为 11 个文件的改动跑了 639 个测试文件（12 分钟）。→ 范围是改动的测试加改动源码旁的测试；整套一天一次。
- 一轮批量门禁在第一个冲突处停下，什么也没测。→ 只中止那一次合并，测其余的。
- 两轮门禁因主干上本来就坏的测试而失败。→ 在确切的主干提交上复现，区分测试过期和产品缺陷。
- 名字过滤器跳过了所有断言，仍然返回 0；一个检查读的是未提交的状态，在已提交的合并上是空的。→ 核对实际执行了什么。
- 负载让测试随机超时。→ 单独重跑两次；间歇性超时可能是负载，单个断言稳定失败是真的。
- 过期的生成文件产生了并不存在的类型错误。→ 相信一个红色的检查之前，先清掉生成产物。

## 发布与构建

- 主干在 32 小时内接了约 136 次 push，每次都是一次付费的生产构建。→ 每批一次 push；文档搭下一批的车。
- 一批在检查运行时不断增长，40 分钟没能 push。→ 检查一开始就冻结。
- 两天里 15 次失败的托管预览构建，每次都全额计费。→ 推预览之前先本地构建。
- 框架的构建拒绝了符号链接到主检出目录的 `node_modules`。→ 每个 worktree 用项目的包管理器做真实安装。
- 评审期间本地主干比远端落后一天。→ 新目标从刚 fetch 的、记下来的提交拉分支。
- `git add docs/brand` 提交了 119 个本地工作文件。→ 添加明确的路径。

## 跟进协作者

- 终端状态显示完成，实际上只是一轮结束。→ 完成 = 结果文件 + 你自己对 diff 和检查的核对。
- 一份说明留在输入框里没发出去；一个会话停在对话框上；三个 Codex 会话启动时被对话框吞掉了第一条消息，停了约 3 分钟才有人读屏幕。→ 每次启动和发送之后确认它在工作。
- 常驻的发布会话在一个失败处停下，干等了三次。→ 停下的会话要读屏幕、归因、处理，不能只是继续等。
- 一个长期运行的会话在它的 PR 合并后被归档了。→ 只关子任务已被接受、没有后续的终端；不碰不是这次运行启动的终端。

## 机器与配额

- 10 核的机器上负载到过 500 以上，swap 几乎满了，同时有六个重会话在跑整套测试。→ 重检查排队轮流跑，一台机器只跑一份整套测试，关掉完成的会话。
- 「负载高于某个值就等」让一个会话等了 2 小时 45 分钟。→ 给重检查排明确的先后，不用负载阈值。
- 一次最高 effort 的轮次跑了一个多小时。→ 最高档只在被要求时用，并说明大概时长。

## 与用户协作

- 一天的时间浪费在等用户回答常规问题上。→ 常规选择自己定，记录，继续。
- 用户给的参考没有被用上。→ 每一条参考都写进子任务说明，交结果时逐条对应。
- 占位的价格进了文案草稿。→ 价格和限额来自源头的模块，不凭记忆。
- 清理删掉了另一个子任务刚加固过的路由。→ 加固之前先定好要删什么；负责的文件不重叠。
- 金钱相关的改动上，两个不同模型的评审者各自发现了对方漏掉的一个高危缺陷。→ 金钱和认证用两个不同模型的验证者。
- 错误追踪里的问题在修复发布后仍然开着。→ 发布的同一轮里标记为已解决。
