# 情形

遇到下面的情形时的第一步。

**截图或设计反馈**（「这看着很廉价」）。把用户的原话和图片原样转给负责那块界面的协作者，不自己修。用户给的每一条参考都写进子任务说明，交结果时逐条说明用在哪里：用户看得出哪些参考被忽略了。

**同一个 bug 被报了两次。** 停止猜测。第三次修之前先拿到证据（日志、事件、复现步骤），回复时说清试过什么、证据说明了什么。

**独立验证两次没通过。** 复审只看之前的阻塞项和返工的改动。还不过，就点名仍未解决的问题、谁受影响、能定论的检查，由你决定返工、换人还是问用户。受影响的工作继续挂起，别的照常推进。

**协作者的结论互相矛盾。** 以工作目录的现状和能复现的证据为准，定下一个结论，在被推翻的那份结果末尾写明修订，让下游只用同一份。

**难以撤销的决定。** 一条存储或隐私的边界、几个子任务共用的接口、一个新的付费功能这类开放的选择：让一个全新的会话只拿到用户的原话、已核实的事实和固定的约束，出一份简短的只读提案，不给它看你的草稿和偏好。两份提案对着代码或数据比较，记下定了什么、否决了什么和为什么。属于用户的决定带着建议去问。

**协作者卡住。** 读它的屏幕。通常是三种：停在一个对话框上（Codex 的目录信任对话框会吞掉第一条消息）；这一轮结束了却没交结果（用它的子任务说明路径催一次）；在一处失败后原地打转（指出问题，或者返工）。

**两个协作者改了同一个文件。** 对账时发现的。先看改动是否真的冲突；分工不清时停下后来的那个，重新划定负责的文件，再让它读最新内容继续。

**合并冲突。** 带回用户的分支时冲突，由你在 worktree 里解决：两边的意图都保留，拿不准保留哪边问用户，然后重跑和这些文件相关的检查。多个目标之间的冲突，由后合并的那个目标合并主干后重新过门禁。

**机器过载。** 重的检查（构建、整套测试）让协作者轮流跑，整套测试一台机器同时只跑一份，关掉已经完成的协作者。「等负载降下来」不管用：有一个会话这样等了 2 小时 45 分钟，要的是明确的先后。

**过夜。** 用户睡前带着授权交接。在看板上写下他们的原话、终点和用量阈值，以及配额用尽后能不能用付费额度。常规的设计和产品选择你来定，从他们之前的消息判断，每一项记下理由；花费、生产数据和线上收费等他们。早间清单的顺序：先是要他们点头的，再是只有他们能提供的输入，最后是你已经定了、待他们确认的决定。

**用户中途加需求。** 当下就把每一项归到它的子任务或目标：正在进行的告诉对应的协作者并更新说明，新的排进下一批，不进已经冻结的那一批。被问进展时，按看板回答：完成了什么、什么在核对、接下来是什么。

**用户直接接管了某个协作者。** 以用户的意思为准。记进看板，别再给那个会话发会打断用户的消息；等用户交还后读它的屏幕，按现状更新说明。

**在等用户的输入。** 每个输入一个编号条目：是什么、在哪里填、回传什么。不依赖它的工作继续做。永远不在对话里索要密钥；凭据文件由用户自己写。

**需要浏览器。** 按协作者实际所在的环境选：它用的是它那台机器上装的浏览器自动化工具，不继承你的浏览器和登录状态。先确认登录状态和需要的能力，没量过的证据不写成通过。一个目标只让一个会话占用浏览器，只关自己开的页面。
