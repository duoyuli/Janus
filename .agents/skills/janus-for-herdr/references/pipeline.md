# 多个目标持续交付：门禁与发布

用户让你长时间推进一批互不相干的改动时读本页。SKILL.md 的原则讲一个目标怎样做完；这里讲软件交付里许多目标怎样安全地进主干。下面的习惯取自一次三天、约 160 个 PR 的生产运行，各条的来由在 `references/lessons.md`。

## 结构

- **一项改动是一个目标**：自己的 worktree 和分支（从刚 fetch 的主干提交拉出，把这个 SHA 记进看板）、自己的子任务和结果，交付成一个草稿 PR，不自己合并。目标之间不共用工作目录。
- **一块总看板**记所有目标：每个目标一行（分支、PR、确切的 head、状态），加上授权、挂起和日志。每个目标自己的子任务表可以放在它自己的目录里。
- **只开工作需要的常驻协作者**。门禁和发布各配一个常驻会话，在每天十几个 PR 的量上才划算；量小时你按下面的规则自己核对就够了。
- 目标的交付只是一种主张。入队前核对 head、相对起点的 diff 和证据。

## 门禁

用项目自己的门禁。构建的人跑限定范围的检查；正式的门禁由另一个会话跑，结论记在它测过的确切 head 上。

- **先对齐主干。** 过期的 head 退回所属目标，让它合并主干后再来。
- **什么算阻塞。** 写出触发场景和后果。处理金钱不正确、丢数据、破坏隐私、扩大访问范围、向团队外发出错误消息、破坏构建或部署或迁移、向用户展示错误或自相矛盾的输出，都阻塞；项目门禁里失败的或没核实的必需检查也阻塞。可选的覆盖率、措辞偏好和文档整理放进「以后」。每份评审的说明都写明这条规则。
- **第二轮及之后**只复核之前的阻塞项和上次评审以来的 diff。两轮之后建议项一律关闭；还要再来一轮，就点名仍未解决的阻塞项、谁受影响、触发场景和能定论的检查。
- **批量。** 每个 PR 单独跑一次门禁太慢：把准备好的 PR 按顺序在一个本地分支上合并到当前主干，测一次，逐个 PR 给结论。冲突只把那一个剔出这一批，所属目标合并主干后回来，其余照测。
- **范围。** 改动过的测试、改动源码旁边的测试、类型检查，加上这些区域变动时项目要求的检查。某个 PR 改了多处依赖的函数（准入、计费、认证）时，连它的每个调用方一起测。
- **确认检查真的跑了。** 看实际执行了什么，不只看退出码：名字过滤器可能跳过了所有断言仍然返回 0。
- **是谁的失败。** 单独重跑该文件：单独跑会超时的是负载问题。在主干上跑：主干也失败就是基线问题，判断是测试过期（行为是有意改的）还是产品错了，修对的那一个。都不是，才是这一批的：按触及的文件归因，或者一次留一个 PR 在外面，其余照发。
- **核验，不要重跑。** 某个目标已经在确切的 head 上跑过完整门禁、head 包含当前主干、主干此后没动时，读它发布的结果，对照两个 SHA，记为通过。这就是「证据可以复用」那条原则。
- **门禁可以并行跑在云端。** 一台机器上排队的门禁会成为瓶颈。那次运行把门禁交给 Claude Code 的云会话，同时跑过十二个：每个从一个 `hc` 终端启动（`claude --model <便宜但可靠的模型> --permission-mode bypassPermissions --cloud "<任务>"`），任务文本写全步骤，结论以 PR 评论的形式发回，写明确切的主干和 head 的 SHA。这一条在 `hc` 上没有重新验证过，用之前先试一个。

## 发布

- **冻结、检查、一次 push。** 检查一开始就冻结这一批，之后通过的等下一批。文档不单独推，搭下一批的车。
- **只发布门禁测过的那个 head**，按门禁的顺序合并，push 后回读远端。
- **挂起的工作。** 高风险的 PR 列在看板的「挂起」里，只在用户点头后单独成一批。冻结之前检查没有候选包含挂起的 head：`git merge-base --is-ancestor <挂起的 head> <候选>`。界面分支经常带着它的后端 PR 的提交。
- **紧急修复**只有这次运行授权过快速通道时才走，否则排在正常队列的最前面。
- **永远不要** force-push、发布没测过的 head、改托管或数据库或环境的设置、执行迁移，除非有覆盖这件事的授权。

发布之后等部署完成，检查生产上发布的页面或接口，看错误追踪里新版本的情况，把这一批修好的问题逐个标记为已解决。新问题开一个小的修复目标；严重问题立刻告诉用户，只回滚到你确知与当前数据库兼容的版本。

## 授权

- 门禁通过是证据，不是许可。那次运行里，发布会话差点凭一个「通过」推了支付相关的 PR。
- 一次运行里的授权（按批发布、快速回滚、某几个迁移、一晚的委托）不延续到另一次运行。每条都带用户的原话、时间和范围，记在看板的「授权」里。
- 没有覆盖性授权时要问用户的事：向生产分支 push、生产数据库变更、高风险发布（金钱、隐私、删除、迁移）、超出授权的花费、生产设置、线上支付、任何向他人发布的内容、删除远端数据。
- 转达用户的同意时，引用原话并附上确切的 head。

## 高风险发布

每一次都要有自己的、经过评审的 runbook 和一份发布包（`templates/release-packet.md`）：确切的 head 和 SQL 的哈希、旧应用与准备好的数据库一起可用的证明、所有写入方和恢复路径、各阶段的顺序和每一步的回读，以及回滚从哪一步起不再安全。不要照搬另一次发布的顺序：那次运行里，支付发布可以「先加迁移、再合并」，因为那个迁移没动线上应用用到的东西，而隐私发布的迁移动了。

一条走通过的顺序（支付，销售已关闭）：计划经评审 → 在测试模式里实现 → 门禁通过 → 合并前评审要求修改 → 修复 → 门禁通过 → 评审第二轮通过 → 发布包放在早间清单第一项 → 用户同意「先跑迁移，再合并」 → 单独跑迁移并回读 → 独占发布，回读远端。
