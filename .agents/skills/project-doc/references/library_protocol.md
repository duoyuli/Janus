# 文档库协议

本协议规定文档库的结构：文档放在哪里、索引怎样组织、何时新建文档、怎样移动与删除、ADR 怎样维护，以及结构检查的范围。阅读与复用、何时更新文档、文档与代码冲突时的处理见 [SKILL.md](../SKILL.md)；锚点见 [anchor_protocol.md](anchor_protocol.md)。

## 位置与成员

按以下顺序选择文档根目录：

1. 用户明确指定的路径。
2. 项目级 skill gate 中声明的根 `index.md` 路径。
3. 仓库中唯一意图明确的既有文档根目录。
4. 以上均不适用时使用 `docs/`。

分类目录直接放在文档根目录下，不加 `project/` 这类没有含义的中间目录。有多个合理的根目录且项目指令没有决断时，在初始搭建时问用户。

文档被根索引或分类索引列为规范条目时，才属于 Project Doc。README、法律声明、宣传材料、生成文档和临时方案即使放在同一目录下，也不属于文档库。

成员命名：

- 文档命名为 `YYYYMMDD-<主题>.md`，例如 `20261201-run_lifecycle.md`。日期是文档的创建日期；报告和 ADR 用报告日或决策日。主题是小写 `snake_case`：`[a-z][a-z0-9_]*`。
- 日期在文档创建后不再修改，内容更新不改文件名。文件名变了，所有链接和代码锚点都要跟着改；想知道最后修改时间看 Git 历史。
- 每个索引文件命名为 `index.md`，不加日期。
- 目录名使用小写 `snake_case`。
- 初始化备忘录命名为 `.project_doc_bootstrap.md`，它是文档库中唯一以点开头的工作文件。
- 收纳进来的遗留文件或目录不符合上述规则时重命名，并修复仓库内的所有引用。文档库外部的文件名保持不变。

主要语言根据既有文档和项目指令确定，保持既有的语言分工。每篇文档使用一种主要语言，明确要求时才创建双语副本。

## 索引层级

根 `index.md` 把仓库任务路由到相应文档，每个会话都会被完整阅读，因此保持精炼，只包含：

- 项目的定位，以及每个任务都用得上的少量全局上下文，例如核心术语和顶层目录。
- 文档库的覆盖范围。
- 每个根级文档的一句话摘要与阅读时机。
- 每个既有分类的一句话摘要、阅读时机与 `index.md` 链接。
- 搭建期间的未完成状态。

总览写在索引里，不另建 `overview` 文档。全局上下文写进根索引，分类的总览（共同原则、组件关系、主流程）写进该分类的 `index.md`，放在文档列表之后并加稳定 ID。索引和概览并列时，两者都是入口，读者要读两份，内容也会重复。模块清单、命令表这类篇幅大的参考内容按主题单独成文，索引只链接过去。

分类从以下固定集合中按需创建，每个分类至少包含一篇文档：

- `architecture/`：系统组件、组件间关系、跨模块数据流及重要不变量。
- `domains/`：领域概念、业务规则、状态机与核心术语。
- `interfaces/`：公开 API、事件、数据格式、配置格式与第三方集成。
- `operations/`：部署、迁移、恢复、可观测性、运维安全与维护流程。
- `decisions/`：记录原因、权衡与后果的架构决策记录（ADR）。
- `research/`：对外部产品、技术、论文和社区进展的调研报告，以及给本项目的借鉴建议。
- `review/`：代码审查、安全审计等审查报告，包括问题清单、证据和修复建议。

前四类是现状文档，随代码更新。后三类带时间点：ADR 记录决策当时的背景，调研和审查报告记录写成当天的判断和代码快照。

每个分类的 `index.md` 列出该分类下的所有文档。每篇文档只在一个索引中有规范条目，其他地方用普通链接引用；同一条目在多个索引中维护会导致描述漂移。

索引条目的格式：

```markdown
- [文档标题](20261201-topic.md)：一句话摘要。阅读时机：需要阅读本文档的任务、代码区域或概念。
```

「阅读时机」是读者决定是否进入的唯一依据，写具体的任务、代码路径或概念。文档范围变化时同步更新它。

搭建期间条目可以带 `[planned]`、`[in_progress]`、`[verified]` 或 `[blocked]` 前缀。目标文件尚不存在时，把计划路径写成行内代码，文件创建后再改成链接。搭建完成后移除状态前缀。

## 文档内容与粒度

每篇现状文档包含：

- 一个一级标题。
- 开篇的范围段落，说明本文涵盖的内容，以及相邻主题归属哪些文档。
- 依据当前代码、测试、配置或运维约束核实过的事实。
- 按主题组织的章节。被锚点引用的章节必须有稳定 ID，其余章节按需添加。
- 必要的关联文档链接。已在其他文档中记录的事实用链接引用，不重复。

文档有 5 个以上主要章节，或读者通常只需要其中一部分时，在开篇附近加简要的章节导航，列出章节名称与阅读时机。

新知识与现有章节的主题、受众和更新周期相同时，扩展现有章节。以下条件全部满足时才新建文档：

1. 该知识在当前任务结束后仍然长期有用。
2. 理解它需要跨多个文件、模块、接口或运维流程。
3. 有可以独立描述的范围和阅读时机。
4. 合并进现有文档会混淆主题、受众或更新周期。

## 删除、移动与合并

以下三项全部满足时才删除现状文档或章节：该主题已从当前系统中彻底消失，不再有受支持的使用方，没有其他文档需要其中的有效知识。

删除前：

1. 检索根索引、分类索引、其他文档和所有 `@project-doc` 锚点。
2. 决定有效内容是删除、移动还是合并到其他文档。
3. 在同一次变更中更新索引、普通链接、锚点及相关说明。
4. 再次检索旧路径和章节 ID，确认引用已清理干净。

仍受支持的已废弃特性保留其状态、替代方案与迁移路径。临时禁用和默认关闭的特性保留文档。

移动文档时尽量保留内容与章节 ID，并在同一次变更中更新所有路径。合并文档时为每个被引用的主题指定具体的目标章节，逐个映射旧锚点；把所有锚点泛泛指向新文档会丢失原始位置信息。

## ADR

可能被再次讨论的重要架构权衡记录在 `decisions/` 中。ADR 至少包含状态、背景、决策、权衡、后果和关联文档。

已采纳 ADR 的历史背景保持原样，现状文档随实现更新。新决策取代旧决策时：

- 创建新的 ADR，在其中指明被取代的决策。
- 把旧 ADR 标记为 `superseded`，并链接到新 ADR。
- 把代码锚点与现状文档指向新决策或现状说明。

## 调研与审查报告

`research/` 和 `review/` 中的报告是时点快照，不是当前实现的说明：

- 每份报告开头写明日期、对象或覆盖窗口、信息来源和范围限制。没有核实的内容标注为未确认。
- 报告写成后不随代码更新，也不回改正文。当前行为以现状文档为准，分类索引的范围段落要说明这一点。
- 报告的结论要有去处：采纳的建议落到现状文档、ADR 或代码；审查问题要么修复，要么在现状文档中写成明确接受的风险。跟进结果记录在现状文档中，报告的索引条目链接过去。
- 代码锚点不指向报告。需要锚点的规则先写进现状文档或 ADR。

## 结构检查

完成写任务前，按影响范围检查以下各项。重读根索引、阅读所有分类索引和全库扫描只在初次验收和明确要求的审计任务中进行：

1. 根索引与分类索引中的链接目标均存在。
2. 每个 Project Doc 文档在索引中有且仅有一个规范条目。
3. 文档命名为 `YYYYMMDD-<主题>.md`，目录与章节 ID 为小写 `snake_case`。
4. 章节 ID 在所属文档内唯一。
5. 每个 `@project-doc` 的路径与章节 ID 均存在。
6. 移动或删除后已清理旧路径、旧 ID 和损坏的链接。
7. 搭建完成后已移除临时状态前缀与初始化备忘录。
8. Git diff 没有空白字符错误，代码变更要求的测试已运行。

前五项由 `python3 <skill_dir>/scripts/check_library.py` 机械检查：写任务加 `--changed` 只报告与改动相关的问题，审计任务不加。脚本只读，退出码非零表示存在问题。其余各项用 `git grep`、针对性阅读与 Git diff 检查；移动或删除内容后，在仓库中检索旧路径与旧 ID 找出所有引用。
